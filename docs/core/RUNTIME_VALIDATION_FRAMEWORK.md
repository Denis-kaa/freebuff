## 1. Принцип

**Каждый Runtime должен пройти полный цикл исследования перед тем, как считаться поддерживаемым.**

Нельзя обещать поддержку Runtime без реального тестирования на целевой платформе.

---

## 2. Этапы валидации

### Этап 1 — Исследование (Research)

**Цель:** понять, возможна ли интеграция в принципе.

- Изучение документации Runtime
- Проверка лицензионной совместимости
- Оценка системных требований (RAM, диск, CPU)
- Проверка совместимости с Android/Termux
- Определение способа интеграции (MCP, CLI, API, subprocess)

**Результат:** отчёт о возможности интеграции, риски, ограничения.

### Этап 2 — Установка (Installation)

**Цель:** установить Runtime на целевой платформе.

- Проверка зависимостей (Node, Python, Go, proot, glibc)
- Установка через менеджер пакетов (npm, pip, git clone)
- Проверка корректности установки (version check)
- Фиксация проблем и workaround'ов

**Результат:** работающая установка, задокументированные шаги.

### Этап 3 — Диагностика (Diagnostics)

**Цель:** проверить, что Runtime работает корректно.

- Health check (ping, version, status)
- Проверка базовых вызовов (list tools, generate simple)
- Проверка обработки ошибок (неверный ввод, таймаут)
- Проверка потребления ресурсов (RAM, CPU, диск)

**Результат:** диагностическая карта, известные проблемы.

### Этап 4 — Поиск ограничений (Limits)

**Цель:** найти границы работоспособности.

- Максимальный размер контекста
- Максимальное время выполнения
- Ограничения по платформе (Android specifics)
- Ограничения по лицензии
- Ограничения по API-ключам

**Результат:** карта ограничений, предельные значения.

### Этап 5 — Разработка Recipe (Recipe)

**Цель:** создать воспроизводимый рецепт установки и настройки.

- Shell-скрипт установки
- YAML-конфиг для Bootstrap Engine
- Wrapper-скрипт (если нужен proot/etc.)
- Инструкция по обновлению
- Инструкция по удалению
- Инструкция по восстановлению

**Результат:** Recipe в `runtime/recipes/<runtime>/`, задокументированные шаги.

### Этап 6 — Тестирование (Testing)

**Цель:** подтвердить работоспособность автоматическими тестами.

- Unit-тесты адаптера
- Интеграционные тесты (Adapter + Registry + MCP)
- Регрессионные тесты (повторные запуски)
- Тесты graceful degradation (отсутствие Runtime, ошибки)
- Тесты на Android (если целевая платформа)

**Результат:** тесты проходят, покрытие > 80%.

### Этап 7 — Регрессионная проверка (Regression)

**Цель:** убедиться, что Runtime продолжает работать после изменений.

- Повторный прогон всех тестов
- Проверка на чистом окружении (новая установка)
- Проверка обновления с предыдущей версии
- Проверка миграции данных

**Результат:** регрессионный отчёт.

### Этап 8 — Документирование (Documentation)

**Цель:** сделать интеграцию понятной для пользователя.

- Запись в COMPATIBILITY_MATRIX.md
- Обновление статуса на Level 4 (Stable)
- Документация в docs/plugin/
- Примеры использования
- Известные проблемы и решения

**Результат:** полная документация, пользователь может повторить.

## 3. Уровни совместимости

| Level | Название | Пройденные этапы | Критерий |
|-------|----------|-----------------|----------|
| **0** | Не исследовано | — | Runtime известен, но не проверялся |
| **1** | Исследуется | Этап 1 (Research) | Изучается принципиальная возможность |
| **2** | Запускается вручную | Этапы 1-2 | Можно запустить с ручной настройкой |
| **3** | Автоматическая установка | Этапы 1-5 | Установка через Bootstrap, Recipe готов |
| **4** | Stable | Этапы 1-6 | Протестирован, работает стабильно |
| **5** | Community Verified | Этапы 1-8 | Подтверждён сообществом, полная документация |

## 5. Требования к адаптеру

Каждый адаптер Runtime должен:

- Реализовывать `RuntimeAdapter` ABC (connect/disconnect/ping/health/generate/list_capabilities)
- Поддерживать MCP транспорт (stdio или HTTP)
- Иметь тесты (unit + integration)
- Иметь Recipe (установка, диагностика, удаление, восстановление)
- Быть задокументирован в COMPATIBILITY_MATRIX.md
