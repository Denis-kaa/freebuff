## 1. Контекст

### 1.1 История продукта

Проект прошёл 4 стадии эволюции позиционирования:

```
v1.x — Local AI Agent         (начало: "агент в Termux")
v2.x — Agent Framework        (расширение: память, контекст, знания)
v3.x — Agent Platform         (интеграция: MCP, плагины, события)
v4.x — Companion Platform     (переосмысление: не агент, а компаньон)

          ↓

v5.0+ — AI Infrastructure Layer  (текущее решение)
```

### 1.2 Текущее состояние

На момент принятия решения проект имеет:

- **836 тестов** — 0 failures
- **~20 Production-компонентов** (Core + Extensions)
- **Bridge Layer** — MCP↔ACP трансляция (60 тестов)
- **MCP Client** — stdio + HTTP транспорт
- **Scenario Engine** — 11 готовых сценариев
- **Knowledge Platform** — Memory + Knowledge + Graph + Semantic Index
- **Event Platform** — Event Bus + subscribers
- **Workflow Engine** — Orchestrator (FSM/DAG)
- **Session Platform** — ContextManager v3
- **OOM Protection** — wrapper, монитор, swap

### 1.3 Внешние условия

- Рынок AI-агентов насыщен: Claude Code, Cursor, Codebuff, GPT-5, OpenClaw, Codex
- Каждый новый агент — борьба за внимание разработчика
- Пользователь использует **несколько** агентов, но каждый начинает с нуля
- Нет единого слоя, который объединяет контекст между агентами
- MCP — шаг в нужном направлении, но это только протокол, не платформа

## 2. Проблема

### 2.1 Проблема позиционирования

«Companion Platform» — это эвфемизм. Он всё ещё звучит как:

- **«агент, который помогает другим агентам»** — слишком сложно для восприятия
- **«ещё одна программа, которую нужно установить»** — не показывает уникальность
- **«инструмент, а не инфраструктура»** — не вызывает желания интегрироваться

### 2.2 Проблема архитектуры

Изначальная архитектура строилась вокруг **одного агента** (Buffy как coding assistant).
После расширения (Bridge, ACP, MCP Client) архитектура стала **много-агентской**,
но позиционирование и документация не успели за кодом.

### 2.3 Проблема восприятия

Разработчик слышит «Companion Platform» и думает:
- «Ещё один AI-помощник? У меня уже есть Claude Code.»
- «Зачем мне это, если я использую Cursor?»
- «Я solo developer, команды у меня нет.»

**Настоящая ценность** — контекст, память, политики — остаётся скрытой за позиционированием.

### 2.4 Ключевой вопрос

> *«Что Claude Code / Cursor / Codebuff не умеют, что Buffy может дать?»*

Ответ: **единая инфраструктура** — память между агентами, политики вместо конфигов,
контекст между сессиями, события вместо логов.

## 3. Варианты решения

### Вариант A: Остаться Companion Platform

**Описание:** Сохранить текущее позиционирование. Доработать документацию, сделать
более понятные формулировки.

| Аргумент | Оценка |
|----------|--------|
| Не требует изменений | 🟢 Низкая стоимость |
| Понятно существующим пользователям | 🟢 Нет путаницы |
| Не решает проблему восприятия | 🔴 Продолжает недопонимание |
| Не подчёркивает уникальность | 🔴 Конкуренты позиционируются чётче |

### Вариант B: AI Operating System

**Описание:** Позиционировать Buffy как «операционную систему для AI-агентов».

| Аргумент | Оценка |
|----------|--------|
| Звучит амбициозно | 🟢 Привлекает внимание |
| Противопоставляет себя другим | 🟢 Чёткая граница |
| Overpromise — мы не ОС | 🔴 Мы не управляем процессами и ресурсами |
| Может вызвать отторжение | 🔴 «Ещё одна ОС? Серьёзно?» |
| Юридические риски | 🔴 Торговая марка «OS» |

### Вариант C: AI Infrastructure Layer ✅ (ВЫБРАН)

**Описание:** Позиционировать Buffy как инфраструктурный слой между AI-агентами
и данными проекта.

| Аргумент | Оценка |
|----------|--------|
| Чётко описывает роль | 🟢 «Мы слой, не агент» |
| Подчёркивает интеграцию | 🟢 Работает с любыми агентами |
| Не конкурирует, а дополняет | 🟢 Усиливает Claude/Cursor/Codebuff |
| Понятно разработчикам | 🟢 «Инфраструктура» — знакомый термин |
| Долгосрочная актуальность | 🟢 Не зависит от конкретных агентов |
| Требует переработки документации | 🟡 Умеренные затраты |
| Может быть абстрактно | 🟡 Нужны примеры и use cases |

### Вариант D: Agent Mesh / Agent Network

**Описание:** Позиционировать как сеть для взаимодействия агентов.

| Аргумент | Оценка |
|----------|--------|
| Хорошо для B2B | 🟢 Актуально для enterprise |
| Подчёркивает collaboration | 🟢 Team mode как фича |
| Игнорирует solo developer | 🔴 80% пользователей — solopreneurs |
| Сложно для понимания | 🔴 Что такое «mesh»? |
| Преждевременно | 🔴 Collaboration ещё не реализован |

## 4. Решение

**Выбран вариант C: AI Infrastructure Layer.**

### 4.1 Формулировка

> **Buffy — AI Infrastructure Layer.**
> Инфраструктурный слой между AI-агентами и данными проекта.
> Сохраняет контекст, управляет памятью, применяет политики,
> оркестрирует работу агентов — независимо от того, какой AI Runtime используется.

### 4.2 Elevator Pitch

> *«Ты используешь Claude Code для кода, Cursor для ревью, GPT-5 для архитектуры.
> Каждый начинает с нуля. Buffy — слой между ними и твоим проектом:
> одна память, одни политики, один контекст. Неважно, какой агент —
> Buffy помнит всё.»*

### 4.3 Позиционирование для разных аудиторий

| Аудитория | Формулировка |
|-----------|-------------|
| **Solopreneur** | «Продолжай с того же места в любом инструменте. Контекст не теряется.» |
| **Dev-команда** | «Единая память для всех агентов команды. Общие политики.» |
| **AI Agent Developer** | «Подключи своего агента через MCP/ACP. Buffy даст ему память проекта.» |
| **Enterprise** | «Policy-driven инфраструктура с полным аудитом событий.» |

### 4.4 Что мы НЕ говорим

- ❌ «Ещё один AI-агент» — мы инфраструктура
- ❌ «Замена Claude/Cursor» — мы их усиливаем
- ❌ «AI OS» — мы слой, не система
- ❌ «Agent Framework» — мы не LangChain
- ❌ «Companion Platform» — слишком размыто, уходит в прошлое
- ❌ «Companion» — слишком размыто

## 5. Обоснование

### 5.1 Почему «Infrastructure» — правильный термин

1. **Infrastructure — это то, что не видно, но без чего не работает**
   - Как сетевой стек, файловая система, CI/CD
   - Пользователь не думает о нём, пока он работает
   - Это именно то, как должен ощущаться Buffy

2. **Infrastructure — это слой, а не продукт**
   - Его *подключают*, а не *используют*
   - Он работает *под* агентами, а не *вместо* них
   - Его *интегрируют*, а не *запускают*

3. **Infrastructure — это долгосрочно**
   - Инфраструктура живёт десятилетиями (Git — 20+ лет)
   - Агенты приходят и уходят
   - Buffy должен пережить любой конкретный AI Runtime

### 5.2 Почему не «Companion»

| Companion Platform | AI Infrastructure Layer |
|-------------------|------------------------|
| Звучит как приложение | Звучит как платформа |
| Подразумевает использование | Подразумевает интеграцию |
| Конкурирует с агентами | Дополняет агентов |
| Зависит от экосистемы | Независим |
| «Помощник» | «Фундамент» |

### 5.3 Соответствие инженерным принципам

| Принцип | Как решение его поддерживает |
|---------|------------------------------|
| **Runtime Agnostic** | Инфраструктура не знает, какой Runtime сверху |
| **Provider Agnostic** | Провайдер — деталь, не архитектура |
| **Model Agnostic** | Инфраструктура не вызывает LLM напрямую |
| **Local First** | Инфраструктура работает на телефоне |
| **Event Driven** | Все изменения — события в инфраструктуре |
| **Policy Driven** | Политики — конфигурация инфраструктуры |
| **Modular** | Core / Extensions / Labs — слои инфраструктуры |

### 5.4 Анализ альтернатив (Weighted Decision Matrix)

| Критерий | Вес | A: Companion | B: AI OS | C: AI Infra | D: Agent Mesh |
|----------|-----|-------------|----------|-------------|---------------|
| Ясность позиционирования | 30% | 5 | 3 | **9** | 4 |
| Соответствие коду | 25% | 7 | 2 | **10** | 6 |
| Долгосрочная актуальность | 20% | 4 | 5 | **9** | 7 |
| Привлекательность для ЦА | 15% | 5 | 6 | **8** | 4 |
| Стоимость перехода | 10% | 10 | 3 | **7** | 5 |
| **Итого (взвешенный)** | **100%** | **5.8** | **3.5** | **8.8** | **5.2** |

> Вариант C набирает 8.8/10 — значительно выше остальных.

> *Примечание: веса определены исходя из анализа целевой аудитории (~70% solopreneur, ~30% enterprise).
> Для enterprise-сегмента вес критерия «Стоимость перехода» был бы ниже, а «Соответствие коду» — выше.
> При изменении структуры аудитории матрицу следует пересчитать.*

## 6. Последствия

### 6.1 Положительные

- **Чёткое позиционирование** — разработчик сразу понимает роль Buffy
- **Не конкурирует с агентами** — снижает барьер интеграции
- **Открывает B2B рынок** — enterprise понимает «инфраструктуру»
- **Позволяет добавлять любые Runtime** — без переосмысления продукта
- **Упрощает объяснение архитектуры** — «инфраструктурный слой»

### 6.2 Отрицательные

- **Требует обновления всей документации** — BUFFY.md, README.md, AGENTS.md, CHANGELOG.md
- **Нужно переписать intro-материалы** — объяснение «что такое AI Infrastructure Layer»
- **Существующие пользователи могут удивиться** — «а что, раньше было не так?»
- **Риск абстрактности** — «инфраструктура» может звучать слишком обобщённо
- **Нужны конкретные примеры** — показать, как «инфраструктура» помогает в daily work

### 6.3 Нейтральные

- Все файлы ADR и VISION_3.0.md уже написаны с новой терминологией
- ARCHITECTURE_3.0.md уже использует новое позиционирование
- PRODUCT_MANIFESTO.md уже утверждён с новыми принципами

## 10. Риски решения

### 10.1 Риск: «Инфраструктура» — слишком абстрактно

**Вероятность:** Средняя  
**Влияние:** Высокое  
**Митигация:** Конкретные examples в документации, use cases для каждой аудитории, демо-сценарии

### 10.2 Риск: Пользователи не увидят разницы

**Вероятность:** Средняя  
**Влияние:** Среднее  
**Митигация:** Сравнительная таблица «v4.x (Companion) vs v5.0 (Infrastructure)» в CHANGELOG, README и BUFFY.md. `freebuff --version` показывает новое описание. Демо-пример: «Было: companion для одного агента. Стало: инфраструктура для всех агентов.»

### 10.3 Риск: Слишком много планов, мало реализации

**Вероятность:** Высокая  
**Влияние:** Критическое  
**Митигация:** Core/Extensions/Labs жёсткое разделение, Bootstrap Engine — первый приоритет, не начинать новое, не закончив старое

### 10.4 Риск: Потеря фокуса на freebuff агенте

**Вероятность:** Низкая  
**Влияние:** Высокое  
**Митигация:** Local First — основной принцип. Будучи инфраструктурой, Buffy работает и как freebuff агент (один из Runtime)

### 10.5 Риск: Feature creep в documentation

**Вероятность:** Средняя  
**Влияние:** Низкое  
**Митигация:** ADR фиксирует решение. Документация не должна расти бесконтрольно — использовать IDEAS.md для идей

## 11. Заключение

### 11.1 Резюме решения

| Параметр | Значение |
|----------|----------|
| **Решение** | Перейти от «Companion Platform» к «AI Infrastructure Layer» |
| **Обоснование** | Чёткое позиционирование, долгосрочная актуальность, не конкурирует с агентами |
| **Архитектурные изменения** | Bootstrap Engine, Runtime Abstraction, Policy Engine (Core) |
| **Без изменений** | Код, данные, тесты, интерфейсы, принципы |
| **Риски** | Абстрактность, потеря фокуса, feature creep |
| **Дата принятия** | 2026-07-29 |
| **Review date** | 2026-10-29 (через 3 месяца) |

### 11.2 Опровержение альтернатив

Мы **не** стали:
- **Companion Platform** — потому что это скрывает настоящую ценность
- **AI OS** — потому что это overpromise и юридические риски
- **Agent Mesh** — потому что collaboration ещё не готов и это не про solo developer

### 11.3 Ключевое сообщение

> *Buffy не конкурирует с AI-агентами. Buffy — это слой, который делает их лучше.*

## Приложение B: Глоссарий нового позиционирования

| Термин | Что означает |
|--------|-------------|
| **Infrastructure Layer** | Слой между AI Runtime и данными проекта |
| **AI Runtime** | Любой AI-агент (Claude Code, Cursor, Codebuff, OpenClaw) |
| **Adapter** | Адаптер для подключения AI Runtime к Buffy |
| **Policy** | Пользовательское правило, определяющее поведение |
| **Capability** | Возможность (coding, planning, review), не привязанная к модели |
| **Bridge** | Универсальный слой интеграции между Runtime и протоколами |
| **Core** | Минимальное ядро, обязательное для работы |
