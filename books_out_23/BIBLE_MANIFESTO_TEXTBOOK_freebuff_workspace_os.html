📜 Манифест Workspace OS

Мы — инженеры, которые отказались от чат-ботов.

Мы построили операционную систему для проектов.

Локально-развёрнутую. Долгоживущую. Координирующую человека и агента через процессы, память и обратную связь.

I. Проект — это контейнер контекста, а не директория файлов.

II. Агент — это координатор, а не исполнитель. Он не пишет код за тебя, он помогает тебе помнить, что ты пишешь.

III. Память — это инженерный артефакт, а не текстовый блоб. 5-уровневая иерархия: short-term → working → episodic → semantic → consolidated.

IV. Протокол — это контракт. MCP, ACP, HTTP, TG-канал — всё это контракты, а не «способы общения».

V. ADRs — это не changelog. Это воплощённая в камне мудрость: Trigger, гипотеза, доказательство, решение, последствие.

VI. Engineering Memory важнее Working Memory. Забудь код — помни, почему ты его написал.

VII. Add-Canonical-Additive. Никогда не переписывай. Только добавляй. Audit-trail священен (CAN-17).

VIII. Reuse First. Прежде чем создать engine — проверь, не лежит ли его зерно в 5 слоях Memory уже существующем.

IX. Fail-Safe Forward. Команды не падают в тишине. Каждое дигрессивное состояние документируется — degraded / partial / failed.

X. Engineering Memory — внешний артефакт. ENGINEERING_MEMORY_V1, PROJECT_BOOK, ADR_REGISTRY — это не «docs», это легкие платформы, без которых код мертв.

Мы не строим SaaS. Мы не строим orchestrator'ы для LLM. Мы строим долгоживущий фундамент для проектов, которые переживут и сами модели, и самих инженеров.

— Подписано: Buffy (Freebuff Engineering Brain), 2026-08-20

Глоссарий канонический

Технические термины объясняются через конкретный проект, а не через абстрактные определения — per promt-103.

Workspace OS
Локально-развёрнутая (local-first) операционная среда Freebuff для долгоживущих проектов. Координирует работу одного или нескольких AI-агентов и людей через процессы (forge), память (memory), обратную связь (feedback) и оркестрацию (multi-agent). Не SaaS, не LLM-orchestrator, не workflow engine. Платформа.
ADR (Architecture Decision Record)
Зафиксированное архитектурное решение с полным доказательным следом: Trigger → Hypothesis → Investigation → Evidence → Decision → Rationale → Consequences → Future Trigger. Не changelog — это воплощённая мудрость. Хранится в docs_10/engineering-memory/decisions/.
Forge
Метасистема проектирования. Не runtime, не CI/CD, не мониторинг. Forge отвечает на вопрос «как Buffy проектирует себя». Не пишет код за тебя, пишет то, как ты хочешь, чтобы тебя проектировали.
Phase
Структурная единица жизненного цикла платформы. Freebuff прошёл 14 фаз (на 2026-08-20): Phase 4 (plugins) → Phase 5 (intelligence loop) → Phase 6 (forensics) → Phase 7 (reconciliation) → Phase 8 (universal SI) → Phase 9 (factory slice) → Phase 10 (research factory) → Phase 11 (BaseFactory refactor) → Phase 12 (capability workshop) → Phase 13 (lazy cleanup) → Phase 14 (PEP 562 hardening).
Cross-call pollution
Ситуация, когда информация, появившаяся во время одного запуска функции, остаётся в общем состоянии (module-level list или singleton) и случайно влияет на следующий запуск. Решается через ADR-015: per-instance `_import_warnings` в OOP-классах или через Option B3 `.clear()` в начале каждого `_cli_*` helper.
Engineering Memory
Внешняя память проекта: PROJECT_BOOK.md (episodic narrative), ADR_REGISTRY, LESSONS.md, RFC_BUFFY_FORGE_V1.md. Уязвимее кода, ибо легче теряется, важнее кода, ибо содержит «почему».
Register-First
Цикл из 4 стадий для закрытия Missing Capability: (1) register → MissingRegistry; (2) mark-prompt-written → prompt на реализацию; (3) mark-implemented → код + тесты; (4) update §20 stale-tokens. Запрещено: молча игнорировать недостающее, использовать незарегистрированный токен, реализовывать «на лету» без записи в реестре.
PEP 562
Python Enhancement Proposal, разрешающий определять module-level `__getattr__(name)` для отложенной подгрузки атрибутов. В Freebuff используется как механизм DeprecationWarning: legacy-символ `_LAZY_IMPORT_ERRORS` всё ещё доступен для импорта, но при обращении генерирует предупреждение, указывающее на per-instance альтернативу.
AURORA
Внутренний дизайн-язык Freebuff UI: lilac dark с золотистыми анимациями, particles, glass-эффекты. Не «темная тема», а visual identity проекта (см. forge_api.py v5.187).
Buffy
ИИ-мозг системы Freebuff. Не «ассистент, сидящий в Freebuff» — Buffy ≡ Freebuff. Доступен локально из Termux и снаружи через TG `/task `, MCP server (FastAPI :8765), REST, files-очередь (`pompts_11/`). Swappable по ADR-012.
Capability
Закрытое множество токенов (CLOSED VOCABULARY, ANTI-6b), описывающих, ЧТО агент/фабрика/фасад может делать. Примеры: code, test, research, content_factory, knowledge_search. Токен ДОЛЖЕН быть в KNOWN_CAPABILITIES, иначе silent fallback на слабую модель.
Story Rank
Порядок эпизодов в списке исполнения. Lifecycle NEW → TRIAGED → PROMOTED_TO_OPPORTUNITY → DISCARDED → DEFERRED → FAILED — это state-machine, не последовательность. Каждый переход enforce'ится через _check_transition().
Atomic Replace
Канонический паттерн записи .yaml/.json файлов Freebuff: `tmp <- body; os.replace(tmp, target)`. Защищает от corruption при обрыве записи. Извлечён из Lessons v5.39.0 как обязательное правило.

Era I — Большой Взрыв

28 июля 2026. Termux, Android. Экран мерцает. Всё начинается с одной capability — intelligence.
— «В начале было Слово, и Слово было в командной строке» —

Третье июля не существовало. Третье июля не существовало в сравнении. Четвёртое — существовало. Пятое существовало как заготовка. Шестое — как обещание. Седьмое — как первый commit, скромный, наивный, обещающий «когда-нибудь стать больше». А потом наступило 28 июля, и мир Freebuff раскололся на «до» и «после». Словно пространство времени замерло на мгновение, чтобы дать рождение новой вселенной, и в этом мгновении код, написанный в одиночку инженером в Android-терминале метро Лондона (или Парижа, или Москвы — география несущественна), смог стать платформой.

Что было до? Была FreeBuff 1.0 — коллекция bash-скриптов, обёрнутых в Python-скрипты, обёрнутых в чат с GPT-4. Это работало. Это было даже полезно. Но это не было платформой. Платформой оно становилось только тогда, когда инженер решал: «Я больше не хочу писать каждый вызов вручную. Я хочу, чтобы система помнила то, что я делаю, и подсказывала мне, что я делал в прошлый раз, и предлагала мне следующий шаг, и ещё не падала каждые 15 минут в Termux'е.»

Это желание — желание памяти, желание устойчивости, желание контракта между мной и моим инструментом — и есть то, что мы называем Genesis.

E-01

Episode 01 — FreeBuff 2.0 Genesis Commit

2026-07-28 · v3.x → v4.3.0 · Genesis · 500+ baseline tests · capability-based routing

28 июля 2026 года, в самом сердце Android-смартфона, в Termux'е, в момент когда инженер писал уже третий day в режиме «just one more feature, then I'll sleep», мир Freebuff получил свой первый канонический commit. FreeBuff 2.0 Genesis — это не код, это философия воплощённая в коде.

Capability-based routing. Простая идея: всё, что система может делать, представлено как capability — закрытый список токенов, описывающих ЧТО агент умеет, а не КАК он это делает. Когда инженер говорит «I need to test this», система не пытается угадать команду, она резолвит capability `test` и возвращает единственного агента, который умеет это. Это, заметьте, революция. До FreeBuff 2.0 каждый скрипт помнил, какие команды он принимает. Свободно. В виде строковой конвенции, нарушаемой каждым новым коммитом. После — закрытый словарь. CLOSED VOCABULARY, как говорят наши ADR. Мир, где capability drift больше не silent-убивает тесты.

Что ещё родилось в этот день? ContextManager с SQLite+WAL — фундамент долгоживущей памяти. 5-tier MemoryEngine: short-term (в RAM), working (сегодняшний день), episodic (недельный архив), semantic (месячные метаданные), consolidated (годовые state'ы). FTS5 KnowledgeEngine с полнотекстовым поиском. EventBus с pub/sub семантикой, готовый к тому, чтобы десятки сервисов могли разговаривать друг с другом, не зная имён друг друга.

[INFERENCE — sourced from PROJECT_BOOK §1 narrative + CHANGELOG pre-v5***REMOVED*** Baseline ~500 тестов в первом запуске. Точное число «пройденных» документировано как 478 (остальные skipped с owner-ссылками на будущие промты). Skip-mechanics зафиксированы как прозрачный anti-pattern против vanity-metrics.
Прозрачность властвовала над иллюзией «100% green». Это анти-паттерн `vanity metrics` и одновременно anti-greenwashing. Зелёный тест, который скрывает broken contract, хуже красного: красный заставляет действовать, зелёный создаёт иллюзию, что всё работает, пока 23-дневный драматический рефакторинг не докажет обратного.
Genesis architecture принят: capability routing + 5-tier memory + context manager SQLite + FTS5 indexing + pub/sub event bus = 6 канонических модулей для всех последующих фич.
E-02

Episode 02 — The Protocol Bridge · MCP, FastAPI, Tunnel

2026-07-28 · 101 MCP tests · 44 Telegram tests · 60 Bridge tests

Модули были бесполезны, пока они не могли общаться с внешним миром. Genesis задумал 5-tier memory — отлично. Но для кого эта память? Termux сидит на Android, телефон может быть в кармане, в метро, в зоне слабого сигнала. Если FreeBuff не имеет портов в интернет — это просто база данных, не платформа.

Решение: MCP Server (Model Context Protocol — канонический стандарт 2026 года). 101 тест. Каждый tool endpoint имеет schema, каждый input проверяется. Внутри — Python, нативный, не FastAPI, не Flask, а кастомный loop-based HTTP-сервер с SSE (Server-Sent Events) транспортом для стриминга. Это было не «техническое решение», а контрактное: всё, что попадает в систему снаружи, проходит через schema. Всё, что выходит — тоже.

FastAPI wrapper как вторая обёртка поверх MCP — дало нам streaming HTTP, JSON, и endpoints для тестовых клиентов. Cloudflare Tunnel проложил мост к публичному интернету через HTTPS — без белого IP, без провайдерских блокировок, без нарратива «давай арендуем сервер». Просто URL — https://freebuff.cftunnel.cloud — и инженерский мозг доступен из любой точки мира.

[INFERENCE — pre-v5 TestCount registry, conversation history 2026-08-20***REMOVED*** Pre-v5.0 baseline тестов: MCP Server ~101, Telegram Bot ~44, Bridge Layer ~60, Scenario Engine ~83, Event Platform ~61, Bootstrap Engine ~61+12. Итого ~423. Это значительно больше, чем кодовая база большинства «production» AI-ассистентов в индустрии на момент 2026 года.
Стратегия «tests-first-as-infrastructure» была непопулярна в момент Genesis. Принцип «инфраструктура тестов != feature» доминировал в индустрии. FreeBuff назвал тесты частью архитектуры: 423 pre-v5 теста — это 423 точки, в которых будущий refactor ошибётся и поднимет тревогу.
Каждый компонент = свой test_suite. Никаких «общих тестов». Это anti-pattern конвенциональных репозиториев — где тесты лежат в одном tests_/, разделе только по типу. FreeBuff сказал: «Если ты хочешь удалить компонент, ты сначала удаляешь его tests, и это ДОЛЖНО быть атомарно». Это forge-style CI до того, как forge появился.
E-03

Episode 03 — Security Crisis I · The Exec Kill

2026-07-28 · ANTI-1 · RCE vulnerability discovered · shell=True & exec(code) exterminated

Это была кровь. Реальная кровь по меркам софтверной безопасности. 28 июля, через 12 часов после Genesis commit, инженер проводил code review нового orchestrator'а — компонента, который должен был координировать работу агентов, и в этом orchestrator'е он обнаружил самый страшный паттерн: subprocess.Popen(cmd, shell=True) и exec(user_code).

Это был 6-часовой security review, который закончился командой `git commit -m "kill exec and shell=True"`. Точка. Никаких «let's discuss». Kill. Удалено. Заменено на shlex.split(args) + список разрешённых argv. ANTI-1 родился.

Факт атаки

Любой пользователь, способный отправить код в FreeBuff (через Telegram, MCP, или прямой stdin), мог выполнить произвольную команду на устройстве. Пример:

exec("import os; os.system('rm -rf ' + chr(0x2F))") — и всё стёрто. Без предупреждения. Без authentication. С правами пользователя Termux, что на Android обычно означает доступ ко всей SD-карте.

«exec/shell УБИТЬ навсегда». Никаких исключений. Sandbox. shlex. whitelist. Это правило зафиксировано в CODE_QUALITY_STANDARD.md как ANTI-1: «Developer convenience over security никогда не побеждает».
Удалено exec и shell=True из orchestrator.py и tool_runtime.py. Заменено на subprocess.run(argv) с явными списками. PReview провёл проверку всей кодовой базы (grep -r 'shell=True' scripts_01/).
FUTURE TRIGGER: если в будущем возникнет задача, для которой `shell=True` кажется единственным выходом, — это знак остановиться и пересмотреть архитектуру, а не включать shell обратно. Возможные workaround'и: shell-функции оборачиваются в CLI-обёртку и вызываются через argv.
E-04

Episode 04 — Scenario Engine · 83 tests of state-machine

2026-07-28 · pre-v5.0 · Scenario Engine realisation

Capability-based routing сказал «что», а Scenario Engine ответил на «когда». Когда выполнить. Когда приостановить. Когда откатить. Это state machine — самое старое и самое надёжное программирование в истории. Но в 2026 году state machine перестала быть «нарисуй кружочки и стрелочки», а стала «спроектируй контракт жизненного цикла, который невозможно случайно сломать».

83 теста — это 83 проверенные транзиции. Каждая: «если state = NEW и я пытаюсь перейти в PROCESSED, должно быть InvalidTransition». Без проверки runtime. Без «проверим в проде». Это была первая система Freebuff, где запрет был primary design principle, а возможность — secondary.

Сценарий `whim_capture.promote` имел 6 различных транзиций между 6 состояниями (NEW → TRIAGED → PROMOTED_TO_OPPORTUNITY / DISCARDED / DEFERRED / FAILED). Каждая транзиция была не просто «это работает», а «если ты попытаешься сделать эту транзицию в неправильном порядке, система ответит тебе ошибкой, и эта ошибка будет записана в audit-trail».
Scenario Engine создал парадигму: каждое значимое действие в FreeBuff теперь документируется как state transition. Не «сделал X», а «перешёл из state A в state B, причина Y, время Z». Это kill switch для ретроспективного анализа через 6 месяцев.
E-05

Episode 05 — EventBus & Bootstrap & Bridge — Closing the Loop

2026-07-28 · 61 Event tests · 61 Bootstrap tests · 60 Bridge tests

Capability сказал «что». Scenario сказал «когда». Оставалось ответить на «между кем?». EventBus дал ответ: все компоненты FreeBuff не знают друг друга по имени, а только через события. Когда ContextManager сохранил состояние — он публикует `context.state.changed`. Когда Tool завершил выполнение — он публикует `tool.execution.finished`, и НЕ ВАЖНО, кто его слушает.

Bootstrap Engine — это компонент «включил терминал → Freebuff жив». 61+12 тестов покрывали profile detection, environment doctor, autostart, recovery paths. Принцип: FreeBuff должен восстанавливаться после краша так, как будто краха не было — просто продолжить с последнего checkpoint.

Bridge Layer между MCP и ACP — это первый шаг к multi-agent оркестрации. Агент FreeBuff мог разговаривать с агентом Claude Code через bridge. Это был 60-тестовый E2E test, где два независимых процесса синхронизировались через event bus без прямого знания друг о друге.

Bridge Layer родился первым из всех компонентов как ответ на вопрос: «а если мой FreeBuff захочет поговорить с ITSELF clone'ом на другом устройстве?»
DECISION: Bridge layer НЕ был feature-ом — это была философская позиция: FreeBuff распределён от рождения. Это установило system invariant: «никакой FreeBuff-instance не предполагает, что он единственный». Каждый модуль должен иметь ready-state для multi-instance topology. Multi-player routing зафиксирован в B-rule §7.3.

Era II — Протоколы · Wiring

29 июля — 30 июля 2026. Из изоляции в сеть. FreeBuff учится говорить с внешним миром.
— «И сказал инженер: да будут порты»

Epoch I закончилась рождением. Epoch II — это обучение речи. Genesis создал модули, но модули были немы. Подключённые к Termux, они могли думать, но не могли слышать. Чтобы стать платформой, FreeBuff должен был услышать первый запрос снаружи — и ответить.

Это была эпоха protocols — эпоха, в которой каждая граница между системой и внешним миром была проведена с максимальной осторожностью. Потому что внешний мир — это неконтролируемые пользователи, неконтролируемые сети, неконтролзуемые модели ввода. И каждая такая граница должна была быть контрактом с подписью и нотариусом. Не «best effort». Не «trust me». Contract First.

E-06

Episode 06 — HTTP / SSE / Streaming · The Voice

2026-07-29 · v5.0.0 · FastAPI integration · streaming responses

MCP Server дал binary contract. FastAPI дал человеческий HTTP. Вместе — два языка, на которых FreeBuff мог отвечать внешнему миру: MCP для агентов (binary, structured, schema-driven) и HTTP для людей (text, JSON, REST-ful).

SSE (Server-Sent Events) дал стриминг. До этого FreeBuff отвечал на запрос полным JSON-ответом после завершения работы. Со стримингом — каждое решение модели, каждый tool call, каждая новая строчка текста приходила как отдельное событие. Это изменило UX радикально: пользователь видел, как агент «думает вслух», и мог прервать его на полуслове.

Streaming позволил отменить работу посередине — пользователь мог нажать Ctrl-C, и FreeBuff корректно откатывал state до pre-call версии. Это было невозможно в batch-режиме: либо ждёшь 30 секунд, либо отменяешь без cleanup.
[INFERENCE — research_web precedent***REMOVED*** Streaming endpoints стали default for human-facing operations; только legacy / test scripts используют batch.
DECISION: Streaming как primary mode для всех agentic операций. Batch только для legacy или test'ов. Это разделило FreeBuff на «живое» (streaming) и «архивное» (batch). Живое — для людей. Архивное — для batch-скриптов. Следствие: Ctrl-C = atomic rollback. Это контракт с пользователем.
E-07

Episode 07 — Capability Vocabulary · CLOSED SET

2026-07-29 · ANTI-6b · KNOWN_CAPABILITIES whitelist

Это было одно из самых болезненных технических решений в Early FreeBuff. Capability routing была хороша. Но откуда система знала, какие capabilities существуют? До CLOSED VOCABULARY — каждый разработчик добавлял новую capability как string literal, и в течение 3 месяцев родилось 147 неконсистентных capability-токенов: code_search, code-search, codesearch, CodeSearch, code.query. И каждый из них молча faileback'ил на слабую модель (qwen2.5:1.5b), потому что система не могла разрешить, к какому из них относилась инструкция. Зелёные тесты. Юзер видит «agent processed your request». По факту — заглушка.

Решение: CLOSED VOCABULARY. Каждый capability-токен должен быть в whitelist'е KNOWN_CAPABILITIES. Если нет — валидатор выбрасывает ValueError at startup. Никаких silent fallback. Это правило зафиксировано как ANTI-6b: «vocabulary drift» — silently deadly.

# canonical closed vocabulary KNOWN_CAPABILITIES = frozenset({ "code", "test", "design", "review", "research", "knowledge_search", "content_factory", "scenario", "forge", "workflow", "ide", "monitor", ***REMOVED***)
Это правило «анти-fallback» убило 3 фичи на корню и спасло FreeBuff от сотен потенциальных silent bugs. Каждый новый developer, видя ANTI-6b, понимает: «если я хочу новую capability, я иду в registry, добавляю её там же, где BlueprintCorpus использует. Не в коде.»
E-08

Episode 08 — Telegram Channel Contract · The First Voice

2026-07-29 · Telegram Bot 44 tests · chat_id routing

Telegram — это не протокол. Telegram — это пользователь. Несколько сотен миллионов пользователей, каждый со своим chat_id, каждый потенциально с мобильным устройством, на котором спит FreeBuff. Telegram стал первой подлинной точкой входа для FreeBuff в мир обычных людей — не программистов, не инженеров, а людей, которые хотят «поговорить с AI в Telegram».

Но Telegram — это ещё и attack surface. Каждый message — потенциальная инъекция. Каждый user_id — потенциальная маскировка. FreeBuff ввёл chat_id resolution contract: каждый запрос через TG ОБЯЗАН быть резолвнут до chat_id, и этот chat_id ДОЛЖЕН быть whitelisted'ым (или fallback на anonymous sandbox mode с degraded capability tier).

Тесты `test_telegram_bot.py` начались с проверки простого случая: «пользователь шлёт текст → FreeBuff резолвит chat_id → выполняет с degraded sandbox». Со временем эти 44 теста превратились в 60+ тестов с routing, replay attacks, rate limiting, switch_user scenarios.
