# MISSION: Закрыть три шероховатости Single-цикла (Telegram → dispatcher → Buffy → отчёт)

## Контекст

Предыдущий промт (roadmap-reconciliation Forge/ScenarioRegistry) — если ещё
не закрыт, эта задача НЕ блокирует его и НЕ блокируется им, это отдельная,
параллельно допустимая ветка (разные файлы: `scripts_01/prompt_dispatcher.py`
+ `scripts_01/prompt_queue.py`, не `core_02/forge_*`). Но если roadmap ещё
идёт — дождись хотя бы Шага 1 (факт-чекинг) прежде чем начинать это, чтобы
не работать над кодовой базой в двух руках одновременно без координации.

Найдены три конкретные, признанные самим кодом (докстринг
`prompt_dispatcher.py`) шероховатости повседневного Single-цикла
(Telegram `/task` → `pompts_11/user/` → диспетчер → Buffy → отчёт):

1. **Задержка цикла** — диспетчер работает через cron, не realtime. Между
   отправкой задачи и результатом — интервал крона.
2. **`running-resumable` зарезервирован, не реализован** — цитата из
   докстринга: "для future `/answer` TG command... пока нигде не
   устанавливается". Buffy не может задать уточняющий вопрос посреди
   долгой задачи и получить ответ тем же путём.
3. **`max_iterations` cap (default 3), "at limit, force-failed"** — жёсткий
   потолок на multi-turn цикл одной задачи.

**Прежде чем чинить — определи связь между ними.** Не независимые баги:
`running-resumable` — это фактически несостоявшаяся дополнительная
итерация в том же multi-turn цикле, который ограничен `max_iterations`.
Если реализовать resumable-ответы, не пересмотрев cap — уточняющий вопрос
может молча упереться в тот же потолок в 3 итерации и провалить задачу,
которая как раз начала нормально работать через resumable-механизм.

## ЗАДАЧА 1 — Реализовать `running-resumable` (закрывает п.2)

Докстринг уже описывает конечное состояние: `.freebuff_result.pending_task`
сигнализирует продолжение цикла, `running-resumable` статус зарезервирован.

1. Реализуй TG-команду `/answer <task_id> <текст>` (или похожий синтаксис —
   определи сам, исходя из существующего формата `/task`), которая:
   - находит промт в статусе `running-resumable` по task_id или по
     последнему pending для этого чата,
   - дописывает ответ пользователя в тело промта (`append_iteration`,
     уже существующий механизм),
   - переводит статус обратно в `running-pending`, чтобы диспетчер
     подхватил его на следующем тике.
2. Установи `running-resumable` статус там, где Buffy реально задаёт
   уточняющий вопрос — найди/добавь триггер (вероятно там же, где
   `_extract_pending_task` уже извлекает pending-задачу, но сейчас не
   переводит в resumable).
3. Тесты: сценарий "Buffy спросила → пользователь ответил → цикл
   продолжился" — end-to-end, не только юнит на отдельные функции.

## ЗАДАЧА 2 — Развести лимит итераций для уточнений и для работы (закрывает п.3, с учётом Задачи 0)

Основываясь на выводе Задачи 0:

- Если технически можно развести счётчики — сделай так, чтобы ответ на
  уточняющий вопрос НЕ тратил ту же итерацию, что рабочий шаг. Например:
  отдельный `clarification_count` с более высоким или отдельным лимитом
  от `max_iterations` для собственно работы.
- Если развести нельзя без большого рефакторинга — как минимум подними
  `max_iterations` default с 3 до значения, разумного для сложных
  архитектурных задач (не подбирай число произвольно — оцени по
  реальным сегодняшним сессиям: сколько итераций реально потребовалось
  промтам 057-059, и возьми это как ориентир, не гадай).
- В обоих случаях: `force-failed` при достижении лимита должен явно
  логироваться с полным контекстом (что было сделано, где остановилось),
  не просто "провалено" — чтобы пользователь, вернувшись, понимал,
  что произошло, а не терял работу молча.

## ЗАДАЧА 3 — Уменьшить задержку цикла для интерактивных задач (закрывает п.1)

Не переписывай весь диспетчер на realtime — это большой архитектурный
сдвиг, не соразмерный масштабу проблемы. Вместо этого:

1. Проверь текущий интервал cron-тика (найди в crontab/systemd timer,
   если есть, или в документации).
2. Если интервал заметно больше нескольких минут — оцени, можно ли
   уменьшить его для `pompts_11/running/` (задачи, уже идущие, включая
   resumable) отдельно от `pompts_11/user/` (новые задачи, где задержка
   не так критична) — то есть более частый опрос для уже начатых
   диалогов, чем для новых входящих.
3. Если технически невозможно или рискованно менять cron-интервал
   сейчас — зафиксируй это как явный, названный компромисс в
   LESSONS.md (не молчаливое "не сделал"), с оценкой, что потребуется,
   чтобы это исправить в будущем.
