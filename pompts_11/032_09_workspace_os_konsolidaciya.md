Вот такой промт я бы дал.


---

MISSION: Workspace OS Consolidation (Architecture Stabilization)

Цель

Перед дальнейшим развитием платформы необходимо привести систему к единому архитектурному состоянию.

На данном этапе запрещается добавлять новые возможности, если только они не требуются непосредственно для консолидации существующей архитектуры.

Главная задача — сделать так, чтобы код, документация, архитектура, промты и внутренняя логика системы представляли собой единое целое.


---

Основной принцип

> Source of Truth должен быть один.



Не должно существовать нескольких вариантов истины.

Если архитектура изменилась — документация должна измениться.

Если появился новый модуль — Registry обязан знать о нём.

Если удалён компонент — все ссылки должны быть актуализированы.

Система не должна противоречить самой себе.


---

Этап 1. Полный аудит

Проведи глубокий анализ всего проекта.

Определи:

что реализовано;

что осталось концепцией;

что устарело;

что дублируется;

что противоречит другим частям проекта;

какие документы потеряли актуальность;

какие промты устарели;

какие архитектурные решения больше не используются;

какие каталоги и файлы являются "мёртвыми".


Сформируй подробный отчёт.


---

Этап 2. Определить каноническую архитектуру

После анализа определить единственную каноническую структуру Workspace OS.

Для каждого компонента определить:

назначение;

ответственность;

зависимости;

жизненный цикл;

место в архитектуре;

владельца (агент/модуль).


Удалить неоднозначности.


---

Этап 3. Архитектурный манифест

Создать документ

ARCHITECTURE_MANIFEST.md

В котором определить:

миссию платформы;

главные архитектурные принципы;

основные правила;

границы ответственности;

Reuse First;

Single Source of Truth;

Event Driven;

Documentation First;

Project State First;

Engineering Memory;

Backward Compatibility;

минимизацию дублирования;

расширяемость;

масштабируемость.

Этот документ становится главным архитектурным законом проекта.


---

Этап 4. Консолидация документации

Проверить всю документацию.

Для каждого документа определить статус:

ACTIVE

LEGACY

ARCHIVED

DRAFT

OBSOLETE

Устаревшие документы:

не удалять;

переместить в архив;

сохранить историю.

Актуальную документацию переписать в соответствии с текущим состоянием проекта.


---

Этап 5. Консолидация промтов

Проверить все системные промты.

Особенно:

главный системный промт Buffy;

архитектурные промты;

инженерные промты;

ревью;

планирование;

кодогенерацию.

Удалить:

дубли;

устаревшие инструкции;

конфликтующие правила.

Выделить единый базовый системный промт (Core Prompt), определяющий личность, обязанности, ограничения и базовое поведение Buffy. Все остальные промты должны расширять его, а не переопределять.


---

Этап 6. Консолидация модулей

Проверить:

Router

Telegram

MCP

Memory

Knowledge

Registry

Context

Tool Runtime

Plugin API

EventBus

Все обнаруженные дубли:

объединить;

либо оформить как адаптеры;

либо задокументировать причину их существования.


---

Этап 7. Единая терминология

Проверить использование терминов.

Например:

Workspace

Project

Module

Agent

Tool

Plugin

Connector

Integration

Knowledge

Memory

Project Book

Engineering Memory

Lifecycle

Registry

Decision Log

Pulse

Во всём проекте использовать одинаковые определения.

Создать единый глоссарий.


---

Этап 8. Lifecycle

Для каждого ключевого компонента определить жизненный цикл.

Создать описание:

создание;

инициализация;

работа;

обновление;

завершение;

архивация;

удаление.

Ни один компонент не должен существовать без описанного Lifecycle.


---

Этап 9. Самоконсистентность

Спроектировать механизм автоматической проверки согласованности системы.

Он должен обнаруживать:

архитектурный дрейф;

устаревшую документацию;

битые ссылки;

дубли;

неиспользуемые модули;

несоответствие Roadmap;

несоответствие Registry;

несоответствие Project Book.


---

Этап 10. Финальная структура

После завершения консолидации представить:

обновлённую архитектурную схему;

новую структуру каталогов;

реестр компонентов;

список архивированных документов;

список обновлённых документов;

список удалённых дублирований;

перечень принятых архитектурных решений;

список задач, оставшихся после консолидации.



---

Ограничения

Во время выполнения этой задачи запрещено:

добавлять новые пользовательские функции;

изменять поведение системы без необходимости;

переписывать рабочий код ради красоты;

удалять историю проекта.


Все изменения должны быть обратимыми, максимально безопасными и сопровождаться обоснованием.


---

Критерий завершения

Консолидация считается завершённой только тогда, когда:

архитектура, код, документация и промты полностью согласованы между собой;

существует единый архитектурный манифест;

существует единый Core Prompt;

устранены критические дублирования;

вся документация имеет актуальный статус;

создан план автоматической проверки консистентности.


Это не рефакторинг. Это переход проекта из стадии активного проектирования в стадию зрелой инженерной платформы. Именно после такого этапа дальнейшее развитие будет происходить быстрее и с гораздо меньшим риском накопления архитектурного долга.
