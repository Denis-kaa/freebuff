PROMPT 13 — UNIVERSAL VIEWS ENGINE

Контекст

Продолжаем разработку существующего приложения управления проектами и производством мерча внутри общей концепции Workspace.

Уже реализовано / проектируется:

- Projects
- Project Items
- Tasks
- Payment
- Documents
- Project Drawer
- Dashboard
- Plug & Play Dashboard
- Dynamic Widgets
- Dynamic Columns
- Custom Fields
- сохранение пользовательской конфигурации

На предыдущем этапе был создан фундамент:

DATA
  ↓
CONFIGURATION
  ↓
UI

Теперь необходимо реализовать следующий слой:

UNIVERSAL VIEWS

Главная идея:

«Одни и те же данные должны отображаться разными способами без создания отдельных бизнес-сущностей и отдельных страниц под каждый сценарий.»

Например:

Projects
   │
   ├── Table View
   ├── Calendar View
   └── Board View

Это разные представления одних и тех же проектов.

---

1. VIEW КАК ОТДЕЛЬНАЯ КОНФИГУРАЦИЯ

Создать сущность:

View

View не хранит проекты.

View хранит только:

- источник данных;
- тип представления;
- отображаемые поля;
- фильтры;
- сортировку;
- группировку;
- настройки отображения.

Пример:

{
  "name": "Мои проекты",
  "entity": "projects",
  "type": "table",
  "filters": [],
  "sorting": [],
  "grouping": null,
  "columns": []
}

---

2. VIEW TYPES

На этом этапе поддержать три типа:

table
calendar
board

Архитектура должна позволять позже добавить:

timeline
gallery
list

но НЕ реализовывать их сейчас.

---

3. ОДИН VIEW ENGINE

Не создавать три независимых системы.

Использовать:

View Engine

с renderer-ами:

TableRenderer
CalendarRenderer
BoardRenderer

Архитектура:

ViewConfig
    ↓
Query Engine
    ↓
Data
    ↓
Renderer

---

4. TABLE VIEW

Table View использует существующий DataTable.

Пользователь может настроить:

Колонки
Фильтры
Сортировку
Группировку

Например:

Мои проекты

Проект | Менеджер | Дедлайн | Риск | Следующее действие

---

5. CALENDAR VIEW

Calendar View должен использовать те же Projects и Tasks.

Не создавать отдельные Calendar Events только ради отображения.

Источники:

Project.deadline
Task.due_date

Минимально поддержать:

Month
Week
Day

7. CALENDAR FILTERING

Calendar должен использовать тот же Filter Engine.

Например:

9. BOARD DRAG & DROP

При переносе:

Design
→
Production

изменяется:

Project.stage

через существующий API.

Например:

PATCH /api/v1/projects/{id}

Никакой отдельной Board Database.

---

10. ЕДИНЫЙ QUERY ENGINE

Это ключевая часть этапа.

Не писать отдельно:

tableQuery()
calendarQuery()
boardQuery()

Создать общий механизм:

QueryEngine

который принимает:

entity
filters
sorting
grouping
pagination

Например:

interface QueryConfig {
  entity: string
  filters?: FilterConfig[]
  sorting?: SortConfig[]
  grouping?: GroupConfig
  pagination?: PaginationConfig
}

---

11. FILTER ENGINE

Создать универсальную структуру фильтров.

Например:

{
  "field": "risk_level",
  "operator": "equals",
  "value": "High"
}

Поддержать минимум:

equals
not_equals
contains
starts_with
greater_than
less_than
greater_or_equal
less_or_equal
is_empty
is_not_empty

---

12. ЛОГИЧЕСКИЕ УСЛОВИЯ

Поддержать:

AND
OR

Например:

Manager = Денис
AND
Risk = High

или:

Risk = High
OR
Risk = Critical

Архитектура должна позволять вложенные группы условий.

Например:

Manager = Денис
AND
(
  Risk = High
  OR
  Risk = Critical
)

15. SORTING ENGINE

Единый механизм:

SortConfig

Например:

{
  "field": "deadline",
  "direction": "asc"
}

Поддержать несколько сортировок:

Risk DESC
Deadline ASC

---

16. GROUPING ENGINE

Добавить:

GroupConfig

Например:

{
  "field": "stage"
}

Table может отображать группы:

DESIGN
────────
P001
P002

PRODUCTION
───────────
P003
P004

Board использует тот же GroupConfig.

---

17. VIEW CONFIGURATION

Общая структура:

interface ViewConfig {
  id: string
  name: string
  entity: string
  type: ViewType

  columns?: ColumnConfig[]

  filters?: FilterConfig[]

  sorting?: SortConfig[]

  grouping?: GroupConfig

  settings?: Record<string, unknown>
}

---

18. VIEW SETTINGS

Разные Renderer могут иметь собственные настройки.

Например:

column_widths

Не смешивать эти настройки с бизнес-данными.

24. DEFAULT VIEW

Каждая сущность может иметь default View.

Например:

Projects
→
Все проекты

Но пользователь может выбрать:

Мои проекты

25. URL STATE

Желательно, чтобы View можно было открыть напрямую:

/projects?view=my-projects

или:

/workspace/views/{view_id}

Предпочтительно использовать стабильный "view_id".

26. BACKEND

API:

GET    /api/v1/views
POST   /api/v1/views
GET    /api/v1/views/{id}
PATCH  /api/v1/views/{id}
DELETE /api/v1/views/{id}

Query:

GET /api/v1/projects

должен принимать:

filters
sorting
grouping
pagination

или эквивалентную структурированную форму.

---

27. НЕ ДОВЕРЯТЬ CLIENT-SIDE FILTERS

Если данных много:

НЕ загружать все проекты во frontend и потом фильтровать JavaScript.

Основные:

filter
sort
pagination

должны выполняться backend/database.

---

28. PAGINATION

Table:

server-side pagination.

Calendar:

запрашивать только нужный диапазон дат.

Например:

2026-09-01
→
2026-09-30

Board:

использовать pagination / lazy loading, если данных много.

---

29. PERFORMANCE

Не выполнять отдельный SQL query для каждого проекта.

Не делать:

100 projects
→
100 additional queries

Избегать N+1.

Использовать:

selectinload
joinedload

там, где это оправдано.

---

30. CUSTOM FIELDS

Query Engine должен уметь работать с Custom Fields.

Например:

Приоритет клиента = VIP

может использоваться как:

filter
sort
group

если тип поля это допускает.

---

31. FIELD CAPABILITIES

Каждое поле должно иметь metadata:

interface FieldDefinition {
  key: string
  label: string
  type: string

  sortable: boolean
  filterable: boolean
  groupable: boolean
  editable: boolean
}

Таким образом UI сам понимает:

можно ли поле использовать в фильтре.

---

32. НЕ ПОКАЗЫВАТЬ НЕПОДХОДЯЩИЕ ОПЕРАЦИИ

Например:

UUID:

group by

не показывать.

Long Text:

sort

не показывать, если backend этого не поддерживает.

File:

numeric comparison

не показывать.

36. ВАЖНЫЙ ПРИНЦИП

Widget не должен копировать QueryConfig View.

Лучше:

widget.view_id

Если View изменился:

Widget автоматически использует новую конфигурацию.

---

37. CALENDAR + TASKS

Calendar View должен уметь объединять несколько типов данных:

Projects
Tasks

Но Query Engine должен сохранить тип сущности.

Например:

CalendarItem {
  entityType: "project" | "task"
  entityId: string
  date: Date
  title: string
}

Клик должен вести к соответствующей сущности.

---

44. DEFINITION OF DONE

Этап считается завершённым, если:

- существует единый View Engine;
- Table / Calendar / Board используют одну модель View;
- существует единый Query Engine;
- существуют универсальные Filters;
- существует Sorting;
- существует Grouping;
- Views можно создавать;
- Views можно сохранять;
- Views можно удалять;
- Views можно делать personal/shared;
- Custom Fields участвуют в View;
- Dashboard Widgets могут ссылаться на Views;
- Board может изменять Stage;
- Calendar показывает Projects и Tasks;
- данные не дублируются;
- server-side filtering работает;
- server-side sorting работает;
- pagination работает;
- нет N+1;
- права доступа проверяются на backend.

---

45. АРХИТЕКТУРНЫЙ РЕЗУЛЬТАТ

После этого этапа система должна иметь:

                     WORKSPACE
                         │
                         ▼
                        DATA
                         │
                   QUERY ENGINE
                         │
                    VIEW CONFIG
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
        TABLE         CALENDAR         BOARD
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                       DRAWER

Один Project:

P001

не принадлежит Table.

Не принадлежит Calendar.

Не принадлежит Board.

Он принадлежит:

DATA

А:

Table
Calendar
Board
Dashboard

— это только разные способы посмотреть на эти данные.

Это фундаментальная архитектура Workspace.

НЕ превращать этот этап в отдельный CRM-модуль.

НЕ добавлять новые бизнес-сущности без необходимости.

НЕ делать отдельные страницы под каждый сценарий.

НЕ дублировать данные.

Сначала добиться стабильной модели:

DATA → QUERY → VIEW → RENDER

И только после этого переходить к следующему крупному этапу.
