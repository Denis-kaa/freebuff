PROMPT 20 — PRODUCTION HARDENING / ФИНАЛЬНЫЙ АУДИТ WORKSPACE

Контекст

Мы завершаем разработку Workspace-приложения для управления проектами и производством мерча.

Это финальный этап разработки.

До этого уже реализованы и должны существовать:

- Projects;
- Project Items;
- Tasks;
- PaymentInfo;
- DocumentStatus;
- Dashboard;
- Plug & Play Widgets;
- Dynamic Columns;
- Custom Fields;
- Universal Views;
- Filters;
- Sorting;
- Grouping;
- Table View;
- Calendar View;
- Universal Entity Drawer;
- Import / Export Excel;
- Google Sheets integration;
- Workspace Settings;
- Permissions;
- базовые Automation / Formula Foundation;
- AI Layer.

Главный принцип:

«Не добавлять новые крупные функциональные подсистемы.»

Задача этого этапа — проверить всё существующее, устранить архитектурные проблемы, закрыть безопасность, ошибки, производительность, тестирование и подготовить приложение к реальному развёртыванию.

---

1. ГЛАВНАЯ ЗАДАЧА

Проведи полный Production Audit всего проекта.

Не переписывай работающие части без необходимости.

Сначала:

1. изучи текущую кодовую базу;
2. определи архитектуру;
3. найди дублирование;
4. найди потенциальные баги;
5. найди security issues;
6. найди проблемы с PostgreSQL;
7. найди проблемы API;
8. найди проблемы frontend state;
9. найди проблемы Workspace isolation;
10. только после этого внеси необходимые изменения.

Не делать «рефакторинг ради рефакторинга».

---

2. НЕ ДОБАВЛЯТЬ НОВЫЕ ФИЧИ

На этом этапе запрещено самостоятельно добавлять:

Если обнаружена проблема архитектуры — исправить её.

Если обнаружена отсутствующая функция, которая не относится к production hardening, занести её в:

"POST_MVP.md"

но не реализовывать.

5. WORKSPACE ISOLATION

Это один из самых важных пунктов.

Проверить ВСЕ API endpoints.

Каждый запрос должен учитывать:

"workspace_id"

Нельзя:

Workspace A

получить:

Project из Workspace B.

То же самое для:

- Projects;
- Tasks;
- Items;
- Payments;
- Documents;
- Custom Fields;
- Views;
- Widgets;
- Dashboard configuration.

Workspace isolation проверять именно на backend.

Нельзя полагаться только на frontend.

15. API ERROR HANDLING

Все API ошибки должны возвращаться предсказуемо.

Например:

400 — validation error

401 — unauthorized

403 — forbidden

404 — not found

409 — conflict

422 — validation

500 — internal server error

Не отдавать пользователю stack trace.

16. GLOBAL ERROR HANDLER

"error": {
"code": "PROJECT_NOT_FOUND",
"message": "Project not found"
}
}

Не показывать пользователю:

Python traceback.

ГЛАВНОЕ ПРАВИЛО

Это PROMPT 19 — ФИНАЛЬНЫЙ ЭТАП.

После его завершения не создавай новый большой архитектурный этап самостоятельно.

Если находишь новую идею или потенциальную фичу:

не реализуй её автоматически.

Запиши её в:

"POST_MVP.md"

Главная цель:

«Не бесконечно расширять Workspace, а остановиться в правильной точке и получить стабильный, безопасный и реально используемый продукт.»

Финальный результат должен быть:

Production-ready Workspace application, а не бесконечный набор экспериментальных функций.
