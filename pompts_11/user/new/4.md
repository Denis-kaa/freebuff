PROMPT 04 — DASHBOARD ENGINE / PLUG & PLAY WIDGETS

Контекст

Уже реализованы:

- Workspace;
- Projects;
- Dynamic Fields;
- Saved Views;
- Project Drawer;
- Project Items;
- Production;
- Tasks;
- Documents;
- Events;
- Activity.

Теперь необходимо реализовать Dashboard Engine.

Это НЕ просто страница с несколькими карточками.

Главная концепция:

«Dashboard — это конструктор рабочего пространства.»

Пользователь должен сам решать:

- какие виджеты видеть;
- какие удалить;
- какие добавить;
- в каком порядке они расположены;
- какого они размера;
- какие данные они показывают;
- какие фильтры используют;
- какой Dashboard является основным.

---

1. Главный принцип

Не делать:

Dashboard.tsx

<Deadlines />
<Risks />
<Tasks />
<Calendar />
<Finance />

с жёстко заданной структурой.

Вместо этого создать:

Dashboard Engine
       ↓
Widget Registry
       ↓
Widget Instances
       ↓
Layout Configuration
       ↓
Data Sources

---

2. Widget Registry

Создать центральный реестр виджетов.

Например:

widgets/
├── registry
├── calendar
├── today-tasks
├── deadlines
├── risks
├── projects
├── finance
├── production
├── activity
└── stats

Каждый виджет должен иметь metadata:

{
  type: "calendar",
  name: "Календарь",
  description: "Проекты, задачи и события по датам",
  icon: Calendar,
  category: "planning",
  defaultSize: {
    w: 6,
    h: 4
  }
}

5. Drag & Drop

Пользователь должен иметь возможность:

перетащить виджет

и изменить его позицию.

Например:

Calendar
↓
перетащили вправо

Конфигурация автоматически сохраняется.

Не требовать отдельной кнопки Save для каждого движения.

---

6. Resize

Каждый виджет должен поддерживать изменение размера.

Например:

Calendar

6 × 4

можно сделать:

12 × 6

или:

4 × 3

Использовать grid layout library, совместимую с React/Next.js.

Не писать сложный drag-and-drop engine вручную, если существует стабильная библиотека.

9. Hide vs Delete

Разделить:

Hide

и:

Delete

Hide:

- виджет исчезает;
- конфигурация сохраняется;
- можно вернуть.

Delete:

- Widget Instance удаляется;
- данные не удаляются.

15. Widget Configuration

У каждого instance должна быть конфигурация.

Например:

{
  "widget_type": "calendar",
  "settings": {
    "view": "month",
    "show_deadlines": true,
    "show_tasks": true,
    "show_payments": true
  }
}

Не создавать отдельную database table под каждый тип виджета.

Использовать общую модель:

dashboard_widgets

  ↓

44. Race Conditions

Если два пользователя одновременно редактируют общий Dashboard:

не должно происходить silent corruption layout.

Минимум:

updated_at

или:

version

Для MVP можно применить optimistic locking.

---

45. Performance

Не делать:

Dashboard
 ↓
GET all projects
 ↓
GET all tasks
 ↓
GET all events
 ↓
frontend filters everything

Это запрещено.

Каждый Widget получает только необходимые данные.

Например:

Deadlines
→ ближайшие 7 дней

Tasks
→ сегодня + просроченные

Risks
→ High/Critical

Фильтрация выполняется backend/database-side.

Ключевая архитектурная цель

После этого этапа должно быть возможно сказать:

««Я сам собираю свой рабочий экран».»

Например:

Мой Dashboard

┌──────────────────────────────┬──────────────┐
│                              │              │
│          КАЛЕНДАРЬ           │ ЧТО СДЕЛАТЬ │
│                              │    СЕГОДНЯ   │
│                              │              │
├──────────────────────────────┴──────────────┤
│             БЛИЖАЙШИЕ ДЕДЛАЙНЫ              │
├──────────────────────────────┬──────────────┤
│         ПРОИЗВОДСТВО         │    РИСКИ     │
└──────────────────────────────┴──────────────┘

Затем пользователь может полностью изменить этот экран.

Например:

Удалить Риски
Удалить Финансы
Добавить KPI
Добавить Производство
Растянуть Календарь
Создать второй Dashboard «Финансы»

И система должна воспринимать это не как изменение кода, а как изменение конфигурации Workspace.

Это фундаментальная архитектура продукта.
