PROMPT 14 — UNIVERSAL DRAWER / ДИНАМИЧЕСКАЯ КАРТОЧКА

Контекст

Продолжаем существующее приложение управления проектами и производством мерча внутри концепции Workspace.

Уже реализовано / проектируется:

- Projects
- Project Items
- Tasks
- PaymentInfo
- DocumentStatus
- Dashboard
- Plug & Play Dashboard
- Dynamic Widgets
- Dynamic Columns
- Custom Fields
- Universal Views
- Table / Calendar / Board
- Filters
- Sorting
- Grouping
- сохранение View Configuration

Архитектурный принцип:

DATA
  ↓
QUERY
  ↓
VIEW
  ↓
RENDER

Теперь необходимо реализовать следующий слой:

ENTITY
  ↓
UNIVERSAL DRAWER

Главная идея:

«Карточка сущности не должна быть жёстко зашитой страницей. Это рабочая панель, которая собирается из блоков.»

Пользователь открывает проект из:

- Table;
- Calendar;
- Board;
- Dashboard Widget.

Во всех случаях открывается одна и та же система Drawer.

2. DRAWER ДОЛЖЕН БЫТЬ UNIVERSAL

Не создавать:

ProjectDrawer
TaskDrawer
ClientDrawer
...

как полностью независимые системы.

Создать общий:

EntityDrawer

который принимает:

entityType
entityId

Например:

<EntityDrawer
  entityType="project"
  entityId={projectId}
/>

Для Task архитектура должна позволять:

<EntityDrawer
  entityType="task"
  entityId={taskId}
/>

Но на этом этапе полноценно реализовать прежде всего Project.

45. DEFINITION OF DONE

Этап завершён, если:

- существует Universal Entity Drawer;
- Project открывается из Table;
- Project открывается из Calendar;
- Project открывается из Board;
- Project открывается из Dashboard;
- Drawer поддерживает inline editing;
- Project Items работают внутри Drawer;
- Tasks работают внутри Drawer;
- Payment работает внутри Drawer;
- Documents работают внутри Drawer;
- Custom Fields работают внутри Drawer;
- блоки Drawer можно добавлять;
- блоки можно скрывать/удалять;
- блоки можно переставлять;
- конфигурация сохраняется;
- данные не дублируются;
- изменения отражаются во всех Views;
- backend проверяет permissions;
- нет необходимости создавать отдельную страницу проекта.

ГЛАВНЫЙ АРХИТЕКТУРНЫЙ РЕЗУЛЬТАТ

После этого этапа приложение должно работать следующим образом:

                       WORKSPACE
                           │
                           ▼
                          DATA
                           │
                    ┌──────┴──────┐
                    ▼             ▼
                 QUERY          ENTITY
                    │             │
              ┌─────┼─────┐       │
              ▼     ▼     ▼       ▼
            TABLE CALENDAR BOARD DRAWER
              │     │     │       │
              └─────┴─────┴───────┘
                            │
                            ▼
                         PROJECT

То есть:

View отвечает за то, как смотреть на данные.

Drawer отвечает за то, как работать с конкретной сущностью.

Workspace Configuration отвечает за то, как пользователь хочет видеть интерфейс.

А сами бизнес-данные остаются независимыми от UI.

НЕ превращать этот этап в новую CRM.

НЕ создавать отдельные страницы для каждого сценария.

НЕ создавать копии Project для Drawer.

НЕ добавлять комментарии, чат, Activity Feed, AI Assistant или Automation Engine.

Это следующий слой архитектуры Workspace, а не расширение бизнес-функционала мерч-системы.
