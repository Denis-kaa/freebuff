PROMPT 05 — CALENDAR & EVENTS ENGINE

Контекст

В предыдущих этапах реализованы:

- Workspace;
- Projects;
- Project Items;
- Production workflow;
- Tasks;
- Documents;
- Dashboard Engine;
- Plug & Play Widgets;
- Widget Registry;
- настраиваемые Dashboard;
- Project Drawer.

Теперь необходимо реализовать Calendar & Events Engine.

Главная идея:

«Календарь не должен быть отдельным независимым модулем, куда менеджер вручную заносит всё подряд.»

Он должен быть единым представлением временных событий всей системы.

Из проектов автоматически попадают:

- дедлайны;
- авансы;
- доплаты;
- отгрузки;
- отгрузки сигналов;
- производственные события.

Из задач:

- сроки задач.

Из Project Items:

- даты сигналов;
- производственные даты;
- даты отгрузок.

Из документов:

- при необходимости даты документооборота.

Также пользователь может создать собственное событие.

---

1. Архитектурный принцип

Не делать отдельные копии данных только ради календаря.

Например, если в Project уже существует:

deadline

не нужно создавать ещё:

calendar_deadline

Источником истины остаётся Project.

Calendar Engine создаёт унифицированное представление события.

Архитектура:

Projects
Tasks
Project Items
Payments
Production
Documents
Custom Events
       ↓
   Event Sources
       ↓
 Calendar Event Service
       ↓
 Unified Calendar Events
       ↓
 Calendar UI

2. Unified Event

Создать единую структуру события:

type CalendarEvent = {
  id: string
  type: EventType

  title: string
  description?: string

  start_at: string
  end_at?: string

  all_day: boolean

  project_id?: string
  project_item_id?: string
  task_id?: string
  document_id?: string

  source_type: string
  source_id: string

  status?: string
  priority?: string

  metadata?: Record<string, unknown>
}

4. Event Sources

Каждый event должен иметь источник.

Например:

source_type = "project"
source_id = "P024"

или:

source_id = "TASK123"

или:

source_type = "project_item"
source_id = "ITEM456"

Это позволит при клике понимать, куда переходить.

24. System Event Editing

Системное событие нельзя редактировать непосредственно в Calendar, если оно является производным от другого объекта.

Например:

P024 deadline

При попытке изменить:

31 августа → 3 сентября

не менять event.

Вместо этого:

Изменить дедлайн проекта?

и открыть соответствующий Project Drawer.

34. Event Aggregation

CalendarService должен собирать:

Projects
+
Tasks
+
Project Items
+
Payments
+
Custom Events

в:

CalendarEvent[]

Сделать отдельные adapters:

ProjectEventAdapter
TaskEventAdapter
ProductionEventAdapter
PaymentEventAdapter
CustomEventAdapter

Тогда новый источник можно добавить без переписывания CalendarService.

---

35. Event Adapter Interface

Например:

interface EventAdapter {
  getEvents(
    from: Date,
    to: Date,
    context: CalendarContext
  ): Promise<CalendarEvent[]>
}

Каждый adapter реализует этот интерфейс.

---

36. Event Deduplication

Система не должна показывать один и тот же event дважды.

Например:

Task deadline

не должен одновременно попасть через TaskAdapter и ProjectAdapter.

Создать deterministic event ID:

task:{task_id}:deadline

или эквивалентный механизм.

---

37. Recurring Events

каждый месяц

Для MVP достаточно модели:

recurrence_rule nullable

38. Timezone

Очень важно.

Все даты/время хранить в UTC.

Workspace/User имеет timezone.

UI показывает локальное время пользователя.

Не использовать:

new Date().toISOString()

как единственную бизнес-логику без понимания timezone.

---

Например:

03:00

из-за timezone conversion.
