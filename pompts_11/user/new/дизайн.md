# PROMPT — WORKSPACE DASHBOARD 2.0: ПОЛНОСТЬЮ КОНФИГУРИРУЕМЫЙ DASHBOARD

## ⚠️ PREAMBLE — ПРИОРИТЕТ АРХИТЕКТУРЫ

**Этот промпт РАСШИРЯЕТ PROMPT 4 из `merged_all.md`.**  
В случае противоречий — приоритет у PROMPT 4.

Архитектурные требования (Widget Registry, Multiple Dashboards, Error Isolation, Widget Data Layer, Permissions, Templates, Race Conditions, Views Integration) уже описаны в PROMPT 4.  
**Этот промпт фокусируется на UX-реализации и детализации**, не дублируя архитектуру.

Перед началом работы **обязательно изучи PROMPT 4** и убедись, что архитектурный фундамент уже заложен. Если нет — сначала реализуй его.

## 🎯 ГЛАВНАЯ КОНЦЕПЦИЯ

«Dashboard — это не фиксированная страница с заранее заданными блоками. Это персональное рабочее пространство, которое пользователь сам собирает из виджетов.»

**Не пользователь подстраивается под интерфейс. Интерфейс подстраивается под пользователя.**

Пользователь должен иметь возможность:
- добавить виджет;
- удалить виджет;
- скрыть виджет;
- переместить виджет;
- изменить его размер;
- изменить количество отображаемых элементов;
- изменить фильтры;
- изменить сортировку;
- настроить период;
- добавлять/удалять/переставлять колонки;
- проваливаться из компактного Dashboard в полный список данных;
- открывать конкретный проект через существующий Project Drawer.

4. Найди существующие Table / Project List.
5. Найди Project Drawer.
6. Найди View Configuration.
7. Найди Custom Fields.
8. Найди API Dashboard / Projects.
9. Проверь, какие функции уже реализованы.
10. Не дублируй существующую функциональность.

Если текущая архитектура уже позволяет реализовать часть требований — используй её.  
Не переписывай рабочие компоненты без необходимости.

## 2. MULTIPLE DASHBOARDS (КРИТИЧНО ИЗ PROMPT 4)

Пользователь должен иметь возможность создавать **несколько Dashboard** в рамках одного Workspace.

### 2.1 Dashboard Switcher

В верхней части Dashboard:
```
┌──────────────────────────────────────────────────────┐
│ [ Мой Dashboard ▼ ]                  + Настроить    │
├──────────────────────────────────────────────────────┤
```

При клике на `[ Мой Dashboard ▼ ]` открывается меню:
```
┌─────────────────────────────┐
│ МОЙ DASHBOARD          ✓    │
│ ПРОИЗВОДСТВО                 │
│ ФИНАНСЫ                      │
│ РУКОВОДИТЕЛЬ                 │
│ ─────────────────────────── │
│ + Новый Dashboard            │
└─────────────────────────────┘
```

### 2.2 Create Dashboard

При нажатии `+ Новый Dashboard`:
```
┌─────────────────────────────┐
│ НОВЫЙ DASHBOARD             │
│                             │
│ Название                    │
│ [ Производство            ] │
│                             │
│ Шаблон                      │
│ ○ Пустой                    │
│ ○ Менеджер                  │
│ ● Производство              │
│ ○ Финансы                   │
│ ○ Руководитель              │
│                             │
│ [ Создать ]                 │
└─────────────────────────────┘
```

### 2.3 Dashboard Actions

У каждого Dashboard в меню `⋮`:
- Переименовать
- Дублировать
- Сделать основным
- Удалить

**Default Dashboard:**
- Только один Dashboard в Workspace может быть `is_default = true`.
- При входе `/` открывается default Dashboard.
- Если пользователь удаляет default Dashboard, система автоматически назначает новый default.

### 2.4 Duplicate Dashboard

При дублировании:
- Копируются: widgets, layout, settings.
- **НЕ копируются** сами проекты/данные.
- Название: `Производство — копия`.

### 2.5 Personal vs Shared Dashboard

**MVP:** Все Dashboard — personal (каждый пользователь видит свой).

**Архитектура должна позволять в будущем:**
- Shared Dashboard (виден всем участникам Workspace).
- Owner/Admin могут редактировать shared Dashboard.

## 3. WIDGET REGISTRY (ДЕТАЛИЗАЦИЯ ИЗ PROMPT 4)

### 3.1 Интерфейс виджета

Каждый виджет должен реализовывать единый интерфейс:

```typescript
interface DashboardWidget {
  type: string;
  title: string;
  description?: string;
  icon: LucideIcon;
  category: WidgetCategory;
  defaultSize: { w: number; h: number };
  supportedSizes: Array<{ w: number; h: number }>;
  settingsSchema: JSONSchema; // для формы настроек
  render(props: WidgetProps): ReactNode;
}

type WidgetCategory = 
  | 'planning'      // Календарь, Задачи, Дедлайны
  | 'projects'      // Проекты, Риски
  | 'finance'       // Оплаты, Финансы
  | 'production'    // Производство, Сигналы
  | 'analytics'     // KPI, Графики
  | 'custom';       // Пользовательские
```

### 3.2 Категории виджетов

В Widget Picker виджеты группируются по категориям:
```
┌─────────────────────────────┐
│ ДОБАВИТЬ ВИДЖЕТ             │
│                             │
│ 🔎 Поиск                    │
│                             │
│ ПЛАНИРОВАНИЕ                │
│ 📅 Календарь                │
│ ✅ Что сделать сегодня      │
│ 📆 Ближайшие дедлайны       │
│                             │
│ ПРОЕКТЫ                     │
│ 📁 Приоритетные проекты     │
│ ⚠ Риски                     │
│ 📊 Последние проекты        │
│                             │
│ ФИНАНСЫ                     │
│ 💳 Оплаты                   │
│ 💰 Финансовый KPI           │
│                             │
│ ПРОИЗВОДСТВО                │
│ 🏭 Производство             │
│ 📦 Сигналы                  │
│                             │
│ АНАЛИТИКА                   │
│ 📈 График                   │
│ 🔢 KPI                      │
└─────────────────────────────┘
```

### 3.3 Расширяемость

Чтобы добавить новый виджет в будущем, разработчик должен:
1. Создать компонент виджета.
2. Зарегистрировать его в `WidgetRegistry`.
3. **НЕ переписывать** Dashboard Engine.

## 4. WIDGET DATA LAYER (КРИТИЧНО ИЗ PROMPT 4)

### 4.1 Архитектура

```
Widget UI
    ↓
Widget Data Hook (useWidgetData)
    ↓
API Endpoint
    ↓
Service Layer
    ↓
Database
```

**Widget UI не должен самостоятельно писать SQL.**

### 4.2 API контракты для каждого типа виджета

Создать отдельные endpoints для каждого типа данных:

```
GET /api/v1/dashboard-data/calendar
    ?from=2026-09-01
    &to=2026-09-30
    &types=deadline,task,payment
    
GET /api/v1/dashboard-data/tasks
    ?period=today
    &assignee=current_user
    &limit=10
    
GET /api/v1/dashboard-data/deadlines
    ?period=7days
    &limit=10
    
GET /api/v1/dashboard-data/risks
    ?levels=high,critical
    &limit=10
    
GET /api/v1/dashboard-data/projects
    ?sort=priority
    &limit=10
    
GET /api/v1/dashboard-data/finance
    ?status=unpaid
    
GET /api/v1/dashboard-data/production
    ?stages=mockup,signal,batch
```

### 4.3 Performance

- **НЕ загружать** все 1000 проектов на Dashboard.
- Каждый виджет запрашивает **только необходимые данные**.
- Фильтрация выполняется **backend/database-side**.

### 4.4 Auto-refresh

Подготовить архитектуру для автоматического обновления:
- **MVP:** manual refresh + refetch при возвращении на вкладку.
- **Будущее:** WebSocket / SSE для real-time updates.

## 5. ERROR ISOLATION (КРИТИЧНО ИЗ PROMPT 4)

### 5.1 Каждый виджет — отдельный Error Boundary

Если один виджет упал, остальные продолжают работать.

```typescript
<ErrorBoundary fallback={<WidgetError widget={widget} />}>
  <WidgetComponent {...widget} />
</ErrorBoundary>
```

### 5.2 Loading States

Каждый виджет должен иметь собственный skeleton:
```
┌──────────────────────┐
│ КАЛЕНДАРЬ            │
│                      │
│ ░░░░░░░░░░░░         │
│ ░░░░░░░░░░░░         │
│ ░░░░░░░░░░░░         │
└──────────────────────┘
```

### 5.3 Error States

Если виджет не смог загрузить данные:
```
┌──────────────────────┐
│ КАЛЕНДАРЬ            │
│                      │
│ Не удалось загрузить │
│ [ Повторить ]        │
└──────────────────────┘
```

**НЕ показывать** пользователю `500 Internal Server Error`.

### 5.4 Empty States

Если данных нет:
```
┌──────────────────────┐
│ БЛИЖАЙШИЕ ДЕДЛАЙНЫ   │
│                      │
│ Нет дедлайнов на     │
│ ближайшие 7 дней     │
└──────────────────────┘
```

## 7. WIDGET GRID (UX-ДЕТАЛИЗАЦИЯ)

Dashboard использовать как grid.

Каждый виджет является отдельным элементом grid.

Пользователь может:
- drag;
- drop;
- resize.

Поддержать произвольные комбинации размеров:
- 1 × 1
- 2 × 1
- 1 × 2
- 2 × 2
- 3 × 1
- 1 × 3
- 3 × 2
- 2 × 3
- 4 × 1
- 4 × 2
- 4 × 4

и другие размеры, которые позволяет текущая сетка.

**Не ограничивать** пользователя искусственным набором из 2–3 размеров.

---

## 8. RESIZE МЫШЬЮ

На desktop пользователь должен иметь возможность растягивать виджет мышью.

При изменении размера виджет должен занимать соответствующее количество grid cells.  
Размер должен привязываться к сетке.

---

## 9. DRAG & DROP

Пользователь берет карточку мышью и перетаскивает её.

Во время drag показывать **placeholder** в том месте, куда попадёт виджет.

После drop виджет занимает именно это место.

**Не просто** «переставить в начало/конец списка».  
Нужна **настоящая grid-компоновка**.

Если пользователь тащит виджет между двумя карточками — сетка должна визуально показывать место вставки.

## 12. REMOVE WIDGET

Каждый виджет имеет меню `⋮`:
- Настроить
- Изменить размер
- Скрыть
- Удалить

**Удаление виджета НЕ удаляет данные.**  
Удаляется только instance виджета из Dashboard configuration.

### 12.1 Hide vs Delete

**Hide:**
- виджет исчезает;
- конфигурация сохраняется;
- можно вернуть через `Настройки Dashboard → Скрытые виджеты`.

**Delete:**
- Widget Instance удаляется;
- данные не удаляются.

## 14. ПРИОРИТЕТНЫЕ ПРОЕКТЫ

Создать виджет: **Приоритетные проекты**.

Он показывает ограниченное количество проектов (по умолчанию 5, настраивается).

### 14.1 Как определяются приоритетные проекты

**Не зашивать** простой `ORDER BY deadline` как единственную логику.

Использовать существующие данные:
- deadline;
- risk;
- stage;
- tasks;
- payment;
- дата входа проекта;
- другие доступные параметры.

Создать понятную сортировку/приоритетизацию:
1. Критический риск.
2. Высокий риск.
3. Ближайший дедлайн.
4. Просроченные задачи.
5. Ближайшая дата производства.

**Алгоритм должен быть прозрачным.**

В интерфейсе желательно показывать: **Почему проект здесь?**

Например:
```
P024  Nike  03.09  Высокий риск
      ↑
      Высокий риск · дедлайн через 2 дня
```

## 18. СВЯЗЬ С SAVED VIEWS (ИЗ PROMPT 4)

Dashboard Widget может ссылаться на View.

### 18.1 Архитектура

```typescript
interface WidgetConfig {
  widget_type: string;
  settings: Record<string, any>;
  view_id?: string; // Ссылка на Saved View
}
```

### 18.2 Пример

Виджет **Приоритетные проекты**:
```
Источник данных:
○ Системный запрос
● Представление: "Срочные проекты"
```

Если View изменён — Widget автоматически использует новую конфигурацию.

**Widget не должен копировать QueryConfig View.**  
Лучше: `widget.view_id`.

- удалить колонку
- переместить колонку
- скрыть колонку
- изменить ширину

Например:
```
Проект | Менеджер | Дедлайн | Риск | Следующее действие
```

или:
```
Проект | Этап | Оплата | Валюта | Дедлайн
```

---

## 27. DRAG & DROP КОЛОНОК

На desktop пользователь перетаскивает заголовок `Дедлайн` и ставит перед `Риск`.

Результат:
```
Проект | Менеджер | Дедлайн | Риск | ...
```

Изменение сохраняется.

---

## 28. DRAG & DROP СТРОК

Также дать возможность менять порядок строк внутри пользовательского представления.

Например:
```
P024
P018
P031
```

Пользователь перетаскивает `P031` вверх.

Получается:
```
P031
P024
P018
```

**Это должно быть именно настройкой представления**, а не изменением реального бизнес-порядка проектов.

**Не менять** `Project.created_at` или другие бизнес-поля только ради UI-порядка.

---

## 29. ROW ORDER

Создать отдельный механизм: `view_order` или аналогичный порядок внутри конкретного View.

Например:
```
View: "Мои проекты"
порядок: P031, P024, P018

View: "Все проекты"
порядок: P001, P002, P003
```

---

## 30. SORTING VS MANUAL ORDER

Разделить:
- **Automatic sorting**
- **Manual ordering**

Если пользователь выбрал `Дедлайн ↑` — таблица сортируется автоматически.

Если включил `Ручной порядок` — появляется drag & drop строк.

**Не смешивать** эти режимы.


**Не создавать** отдельную фильтрацию специально для Dashboard.

- как показать;

## 🎯 ГЛАВНАЯ ИДЕЯ

Не воспринимай Dashboard как страницу.

Воспринимай его как: **PERSONAL WORKSPACE CANVAS**.

На нём пользователь сам собирает рабочее пространство:

```
┌───────────────┐ ┌───────────────┐
│ КАЛЕНДАРЬ     │ │ ЧТО СЕГОДНЯ   │
│               │ │               │
└───────────────┘ └───────────────┘

┌─────────────────────────────────┐
│ ПРИОРИТЕТНЫЕ ПРОЕКТЫ            │
│                                 │
│ P024                            │
│ P018                            │
│ P031                            │
│                                 │
│ Показать все →                  │
└─────────────────────────────────┘
```

Но другой пользователь может сделать:

```
┌─────────────────────────────────┐
│ МОИ ПРОЕКТЫ                     │
└─────────────────────────────────┘

```

И это всё один и тот же Workspace.

**Не пользователь подстраивается под интерфейс. Интерфейс подстраивается под пользователя.**

Именно это должно быть главным архитектурным принципом реализации.
