PROMPT 17 — WORKSPACE SETTINGS & PERMISSIONS

Контекст

Продолжаем разработку Workspace-приложения для управления проектами и производством мерча.

Уже реализованы / спроектированы:

- Projects;
- Project Items;
- Tasks;
- PaymentInfo;
- DocumentStatus;
- Dashboard;
- Plug & Play Widgets;
- Dynamic Columns;
- Custom Fields;
- Views;
- Filters;
- Sorting;
- Grouping;
- Universal Entity Drawer;
- Calendar View;
- Import / Export Excel;
- интеграция с Google Sheets.

Главная архитектурная идея проекта:

«Workspace — это рабочая оболочка, внутри которой пользователь сам собирает своё рабочее пространство.»

Приложение не должно превращаться в жёстко зашитую CRM.

Один и тот же Workspace может иметь:

- разные Dashboard;
- разные Views;
- разные наборы колонок;
- разные фильтры;
- разные виджеты;
- разные права доступа.

---

1. ЦЕЛЬ ЭТАПА

Реализовать:

Workspace Settings

и

Permissions / Roles

Необходимо отделить:

Workspace-level configuration

от:

User-level configuration

и:

Access permissions.

Архитектура должна позволять нескольким пользователям работать внутри одного Workspace, не ломая существующую систему персональных представлений.

---

2. WORKSPACE

Создать доменную сущность:

Workspace

Минимальные поля:

id
name
slug
description
owner_id
created_at
updated_at

"id" — UUID.

"slug" — уникальный идентификатор Workspace для URL/навигации.

Например:

workspace_id = ...
name = "Мерч"
slug = "merch"

3. WORKSPACE MEMBERS

Создать сущность:

WorkspaceMember

id
workspace_id

updated_at

Workspace
   │
   └── WorkspaceMember

            └── User

Один Workspace может содержать нескольких пользователей.

---

4. ROLES

На первом этапе использовать простую ролевую модель:

Owner
Admin
Manager
Viewer

Owner

Полный доступ.

Может:

- изменять Workspace;
- добавлять/удалять участников;
- изменять роли;
- удалять Workspace;
- изменять системные настройки.

Admin

Почти полный доступ.

Может:

- управлять участниками;
- управлять настройками;
- создавать Views;
- изменять Dashboard;
- работать с проектами.

Но не может удалить Workspace или изменить Owner.

Manager

Работает с данными.

Может:

- создавать проекты;
- редактировать проекты;
- создавать задачи;
- редактировать задачи;
- использовать Views;
- настраивать собственный Dashboard;
- создавать собственные Custom Fields/View Configuration, если это разрешено настройками Workspace.

Viewer

Только просмотр.

Может:

- просматривать проекты;
- открывать Drawer;
- просматривать Calendar;
- использовать фильтры;
- использовать существующие Views.

Не может изменять бизнес-данные.

---

5. НЕ СОЗДАВАТЬ СЛОЖНУЮ RBAC-СИСТЕМУ

Не создавать сейчас:

- десятки ролей;
- permission builder;
- ACL для каждого отдельного поля;
- сложную матрицу разрешений;
- enterprise policy engine.

Нужна простая и надёжная RBAC-модель.

Архитектура при этом должна позволять расширение в будущем.

---

6. PERMISSIONS

Внутри backend создать единый слой проверки:

Permission Service

Например:

can_view_project()
can_create_project()
can_update_project()
can_delete_project()

can_view_task()
can_create_task()
can_update_task()

can_manage_members()
can_update_workspace_settings()

Не размазывать проверки ролей по каждому endpoint вручную.

---

7. WORKSPACE ISOLATION

Это критически важно.

Любой объект должен принадлежать Workspace.

Например:

Project.workspace_id
Task.workspace_id
CustomFieldDefinition.workspace_id
WorkspaceView.workspace_id
DashboardConfig.workspace_id

Если сущность логически принадлежит проекту, её Workspace может определяться через Project.

Но backend должен всегда проверять принадлежность текущему Workspace.

---

8. НЕЛЬЗЯ ПОЛУЧИТЬ ДАННЫЕ ДРУГОГО WORKSPACE

Запрещён сценарий:

User A:

workspace_id = A

пытается запросить:

project_id = project_from_workspace_B

Backend должен вернуть:

403 Forbidden

или соответствующий безопасный ответ согласно существующей архитектуре.

Нельзя полагаться только на frontend.

---

9. USER SETTINGS VS WORKSPACE SETTINGS

Разделить настройки.

User settings

Принадлежат конкретному пользователю:

- Dashboard layout;
- личные Views;
- порядок виджетов;
- отображаемые колонки;
- персональные фильтры;
- предпочтительный Calendar View.

Workspace settings

Принадлежат Workspace:

- название;
- описание;
- участники;
- роли;
- доступные Custom Fields;
- общие Views;
- общие настройки приложения.

20. CHANGE ROLE

Admin/Owner может изменить:

Manager → Viewer
Viewer → Manager

Но:

Owner нельзя изменить через обычный интерфейс.

Должен существовать только один Owner, если это ограничение выбрано архитектурой.

Если потребуется передача владения:

использовать отдельную безопасную операцию:

Transfer Ownership

Не делать её обычным dropdown.

21. REMOVE MEMBER

Например:

Удалить Катю из Workspace?

Её проекты и задачи НЕ будут удалены.

Важно:

удаление участника ≠ удаление его данных.

22. DEACTIVATE MEMBER

История данных сохраняется.

23. DATA OWNERSHIP

Не привязывать бизнес-данные напрямую к существованию пользователя.

Например:

Если менеджер удалён или деактивирован:

Project не должен исчезнуть.

UI должен показать:

Неактивный пользователь

или соответствующий fallback.

38. CASCADE POLICY

Очень осторожно определить:

что должно удаляться вместе с Workspace,

а что нет.

Например:

Workspace удаляется:

→ его Projects
→ Tasks
→ Custom Fields
→ Views
→ Dashboard configs
→ Audit logs

Но User не удаляется.

Удаление Workspace должно быть защищённой операцией.

46. DEFINITION OF DONE

Этап считается завершённым, если:

- существует Workspace;
- существует Membership;
- реализованы Owner/Admin/Manager/Viewer;
- работает Workspace Switcher;
- реализован Workspace Settings;
- реализовано управление участниками;
- реализована смена ролей;
- реализована проверка permissions;
- реализована Workspace isolation;
- Custom Fields изолированы по Workspace;
- Views изолированы по Workspace;
- Dashboard Configuration изолирован по Workspace + User;
- существует минимальный Audit Log;
- существующие Projects/Tasks/Calendar/Dashboard продолжают работать;
- backend не доверяет permissions frontend;
- созданы Alembic migrations;
- написаны тесты;
- acceptance test проходит.

47. ГЛАВНЫЙ АРХИТЕКТУРНЫЙ РЕЗУЛЬТАТ

                    WORKSPACE
                        │
              ┌─────────┴─────────┐
              │                   │
          MEMBERS              DATA
              │                   │
       ┌──────┼──────┐       ┌────┼────┐
       │      │      │       │    │    │
     Owner  Admin  Manager  Projects Tasks ...
                            │
                            ▼
                     Workspace Scope
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
       Dashboard          Views           Calendar
          │                 │                 │
          └─────────────────┼─────────────────┘

Главный принцип:
