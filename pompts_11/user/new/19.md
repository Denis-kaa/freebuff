PROMPT 19 — AI LAYER / WORKSPACE INTELLIGENCE

Контекст

Продолжаем разработку Workspace-приложения для управления проектами и производством мерча.

К этому этапу уже существуют:

- Projects;
- Project Items;
- Tasks;
- PaymentInfo;
- DocumentStatus;
- Dashboard;
- Plug & Play Widgets;
- Dynamic Columns;
- Custom Fields;
- Universal Views;
- Filters;
- Sorting;
- Grouping;
- Table View;
- Calendar View;
- Universal Entity Drawer;
- Workspace Configuration;
- Import / Export;
- базовый Automation / Formula Foundation.

Главный принцип:

AI не является отдельным приложением внутри Workspace.

AI должен понимать Workspace как рабочую среду и работать с существующими данными, представлениями, задачами и сущностями.

Не создавать очередной «AI Chat».

AI должен быть инструментом Workspace.

---

1. ЦЕЛЬ

Создать AI Layer, который позволяет пользователю обращаться к данным Workspace естественным языком.

Например:

«Что мне сегодня нужно сделать?»

AI анализирует:

- задачи;
- дедлайны;
- риски;
- проекты;
- оплаты;

и формирует ответ.

Другой запрос:

«Покажи проекты с высоким риском и дедлайном в ближайшие 3 дня.»

AI не придумывает ответ.

Он выполняет структурированный запрос к Workspace.

---

2. AI НЕ ДОЛЖЕН ИМЕТЬ ПРЯМОЙ ДОСТУП К БАЗЕ

AI не должен самостоятельно генерировать SQL и выполнять его напрямую.

Архитектура:

User

↓

AI

↓

Tool / Query Layer

↓

Workspace API

↓

PostgreSQL

AI получает только разрешённые данные.

---

3. WORKSPACE TOOLS

Создать ограниченный набор инструментов.

Например:

get_projects

get_project

search_projects

get_tasks

get_today_tasks

get_deadlines

get_calendar_events

get_risks

get_payment_status

get_workspace_views

---

4. WRITE TOOLS

AI должен постепенно уметь не только читать.

Минимально:

create_task

update_task

update_project

create_project

update_custom_field

---

Но любые изменения должны проходить через существующий API.

AI:

не изменяет PostgreSQL напрямую.

AI вызывает:

POST /api/v1/tasks

PATCH /api/v1/projects/{id}

и т. д.

---

5. CONFIRMATION BEFORE WRITE

Любое потенциально опасное изменение требует подтверждения пользователя.

Например:

AI:

«Я нашёл проект P024. Изменить риск с Medium на High?»

[ Отмена ]

[ Подтвердить ]

Только после подтверждения выполняется действие.

---

6. READ OPERATIONS

Для операций чтения подтверждение не требуется.

Например:

«Какие задачи просрочены?»

AI сразу выполняет запрос.

---

7. AI CONTEXT

AI должен получать структурированный контекст Workspace.

Например:

workspace_id

current_user_id

current_view

current_filters

current_project

current_date

permissions

Это позволяет понимать контекст.

---

8. CONTEXTUAL AI

Если пользователь находится внутри:

Project P024

и спрашивает:

«А что здесь осталось сделать?»

AI должен понимать:

"здесь"

как текущий Project P024.

Не требовать от пользователя каждый раз писать ID проекта.

---

9. CONTEXT FROM DRAWER

Если открыт:

Universal Entity Drawer

AI получает:

entity_type

entity_id

Например:

entity_type = project

entity_id = UUID

Тогда запрос:

«Есть ли проблемы с этим проектом?»

анализирует именно этот проект.

---

10. DASHBOARD AI

Добавить небольшой AI entry point на Dashboard.

Например:

┌────────────────────────────────────┐

│                                   │

Не превращать Dashboard в чат.

Например:

┌──────────────────────────────────┐

12. NATURAL LANGUAGE SEARCH

Поддержать запросы:

«Найди все проекты Nike»

«Покажи проекты Дениса»

«Какие проекты просрочены?»

«Что дедлайнится на этой неделе?»

«Какие проекты имеют Critical risk?»

AI преобразует запрос в структурированный вызов существующих API.

---

13. STRUCTURED QUERY

Не заставлять LLM генерировать произвольный SQL.

Например:

{
"entity": "projects",
"filters": [
{
"field": "risk_level",
"operator": "in",
"value": ["High", "Critical"]
}
],
"sort": [
{
"field": "deadline",
"direction": "asc"
}
]
}

После этого backend выполняет обычный безопасный запрос.

---

14. AI + VIEWS

AI должен понимать существующие Views.

Например:

«Открой мои срочные проекты.»

Если существует View:

"Срочные"

AI может открыть/переключить существующее представление.

Не создавать новую View без необходимости.

---

15. AI + FILTERS

Запрос:

«Покажи проекты с дедлайном до пятницы и высоким риском.»

AI преобразует запрос в:

deadline <= date

AND

risk_level IN [High, Critical]

После чего использует существующий Filter Engine.

Не создавать отдельный AI Filter Engine.

---

16. AI + CALENDAR

Запрос:

«Что у меня завтра?»

AI использует существующий Calendar API.

Результат:

Завтра:

3 задачи
1 дедлайн
1 оплата

P024
Получить ОС

P018
Отправить трек

P031
Дедлайн

---

17. AI + TASKS

Запрос:

«Создай мне задачу на завтра — проверить готовность P024.»

AI должен определить:

entity:

task

title:

Проверить готовность P024

due_date:

tomorrow

project:

P024

Но перед созданием показать:

Создать задачу?

[ Создать ]

[ Отмена ]

---

18. AI + PROJECTS

Запрос:

«Создай новый проект Nike на 15 сентября.»

AI должен собрать форму:

Название:
Nike

Дедлайн:
15.09.2026

Остальные обязательные поля:

попросить пользователя заполнить или использовать UI формы.

Не придумывать отсутствующие данные.

---

19. AI + CUSTOM FIELDS

AI должен уметь читать Custom Fields.

Например:

«Какие проекты имеют приоритет VIP?»

AI использует metadata Custom Fields.

Не зашивать конкретные custom fields в код AI.

---

20. AI + AUTOMATIONS

AI может помогать создавать Automation Rule.

Например:

«Сделай так, чтобы за 3 дня до дедлайна создавалась задача менеджеру.»

AI предлагает:

Trigger:
deadline approaching

Offset:
3 days

Condition:
stage != Completed

Action:
create task

Показывает пользователю конфигурацию.

После подтверждения:

создаёт Automation Rule через API.

---

21. AI + FORMULAS

AI может помогать создавать формулы.

Например:

«Сделай поле, которое показывает сколько дней осталось до дедлайна.»

AI предлагает:

DATEDIFF(deadline, TODAY())

Но AI не должен выполнять произвольный код.

Формула проходит через существующий безопасный Formula Foundation.

---

22. AI SUMMARY

Добавить возможность:

"Сводка проекта"

Например внутри Project Drawer:

[ AI Сводка ]

AI анализирует:

- этап;
- задачи;
- дедлайн;
- риск;
- позиции;
- оплаты;
- документы.

И выдаёт короткую сводку:

Средний.

4 дня.

Следующее действие:
Запросить подтверждение клиента.

Не выдумывать информацию.

---

24. AI EXPLANATIONS

AI может объяснять:

Почему этот проект попал в риски?

Например:

Проект P024 отмечен как высокий риск, потому что:

- дедлайн через 2 дня;
- сигнал ещё не подтверждён;
- открыта задача;
- стадия проекта — SampleReview.

Все факты должны иметь источник в Workspace.

---

25. ANTI-HALLUCINATION

Критически важно.

AI не имеет права:

- придумывать проекты;
- придумывать задачи;
- придумывать суммы;
- придумывать даты;
- придумывать статусы;
- утверждать выполнение операции без подтверждения backend.

Если данных нет:

«В Workspace нет данных, подтверждающих это.»

---

26. SOURCE REFERENCES

AI должен по возможности указывать, откуда взята информация.

Например:

P024
Project

или:

Задача:
"Получить ОС по сигналу"

Клик по ссылке:

→ Universal Entity Drawer.

---

27. AI ACTION RESULT

После write operation backend должен вернуть реальный результат.

Например:

Task created:

id = ...

AI сообщает:

«Задача создана.»

[ Открыть задачу ]

Не считать действие выполненным только потому, что LLM решила, что tool вызван.

---

28. ERROR HANDLING

Если API вернул ошибку:

AI должен честно сообщить:

«Не удалось создать задачу: у проекта отсутствует обязательный менеджер.»

Не пытаться самостоятельно «додумать» значение.

---

29. PERMISSIONS

AI работает с теми же permissions, что и пользователь.

Если пользователь не может:

видеть проект

AI тоже не может его видеть.

Если пользователь не может:

изменять проект

AI не может изменить его.

Нельзя создавать отдельный обход permissions для AI.

---

30. MODEL ABSTRACTION

Не привязывать архитектуру Workspace к одной LLM.

Создать abstraction:

AIProvider

Например:

OpenAI
Anthropic
Gemini
локальная модель

AI Layer должен работать через единый интерфейс.

---

31. TOOL CALLING

Использовать structured tool calling / function calling.

Например:

{
"filters": {},
"sort": [],
"limit": 50
}

Output:

строго типизированный результат.

42. DEFINITION OF DONE

Этап завершён, если:

- AI является встроенным Workspace Layer;
- AI понимает текущий Workspace Context;
- AI умеет читать Projects;
- AI умеет читать Tasks;
- AI умеет работать с Calendar;
- AI умеет использовать Filters;
- AI понимает Custom Fields;
- AI может создавать Tasks после подтверждения;
- AI может изменять данные только через API;
- AI не имеет прямого доступа к БД;
- permissions применяются к AI;
- write actions логируются;
- используется structured tool calling;
- LLM можно заменить через AIProvider;
- AI не создаёт параллельную бизнес-модель;
- AI не превращает приложение в отдельный чат.

                   │
            DOMAIN SERVICES
                   │
         ┌─────────┼─────────┐

      Projects   Tasks    Calendar
         │
         ▼

AI не создаёт отдельную реальность.

AI
↓
Tools

Workspace API
↓
Domain Services
↓
Database

Главный принцип:

AI должен не заменять Workspace, а делать его управляемым естественным языком.
