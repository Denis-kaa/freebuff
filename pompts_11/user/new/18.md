PROMPT 18 — AUTOMATION FOUNDATION

Контекст

Мы продолжаем разработку Workspace.

Workspace — универсальная рабочая оболочка, внутри которой могут существовать разные приложения и рабочие процессы.

Первый реализуемый use case:

B2B-система управления проектами и производством мерча.

Уже реализованы/спроектированы:

- Workspace
- Members
- Roles / Permissions
- Projects
- Project Items
- Tasks
- Payments
- Documents
- Dashboard
- Dynamic Widgets
- Dynamic Columns
- Custom Fields
- Views
- Filters
- Sorting
- Grouping
- Calendar
- Project Drawer
- Personal / Global Configuration
- Import / Export

Теперь необходимо заложить фундамент автоматизаций, но НЕ создавать огромный workflow engine.

Главная идея:

«Пользователь должен постепенно получить возможность сказать Workspace: «Когда происходит X — сделай Y».»

---

1. ГЛАВНЫЙ ПРИНЦИП

Automation должна работать поверх существующих сущностей.

Например:

Project
Task
Custom Field
Payment
Document

Automation не должна дублировать бизнес-данные.

Архитектура:

EVENT
   ↓
TRIGGER
   ↓
CONDITIONS
   ↓
ACTIONS

Например:

Project deadline approaching
        ↓
за 3 дня
        ↓
если Project.status != Completed
        ↓
создать Task

---

2. НЕ ДЕЛАТЬ ПОЛНОЦЕННЫЙ ZAPIER

На этом этапе НЕ реализовывать:

- сложные визуальные workflow;
- бесконечные branching trees;
- циклы;
- внешние интеграции;
- webhooks marketplace;
- AI automation;
- cron builder;
- десятки trigger types;
- полноценный BPMN;
- сложный expression language.

Нам нужен минимальный универсальный фундамент.

4. ПОЧЕМУ CONFIG JSON

Trigger / conditions / actions могут храниться в JSON.

Например:

{
  "trigger": {
    "type": "project_created"
  },
  "conditions": [],
  "actions": [
    {
      "type": "create_task",
      "config": {
        "title": "Проверить новый проект"
      }
    }
  ]
}

Но:

JSON используется только для конфигурации automation.

Не переносить в JSON основную бизнес-модель.

8. TASK COMPLETED

Пример:

Когда задача "Получить ОС по сигналу"
завершена

обновить поле проекта

На MVP достаточно ограниченного набора действий.

---

9. DEADLINE APPROACHING

Особенно важный trigger.

Например:

deadline_approaching

config:

{
  "days_before": 3
}

Система находит проекты:

deadline - today <= 3

и создаёт действие.

Важно:

не создавать одну и ту же задачу каждый день.

Automation должна быть идемпотентной.

---

10. ACTIONS

На MVP:

create_task
update_project
update_custom_field

Дополнительно:

notify

если существует уже реализованный notification layer.

Не создавать отдельную сложную notification system только ради этого этапа.

create_task

config:

{
  "title": "Получить ОС по макету",
  "priority": "high",

Если:

можно создать:

Task due_date = 09.09

14. CONDITIONS

Создать минимальную систему условий.

Поддержать:

equals
not_equals
contains
greater_than
less_than
is_empty
is_not_empty

Например:

stage equals Delivery

---

15. AND / OR

На MVP поддержать:

ALL
ANY

Например:

ALL:

stage = Delivery
risk != Critical

или:

ANY:

risk = High
risk = Critical

Не создавать пока визуальный nested condition builder.

---

16. AUTOMATION ENGINE

Создать:

AutomationEngine

Он получает событие:

DomainEvent

Например:

ProjectCreated
ProjectUpdated
TaskCompleted
PaymentUpdated

Engine:

1. Получить event
2. Найти активные automations Workspace
3. Проверить trigger
4. Проверить conditions
5. Выполнить actions
6. Записать результат

---

17. DOMAIN EVENTS

Создать базовый event interface:

DomainEvent

Например:

event_type
workspace_id
entity_type
entity_id
payload
created_at

Не привязывать AutomationEngine напрямую к HTTP endpoints.

18. EVENT DISPATCHING

Например:

POST /projects
        ↓
ProjectService.create()
        ↓
ProjectCreated
        ↓
EventDispatcher
        ↓
AutomationEngine

То есть automation работает на уровне application/domain layer.

Не:

frontend → automation

---

19. IDEMPOTENCY

Критически важно.

Если событие обработалось дважды:

automation не должна создать:

Task A
Task A
Task A

для одного и того же события.

Создать механизм:

AutomationExecution

с уникальным ключом:

automation_id
event_id

UNIQUE.

20. AUTOMATION EXECUTION

Создать:

AutomationExecution

Поля:

id
automation_id
event_id
workspace_id
status
started_at
completed_at
error
result

Статусы:

pending
running
success
failed

---

21. FAILURE

Если Action завершился ошибкой:

не ломать основную бизнес-операцию.

Например:

Project created

должен успешно сохраниться даже если:

Automation failed

Automation должна иметь собственный lifecycle.

---

22. RETRY

Добавить минимальную возможность повторной обработки failed execution.

Например:

retry_count

и:

max_retries

Но не создавать пока сложную distributed queue.

---

23. TRANSACTION BOUNDARY

Особенно внимательно продумать:

Business transaction

и:

Automation execution

Не держать длинную транзакцию базы во время выполнения automation.

Если проект создан:

commit
↓
publish event
↓
automation

Использовать подходящий механизм из существующей архитектуры.

Если нужен Outbox Pattern — реализовать минимальный вариант.

Workspace-level

31. SECURITY

Automation всегда выполняется в контексте:

workspace_id

Нельзя automation из:

Workspace A

работать с:

Workspace B

32. CUSTOM FIELDS

Automation должна уметь работать с Custom Fields.

Например:

Не создавать отдельную систему Custom Automation Fields.

Использовать существующий CustomField layer.

ГЛАВНАЯ ЦЕЛЬ

После этого этапа Workspace должен перейти от:

Пользователь
    ↓
сам всё делает

к:

Пользователь
    ↓
создаёт правило
    ↓
Workspace реагирует автоматически

Но архитектура должна оставаться лёгкой:

DATA
 ↓
EVENT
 ↓
AUTOMATION
 ↓
ACTION

а не превращаться в отдельную огромную платформу автоматизации.

Не добавлять новые подсистемы, которые не нужны для этого фундамента.
