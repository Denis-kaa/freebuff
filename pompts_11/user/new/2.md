PROMPT 02 — PROJECTS, DYNAMIC FIELDS & SAVED VIEWS

Контекст

В предыдущем этапе была создана базовая архитектура приложения:

CORE DATA
    ↓
CONFIGURATION
    ↓
WORKSPACE UI

Основная концепция продукта:

«Это не обычный CRUD и не копия Excel. Это configurable workspace, в котором пользователь самостоятельно формирует представление данных.»

На этом этапе НЕ нужно реализовывать весь Dashboard.

Главная задача текущего этапа:

«Создать полноценный раздел «Проекты» с динамическими пользовательскими полями, настраиваемыми колонками и сохранёнными представлениями.»

---

- frontend architecture;

9. Не создавать физические колонки PostgreSQL

КАТЕГОРИЧЕСКИ НЕ ДЕЛАТЬ:

ALTER TABLE projects ADD COLUMN ...

при каждом создании пользователем новой колонки.

Система должна использовать динамическую модель.

Например:

custom_fields

id
workspace_id
entity_type
name
slug
field_type
description
required
default_value
options
formula
position
is_active
created_at
updated_at

и:

custom_field_values

id
custom_field_id
entity_id
value
created_at
updated_at

Если выберешь JSONB-гибридную модель вместо отдельной таблицы значений — обоснуй решение и убедись, что сохраняются:

- фильтрация;
- сортировка;
- типизация;
- индексация;
- экспорт;
- масштабируемость.

21. Formula Field

На этом этапе можно реализовать минимальную инфраструктуру FORMULA, но полноценный Formula Engine будет отдельным этапом.

Пользователь должен иметь возможность создать:

Маржа
Тип: Formula

Но архитектура должна быть совместима с будущим Formula Engine.

НЕ использовать:

eval()

НЕ использовать выполнение произвольного JavaScript.

Если полноценный parser ещё не реализован, можно временно ограничить доступные формулы или создать placeholder UI, но не закладывать небезопасный механизм.

23. API Filtering

Backend должен принимать структурированные фильтры.

Не принимать raw SQL.

Например:

{
  "filters": [
    {
      "field": "payment_percent",
      "operator": "lt",
      "value": 100
    }
  ]
}

Backend валидирует поле и оператор перед построением SQLAlchemy query.

---

24. Security

Пользователь не должен иметь возможность через API:

- читать чужой workspace;
- изменять чужой workspace;
- создавать поля в чужом workspace;
- менять чужие View.

Каждый запрос должен проверять:

user
→ workspace
→ permission
→ entity

Не доверять "workspace_id", пришедшему от frontend.

26. Optimistic UI

Для простых действий можно использовать optimistic updates:

- hide/show column;
- изменение ширины;
- изменение порядка;
- отметка задачи и т. п.

Но бизнес-критичные операции:

- создание проекта;
- изменение оплаты;
- архивирование;

должны подтверждаться сервером.

Если API возвращает ошибку — интерфейс обязан откатить optimistic state и показать понятное сообщение.
