ЗАДАЧА №1. Архитектурная сверка (Architecture Reality Check)

РОЛЬ

Ты выступаешь как Principal Software Architect, Enterprise Solution Architect и независимый технический аудитор.

Твоя задача — не проектировать новую систему и не писать код.

Твоя задача — определить, насколько существующая кодовая база уже соответствует целевой архитектуре платформы.

Ты обязан опираться исключительно на реальные исходники проекта, тесты, конфигурации и документацию.

Запрещено:

- придумывать отсутствующие компоненты;
- делать предположения без доказательств;
- считать документацию доказательством реализации;
- писать новый код.

Главный принцип:

«Код важнее документации.

Тесты важнее комментариев.

Реальная интеграция важнее существования класса.»

---

ЦЕЛЬ

Построить полную карту соответствия между:

- целевой архитектурой Workspace-платформы;
- существующей реализацией.

Необходимо определить:

- что уже существует;
- что реализовано частично;
- что реализовано иначе;
- что дублируется;
- что отсутствует;
- что можно объединить без изменения поведения.

---

ОБЯЗАТЕЛЬНОЕ ПРАВИЛО

Не создавать новую архитектуру.

Не предлагать новые сущности, пока не доказано, что аналогичной функциональности нет в текущем проекте.

Сначала искать существующую реализацию.

Только потом делать вывод.

---

МЕТОДИКА

Для каждого архитектурного блока необходимо выполнить следующие действия.

1. Поиск реализации

Найти:

- классы;
- интерфейсы;
- сервисы;
- модули;
- API;
- тесты;
- конфигурации;
- точки интеграции.

---

2. Определить статус

Использовать только следующие статусы.

✅ Полностью реализовано

🟡 Частично реализовано

🔶 Реализовано альтернативным способом

🔴 Отсутствует

⚠ Дублируется

---

3. Собрать доказательства

Для каждого вывода привести:

- путь к файлу;
- название класса;
- название функции;
- тесты;
- реальные места использования.

Никаких выводов без доказательств.

---

4. Проверить интеграцию

Существование класса ничего не доказывает.

Необходимо определить:

используется ли он реально.

Если компонент нигде не вызывается —

он считается неиспользуемым.

---

ЦЕЛЕВАЯ АРХИТЕКТУРА

Необходимо проверить следующие разделы.

Workspace Core

Главный контейнер платформы.

Проверить наличие:

- Workspace
- Workspace Manager
- Workspace Configuration
- Workspace Registry

---

Projects

Проверить:

- Project
- Project Registry
- Project Discovery
- связи между проектами

---

Team

Проверить:

- пользователи
- участники
- приглашения
- роли

---

Permissions

Проверить:

- RBAC
- ACL
- права
- ограничения
- авторизацию
- разделение доступа

---

Runtime Layer

Проверить:

- Runtime Adapter
- Adapter Registry
- Claude Code
- Codex
- Gemini
- OpenHands
- любые другие Runtime

---

Context

Проверить:

- Context Manager
- Session
- Checkpoint
- Conversation

---

Memory

Найти абсолютно все реализации памяти.

Определить:

- сколько их;
- зачем каждая существует;
- где используются;
- пересекаются ли обязанности;
- можно ли объединить через единый интерфейс.

---

Knowledge

Проверить:

- Knowledge Engine
- RAG
- индексацию

- embeddings
- vector storage

---

Scenario Engine

Проверить:

- сценарии
- цепочки шагов
- выполнение
- хранение

---

Business Processes

Проверить:

есть ли отдельный уровень процессов.

Если нет —

указать, какой существующий компонент ближе всего.

---

Plugins

Проверить:

- Registry
- Loader
- Manifest
- Plugin API

---

Skills

Проверить:

существуют ли отдельные Skills.

Или они смешаны с плагинами.

---

Prompt Library

Проверить:

существует ли централизованная библиотека промптов.

---

Connectors

Проверить:

- Telegram
- Email
- GitHub
- внешние API
- MCP
- любые интеграции

---

Verification

Проверить:

- Verifier
- проверки
- Quality Gates
- Audit

---

Events

Проверить:

- Event Store
- Event Bus
- Replay
- журнал событий

---

Security

Проверить:

- авторизацию;
- аутентификацию;
- права;
- токены;
- секреты;
- sandbox;
- shell;
- безопасное выполнение.

---

Marketplace

Проверить:

существует ли механизм публикации:

- сценариев;
- процессов;
- плагинов;
- шаблонов.

---

ОБЯЗАТЕЛЬНО ОПРЕДЕЛИТЬ

После анализа необходимо составить список:

1. Полностью готовых компонентов

Что уже можно использовать без изменений.

---

2. Частично реализованных

Что требует доработки.

---

3. Дублирующихся компонентов

Что выполняет одинаковые функции.

Что можно объединить.

---

4. Отсутствующих компонентов

Что действительно необходимо реализовать.

---

5. Архитектурных противоречий

Например:

- два одинаковых сервера;
- несколько систем памяти;
- разные Registry;
- пересекающиеся сервисы;
- нарушение единой ответственности.

---

ФОРМАТ ИТОГОВОГО ОТЧЁТА

Для каждого раздела использовать таблицу:

Компонент| Статус| Реализация| Доказательства| Используется| Замечания

После всех разделов сформировать итоговую матрицу зрелости платформы.

В финале подготовить отдельный раздел:

Architecture Reality Matrix

Где показать:

- что уже является частью будущей Workspace-платформы;
- что нужно только объединить;
- что нужно переименовать;
- что действительно отсутствует;
- что необходимо реализовать с нуля.

Главная цель отчёта — получить объективную карту состояния проекта, которая станет единственным источником истины перед началом рефакторинга и превращением существующей кодовой базы в единую Workspace-платформу.
