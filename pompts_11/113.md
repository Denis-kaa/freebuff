ДОПОЛНЕНИЕ: MULTI-USER CONCURRENCY, FAIRNESS И ДИНАМИЧЕСКОЕ МАСШТАБИРОВАНИЕ

Главная задача

Теперь необходимо спроектировать pipeline не только для одного пользователя, но и для нескольких пользователей, одновременно загружающих и обрабатывающих YouTube-видео.

Критически важно:

«Не создавать отдельный постоянный процесс/worker на каждого пользователя.»

Вместо этого использовать:

USER
  ↓
JOB
  ↓
CHUNKS
  ↓
QUEUE
  ↓
SHARED WORKER POOL

Пользователь должен быть логически изолирован, но вычислительные workers должны быть общими.

---

1. MULTI-USER ARCHITECTURE

Целевая архитектура:

                         USERS
             ┌────────────┼────────────┐
             ▼            ▼            ▼
          User A       User B       User C
             │            │            │
             ▼            ▼            ▼
          Job A1       Job B1       Job C1
             │            │            │
             ▼            ▼            ▼
          Chunks        Chunks        Chunks
             │            │            │
             └────────────┼────────────┘
                          ▼
                    Redis / Queue
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
           Worker 1    Worker 2    Worker 3
              │           │           │
              ▼           ▼           ▼
             TTS         TTS         TTS
              │           │           │
              ▼           ▼           ▼
           Media       Media       Media

Workers являются shared resources.

---

2. ИЗОЛЯЦИЯ ПО USER_ID / JOB_ID

Каждая задача должна иметь минимум:

user_id
job_id
chunk_id
chunk_index
task_type
priority
status
created_at

Пример:

{
  "user_id": "user_123",
  "job_id": "job_456",
  "chunk_id": "chunk_002",
  "chunk_index": 2,
  "task_type": "tts",
  "priority": 5
***REMOVED***

Никакой worker не должен полагаться на глобальное состояние конкретного пользователя.

---

3. НЕ ДЕЛАТЬ WORKER НА КАЖДОГО USER

Неправильная архитектура:

User A → Worker A
User B → Worker B
User C → Worker C
...

Правильная:

User A ─┐
User B ─┼──→ Queue ──→ Shared Worker Pool
User C ─┘

Workers должны брать следующую доступную задачу из очереди.

---

4. PER-USER CONCURRENCY LIMIT

При этом один пользователь не должен иметь возможность занять весь сервер.

Например:

MAX_CONCURRENT_JOBS_PER_USER=2
MAX_TTS_TASKS_PER_USER=2
MAX_MEDIA_TASKS_PER_USER=1

Значения должны быть конфигурируемыми.

Если User A отправил 20 видео:

User A
20 jobs
   ↓
только ограниченное количество
одновременно выполняется

Остальные остаются в очереди.

---

5. GLOBAL CONCURRENCY LIMIT

Также должен существовать глобальный предел:

MAX_TOTAL_TTS_WORKERS=4
MAX_TOTAL_MEDIA_WORKERS=2
MAX_TOTAL_JOBS=10

То есть:

Per-user limit
       +
Global limit
       ↓
Scheduler

Scheduler должен соблюдать оба ограничения.

---

6. FAIRNESS

Нельзя допускать starvation других пользователей.

Пример неправильного поведения:

User A загрузил 30 видео

Queue:

A A A A A A A A A A A A A A
B
C

В результате B и C ждут бесконечно.

Нужно реализовать fair scheduling.

Предпочтительно использовать:

- round-robin;
- weighted round-robin;
- fair queue;
- или другой механизм, подходящий существующей Celery/Redis архитектуре.

Цель:

A → task
B → task
C → task
A → task
B → task
C → task

если ограничения и приоритеты одинаковые.

---

7. PRIORITY

Архитектура должна позволять добавить priority.

Например:

priority = 10
priority = 5
priority = 1

Но priority не должен полностью ломать fairness.

Если priority уже реализован в проекте — переиспользовать существующий механизм.

---

8. ОТДЕЛЬНЫЕ ОЧЕРЕДИ

Исследовать разделение очередей:

Redis
 │
 ├── download_queue
 │
 ├── transcription_queue
 │
 ├── translation_queue
 │
 ├── tts_queue
 │
 ├── media_queue
 │
 └── publish_queue

Основное внимание:

TTS_QUEUE
MEDIA_QUEUE

поскольку именно TTS и media compositing сейчас являются bottleneck.

---

9. НЕ ДАТЬ TTS ЗАБИТЬ MEDIA

Если TTS workers работают на максимальной concurrency:

TTS TTS TTS TTS TTS TTS

они не должны автоматически уничтожать ресурсы, необходимые для media processing.

Поэтому рассмотреть resource budgets:

TTS:
max concurrency = N

MEDIA:
max concurrency = M

Например:

TTS = 4
MEDIA = 2

Но реальные значения определить benchmark'ом.

---

10. USER → JOB → CHUNK

Очень важно не путать эти уровни.

USER
 │
 ├── JOB 1
 │    ├── Chunk 1
 │    ├── Chunk 2
 │    └── Chunk 3
 │
 ├── JOB 2
 │    ├── Chunk 1
 │    ├── Chunk 2
 │    └── Chunk 3
 │
 └── JOB 3
      ├── Chunk 1
      ├── Chunk 2
      └── Chunk 3

Concurrency должна контролироваться как минимум на:

1. user level;
2. job level;
3. chunk/task level;
4. global worker level.

---

11. PROGRESSIVE PLAYBACK ПРИ НЕСКОЛЬКИХ ПОЛЬЗОВАТЕЛЯХ

Предыдущая задача по progressive playback сохраняется.

Например:

User A
Job A1
 ├── Chunk 1 → READY → PLAY
 ├── Chunk 2 → PROCESSING
 └── Chunk 3 → QUEUED


User B
Job B1
 ├── Chunk 1 → PROCESSING
 ├── Chunk 2 → QUEUED
 └── Chunk 3 → QUEUED

User A не должен блокировать User B полностью.

После освобождения worker:

User B → Chunk 1

а после следующего:

User A → Chunk 2

согласно scheduler/fairness policy.

---

12. TIME TO FIRST PLAYABLE ДЛЯ КАЖДОГО USER

Измерять:

user_id
job_id
time_to_first_playable

Например:

User A → 18 sec
User B → 24 sec
User C → 21 sec

Нельзя оценивать систему только по average total processing time.

Особенно важен:

Time To First Playable Chunk

---

13. LOAD TEST

Обязательно протестировать multi-user сценарии.

Минимально:

Scenario 1:
1 user × 1 video

Scenario 2:
2 users × 1 video

Scenario 3:
5 users × 1 video

Scenario 4:
10 users × 1 video

Scenario 5:
1 user × 10 videos

Scenario 6:
5 users × 3 videos

Если текущая инфраструктура не позволяет провести все сценарии — провести максимально возможные и зафиксировать ограничение.

---

14. ЧТО ИЗМЕРЯТЬ

Для каждого сценария:

Total processing time
Time to first playable
Queue wait time
TTS processing time
Media processing time
Number of active TTS workers
Number of active media workers
CPU
RAM
GPU / VRAM
Redis load
Celery queue depth
Errors
Retries
Failed chunks

Особенно:

queue wait time

Потому что при нескольких пользователях bottleneck может переместиться с TTS на очередь.

---

15. MODAL + MULTI-USER

Исследовать возможность использовать Modal как динамический worker pool, а не как отдельный сервер для каждого пользователя.

Целевая модель:

                    Redis
                      │
                  Scheduler
                      │
                TTS Queue
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Modal #1    Modal #2    Modal #3
          │           │           │
        User A      User B      User C

Но физическая привязка:

User A → Modal #1

не обязательна.

Worker может обработать:

User A → Chunk 1

затем:

User C → Chunk 4

и так далее.

Нужно исследовать стоимость и latency cold start.

---

16. MODAL НЕ ДОЛЖЕН ЛОМАТЬ USER ISOLATION

Каждая задача должна явно передавать:

user_id
job_id
chunk_id

Результат должен возвращаться именно в соответствующий job.

Никакого общего mutable state между пользователями.

---

17. РЕСУРСНЫЕ ЛИМИТЫ

Добавить защиту от одного пользователя, который создаёт чрезмерную нагрузку:

MAX_ACTIVE_JOBS_PER_USER
MAX_QUEUED_JOBS_PER_USER
MAX_ACTIVE_TTS_PER_USER
MAX_ACTIVE_MEDIA_PER_USER

При необходимости:

MAX_VIDEO_DURATION_PER_JOB
MAX_FILE_SIZE

Но существующие бизнес-ограничения проекта не менять без необходимости.

---

18. IDEMPOTENCY

Multi-user architecture не должна создавать дубли.

Уникальность задачи:

user_id
+
job_id
+
chunk_id
+
task_type
+
processing_version

Повторная доставка Celery task не должна приводить к двойному:

- TTS;
- media processing;
- publish;
- начислению ресурсов;
- изменению статуса.

---

19. RECOVERY

При:

- restart backend;
- restart Celery worker;
- restart Modal worker;
- network failure;
- timeout;
- worker crash;

система должна понимать:

PENDING
PROCESSING
READY
PUBLISHED
FAILED

и корректно восстанавливать только действительно незавершённые задачи.

Не создавать дубликаты уже завершённых chunks.

---

              ┌───────────┼───────────┐
              ▼           ▼           ▼
            User A      User B      User C
              │           │           │
              ▼           ▼           ▼
             JOB         JOB         JOB

              ▼           ▼           ▼
            CHUNKS      CHUNKS      CHUNKS

                    FAIR SCHEDULER
                          │
             ┌────────────┴────────────┐
             ▼                         ▼
         TTS QUEUE                 MEDIA QUEUE
             │                         │
             ▼                         ▼
       TTS WORKER POOL           MEDIA WORKER POOL
       ┌─────┼─────┐             ┌─────┼─────┐
       ▼     ▼     ▼             ▼     ▼     ▼
      W1    W2    W3            M1    M2    M3

                        ▼

                        │
                        ▼
                PROGRESSIVE PLAYBACK

21. КРИТЕРИЙ УСПЕХА

Система должна позволять:

- нескольким пользователям одновременно обрабатывать видео;
- нескольким пользователям получать progressive playback;
- одному пользователю не занимать весь worker pool;
- масштабировать TTS независимо от media processing;
- масштабировать media processing независимо от TTS;
- использовать Modal при необходимости;
- сохранять порядок chunks;
- не создавать duplicate tasks;
- переживать worker/backend restart;
- контролировать per-user и global concurrency.

Главный принцип:

«Пользователь — это логическая единица изоляции, а не отдельный физический worker.»

И второй принцип:

«Масштабируем не пользователей, а очереди и ресурсы.»


ДОПОЛНЕНИЕ К ТЗ: ДОПОЛНИТЕЛЬНАЯ ОПТИМИЗАЦИЯ ПРОИЗВОДИТЕЛЬНОСТИ И МАСШТАБИРОВАНИЯ

Уже определены основные принципы:

- TTS и media compositing являются текущими bottleneck;
- TTS должен выполняться параллельно;
- media processing должен иметь собственный worker pool;
- несколько пользователей должны обслуживаться одновременно;
- один пользователь не должен занимать все ресурсы;
- необходим progressive playback;
- необходимо рассмотреть Modal как эластичный compute layer;
- необходимо измерять Time To First Playable и Total Processing Time.

Теперь дополнительно исследуй и, где это действительно оправдано, реализуй следующие пять направлений.

---

1. ADAPTIVE RESOURCE SCHEDULER

Не задавай количество workers исключительно статическими значениями.

Исследуй возможность динамически изменять concurrency в зависимости от текущей нагрузки.

Scheduler должен учитывать:

Queue depth
Active users
Active jobs
CPU utilization
RAM utilization
GPU utilization
VRAM utilization
TTS latency
Media processing latency
Error rate

Логика должна стремиться к:

Низкая нагрузка
    ↓
минимум workers
    ↓
экономия ресурсов


Высокая нагрузка
    ↓
очередь растёт
    ↓
увеличиваем concurrency
    ↓
обрабатываем больше задач


Критическая нагрузка
    ↓
достижение resource limits
    ↓
НЕ увеличивать workers
    ↓
очередь остаётся под контролем

Не допускай ситуации:

Queue растёт
→ workers бесконтрольно увеличиваются
→ RAM/CPU заканчиваются
→ сервер падает

Если Modal используется, исследуй возможность использовать его autoscaling вместо самостоятельного управления всеми GPU workers.

Обязательно определить:

- minimum workers;
- maximum workers;
- scale-up condition;
- scale-down condition;
- cooldown;
- cold-start impact.

Не усложняй систему без необходимости. Если статический worker pool на текущем масштабе эффективнее — зафиксируй это результатами benchmark.

---

2. SLIDING WINDOW ДЛЯ CHUNKS

Не отправляй сразу все chunks огромного видео на обработку.

Исследуй модель:

              CURRENT WINDOW

        ┌─────────────────────┐
        │ Chunk 1             │
        │ Chunk 2             │
        │ Chunk 3             │
        └─────────────────────┘
                  ↓
             processing


После продвижения:

        ┌─────────────────────┐
        │ Chunk 2             │
        │ Chunk 3             │
        │ Chunk 4             │
        └─────────────────────┘

Размер окна должен быть конфигурируемым:

CHUNK_PROCESSING_WINDOW=3

или эквивалентным механизмом.

Цель:

- уменьшить очередь;
- ограничить RAM;
- уменьшить количество временных файлов;
- не перегружать TTS;
- не создавать тысячи задач Celery;
- обеспечить быстрый первый playable chunk;
- поддерживать небольшой buffer впереди позиции пользователя.

---

3. РАЗДЕЛИТЬ TTS И MEDIA RESOURCE POOLS

TTS и FFmpeg/media processing имеют разные характеристики нагрузки.

Не допускать:

TTS × N
    ↓
CPU/RAM exhaustion
    ↓
FFmpeg ждёт

Ввести независимые concurrency limits:

TTS_CONCURRENCY=4
MEDIA_CONCURRENCY=2

Реальные значения определить benchmark'ом.

Если TTS работает через внешний API, учитывать rate limits API.

Если TTS локальный:

- CPU;
- RAM;
- GPU;
- VRAM.

Если media processing выполняется через FFmpeg:

- CPU;
- RAM;
- disk I/O.

Цель:

«TTS не должен съедать ресурсы, необходимые media pipeline, и наоборот.»

---

4. МИНИМИЗИРОВАТЬ ПОВТОРНОЕ ВИДЕО-КОДИРОВАНИЕ

Проведи аудит всех FFmpeg операций.

Найди места, где происходит:

decode
→ encode

без необходимости.

Проверь возможность использовать:

stream copy

для video stream там, где это технически безопасно.

Сравнить два подхода:

VIDEO RE-ENCODE

против:

VIDEO STREAM COPY + AUDIO MUX

Измерить:

- CPU;
- RAM;
- disk I/O;
- latency;
- output compatibility;
- качество;
- размер файла.

Если stream copy невозможен для конкретного pipeline — объяснить почему.

Не жертвовать совместимостью ради benchmark.

---

5. CACHE + DEDUPLICATION

Исследовать кэширование результатов.

Особенно для одинаковых YouTube-видео.

Пример:

User A
YouTube URL X
       ↓
    PROCESS


User B
YouTube URL X
       ↓
    CACHE HIT


User C
YouTube URL X
       ↓
    CACHE HIT

Минимально исследовать возможность кэшировать:

YouTube video metadata
Downloaded source
Transcript
Translation
TTS chunks
Generated media segments

Но учитывать:

- язык;
- voice;
- TTS settings;
- translation settings;
- processing version;
- output format.

Например, одинаковое видео с разными голосами:

Video X + Voice A
Video X + Voice B

не должно ошибочно получать один и тот же TTS результат.

Использовать deterministic cache key.

Например:

video_id
+
source_language
+
target_language
+
voice_id
+
TTS configuration
+
processing_version

Необходимо также определить lifecycle cache:

TTL
Maximum storage
LRU / другой policy
Cleanup

---

6. PLAYBACK BUFFER AHEAD

Дополнительно реализовать принцип:

«Backend должен стараться держать несколько готовых chunks впереди текущей позиции пользователя.»

Например:

CURRENTLY PLAYING
Chunk 3

READY BUFFER
Chunk 4
Chunk 5
Chunk 6

PROCESSING
Chunk 7
Chunk 8

QUEUED
Chunk 9+

Если пользователь смотрит Chunk 3, scheduler должен отдавать приоритет задачам, необходимым для поддержания непрерывного playback.

Это особенно важно при multi-user нагрузке.

---

7. PRIORITY ДЛЯ ПЕРВОГО PLAYABLE CHUNK

Не допускать ситуации, когда новый job создаёт огромную очередь:

Chunk 1
Chunk 2
Chunk 3
...
Chunk 30

и первый playable chunk ждёт выполнения всех предыдущих задач других пользователей.

Ввести при необходимости отдельный приоритет:

FIRST_PLAYABLE
BUFFER_AHEAD
NORMAL_PROCESSING
BACKGROUND

Например:

FIRST_PLAYABLE
      ↓
BUFFER_AHEAD
      ↓
NORMAL
      ↓
BACKGROUND / FINALIZATION

Но priority должен работать совместно с fairness и per-user limits.

---

8. PREFETCH И BACKPRESSURE

Реализовать backpressure.

Если downstream pipeline не успевает:

TTS
 ↓
Media
 ↓
Publish

TTS не должен бесконтрольно генерировать новые chunks.

Например:

TTS готовит 20 chunks
Media может обработать только 2

Так делать нельзя.

Нужна ограниченная очередь:

TTS
 ↓
small buffer
 ↓
Media
 ↓
Publish

Цель:

- ограничить RAM;
- ограничить disk;
- избежать очереди из тысяч временных файлов;
- предотвратить resource exhaustion.

---

9. РАЗДЕЛИТЬ HOT PATH И BACKGROUND TASKS

Определи:

HOT PATH

То, что необходимо пользователю для начала и продолжения просмотра:

First playable chunk
Buffer ahead
Publish
Playback

BACKGROUND

То, что можно выполнять после:

Full finalization
Archive
Cache optimization
Cleanup
Analytics
Non-critical metadata

Hot path должен иметь более высокий приоритет.

---

10. ИЗМЕРЯТЬ НЕ ТОЛЬКО СКОРОСТЬ, НО И LATENCY DISTRIBUTION

Не ограничиваться average.

Измерять:

P50
P90
P95
P99

для:

Time To First Playable
TTS latency
Media latency
Queue wait time
Total processing time

Например:

TTFP
P50 = 18s
P95 = 31s

Это гораздо полезнее, чем просто:

Average = 20s

12. ОПРЕДЕЛИТЬ ТРЁХУРОВНЕВУЮ ТОЧКУ МАСШТАБИРОВАНИЯ

После benchmark определить:

Level 1 — Local

Что сервер может стабильно выдержать сам.

CPU workers
TTS workers
Media workers

Level 2 — Modal

15. ФИНАЛЬНАЯ ЦЕЛЬ

Целевая система должна вести себя примерно так:

                    USERS
               /      |      \
              /       |       \
          User A    User B    User C
             │         │         │
             ▼         ▼         ▼
            JOB       JOB       JOB
             │         │         │
             ▼         ▼         ▼
           CHUNKS    CHUNKS    CHUNKS
              \        |        /
               \       |       /
                ▼      ▼      ▼
                FAIR SCHEDULER
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        TTS WORKERS         MEDIA WORKERS
             │                   │
       ┌─────┼─────┐       ┌─────┼─────┐
       ▼     ▼     ▼       ▼     ▼     ▼
      T1    T2    T3      M1    M2    M3
             │                   │
             └─────────┬─────────┘
                       ▼
                  PUBLISH BUFFER
                       │
                       ▼
                FIRST PLAYABLE
                       │
                       ▼
                PROGRESSIVE
                  PLAYBACK
                       │
                       ▼
                 FINALIZATION
                       │
                       ▼
                     CACHE

Главный принцип:

«Система должна масштабироваться не за счёт бесконтрольного увеличения количества процессов, а за счёт управления очередями, concurrency, backpressure, fairness, caching и эластичного compute.»

И ещё важнее:

«Сначала оптимизируем путь до первого воспроизводимого чанка, затем обеспечиваем непрерывный playback, и только после этого оптимизируем полное время финализации видео.»
