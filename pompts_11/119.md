    ↓

    ↓

    ↓

    ↓

    ↓
ACTION

Но:

    → no deep retrieval

    → consult

    → consult

    → consult existing architecture / lessons / decisions

    → consult

Политика должна быть детерминированной и тестируемой.

LLM не должна самостоятельно решать, надо ли соблюдать архитектурный guardrail.

Не доверять документации без проверки кода.

Если документация утверждает наличие механизма, а код его не подтверждает:

UNKNOWN / DOCUMENTATION-ONLY

---

5. ГЛАВНОЕ ПРАВИЛО

REUSE FIRST

Если существующий механизм уже умеет нужную операцию:

использовать его.

Не создавать:

NewKnowledgeEngine
NewSearchEngine
NewVectorStore
NewGraphStore
NewMemoryStore
NewDocumentRetriever

Только потому, что новый фасад должен их объединить.

---

6. ЦЕЛЕВАЯ МИНИМАЛЬНАЯ МОДЕЛЬ

После forensic определить минимальное место для:

RetrievalFacade

или аналогичной существующей абстракции, если она уже есть.

Предпочтительно:

retrieve(
    query: str,
    context: RetrievalContext | None = None,
    intent: RetrievalIntent | None = None,
) -> EvidenceBundle

Названия должны соответствовать существующей терминологии проекта.

Не создавать новые сущности только ради красивой архитектуры.

---

7. EvidenceBundle

Спроектировать минимальный типизированный результат.

Он должен позволять агенту понять:

1. что найдено;
2. откуда это найдено;
3. насколько результат релевантен;
4. к какой сущности/проекту относится;
5. можно ли использовать результат как evidence.

Минимально исследовать необходимость полей:

query
items / findings
source
source_type
entity_id
project_id
relevance
confidence
provenance
metadata

Не добавлять поля без реальной необходимости.

Если provenance/evidence-модель уже существует — использовать её, а не создавать вторую.

---

8. SIMPLE RETRIEVAL POLICY

На текущем этапе допускается только заранее определённая детерминированная политика.

Например:

query
 │
 ├── exact / lexical search
 │
 ├── semantic search, если существующий механизм доступен
 │
 ├── graph lookup, если определён entity/context
 │
 └── structured lookup, если передан явный project/entity context
 │
 ▼
merge
 │
 ▼
deduplicate
 │
 ▼
EvidenceBundle

Но этот порядок нельзя принимать как догму.

Сначала выясни, какие механизмы реально существуют.

Политика должна быть:

- простой;
- детерминированной;
- объяснимой;
- тестируемой;
- легко заменяемой в будущем.

---

9. ДОКУМЕНТАЦИЯ — ПОЛНОЦЕННЫЙ ИСТОЧНИК

Отдельно исследовать проблему документации.

Платформа содержит:

- архитектурные документы;
- ADR;
- Lessons;
- Changelog;
- manifests;
- audits;
- project documentation;
- README;
- RFC;
- design documents.

Большие документы, включая потенциально огромный "CHANGELOG.md", не должны автоматически передаваться целиком в LLM.

Нужно определить, какие существующие механизмы позволяют сделать документацию retrievalable.

Цель:

Agent
  ↓
"Было ли уже принято решение по X?"
  ↓
retrieve()
  ↓
ADR / Lessons / docs / code evidence
  ↓
EvidenceBundle

или:

"Есть ли уже Registry для этой ответственности?"
  ↓
retrieve()
  ↓
existing Registry / code / ADR / lessons
  ↓
EvidenceBundle

---

10. КЛЮЧЕВОЙ USE CASE

Система должна поддерживать паттерн:

AGENT WANTS TO CREATE
        │
        ▼
"IS THERE ALREADY SOMETHING?"
        │
        ▼
RETRIEVE
        │
        ▼
EVIDENCE
        │
   ┌────┴────┐
   │         │
 EXISTS    NOTHING FOUND
   │         │
   ▼         ▼
REUSE      MAY CREATE

Это особенно важно для предотвращения:

- новых Registry;
- новых Storage;
- новых Engines;
- новых abstractions;
- дублирующих Factory;
- дублирующих Forge;
- параллельных Intelligence Layers.

Retrieval не запрещает создание.

Он создаёт обязательную возможность сначала проверить существующее.

---

11. SELF-QUESTION PATTERN

Архитектура должна позволять агенту перед значимым действием самостоятельно формировать внутренний информационный запрос:

BEFORE CREATE
    ↓
WHAT DO I NEED TO KNOW?
    ↓
RETRIEVE
    ↓
EVIDENCE
    ↓
DECISION
    ↓
ACTION

Но на текущем этапе:

не создавать отдельный autonomous question planner.

Достаточно предоставить надёжный retrieval-интерфейс, который будущий agent runtime сможет вызывать перед действиями.

---

12. AGENT ≠ RETRIEVAL

Retrieval Layer не должен становиться ещё одним агентом.

Нельзя делать:

Agent
 ↓
Retrieval Agent
 ↓
Knowledge Agent
 ↓
Graph Agent

Предпочтительно:

Agent
 ↓
RetrievalFacade
 ↓
existing deterministic mechanisms

---

13. INTELLIGENCE BOUNDARY

Особенно проверить:

INTELLIGENCE
       │
       │ information request
       ▼
RETRIEVAL
       │
       │ evidence
       ▼
INTELLIGENCE

Retrieval предоставляет evidence.

Он не принимает архитектурное решение.

Например:

Retrieval:
"Найдены Registry A, B, C."

Intelligence:
"Registry B уже покрывает эту ответственность,
поэтому создавать новый Registry не нужно."

---

14. НЕ РЕШАТЬ СЕЙЧАС

Не пытаться одновременно решить:

- полноценный Project Intelligence;
- Opportunity Engine;
- Autonomous Intelligence;
- Scenario Intelligence;
- multi-agent orchestration;
- dynamic model routing;
- self-question planner;
- full lineage system;
- universal RAG architecture;
- отдельные RAG для каждого domain;
- migration на другую БД.

Это отдельные задачи.

---

15. DATABASE / VECTOR POLICY

Если для существующего retrieval уже используется SQLite / FTS5 / embeddings — сначала использовать существующее.

Если PostgreSQL + pgvector уже реально присутствует в платформе — исследовать его фактическое назначение.

Если его нет:

не добавлять PostgreSQL + pgvector только ради этой задачи.

Архитектурное решение:

one storage first
specialized storage later if evidence requires it

---

16. ДОКУМЕНТАЦИЯ И CHANGELOG

Исследовать:

- размер документации;
- повторяющиеся сведения;
- churn;
- необходимость индексации;
- возможность chunking;
- metadata;
- provenance;
- version/date;
- document type;
- project association.

Не переписывать документацию.

Не делать глобальный рефакторинг документации.

Только определить и реализовать минимальный путь retrieval, если существующая инфраструктура позволяет.

---

17. ТЕСТЫ

Обязательно создать тесты для минимального контракта.

Минимальные сценарии:

TEST 1 — exact knowledge

Запрос должен находить известный документ/запись.

TEST 2 — semantic/lexical retrieval

Если существующий semantic retrieval доступен — проверить его через фасад.

TEST 3 — project context

При переданном project context результаты должны быть ограничены/приоритизированы соответствующим проектом согласно существующей политике.

TEST 4 — provenance

Каждый возвращённый evidence item должен иметь источник.

TEST 5 — empty result

Если ничего не найдено:

не hallucinate
не создавать fake evidence

возвращается корректный empty EvidenceBundle.

TEST 6 — deduplication

Одна и та же сущность, найденная несколькими retrieval-механизмами, не должна бессмысленно дублироваться.

TEST 7 — existing components reused

Тест/проверка должна подтверждать, что фасад использует существующие engines, а не параллельные реализации.

---

18. НАБЛЮДАЕМОСТЬ

Каждый retrieval желательно сделать трассируемым:

query
context
intent
sources consulted
result count
latency
errors

Но не создавать новую observability system.

Использовать существующую.

21. DEFINITION OF DONE

Работа завершена только если:

Agent
  ↓
retrieve(query, context, intent)
  ↓
existing retrieval mechanisms
  ↓
EvidenceBundle
  ↓
agent can make decision

и одновременно:

- нет нового Knowledge Framework;
- нет нового Memory Framework;
- нет нового Graph Framework;
- нет Retrieval Planner;
- нет dynamic LLM routing;
- нет новой vector DB без доказанной необходимости;
- нет глобального рефакторинга;
- нет дублирования существующих механизмов;
- provenance сохраняется;
- тесты проходят.

---

22. ВАЖНЕЙШЕЕ ПРАВИЛО

Не превращай эту задачу в архитектурный марафон.

Нам сейчас нужен не:

««идеальный RAG для автономного AI».»

Нам нужен:

«один надёжный вход в существующее знание системы, которым агент может пользоваться перед принятием решения.»

Сначала:

RETRIEVE

Потом:

EVIDENCE

Потом:

DECISION

И только после накопления реальных случаев использования решаем, нужен ли:

RETRIEVAL PLANNER

---

ФОРМАТ ФИНАЛЬНОГО ОТЧЁТА

В конце предоставить:

1. Что было найдено
2. Что уже существовало
3. Что дублировалось
4. Чего реально не хватало
5. Почему выбран именно такой минимальный контракт
6. Какие файлы изменены
7. Какие тесты добавлены
8. Что сознательно НЕ реализовано
9. Какие следующие архитектурные вопросы появились
10. Evidence для каждого существенного утверждения

Если обнаружится, что RetrievalFacade или эквивалент уже существует:

не создавать второй.

Сначала показать его фактические возможности и предложить минимальное расширение.
