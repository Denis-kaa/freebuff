1. ГЛАВНЫЙ ВОПРОС

Исследуй следующую гипотезу:

«Агент Buffy перед принятием решения, созданием нового компонента, выполнением задачи или формированием ответа должен иметь возможность самостоятельно сформулировать информационную потребность и запросить существующую внутреннюю информацию, не зная заранее, где именно она хранится.»

Например:

««Есть ли уже решение этой проблемы?»»

««Создавался ли ранее похожий Registry?»»

««Есть ли Lesson, запрещающий такой подход?»»

««Какие проекты уже решали похожую задачу?»»

««Есть ли существующий компонент, который можно переиспользовать?»»

««Почему было принято это архитектурное решение?»»

««Какие ошибки уже совершались в похожем сценарии?»»

Агент не должен быть обязан знать, искать ли это в:

- SQL;
- FTS;
- vector search;
- Graph;
- Events;
- документации;
- Lessons;
- ADR;
- проектах;
- артефактах;
- коде;
- других источниках.

Это должно быть ответственностью инфраструктуры retrieval.

2. ВАЖНО: НЕ ПРЕДПОЛАГАЙ, ЧТО ЭТА АРХИТЕКТУРА УЖЕ СУЩЕСТВУЕТ

Ни Internal Retrieval, ни Retrieval Planner, ни Knowledge Fabric, ни Query Planner нельзя считать реализованными только потому, что они существуют в документации или концептах.

Для каждой найденной сущности определить:

IMPLEMENTED
VERIFIED
PARTIAL
DESIGNED
PROPOSED
EXPERIMENTAL
DEPRECATED
UNKNOWN

Если название существует в документации, но отсутствует соответствующая реализация:

DESIGNED / PROPOSED

а не IMPLEMENTED.

3. НЕ ПРИНИМАЙ СЛОВО "RAG" КАК АРХИТЕКТУРУ

Критически важно:

Не своди задачу к:

"Нам нужен RAG"

Исследуй более фундаментальную проблему:

INFORMATION NEED
       ↓
RETRIEVAL DECISION
       ↓
SOURCE SELECTION
       ↓
RETRIEVAL
       ↓
EVIDENCE
       ↓
AGENT REASONING

RAG может быть одним из механизмов retrieval.

SQL может быть другим.

FTS — другим.

Graph — другим.

Events — другим.

Комбинация нескольких механизмов — допустима.

8. INFORMATION NEED

Исследуй возможность появления отдельного понятия:

INFORMATION NEED

Пример:

{
  "question": "Есть ли уже похожий Registry?",
  "purpose": "avoid_duplication",
  "scope": "platform",
  "required_evidence": [
    "existing_components",
    "architectural_decisions",
    "lessons"
  ]
}

Но НЕ создавай такую модель в коде.

Сначала ответь:

- нужна ли она вообще;
- где она должна находиться;
- не существует ли уже аналогичной сущности;
- является ли это частью Agent Runtime, Intelligence или Retrieval Layer.

15. ОСОБЫЙ ПРИНЦИП

Введи как исследуемую архитектурную гипотезу:

«Agent should ask the system for knowledge, not know where knowledge lives.»

То есть агент говорит:

"I need evidence that..."

а не:

"Search lessons.md"
"Query table X"
"Use vector DB Y"
"Search GraphIndex"

Это позволит менять внутреннюю реализацию retrieval без переписывания агентов.

→ "Есть ли ADR?"

→ "Есть ли соответствующий Lesson?"

→ "Какой источник это подтверждает?"

Перед изменением системы:
→ "Какие зависимости будут затронуты?"

Но сначала установить, есть ли уже такой механизм.
