# MISSION: Content Intelligence как domain внутри Workspace OS — самостоятельный масштабный план

## Контекст

Есть внешнее исследование (приложено как `IDEA_EXPLORER_CONTENT_FACTORY.md`) —
проработка идеи "контент-завод" через IDEA EXPLORER до концепции Personal
Content Engine / Workspace Intelligence. Идея сильная: не генератор контента,
а domain внутри платформы, использующий накопленную память об авторе и
проектах для поиска content opportunities, построения portfolio, генерации
и QA с provenance.

**Критично:** это исследование написано без доступа к реальной кодовой
базе — упоминает компоненты (KeyPool, LLMFactory, CircuitBreaker), которых
нет в реальном коде. Не следуй его Integration Map буквально. Используй
только: постановку проблемы, доменную модель (IntelligenceObject,
Opportunity, Portfolio, epistemic types), и общую архитектурную идею
(Content Intelligence = domain, не отдельный продукт).

**У тебя уже есть свой собственный RFC на близкую тему** —
`docs_10/engineering-memory/RFC_DECISION_INTELLIGENCE_SYSTEM_V1.md` (DIS).
Прежде чем проектировать что-либо новое — прочитай его. Если DIS уже
покрывает часть того, что предлагает внешнее исследование (provenance,
epistemic types, decision tracking) — расширяй DIS, не создавай
параллельную "Intelligence Layer" под чужим именем.

## ЗАДАЧА 0 — Repository Forensics + AFC (обязательно первым, самостоятельно)

Прежде чем проектировать что-либо:

1. Прочитай `RFC_DECISION_INTELLIGENCE_SYSTEM_V1.md`, `RFC_BUFFY_FORGE_V1.md`,
   `ARCHITECTURE_MANIFEST.md`, `GLOSSARY.md` (термины Memory/Knowledge/EM
   уже разграничены — используй эти определения, не изобретай новые).
2. Составь Architectural Fit Check (тот же формат, что уже использовался
   в `ARB_REVIEW_FACTORY_FORGE_MANIFEST_V1.md` §0) — по каждой сущности
   из внешнего исследования (IntelligenceObject, ContentOpportunity,
   ContentPortfolio, provenance-модель) явно определи: уже покрыто
   существующим (какой процент), частично покрыто, или реально ново.
3. Реши сам порядок исследования и зафиксируй explain-first (по формату
   promt58/61) — с чего начинаешь, почему, что может изменить план по ходу.

**Это не формальность.** Именно этот шаг определяет, будет ли план ниже
реалистичным или снова окажется построен на выдумке.

## ЗАДАЧА 1 — Спроектировать масштаб, вписанный в First Vertical Slice

Проверь актуальный статус §34 First Vertical Slice
(`WORKSPACE_OS_ARCHITECTURE_RESEARCH_V1.md` §34, промт про
Forge Pipeline+Evolution slice) — выполнен ли он уже. Content Intelligence
НЕ должен создавать вторую, параллельную "Intelligence Layer" —
он должен использовать тот же substrate (Memory/Knowledge/EM границы
уже определены в GLOSSARY.md), что и уже работающий slice.

Спроектируй Content Intelligence как domain по аналогии с тем, как уже
устроен Blueprint v3 / ScenarioRegistry — не изобретай новый паттерн
интеграции, переиспользуй уже проверенный (auto-discovery YAML,
Facade-граница, как в §7.6 gap 2 из research-документа).

## ЗАДАЧА 2 — Построить полный, самостоятельно исполняемый Roadmap

Ты уже делал это раньше (`ROADMAP_FORGE_RECONCILIATION.md`,
`ROADMAP_MIN_V0_1.md`) — используй тот же формат: явные Phase с atomic-
шагами, acceptance criteria как исполняемые команды (не "сделано", а
`grep`/`pytest`/конкретный факт), sequential gates с verify-командами
между фазами, Risk Registry.

**Масштаб — весь путь целиком, не один узкий срез**, потому что
пользователь физически не может присутствовать для координации каждого
маленького шага в течение нескольких часов подряд. План должен быть
самодостаточным: если ты доходишь до развилки, которую не можешь
разрешить сам фактом из кода — не жди ответа, зафиксируй как открытый
вопрос с default-решением (по аналогии с §9 в
`ROADMAP-VV-001_promt62.md` — "если ответ 'на твой judgement' —
двигаемся с разумным default") и продолжай.

Обязательно включи в Roadmap:
- Явную привязку каждой фазы к тому, что уже проверено в AFC (Задача 0) —
  не дублировать существующее.
- STEPS.md + LESSONS.md внутри создаваемого домена (уже стандартный
  паттерн, использовавшийся в vkusvill_demo/vkusvill_research).
- Ограничение по объёму: если на каком-то этапе обнаружишь, что план
  requires больше 15-20 новых файлов до первого работающего результата —
  остановись и сократи scope, зафиксировав в LESSONS.md почему (Rule 2
  из §27.7 WORKSPACE_OS_ARCHITECTURE_RESEARCH_V1.md — тот же принцип,
  который уже доказал себя).

## ЗАДАЧА 3 — Самостоятельное исполнение без постоянного присмотра

После того как Roadmap зафиксирован — исполняй его последовательно,
фаза за фазой, тем же порядком, каким выполнялся `060_04_telegram_bot_aiogram-67` цикл
(explain-first → implementation → tests → LESSONS.md запись → next phase).

Не жди подтверждения на каждом шаге. Останавливайся только при:
- критической неоднозначности, которую нельзя разрешить фактом из кода;
- необратимом destructive action;
- конфликте с уже работающим First Vertical Slice (§34), который нельзя
  безопасно разрешить самостоятельно.

## Формат ответа (по завершении каждой фазы, не только в самом конце)

1. AFC (Задача 0) — что покрыто, что ново.
2. Roadmap-документ (Задача 1-2) целиком, до начала реализации.
3. Прогресс по фазам — с STEPS.md/LESSONS.md updates.
4. Финальный отчёт: что реализовано, что осталось открытым, почему.
