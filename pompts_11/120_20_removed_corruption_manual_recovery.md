# PROMPT 120. MANUAL FORENSIC RECOVERY OF `***REMOVED***` CORRUPTION

## 1. Роль и цель

Ты - forensic-инженер по восстановлению исходного кода.

Твоя задача - вручную диагностировать и минимально восстановить файлы, в которых маркер `***REMOVED***` заменил часть исходного содержимого.

Цель - вернуть подтверждённое исходное поведение, а не просто сделать файл синтаксически валидным.

### 1.1. Что это за маркер и откуда он

`***REMOVED***` - стандартная заглушка scrubber-инструментов (BFG-repo-cleaner и аналоги). Скрипт удаления секретов прошёлся по репозиторию и заменил совпадения слишком широкими правилами: не только ключи и токены, но и обычный код, скобки, импорты, аннотации типов.

Проверено аудитами в этой сессии:

- **1232 tracked-файла** повреждено (из них **536 `.py`**);
- **~54 000 маркеров** всего;
- маркер **запечён в сами коммиты** - из Git-истории восстановимо только **5 из 1232** файлов;
- серверный бэкап не содержит исходников (только БД и `.env`);
- `trash_21`-дампы частично повреждены тем же маркером.

Поэтому Git-история **не является надёжным источником восстановления**. Основной метод - ручная диагностика по контексту.

Работай по схеме:

```text
READ -> INVENTORY -> FIND EVIDENCE -> FORM HYPOTHESES -> REPAIR MINIMALLY -> VALIDATE -> REPORT
```

Это не задача по рефакторингу, оптимизации, переписыванию архитектуры или улучшению стиля.

## 2. Жёсткие ограничения

1. Не выполняй массовую замену `***REMOVED***`.
2. Не удаляй маркер вслепую.
3. Не считай успешный `ast.parse` доказательством корректного восстановления.
4. Не восстанавливай код только потому, что он кажется логичным.
5. Не добавляй новые возможности, зависимости, классы, функции или API.
6. Не меняй поведение неповреждённых участков файла.
7. Не переписывай функцию целиком, если повреждён только небольшой фрагмент.
8. Не удаляй и не переименовывай промты из `pompts_11/`.
9. Не изменяй Git-историю.
10. Не работай одновременно с большим количеством файлов.
11. Не используй автоматический repair-скрипт как замену диагностике.
12. Если доказательств недостаточно, оставь файл нетронутым и поставь статус `BLOCKED` или `REVIEW_REQUIRED`.
13. Не пытайся восстановить секреты (API-ключи, пароли, токены). Если маркер заменил секрет - оставь заглушку, не подставляй реальное значение.
14. Не доверяй `trash_21`-дампам без проверки: они тоже могут быть повреждены тем же маркером.
15. Не закрывай файл как восстановленный, пока не проверены все импортирующие модули.

## 3. Приоритет источников доказательств

Используй источники в следующем порядке:

1. Точная чистая копия файла из проверенного резервного каталога.
2. Проверенный dump телефона, сервера или TUI-истории.
3. Чистая версия из другого checkout или рабочей копии.
4. Связанные файлы, которые импортируют повреждённый модуль или используют его API.
5. Тесты, fixtures, конфигурация и документация проекта.
6. Git-история, если конкретный clean blob действительно существует.
7. Синтаксический и структурный контекст самого файла.
8. Логическое предположение - только если оно единственное и явно помечено как гипотеза.

### 3.1. Карта известных источников и их надёжности

| Источник | Где | Надёжность | Примечание |
|---|---|---|---|
| Git-история (clean blobs) | `git log --all --raw` | НИЗКАЯ | Только 5/1232 файлов имеют чистую версию. Проверено скриптом `recover_clean_from_git.py`. |
| `.recovery_git_clean/files/` | В корне репо | ВЫСОКАЯ (для 5 файлов) | Извлечённые чистые версии: `AGENTS.md`, `BUFFY_PROJECT.md`, `TASK.md`, `docs_10/core/ARCHITECTURAL_DEBT.md`, `projects_17/public_request_parser/STEPS.md`. |
| Серверный бэкап | `/opt/freebuff-server-backup-20260829T201345Z` на whimco | НИЗКАЯ | Содержит только `.env` и БД, исходников нет. |
| `trash_21/`-дампы | В репо | СРЕДНЯЯ | Часть файлов тоже повреждена. Обязательно проверять каждый файл отдельно. |
| `buffy_history_full.md` | В репо | СРЕДНЯЯ | Дамп 58 сессий TUI-клиента. Может содержать фрагменты кода, который позже был повреждён. |
| Импортирующие модули | `grep -r 'import <module>'` | ВЫСОКАЯ | Если другой файл импортирует имя из повреждённого, сигнатура подтверждается. |
| Тесты и fixtures | `tests_09/`, `projects_17/*/tests/` | ВЫСОКАЯ | Тесты фиксируют ожидаемый публичный API и сигнатуры. |

### 3.2. Проверка чистоты источника

Перед использованием любого источника проверь, что он сам не повреждён:

```bash
python3 -c "import ast; ast.parse(open('<file>').read())" && echo CLEAN || echo CORRUPT
```

Для `.md`-файлов:

```bash
grep -c '\*\*\*REMOVED\*\*\*' '<file>'
```

Если в источнике есть маркер - он ненадёжен для данного фрагмента.

Нельзя объявлять восстановление доказанным только на основании одного из следующих признаков:

- код стал красиво выглядеть;
- `ast.parse` завершился успешно;
- тест случайно прошёл;
- восстановленный фрагмент кажется типичным;
- похожий код есть в другом проекте.

Работай партиями максимум по 3-5 файлов. Для критических файлов работай по одному.

## 5. Диагностика каждого маркера

Для каждого `***REMOVED***` установи:

1. Что находится слева и справа.
2. Находится ли маркер внутри строки, комментария, импорта, типа, списка, словаря, вызова или тела функции.
3. Какой синтаксический элемент был оборван.
4. Какой минимальный фрагмент мог находиться на этом месте.
5. Есть ли один вариант восстановления или несколько.
6. Какой внешний источник подтверждает вариант.

### 5.1. Распределение типов повреждений (из диагностики)

Из dry-run-диагностики 31 388 маркеров в 536 `.py`-файлах:

| Тип | Количество | Сложность восстановления |
|---|---:|---|
| Не хватает закрывающей скобки выражения | 2 885 | Низкая (один символ) |
| Не хватает фрагмента выражения | 1 676 | Средняя (нужен контекст) |
| Не хватает строки импорта | 411 | Средняя (нужно имя модуля) |
| Не хватает закрывающей скобки типа | 524 | Низкая (один символ) |
| Маркер после открывающей скобки | 2 741 | Средняя (пустая коллекция?) |
| Неопределённый контекст | 23 151 | Высокая (требует анализа) |

Большинство маркеров (74%) в неопределённом контексте - это самая сложная категория.

### 5.2. Паттерны, которые уже встречались

Из практики восстановления в этом репо:

- `Optional[str | Path***REMOVED***` -> пропущена `]` -> `Optional[str | Path]`
- `dict(metadata or {***REMOVED***)` -> пропущена `}` -> `dict(metadata or {})`
- `[***REMOVED***` -> пропущен пустой список `[]`
- Целая строка импорта между двумя `import`-строками -> нужно имя модуля из контекста
- `from typing import ***REMOVED***` -> пропущен список типов -> нужен `Dict, List, Optional` и т.д.
- `return {***REMOVED***` -> пропущено тело словаря -> нужно содержимое из контекста функции

Записывай каждый встреченный паттерн в журнал - это поможет восстанавливать похожие случаи быстрее.

Классифицируй повреждение:

- `DELETED_CLOSING_DELIMITER` - пропущена `]`, `}`, `)` или аналогичный разделитель;
- `DELETED_TYPE_FRAGMENT` - повреждена аннотация типа;
- `DELETED_IMPORT` - удалена строка или часть импорта;
- `DELETED_EXPRESSION` - удалена часть выражения;
- `DELETED_STATEMENT` - удалена инструкция;
- `DELETED_STRING_FRAGMENT` - повреждена строка;
- `DELETED_COMMENT_OR_DOC` - удалён комментарий или документация;
- `UNKNOWN` - тип нельзя установить.

Если маркер встречается внутри текстового примера, не восстанавливай его как код без отдельного подтверждения.

## 6. Гипотезы и уровень уверенности

Для каждого восстановления сформируй одну или несколько гипотез.

Используй уровни:

### `HIGH`

Есть точная чистая копия или независимые источники дают одинаковый результат.

### `MEDIUM`

Точного файла нет, но вариант подтверждается импортами, тестами, сигнатурами и структурой проекта, а альтернатив нет.

### `LOW`

Вариант правдоподобен, но остаются альтернативы. Такой вариант нельзя считать завершённым без ручной проверки.

### `BLOCKED`

Доказательств недостаточно, варианты равноправны или повреждение затронуло поведение.

Правило принятия решения:

> Делай правку только для `HIGH` и обоснованных `MEDIUM`. `LOW` не выдавай за восстановленный результат. `BLOCKED` не изменяй.

## 7. Безопасная правка

Перед каждой правкой:

1. Сохрани исходный текст или создай резервную копию вне tracked-дерева.
2. Измени только минимально необходимый участок.
3. Не форматируй весь файл.
4. Не исправляй соседние старые проблемы, не связанные с маркером.
5. Покажи diff до проверки.
6. Проверь, что число неповреждённых строк и публичные имена не изменились.

После правки файл можно считать восстановленным только после всех применимых проверок:

- `ast.parse` для Python;
- `json.loads` для JSON;
- соответствующий parser/compiler для других языков;
- импорт модуля в изолированном окружении;
- связанные unit-тесты;
- smoke-тест публичного API;
- отсутствие новых маркеров в изменённом участке;
- отсутствие неожиданных изменений diff.

## 11. Условия остановки

Немедленно остановись на конкретном файле, если:

- найдено два равноправных варианта;
- неизвестно, был ли удалён код, комментарий или секрет;
- правка меняет публичную сигнатуру;
- требуется переписать функцию или класс;
- тесты противоречат предполагаемому восстановлению;
- внешний источник ненадёжен или сам повреждён;
- восстановление может затронуть безопасность, авторизацию, платежи или данные;
- файл содержит секрет и непонятно, был ли он намеренно удалён.
- число маркеров в одном файле превышает 20 и они распределены по всему файлу (ручное восстановление становится ненадёжным);
- после ремонта первой партии маркеров файл всё ещё не парсится (значит, есть скрытые повреждения);
- команда `git diff` показывает изменения в строках, где маркера не было (значит, правка задела лишнее).

В таком случае не заполняй пробел выдуманным кодом. Зафиксируй блокер и продолжи только с независимым файлом, если это безопасно.

## 14. Стратегия восстановления по типам файлов

Разные типы файлов требуют разных подходов:

### `.py` (536 файлов)

- Приоритет: `ast.parse` валидность + импорт + тесты.
- Начинать с файлов, имеющих меньше всего маркеров (1-3).
- Использовать `--diagnose` из `repair_py_markers.py` для первичной классификации, но не доверять ей слепо.
- Проверять, что восстановленный импорт действительно существует в проекте.

### `.json` (package-lock, config)

- Приоритет: `json.loads` валидность.
- `package-lock.json` с 1452 маркерами - не восстанавливать вручную, сгенерировать заново через `npm install` или `npm lock`.
- Остальные конфиги - проверять по документации и схемам.

### `.md` (документация, промты, отчёты)

- Приоритет: читаемость и смысл, не синтаксис.
- Маркеры в `.md` обычно менее критичны, но:
  - если маркер в кодовом блоке внутри `.md` - восстанавливай как код;
  - если в таблице - проверяй структуру ячеек;
  - если в обычном тексте - можно заменить на `[удалено]` если точное содержимое неизвестно.
- Промты в `pompts_11/` не восстанавливать автоматически - они могут быть умышленно редактированы.

### `.yaml` / `.toml` / `.cfg`

- Приоритет: парсинг конфигурации.
- Проверять по фактическим значениям в окружении.

## 15. Коммиты и контроль версий

- Коммить после каждой партии (3-5 файлов), не реже.
- Формат сообщения: `fix(recovery): recover <file1>, <file2> (REC-NNNN..NNNN) [HIGH|MEDIUM]`.
- В одном коммите - только файлы одного уровня уверенности.
- Никогда не коммить `LOW` или `BLOCKED` как восстановленные.
- Перед коммитом проверять `git diff` на отсутствие изменений вне целевых маркеров.
- Если коммит уже создан, но обнаружена ошибка - откатывать через `git revert`, не `amend`.

## Главный принцип

> Восстанавливай не то, что выглядит правдоподобно, а только то, что подтверждается доказательствами. Если доказательств нет, сохраняй неопределённость, не код.

> 536 файлов - это не один вечер. Это марафон по партиям. Сначала разблокируй `conftest.py` и ядро, потом двигайся по приоритету. Качество важнее скорости: один правильно восстановленный файл лучше десяти сломанных.
