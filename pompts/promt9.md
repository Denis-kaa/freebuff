## Что хорошо

"Один мозг — много моделей" и разделение на 9-10 слоёв (Context Manager, Task Mgr, Memory Engine, Context Builder, Orchestrator, Router, Tool Runtime, Knowledge Engine, Memory Layers, Event Bus, Streaming Context) — это правильная декомпозиция. Ключевая идея — **Project State First**: главная сущность не диалог, а состояние проекта на диске. Это концептуально верно для среды, где термакс может вылететь в любой момент — ты строишь систему вокруг того, что LLM-сессия эфемерна, а истина живёт в файлах и SQLite. Это не типичный подход "чат с памятью", это ближе к тому, как проектируют распределённые системы: состояние снаружи процесса, процесс — сменный.

Пять уровней памяти (Working → Project → Knowledge → Personal → Archive) — тоже разумная иерархия, она соответствует реальным скоростям затухания релевантности информации. Capability-based Router вместо `if model == "qwen"` — тоже правильный инстинкт: data-driven вместо хардкода.

## Но вот проблема, и она структурная, не косметическая

Я прочитал `BUFFY_PROJECT.md` целиком — это твой собственный документ концепции, "визитная карточка" системы. Там есть таблица "что уже реализовано", и она утверждает:

| Блок | Статус |
|---|---|
| Knowledge Engine | 🔴 Не начат |
| Event Bus | 🔴 Не начат |
| Orchestrator | 🔴 Не начат |

Я проверил код напрямую. `scripts/knowledge_engine.py` — **1437 строк**, с TF-IDF индексом, SVD-разложением (реальные `.npy`-файлы векторов на диске), тремя видами поиска. `scripts/event_bus.py` — **534 строки** плюс `event_subscribers.py` с реальными подписками (`memory.stored → auto_index_subscriber`, `checkpoint.created → checkpoint_logger`). `scripts/orchestrator.py` — **981 строка**, с полноценным FSM: `Planner → Step → ToolExecutor → Validator`, поддержкой шести типов инструментов, параллельным выполнением шагов.

Три центральных, самых сложных слоя архитектуры реализованы — а главный документ концепции говорит, что их нет.

## Почему это важнее, чем кажется

Это та же болезнь, что и с TASK.md, только на уровень выше. Ты построил систему вокруг принципа "Project State First" — состояние проекта важнее диалога, документация и есть память между сессиями. Но если сам документ-концепция (`BUFFY_PROJECT.md`) не синхронизирован с фактическим состоянием кода — то первый слой памяти, к которому обратится любой новый агент или ты сам после перерыва, **лжёт о фундаменте системы**. Buffy, читая свою же концепцию при старте новой сессии, получит вводную "Event Bus не начат" и либо не будет пытаться его использовать, либо начнёт реализовывать заново то, что уже работает.

Это структурный парадокс: система, спроектированная вокруг идеи "истина — в файлах, не в разговоре", регулярно теряет синхронизацию между файлами и реальностью, потому что ничего не проверяет файлы против реальности автоматически. Ты построил персистентность (файлы переживают перезапуск), но не построил консистентность (файлы соответствуют коду). Это разные свойства, и первое без второго создаёт иллюзию надёжности — данные-то на диске есть, только они устарели.

## Итог

Концепция сама по себе — грамотная инженерная попытка решить реальную и непростую проблему (агент без постоянной памяти в нестабильной среде). Слабое место не в архитектуре слоёв, а в том, что документация уровня "истина о системе" (`BUFFY_PROJECT.md`, `RULES.md` про структуру docs/, `seed_knowledge.py` про источники знаний) — это ещё один слой состояния, который тоже должен обновляться механически, а не вручную по памяти автора.
