# PARSED REQUIREMENTS

## ЧТО ХОЧЕТ ЗАКАЗЧИК
Построить архитектуру **D2** — конфигурируемый генератор Excel-дашбордов, где структура XLSX, данные, стили и проверки вынесены из кода генератора в декларативный CONFIG. Первый результат — эталонный проектный дашборд; затем новые XLSX создаются сменой CONFIG, не переписывая ядро.

## КЛЮЧЕВЫЕ ТРЕБОВАНИЯ (explicit)
- CONFIG → GENERATOR → XLSX с раздельными DATA / STYLES / VALIDATION.
- Структура XLSX (листы, колонки, типы, KPI, блоки, карточки, справочники, формулы, условное форматирование) — декларативно, не в коде.
- DATA нормализованы и не зависят от источника.
- VALIDATOR работает отдельно; разделять structural vs calculation validation.
- Первый шаблон — управление проектами; минимум один архитектурный тест «CONFIG меняется → XLSX меняется без правки ядра».

## СКРЫТЫЕ ТРЕБОВАНИЯ (implicit)
- **Расширяемость:** новые шаблоны (продажи/производство) без модификации ядра — только точки расширения, не реализация.
- **Честность про формулы:** не заявлять «формула вычислена», если Excel/LibreOffice расчёт не выполнялся.
- **Проверяемость:** каждое архитектурное решение проверяется на первом шаблоне.
- **Минимализм:** не добавлять сущности/универсальность, которые не нужны первому шаблону.

## ПОДВОДНЫЕ КАМНИ
- **openpyxl не считает формулы** — риск ложной уверенности, если смешать структурную и расчётную проверку.
- **Соблазн зашить бизнес-логику** конкретного проекта в универсальные модули (анти-паттерн).
- **Соблазн создать отдельный генератор под шаблон** вместо одного ядра.
- **Переусложнение** ради гипотетических D3/D4-требований.

## РЕАЛИСТИЧНОСТЬ
Высокая. Python 3 + openpyxl (3.1.5) установлены; openpyxl покрывает листы, формулы, стили, выпадающие списки, условное форматирование и чтение результата. Расчёт формул — явно отдельный слой (LibreOffice headless, опционально). Единственная осознанная граница — calculation validation.

## ВОПРОСЫ ЗАКАЗЧИКУ
1. Какой приоритет у первого эталонного XLSX: минимально рабочий (MVP) или с полным набором KPI/карточек?
2. Нужен ли экспорт/чтение данных из реального источника уже сейчас, или sample_data (Python/JSON) достаточно? (по ТЗ — только интерфейс)
3. Требуется ли расчётная валидация формул на первом этапе (LibreOffice), или структурная достаточна?

## DEPENDENCY GRAPH (критический путь)
```
FR-01 (доменная модель)
  → FR-02 (неизменяемое/изменяемое)
  → FR-03 (CONFIG шаблона)
  → FR-04 (DATA контракт)
  → FR-05 (GENERATOR)
  → FR-06 (VALIDATOR) + FR-07 (эталонный XLSX)
  → FR-08 (архитектурный тест)
```

## DEFINITION OF DONE (из ТЗ)
1. Первый проектный XLSX успешно генерируется.
2. Структура задаётся CONFIG.
3. DATA отделён от GENERATOR.
4. STYLES отделены от GENERATOR.
5. VALIDATOR работает отдельно.
6. Ядро без привязки к конкретному шаблону.
7. Смена CONFIG меняет XLSX без правки ядра.
8. Ограничения проверки явно обозначены.
9. Архитектура остаётся достаточно простой для развития.
