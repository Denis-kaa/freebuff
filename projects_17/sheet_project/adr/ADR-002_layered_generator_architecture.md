# ADR-002: Layered Generator Architecture (CONFIG/DATA/STYLES/GENERATOR/VALIDATOR)

> **Роль:** architect (blueprint `06_architect.md`, output `adr/*.md`)
> **Статус:** Accepted
> **Связанные:** `decisions/ADR-001_python_openpyxl_stack.md` (выбор стека), `architecture.md` (полная архитектура), `contracts.yaml` (формальный контракт).

## Context
D2 — конфигурируемый генератор Excel-дашбордов. Ключевое требование: **структура XLSX / данные / стили / проверки отделены от кода генератора**. Без явной границы между «неизменяемым ядром» и «изменяемым CONFIG» бизнес-логика конкретного шаблона неизбежно «протечёт» в ядро (хардкод названий листов, ветки `if project_dashboard:`), и каждый новый дашборд потребует правки ядра.

## Decision
Разбить систему на **5 bounded contexts** с однонаправленными зависимостями:

```
CONFIG (декларация) ──┐
DATA   (вход) ────────┼──→ GENERATOR (неизменяемое ядро) ──→ XLSX ──→ VALIDATOR (структура)
STYLES (визуал) ──────┘
```

- **GENERATOR** — единственный неизменяемый модуль; принимает `Workbook` + `list[Record***REMOVED***` + `Theme`, возвращает `openpyxl.Workbook`.
- **openpyxl** изолирован внутри GENERATOR (запись) и VALIDATOR (чтение); `config/`/`data/`/`styles/` не знают openpyxl.
- **Расчёт формул** вынесен за границы: GENERATOR пишет формулы структурно, VALIDATOR проверяет только структуру; расчёт — будущий слой LibreOffice (не validator).
- Формальные контракты на стыках зафиксированы в `contracts.yaml`.

## Alternatives
- **A. Монолит без границ** (всё в одном `main.py`) — быстрее для одного шаблона, но конфигурируемость (суть D2) теряется, ядро обрастает хардкодом.
- **B. Plugin-архитектура** (каждый шаблон — плагин-класс) — гибче, но избыточно для MVP и усложняет добавление шаблонов (нужен класс + регистрация вместо одного CONFIG-файла).
- **C. Расчёт формул внутри validator** — rejected: openpyxl не вычисляет формулы; засовывать LibreOffice в validator смешивает structural/calculation ответственности.

## Trade-offs
- **Выигрываем:** конфигурируемость без правки ядра (архитектурный тест «смена CONFIG»), низкая связанность, тестируемость каждого контекста, предсказуемое расширение (новый шаблон = новый CONFIG).
- **Теряем:** скорость «быстрого» добавления логики напрямую в ядро; чуть больше файлов на старте.

## Consequences
- Инвариант: `generator/*` не импортирует `config/project_dashboard.py` — защищается тестом.
- Новая сущность CONFIG (новый тип блока/поля) требует правки `schema.py` (ядро контракта) — это осознанная точка расширения.
- Расчёт формул остаётся внешним слоем до Production Scale (см. `architecture.md` §6).
