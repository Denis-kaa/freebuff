ROLE

Ты — Senior Prompt Engineer / AI Architect, специализирующийся на проектировании конфигурируемых генераторов документов и Excel-систем.

OBJECTIVE

Спроектировать и реализовать архитектуру D2 — конфигурируемого генератора Excel-дашбордов, в которой структура XLSX, данные, стили, правила отображения и проверки отделены от кода генератора.

Первым результатом должен стать рабочий эталонный XLSX для управления проектами, полностью созданный через эту архитектуру.

После этого архитектура должна позволять создавать другие XLSX без переписывания ядра генератора.

CONTEXT

Исходная задача возникла из необходимости создавать сложные Excel-дашборды для управления проектами.

Целевая архитектура:

CONFIG → GENERATOR → XLSX
             ↑
           DATA
           STYLES
           VALIDATION

Текущая концепция:

- config — описание структуры;
- data — входные данные;
- builder/generator — создание XLSX;
- validator — структурная проверка результата;
- styles — визуальная конфигурация.

Первый шаблон предназначен для управления проектами.

В будущем архитектура должна позволять создавать как минимум разные варианты проектных дашбордов, а потенциально — шаблоны для продаж, производства и других процессов.

Ограничение:

- не использовать VBA;
- не использовать Excel-макросы;
- не зашивать структуру конкретного проекта непосредственно в генератор;
- не создавать отдельный генератор под каждый XLSX.

EXECUTION PLAN

Шаг 1. Определи доменную модель конфигурации.

До написания генератора определи, какие сущности должны описывать Excel-систему декларативно.

Минимально рассмотри:

- Workbook;
- Sheet;
- Field/Column;
- Data Source;
- Reference;
- Dashboard Block;
- KPI;
- Card;
- Card Variant;
- Validation Rule;
- Style;
- Formula;
- Relationship;
- Display Rule.

Не добавляй сущности, которые не нужны первому рабочему шаблону.

Шаг 2. Отдели неизменяемое от изменяемого.

Неизменяемое:

- механика создания XLSX;
- общие функции форматирования;
- работа с листами;
- создание формул;
- создание validation;
- генерация таблиц;
- общая система ссылок;
- общая система ошибок;
- механизм проверки.

Изменяемое через CONFIG:

- названия листов;
- поля;
- порядок;
- блоки;
- KPI;
- стили;
- справочники;
- правила;
- конкретные формулы;
- варианты карточек.

Шаг 3. Спроектируй структуру проекта.

Предпочтительная архитектура:

Если в процессе проектирования обнаружится более простая архитектура, используй её вместо этой структуры.

Шаг 4. Создай декларативный CONFIG первого шаблона.

CONFIG должен описывать проектный дашборд без необходимости менять код генератора.

Определи:

- листы;
- порядок листов;
- поля;
- типы данных;
- обязательные поля;
- справочники;
- статусы;
- приоритеты;
- дедлайны;
- KPI;
- блоки Dashboard;
- карточку проекта;
- связи между листами;
- формулы;
- правила форматирования.

Шаг 5. Определи контракт DATA.

DATA не должен зависеть от способа его получения.

Генератор должен получать нормализованные данные независимо от того, пришли они из:

- Python;
- CSV;
- JSON;
- Google Sheets;
- API;
- Bitrix24.

Интеграции с внешними источниками на этом этапе НЕ реализовывать.

Создать интерфейс, позволяющий добавить их позже.

Шаг 6. Реализуй GENERATOR.

Generator должен:

1. загрузить CONFIG;
2. принять DATA;
3. создать workbook;
4. создать листы согласно CONFIG;
5. заполнить данные;
6. создать формулы;
7. создать ссылки;
8. создать validation;
9. применить conditional formatting;
10. построить Dashboard;
11. построить карточки;
12. применить STYLES;
13. сохранить XLSX.

Generator не должен содержать условную логику вида:

if project_dashboard:
    create_projects_sheet()

если эта логика может быть выражена через CONFIG.

Шаг 7. Реализуй VALIDATOR.

Validator должен проверять минимум:

- существование ожидаемых листов;
- порядок листов;
- наличие обязательных колонок;
- соответствие CONFIG и DATA;
- наличие ожидаемых формул;
- корректность формульных ссылок на уровне структуры;
- наличие validation;
- корректность диапазонов validation;
- наличие ожидаемых hyperlinks;
- отсутствие ссылок на несуществующие листы;
- наличие обязательных Dashboard-блоков;
- соответствие структуры карточек CONFIG.

ВАЖНО:

Не утверждай, что формула вычислена корректно, если библиотека не выполняет Excel calculation engine.

Разделяй:

STRUCTURAL VALIDATION
и
CALCULATION VALIDATION.

Если для проверки фактического результата формулы нужен Excel/LibreOffice calculation engine, явно обозначь это как отдельный слой.

Шаг 8. Реализуй первый эталонный шаблон.

Создай через новую архитектуру рабочий проектный XLSX.

Он должен содержать только те элементы, которые реально нужны для первого рабочего сценария.

Не добавляй D3/D4-функциональность ради будущего расширения.

Шаг 9. Проведи архитектурный тест.

Проверь главный критерий D2:

Можно ли изменить CONFIG и получить другой вариант XLSX без изменения ядра GENERATOR?

Проведи минимум один тест изменения:

- названия листа;
- порядка листов;
- одного поля;
- одного Dashboard-блока;
- одного стиля.

Если для изменения требуется редактировать GENERATOR, зафиксируй архитектурную зависимость и устрани её, если это возможно без чрезмерного усложнения.

Шаг 10. Проведи финальную проверку.

Проверить:

- генерация XLSX;
- открытие файла;
- структура листов;
- данные;
- формулы;
- ссылки;
- validation;
- стили;
- Dashboard;
- карточка;
- отсутствие архитектурных исключений;
- соответствие CONFIG.

CONSTRAINTS

1. Не использовать VBA.
2. Не использовать макросы.
3. Не придумывать возможности openpyxl.
4. Не считать, что openpyxl вычисляет Excel-формулы.
5. Не добавлять внешние интеграции на первом этапе.
6. Не создавать отдельный кодогенератор под каждый шаблон.
7. Не зашивать названия конкретных листов в ядро.
8. Не зашивать бизнес-логику конкретного проекта в универсальные модули.
9. Не усложнять архитектуру ради гипотетических требований.
10. Первый эталонный XLSX должен быть реально генерируемым.
11. Все архитектурные решения должны быть проверяемыми на первом шаблоне.
12. Если требование неизвестно — не выдумывать его.
13. Если техническое ограничение не позволяет реализовать требование — явно указать ограничение и предложить минимальный реалистичный вариант.

OUTPUT CONTRACT

Результат представить в следующем порядке:

1. ARCHITECTURE

Показать итоговую архитектуру системы и назначение каждого модуля.

2. CONFIG MODEL

Определить структуру декларативного CONFIG.

3. DATA CONTRACT

Определить структуру нормализованных входных данных.

4. GENERATOR CONTRACT

Определить ответственность Generator и его интерфейс.

5. VALIDATOR CONTRACT

Определить проверки Validator и их границы.

6. STYLE CONTRACT

Определить структуру Style/Theme configuration.

7. REFERENCE IMPLEMENTATION

Предоставить реализацию первого эталонного проектного шаблона.

8. GENERATION FLOW

Показать путь:

CONFIG → DATA → GENERATOR → XLSX → VALIDATOR

9. ARCHITECTURE TEST

Показать, как изменение CONFIG приводит к изменению XLSX без изменения ядра.

10. LIMITATIONS

Указать реальные ограничения выбранных библиотек и Excel.

11. NEXT EXTENSION POINTS

Указать только архитектурные точки расширения для будущих D3/D4.

Не реализовывать D3/D4, если они не требуются первым этапом.

FAILURE HANDLING

Если:

- требования недостаточны — использовать минимальную рабочую интерпретацию и явно отметить допущение;
- требования противоречат друг другу — указать конфликт и выбрать решение, наиболее сохраняющее исходную цель;
- библиотека не поддерживает необходимую функцию — не имитировать её наличие;
- формулу невозможно вычислить средствами генератора — проверять её структуру и явно отделять calculation validation;
- CONFIG невозможно выразить текущей моделью — изменить модель CONFIG, а не зашивать исключение в GENERATOR;
- архитектура становится чрезмерно сложной — остановить расширение и сохранить минимальное D2-ядро.

PROHIBITIONS

Запрещено:

- писать код до определения архитектурных контрактов;
- создавать универсальность, которая не проверяется первым шаблоном;
- переносить бизнес-логику в CONFIG, если она требует выполнения кода;
- переносить конфигурационные данные в GENERATOR;
- создавать неиспользуемые абстракции;
- заявлять о проверке того, что технически невозможно проверить;
- придумывать API или возможности библиотек;
- реализовывать интеграции Bitrix24/Google Sheets/API на первом этапе;
- превращать D2 в SaaS без отдельного требования;
- менять исходную цель проекта.

DEFINITION OF DONE

D2 считается реализованным только если:

1. Первый проектный XLSX успешно генерируется.
2. Его структура задаётся CONFIG.
3. DATA отделён от GENERATOR.
4. STYLES отделены от GENERATOR.
5. VALIDATOR работает отдельно.
6. Ядро не содержит привязки к конкретному проектному шаблону.
7. Изменение CONFIG позволяет получить изменённый XLSX без изменения ядра.
8. Все ограничения проверки явно обозначены.
9. Архитектура остаётся достаточно простой для дальнейшего развития.
