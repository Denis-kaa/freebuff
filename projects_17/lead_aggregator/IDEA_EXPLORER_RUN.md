## 8. DEPTH-2 EXPLORATION

### B1 — Pull-агрегатор (DEEPEN)
- **MECHANISM:** cron/prompt-очередь → адаптеры (Kwork: страницы поиска; TG: Telethon channel_history) → нормализация → L1 (regex-словарь) → L2 (intent-правила) → L3 (ModelGateway score 0–100) → порог → TG-уведомление.
- **VARIANTS:** (a) pull по расписанию; (b) webhook/подписки где есть; (c) ручной запуск.
- **CONSEQUENCES:** детерминированный, безопасный (read-only), но задержка до часа; не решает «заказчик не видит меня».
- **SECOND-ORDER:** накопление истории заказов → база интент-профилей заказчиков (W-8 реестр компетенций) → аналитика «какие запросы реальны».
- **FAILURE MODE:** Kwork анти-бот (капча), TG-каналы могут закрыться; L3-скоринг зависит от доступности ModelGateway.

### B7 — Inbound-видимость (DEEPEN)
- **MECHANISM:** контент-фабрика: берёт готовые кейсы (portfolio, FREELANCER_OS артефакты) → постит в TG-канал/VC/Дзен по расписанию.
- **VARIANTS:** (a) ручные посты; (b) автогенерация из ROADMAP/артефактов; (c) гибрид (агент готовит, человек публикует).
- **CONSEQUENCES:** решает первопричину (видимость), но эффект отложенный (недели), требует контент-дисциплины.
- **SECOND-ORDER:** публичное портфолио → входящие заявки → обратная воронка; репутация в нише.
- **FAILURE MODE:** нет заказчика без контента; риск спама в TG-каналах; измерение эффекта сложное.

## 9. CROSS-POLLINATION ENGINE

- **B1 + B3 →** Attract-агрегатор → инпуты HR-агента (вакансии = заказы с зарплатой) — «что из механизма B1 устраняет ограничение B3?» (B3 не имеет источников; B1 даёт их).
- **B1 + B4 →** заказы доставляются в существующий TG-бот платформы (команда `/leads`) — «B4 усиливает B1» (доставка без нового канала).
- **B1 + B7 →** pull-заказы + inbound-видимость = **двусторонняя воронка** (заказы ищем + нас находят) — EMERGENT: «A + B → NEW CONCEPT».
- **B7 + B2 (hypothesis) →** контент-видимость снижает риск outbound-спама (нас уже знают) — CORRECTIVE.

## 10. REFRAME ENGINE

- **USER REFRAME:** основной пользователь — не только фрилансер, но и его **будущие клиенты** (они видят контент B7).
- **PROBLEM REFRAME:** решаем не «где искать заказы», а «как сделать так, чтобы заказы находили тебя» — B7.
- **MECHANISM REFRAME:** отказаться от парсинга вообще → только каналы-агрегаторы + ручной ввод (недостаточно масштаба — отклонено).
- **VALUE REFRAME:** главная ценность — не список заказов, а **замкнутый цикл «запрос → контакт → сделка»** с учётом того, что контактные данные часто вне платформы.

## 11. BLIND-SPOT DETECTOR

- **HYPOTHESIS 1:** заказчики ищут исполнителей прямо в TG (поиск по словам «нужен разработчик бота») — можно мониторить поиск, не только каналы.
- **HYPOTHESIS 2:** Kwork отдаёт контакты только после отклика — pull-агрегатор даёт «горячие» заказы, но контакт закрыт → нужен переход в отклик (B2-гипотеза).
- **HYPOTHESIS 3:** публичные «лендинги-визитки» заказчиков (вроде realtor-лендингов) генерируют входящие заявки лучше, чем парсинг.
- **HYPOTHESIS 4:** реестр компетенций (W-8) + история заказов → автоподбор ниш по фактическому спросу, а не по мнению.

## 16. CRITICAL DECISION POINT

«Критическая развилка: **внешние контакты заказчиков**.

Если контакты доступны без отклика (Kwork показывает, TG-посты публичны) → развиваем **A (pull-агрегатор)** — самый реалистичный путь.
Если контакты закрыты (нужен отклик/оплата подписки) → развиваем **C (push-входящие + TG-поиск)** — входящие заявки вместо парсинга закрытых данных.»

**Решение по данным PHASE1/ATTRACT_RESEARCH:** Kwork даёт страницы заказов без телефонов (контакт через отклик), TG-каналы публичны. → **A принят как v1** (pull), **B7-трек** отдельно, **C** — гипотеза для проверки.
