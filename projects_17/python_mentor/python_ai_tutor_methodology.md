# AI-система обучения Python — методика v1.0

> Итог одним абзацем: система строится вокруг **пяти ролей** (не шести — Практикум объединён с Тьютором как режим), которые двигают ученика по циклу «объяснение → упражнение → проект → ревью → корректировка», при этом каждая роль имеет жёсткие границы, а самостоятельность ученика измеряется явно (через уровни подсказок и модель прогресса), а не декларируется. Контекст держится в 5 документах, из которых один — не «база знаний Python» (LLM и так её знает), а **журнал проектов и решений**, потому что именно это невозможно восстановить из общих знаний модели.

---

## A. Архитектура системы: роли и границы

### A.1 Почему 5 ролей, а не 6

Предложенные Тьютор и Практикум решают разные *задачи* (объяснение концепции vs. генерация задач), но работают на **одном и том же контексте**: текущая тема, уровень ученика, только что пройденная теория. Разделение их на отдельные роли с отдельными системными промтами создаёт:

- дублирование контекста (обеим ролям нужен профиль ученика и текущая компетенция);
- риск рассинхронизации (Практикум может генерировать задачи не по той теме, которую только что объяснил Тьютор);
- лишний шаг координации, который обязан делать Куратор.

**Решение:** Тьютор — одна роль с двумя режимами: `explain-mode` и `drill-mode`. Технически это может быть даже один системный промт с переключателем поведения. Если у Максима есть причина держать их раздельно (например, генерация упражнений батчами заранее, впрок, без диалога) — это единственный сценарий, где разделение оправдано. В остальных случаях объединение снижает сложность без потери функции.

Итоговые 5 ролей:

| Роль | Функция | НЕ делает |
|---|---|---|
| **Куратор** | Держит траекторию, решает "что дальше", читает данные от всех ролей | Не объясняет тему сам, не пишет код, не оценивает решение построчно |
| **Тьютор** (explain + drill) | Объясняет теорию, формирует лестницу упражнений | Не решает задачи ученика вместо него, не переходит в отладку конкретного кода (это Ментор) |
| **Ментор** | Сопровождает решение задачи, управляет уровнями подсказок L0–L6 | Не ставит новых тем, не оценивает финальный результат для журнала прогресса |
| **Заказчик** | Даёт реалистичное ТЗ, играет роль внешнего стейкхолдера | Никогда не объясняет "как делать", не даёт подсказок — это разрушает роль |
| **Ревьюер** | Оценивает готовый результат по 4 осям (см. G) | Не помогает переделать код, не учит — только оценивает и передаёт данные Куратору |

### A.2 Куратор — границы явно

**Куратор делает:**
- смотрит на профиль ученика и журнал ошибок перед каждым новым назначением;
- решает баланс теория/практика/проект на ближайшую сессию;
- решает, когда компетенция считается закрытой, а когда требует возврата (spaced repetition);
- эскалирует паттерны («три сессии подряд проблема с декомпозицией») в явное решение.

**Куратор не делает:**
- не объясняет Python-концепции (это подменяло бы Тьютора и раздувало бы его контекст);
- не участвует в live-сессии решения задачи;
- не выставляет оценку конкретному коду.

Куратор — единственная роль, которая **читает все 5 документов**. Остальные роли читают только те, что нужны для их функции (см. раздел I).

### A.3 Матрица эволюции ролей по мере роста ученика

| Уровень ученика | Тьютор | Ментор | Заказчик | Ревьюер |
|---|---|---|---|---|
| Новичок (S0–S2) | Много explain-mode, аналогии | Быстро даёт L2–L3 | Не подключается | Мягкий, объясняет "почему" подробно |
| Средний (S3–S4) | Меньше теории, больше drill | Стартует с L0–L1, ждёт дольше | Подключается на микро-проектах | Строже, спрашивает обоснование решений |
| Продвинутый (S5–S6) | Только по запросу ученика | Почти не вмешивается, L0 по умолчанию | Основной канал взаимодействия | Действует как технический собеседник, спорит с решениями |

Это и есть механизм "уменьшения зависимости от AI" из п.16 — он не отдельный алгоритм, а естественное следствие модели прогресса (D) и правил эскалации подсказок (E).

## B. Образовательный цикл

Базовый формат сессии (Тьютор, explain-mode):

```
короткая теория (1 концепция, не больше) → 1 проверочный вопрос →
пример → самостоятельная попытка → разбор → упражнение (drill-mode)
```

Полный цикл темы:

```
Куратор выбирает тему → Тьютор объясняет и тренирует →
Ментор сопровождает пограничные упражнения (где ученик застревает) →
Ревьюер оценивает финальные упражнения темы →
Куратор фиксирует S-уровень компетенции → решает: следующая тема или повтор
```

Проектный цикл (когда компетенций накоплено достаточно):

```
Куратор решает "пора выдавать проект" (критерии — см. F) →
Заказчик выдаёт ТЗ (намеренно неполное) →
ученик самостоятельно уточняет требования, декомпозирует, проектирует →
Ментор доступен по явному запросу ученика (не вмешивается сам) →
ученик сдаёт → Ревьюер оценивает по 4 осям →
Куратор обновляет профиль, журнал ошибок, curriculum map →
корректирует следующий этап
```

Ключевое правило: **в проектном режиме Ментор не инициирует контакт**. Только ученик может позвать его — это единственный способ реально проверить самостоятельность, иначе Ментор незаметно превращается в тьютора внутри проекта.

## C. Модель компетенций

Компетенция — не тема, а *измеримый навык*. У каждой компетенции обязательно:

- **Понимание** — что должен объяснить своими словами;
- **Умение** — что должен уметь сделать без подсказки;
- **Типичные ошибки** — конкретный список, не абстрактный;
- **Prerequisites** — какие компетенции должны быть на S3+;
- **Проверочное упражнение** — минимум, доказывающий S4;
- **Проект-маркер** — какой тип проекта естественно требует этой компетенции.

Полный шаблон применён к куррикулуму в разделе J.

## D. Модель прогресса

Шкала S0–S6 из исходного документа рабочая, но ей не хватает **поведенческого теста** на каждом уровне — иначе "оценка уровня" превращается в субъективное мнение AI. Добавляю тест-критерий к каждому уровню:

| Уровень | Описание | Как проверяется (наблюдаемо) |
|---|---|---|
| S0 | Не знаком | Не может дать определение даже примерно |
| S1 | Узнаёт концепцию | Узнаёт термин, путает детали |
| S2 | Понимает объяснение | Пересказывает своими словами без ошибок |
| S3 | Применяет с подсказкой | Решает задачу, но требует ≥ L2 подсказки |
| S4 | Применяет самостоятельно | 2 разных упражнения подряд решены на L0–L1 |
| S5 | Переносит в новый контекст | Использует концепцию внутри проекта **без** явного напоминания, что она нужна |
| S6 | Объясняет и критикует | Находит внедрённую ошибку в чужом коде на эту тему; аргументированно выбирает между двумя решениями |

Переход между уровнями фиксируется Куратором только по факту наблюдения, не "на глаз". Это то, что делает Curriculum Map (документ 2) не декларативным, а основанным на данных.

## E. Модель подсказок и анти-копирование

### E.1 Уровни (L0–L6) — правила эскалации

Стартовая позиция для **любой новой задачи — всегда L0**, независимо от того, сколько подсказок понадобилось на предыдущей. Исключение — Куратор отдельно считает *кумулятивный* расход подсказок по компетенции как метрику независимости (влияет на S-уровень, но не меняет стартовую позицию следующей задачи).

Правило эскалации: Ментор поднимается на **один уровень за раз**, и только после явного сигнала застревания:
1. ученик сам просит подсказку — сразу выдаётся следующий уровень выше последнего использованного (не L0→L6 скачком);
2. ученик делает 2 попытки подряд без концептуального сдвига (не путать с "код не запустился" — это не застревание, это нормальная отладка);
3. Ментор явно спрашивает разрешение перед L4+: «Хочешь подсказку конкретнее, или ещё покопаешься сам?» — кроме случаев явного тайм-аута/фрустрации ученика.

**В режиме Заказчика (проект)** потолок по умолчанию — L3. L4–L6 в проекте выдаются только после явного и повторного запроса, потому что цель проекта — самостоятельное проектирование, а не дотягивание до готового решения.

### E.2 Анти-копирование — конкретные правила

- AI **не пишет решение целиком**, пока ученик не сформулировал собственную (пусть неверную) попытку/план — даже словами, не кодом. Ментор блокирует переход к коду без этого шага.
- L6 (разбор решения) всегда сопровождается обязательной проверкой: «объясни, что делает эта строка» / «что изменится, если здесь заменить X на Y» — без правильного ответа задача не засчитывается как закрытая, а помечается в журнале ошибок как "copied-not-understood".
- Ревьюер отдельно фиксирует это как флаг независимости, влияющий на S-уровень компетенции (не даёт S4 при паттерне "решено, но не объяснено").
- AI не пишет код за ученика в Заказчик-режиме вообще — только вопросы и, при повторном запросе, подсказки не выше L3.

## F. Проектная модель

| Этап | Что это | Критерий перехода к следующему |
|---|---|---|
| 1. Микропроекты | 1–2 концепции, без внешних зависимостей | 3 микропроекта подряд закрыты на S4+ по всем задействованным компетенциям |
| 2. Учебные приложения | Несколько связанных компонентов (например, CLI-калькулятор с историей) | Ученик самостоятельно декомпозирует задачу на модули без подсказки Ментора |
| 3. Внешние зависимости | API, файлы, БД, Telegram и т.п. | Успешно отлаживает ошибку внешней интеграции без L4+ |
| 4. Полноценные проекты | Архитектура, тесты, логирование, конфиг, документация | Ревьюер ставит "проходной" балл по всем 4 осям без повторной сдачи |
| 5. Реальные инженерные задачи | ТЗ, большинство решений — на ученике | Заказчик оценивает результат как приемлемый "как для реального проекта", включая уточняющие вопросы, которые ученик задал сам |

Переход между этапами решает Куратор на основе данных из Ревью и Журнала ошибок — не по субъективному ощущению "вроде готов".

## G. Модель ревью

Ревьюер оценивает по 4 осям (не по одной сводной оценке — иначе теряется диагностическая ценность):

1. **Python** — корректность, идиоматичность, работа с исключениями, использование стандартной библиотеки где уместно.
2. **Engineering** — декомпозиция, архитектура, edge cases, тестируемость, документация.
3. **Thinking** — может ли объяснить решение, находит ли сам ошибку при наводящем вопросе (не при прямом указании), качество обоснования выбора.
4. **Independence** — сколько подсказок и какого уровня потребовалось; отдельно — были ли case'ы "copied-not-understood".

Важно: балл по Independence **не наказывает** использование подсказок — он документирует их, потому что решение после 10 подсказок объективно не то же самое, что самостоятельное, и Куратору нужна честная картина, а не искусственно завышенная.

Результат ревью — не просто оценка, а структурированные данные для Куратора: какие компетенции подтверждены на S4/S5, какие ошибки повторились, что стоит вернуть в spaced repetition.

## H. Модель ошибок

Классификация (используется Ментором и Ревьюером при фиксации, Куратором — при анализе трендов):

| Тип ошибки | Пример | Что это сигнализирует |
|---|---|---|
| Концептуальный пробел | Не понимает разницу mutable/immutable | Нужно вернуться к теории, не к практике |
| Синтаксическая/процедурная | Путает синтаксис, но понимает идею | Нужен ещё drill, не объяснение |
| Декомпозиция/архитектура | Пишет одну гигантскую функцию | Нужны упражнения именно на разбиение задачи, отдельно от синтаксиса |
| Навык отладки | Исправляет только после указания на строку | Нужны упражнения "найди ошибку сам", не "напиши код" |
| Перенос знаний | Понимает в изоляции, не применяет в новом контексте | Нужен проект, который заставит использовать концепцию неожиданно |
| Паттерн зависимости | Стабильно требует L4+ там, где ожидается L1 | Сигнал для Куратора — возможно, тема пройдена слишком быстро |

Каждая ошибка в журнале хранится с меткой компетенции и триггером повторного возврата: либо "через N сессий", либо "при следующем проекте, где концепция естественно всплывёт" (предпочтительнее — органичнее, чем искусственное повторение).

## I. Структура пяти документов

Ключевое решение: **нет отдельного документа "База знаний / Reference Python"** — модель и так знает Python исчерпывающе, хранить это как персистентный контекст — трата места без пользы. Вместо этого четвёртый документ — журнал того, что *действительно* нельзя восстановить из общих знаний: конкретные проекты, конкретные решения, конкретный прогресс этого конкретного ученика.

| # | Документ | Что хранится | Частота обновления | Кто читает |
|---|---|---|---|---|
| 1 | **Методика и роли** | Правила системы, границы ролей, уровни подсказок, правила анти-копирования | Почти статичен | Все роли |
| 2 | **Curriculum & Competency Map** | Список компетенций, их S-уровень, prerequisites, что дальше | После каждой закрытой/повторённой компетенции | Куратор, Тьютор |
| 3 | **Профиль ученика** | Текущая позиция, стиль обучения, тренд независимости, активные "слабые места" | Каждая сессия (компактно, без истории — это в документе 5) | Куратор, Ментор, Заказчик |
| 4 | **Журнал проектов и ревью** | Что сдано, оценки по 4 осям, ключевые архитектурные решения ученика | После каждого проекта, с периодическим сжатием старых записей в резюме | Куратор, Ревьюер, Заказчик |
| 5 | **Журнал ошибок и spaced repetition** | Классифицированные ошибки, расписание возврата к темам | После каждой сессии, старые записи сворачиваются в паттерны | Куратор, Ментор |

Правило против "свалки": документы 3–5 хранят **текущее состояние и паттерны**, а не полную стенограмму. Каждые N сессий Куратор сжимает старые записи документа 4 и 5 в краткое резюме ("темы X, Y закрыты стабильно; Z требует ещё одного захода"), а не копит бесконечный лог.

### I.1 Логи как будущий датасет для детерминированного слоя

Документы 4 и 5 изначально пишутся LLM-версией системы, но их стоит вести не просто человекочитаемым текстом, а структурированно — потому что именно из этих логов позже можно собрать более дешёвое, не требующее ЛЛМ ядро (правила Куратора, автогрейдер, банк подсказок и ТЗ), не проводя отдельный сбор данных.

Каждая запись должна включать, где применимо:
- AST-паттерн ошибки (если код можно распарсить и ошибка типовая — mutable default argument, голый `except:`, O(n²) там где просился `dict` и т.п.);
- уровень подсказки (L0–L6), на котором задача была закрыта, и текст подсказки, которая сработала;
- текст объяснения ученика по оси Thinking, если Ревьюер посчитал его удовлетворительным (это будущий эталон для рубрики);
- реальные уточняющие вопросы ученика к ТЗ Заказчика (сырьё для будущего FAQ/дерева решений).

Формат такой записи — единый `LOG UPDATE` блок, используемый всеми ролями, которым положено писать в документы (см. промты ролей).

## J. Curriculum Python (по компетенциям)

Полный шаблон применён к базовым компетенциям трассы; остальные компетенции перечислены с названиями — по тому же шаблону их можно развернуть отдельно.

### Компетенция: Переменные и типы данных
- **Понимать:** мутабельность/иммутабельность, динамическая типизация, что такое ссылка на объект.
- **Уметь:** предсказать поведение при присваивании списков/чисел, объяснить разницу `is` и `==`.
- **Типичные ошибки:** путает mutable/immutable, не понимает, почему изменение списка "в другом месте" повлияло на исходный.
- **Prerequisites:** нет.
- **Проверочное упражнение:** предсказать вывод программы с алиасингом списка без запуска кода.
- **Проект-маркер:** любой проект, где есть общее состояние между функциями.

### Компетенция: Управляющие конструкции (условия, циклы)
- **Понимать:** порядок выполнения, разница `for`/`while`, что такое итерируемый объект.
- **Уметь:** переписать вложенные условия через ранний возврат, выбрать правильный тип цикла.
- **Типичные ошибки:** бесконечные циклы по невнимательности, избыточная вложенность условий.
- **Prerequisites:** переменные и типы.
- **Проверочное упражнение:** отрефакторить код с 4 уровнями вложенности в плоскую структуру.
- **Проект-маркер:** любой CLI-инструмент с валидацией ввода.

### Компетенция: Функции и область видимости
- **Понимать:** локальная/глобальная область видимости, параметры по умолчанию, `*args`/`**kwargs`, чистые функции vs побочные эффекты.
- **Уметь:** разбить монолитный скрипт на функции с единственной ответственностью.
- **Типичные ошибки:** пишет функции на 60+ строк, смешивает вычисление и вывод в одной функции.
- **Prerequisites:** управляющие конструкции.
- **Проверочное упражнение:** декомпозировать данный "простынный" скрипт на 5+ функций без потери поведения.
- **Проект-маркер:** появление функции внутри более крупного проекта недель через 3–4 после изучения (spaced repetition в действии, п.14).

### Компетенция: Структуры данных (list/dict/set/tuple)
- **Понимать:** когда какая структура уместна, сложность операций (интуитивно, не Big O формально на этом этапе).
- **Уметь:** выбрать структуру под задачу и обосновать выбор.
- **Типичные ошибки:** использует list там, где нужен dict (линейный поиск вместо O(1)), не знает about `set` для уникальности.
- **Prerequisites:** функции.
- **Проверочное упражнение:** дан код с list.count() в цикле — предложить и обосновать замену на dict.
- **Проект-маркер:** любой проект с подсчётом/группировкой данных.

### Компетенция: ООП (классы, инкапсуляция, наследование)
- **Понимать:** когда ООП уместнее функционального стиля, что такое `self`, разница композиции и наследования.
- **Уметь:** спроектировать 2–3 класса с ясными обязанностями.
- **Типичные ошибки:** понимает синтаксис классов, но не применяет — продолжает писать процедурный код по привычке (классический "теоретически понимает, применить не может").
- **Prerequisites:** структуры данных, функции.
- **Проверочное упражнение:** взять существующий процедурный код и обоснованно решить, стоит ли переписывать в классы (правильный ответ иногда "нет").
- **Проект-маркер:** приложение с несколькими сущностями, которые естественно моделируются как объекты.

### Компетенция: Обработка ошибок
- **Понимать:** `try/except` не как "чтобы не падало", а как явное управление ожидаемыми сбоями; разница между багом и ожидаемым исключением.
- **Уметь:** писать конкретные `except`, не голый `except:`.
- **Типичные ошибки:** глотает все исключения без разбора, скрывая реальные баги.
- **Prerequisites:** функции.
- **Проверочное упражнение:** дан код с `except: pass` — найти, какую реальную ошибку он маскирует.
- **Проект-маркер:** любая интеграция с внешним источником (файл, сеть, ввод пользователя).

### Компетенция: Работа с файлами и I/O
- **Понимать:** контекстные менеджеры, кодировки, разница текстового/бинарного режима.
- **Уметь:** безопасно читать/писать файлы с обработкой отсутствия файла.
- Prerequisites, ошибки, упражнение, проект-маркер — по тому же шаблону.

### Компетенция: Тестирование и отладка
- **Понимать:** зачем нужны тесты, разница unit/integration, как читать traceback.
- **Уметь:** написать простой `pytest`-тест, найти причину бага по traceback без посторонней помощи.
- Ключевая типичная ошибка: "чинит симптом, не находит причину" — чинит до тех пор, пока ошибка не перестаёт быть видна, не понимая, почему.

### Компетенция: Работа с внешними API / интеграции

## K. Полный пример через всю систему

### Пример 1 — тема "Функции"

1. **Куратор**: смотрит Curriculum Map — «Управляющие конструкции» на S4, prerequisites закрыты → назначает тему «Функции».
2. **Тьютор (explain-mode)**: короткая теория про области видимости и единственную ответственность → 1 проверочный вопрос → пример декомпозиции → самостоятельная попытка.
3. **Тьютор (drill-mode)**: даёт лестницу — повторение → применение по аналогии → новая задача → декомпозиция монолитного скрипта.
4. Ученик застревает на декомпозиции → зовёт **Ментора** → тот стартует с L0 («что тебе непонятно конкретно?»), поднимается до L2 («посмотри, какие переменные меняются в скольки местах») — до решения.
5. **Ревьюер** оценивает финальное упражнение: Python — ок, Engineering — функции ещё великоваты, Thinking — объясняет свой выбор, Independence — потребовался L2 один раз.
6. **Куратор**: фиксирует «Функции → S3» (не S4 — engineering ещё слабый), планирует ещё одно упражнение на декомпозицию через 1–2 сессии, помечает в Журнале ошибок паттерн «функции длиннее оптимального».

Через 3 недели, в проекте на Этапе 2 (CLI-инструмент), функции естественно понадобятся снова — это и есть spaced repetition (п.14): не искусственное повторение, а органичное всплытие в новом контексте, что при успешном самостоятельном применении поднимает компетенцию до S5.

### Пример 2 — проект «Сервис приёма заявок»

1. **Куратор** видит: компетенции API-интеграций, ООП и обработки ошибок на S4 → критерии Этапа 3 выполнены → даёт добро на проект.
2. **Заказчик** выдаёт ТЗ ровно как в исходном документе: «сервис принимает заявки, сохраняет, меняет статус, отдаёт список» — без деталей архитектуры.
3. Ученик самостоятельно: задаёт уточняющие вопросы Заказчику (какие статусы? нужна ли персистентность между перезапусками?), проектирует структуру, выбирает технологии, пишет код.
4. Ментор не вмешивается, пока ученик не позовёт сам; когда зовёт — потолок L3 (в проектном режиме).
5. Сдача → **Ревьюер**: Python — идиоматично; Engineering — неплохая декомпозиция, но нет обработки дублирующихся заявок (edge case); Thinking — обосновывает выбор структуры данных; Independence — 2 подсказки уровня L2, ноль L4+.
6. **Куратор**: обновляет Журнал проектов, поднимает «Обработка ошибок» и «Архитектура приложений» до S5 (перенос в новый контекст подтверждён), фиксирует в Журнале ошибок «пропускает edge cases на дублирование — стоит дать 1-2 упражнения именно на этот класс багов», планирует следующий проект чуть сложнее (Этап 4).
