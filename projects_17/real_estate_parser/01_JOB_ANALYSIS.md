# 01_JOB_ANALYSIS — вакансия «парсер недвижимости + Telegram-бот + деплой»

## Вакансия (дословно)

> «Нужен парсер, который ежедневно по расписанию собирает объекты недвижимости и записывает их в БД.
> Требования: прокси, многопоточность, асинхронность.
> Нужен бот для управления.
> Деплой и запуск на сервере.
>
> Парсер собирает ТОЛЬКО объекты недвижимости: площадь; цена; количество комнат; и другие характеристики объекта.»

## USER REQUIREMENT → TECHNICAL REQUIREMENT

| USER | TECHNICAL | IMPLEMENTATION | INFRA |
|---|---|---|---|
| «ежедневно по расписанию» | scheduler + идемпотентные прогоны | systemd timer или APScheduler cron | сервер, таймзона |
| «собирает объекты недвижимости» | discovery URL → fetch → parse | httpx + bs4 (SSR) или API | сеть, прокси |
| «площадь, цена, комнаты, другие характеристики» | нормализация полей в единую схему | парсеры per-source + валидатор | — |
| «записывает их в БД» | upsert + дедупликация | PostgreSQL (или SQLite v1), natural key | БД-сервер |
| «прокси» | ротация + health-check | ProxyRotator (интерфейс уже есть) | платный провайдер |
| «многопоточность, асинхронность» | bounded concurrency | asyncio + semaphore (threads НЕ нужны) | — |
| «бот для управления» | команды статуса/запуска | Telegram-бот (aiogram) | TG token |
| «деплой и запуск на сервере» | воспроизводимый деплой | Docker Compose или systemd + docs | сервер |

### EXPLICIT / INFERRED / OPTIONAL

- **EXPLICIT:** ежедневное расписание; парсинг только объектов недвижимости; поля площадь/цена/комнаты+; запись в БД; прокси; асинхронность/потоки; Telegram-бот управления; деплой на сервере.
- **INFERRED (не додумываем как факт, помечаем):** дедупликация и отслеживание изменений цены (объекты повторяются день ото дня); resume после падения; алертинг об ошибках прогона; хранение истории цены (last_seen/price-change); источник данных не указан — сайт(ы) нужно выбрать.
- **OPTIONAL:** дашборд, уведомления о новых объектах в боте, экспорт CSV, ротация UA.

## Минимально необходимая реализация (без over-engineering)

Прокси нужен заказчику, скорее всего, из-за rate limits/блокировок по IP — **не строим распределённый proxy-pool**. Минимум: 1–N прокси из конфига, ротация round-robin + health-check, пауза при 403/429. Если источник один и отдаёт SSR — curl_cffi не обязателен на старте (абстракция TLSClient с fallback).

Concurrency: **async I/O workers + bounded concurrency (semaphore ~4–8) + rate limit per host**. Многопоточность (threads) не нужна — задача I/O-bound; asyncio покрывает «многопоточность + асинхронность» из вакансии одним механизмом.

Scheduler: **systemd timer** (деплой на Linux-сервере, ноль новых зависимостей) или APScheduler внутри процесса, если бот должен уметь /run вручную. Выбор: APScheduler в одном процессе с ботом — «ежедневно по расписанию» + ручной /run из бота в одном юните.

Бот MVP: /status (последний прогон, счётчики), /run (запуск прогона вручную), /stop (мягкая отмена), /stats (кол-во объектов, новые/обновлённые), /errors (последние ошибки). Не реализуем команды «на всякий случай».

## Оценка

| Метрика | Оценка |
|---|---|
| TECHNICAL COMPLEXITY | 4/10 (без CAPTCHA/headless), 6–7/10 (если источники под Cloudflare/SPA) |
| IMPLEMENTATION TIME | LOW–MEDIUM (ядро 1–2 дня; +прокси/деплой 1 день) |
| RISK | MEDIUM: выбор источников не указан; anti-bot; юридический ToS-гейт |

| BLOCKERS | нет критических; всё решаемо конфигурацией |

## AUTONOMY SCORE: ~85%

Код, тесты, архитектура, Docker, локальный деплой — 100% агентом. Прокси-провайдер (выбор+оплата), TG-токен, SSH-доступ и финальный выбор сайтов — человек (~15%).
