## 3. Вердикт (Thinker-Gemini, 2026-08-11)

### 3.1. Production-readiness
**❌ RISK → UNSAFE для hero-роли «Показать smartdry™ текстуру».**

Причина: при 0.27 B/px JPEG типично использует chroma-subsampling **4:2:0** + DCT-blocking на границах → на текстуре плетения ткани будут видны «зёрна» и смазывание цветов (особенно на складках, где соседние пиксели имеют разный тон).

### 3.2. Действие
**✅ НЕ КОНВЕРТИРОВАТЬ** в PNG через `convert` или Pillow.

Причина: декодирование с потерями → повторное кодирование без потерь **запирает артефакты** в файле. `-compress None image6.jpeg image6.png` даёт ~700-900 KB PNG с теми же самыми visual artifacts → нет выигрыша + рост веса ×4.

### 3.3. Правильный путь
**📩 Запросить у клиента ОРИГИНАЛ**, один из вариантов:
- **(A)** Исходный несжатый (или q≥90) JPEG-файл напрямую с камеры/фотостока.
- **(B)** Исходный PNG/TIFF от дизайнера (если был).
- **(C)** Ссылка на материал в фирменном банке фотографий Рокус-Спорт.

Все три варианта должны иметь размер **≥ 1920 × 1080 px** и **bytes/pixel ≥ 0.50** для уверенного hero-рендеринга на Tilda `t-cover` / Zero Block 100vh.

## 4. Quality-QA Checklist (для Master Roadmap §14)

> Эти 4 пункта добавлены подсекцией **14.6 «Image Quality QA (PIL-автоматизация)»** в Master Roadmap.

### 4.1. Hero JPEG (фотография, full-screen / half-screen)
- **`bytes/pixel ≥ 0.50`** — иначе flag RISK.
- **DPI ≥ 96** для web; ≥ 150 если планируется печать.
- **EXIF orientation = 1** (или 0) — иначе фото «лежит на боку» на iOS/Android.
- **ICC profile present** — иначе цвет может «поплыть» в Safari.

### 4.2. Product Photo / Texture (smartdry™ как у нас)
- **bytes/pixel ≥ 0.70** — для текстур нужно ещё больше деталей (ткань, ручка, шов).
- **Chroma subsampling = 4:4:4** — без смазывания цветов на границах плетения.
- **Visual diff test**: открыть в Chrome @ 100% zoom и сравнить с эталонным PNG (если есть).

### 4.3. Decorative PNG (иконки, фоны, иллюстрации)
- **mode ∈ {RGBA, P-with-transparency***REMOVED***** — для наложения на цветной фон.
- **Edge test**: в Tilda Zero Block поставить на тёмный фон и проверить, нет ли белого/чёрного «halo» по краям.
- **Bytes ≤ 250 KB** (если больше — ужать через `Pillow optimize` или tinypng).

### 4.4. Screenshot / Reference PNG (референсы из ТЗ — image3, image10-14)
- **bytes/pixel ≤ 0.40** — UI-скриншоты жмутся хорошо; если > 0.5 → unoptimized.
- **Разрешение = исходное** (никакого upscale).
- **Соответствие layout**: image1 используется как hero на 5 страницах — все должны смотреть единообразно (зафиксировать aspect-ratio 1187:667 → стандарт 16:9, можно подрезать).

### 5.1. ✅ Variant Б — РЕАЛИЗОВАНО (Temporary q=95, 2026-08-11)

> **После обсуждения с заказчиком** принят Variant Б как **временное** решение до получения оригинала. Реализовано через `/tmp/image6_repack_q95.py` (code-reviewer passed).

#### Trade-offs честно (по verdict thinker-Gemini):

- **Визуального выигрыша на текстуре НЕ будет**: высокочастотные детали уже уничтожены первым сжатием source @ q≈75, q=95 их **не восстановит** — только «забетонирует» текущее качество.
- **Риск double-compression**: ringing на краях нитей возможен при загрузке в Tilda (движок может сделать свой re-encode).
- **Subsampling=0 (4:4:4)**: **защищает** от дальнейшего цветового смазывания (но не возвращает утраченное).
- **ICC sRGB**: стабилизирует отображение в Safari/iOS (исходник без профиля мог рендериться тускло).

Итог: Variant Б — **не улучшение**, а **«капсулирование» в защищённый контейнер**, чтобы Tilda не сделала хуже на своей стороне.
