## Часть I. Что построено

### 1. Движок printcalc (Этап 2 миграции, база Фазы 1)

- **Контракт CALC-\***: `CalculatorSpec` (метаданные + input_schema) → валидация по схеме → pure `compute()` → `CalcResult` (price, cost, net_profit, unit_price, breakdown, warnings).
- **Реестр с закрытым словарём** (дух ANTI-6b): дубликат/неизвестный id = ошибка, без silent fallback.
- **Порт Riso 1:1** (`riso_calc.py:644–760`): порядок операций, float-семантика, тиражные диапазоны, мин.заказ до поиска диапазона, наценка только на мастера+допы. Legacy-глобалы → инъекция frozen `RisoConfig`.
- **Golden-тесты**: значения выведены независимой деривацией и закреплены литералами (5 кейсов: базовый, дуплекс+все допы, границы диапазонов 999/1000/10000, мин.заказ 499→500, кастомный конфиг).

### 3. Архитектура и границы доверия

- Клиент присылает только **выбор** (id позиции, параметры калькулятора, название+цена ручной позиции); все цены каталога и все расчёты — **серверные** (движок — единственный источник цены).
- Разделы: закрытый словарь `SECTION_KINDS`; обязательные разделы проверяются сервером; значения select валидируются по вариантам.
- SQLite: `price_list_items`, `orders` (+`wishes`), `order_items`, `ui_sections`, `order_section_values`, `settings`. Миграции идемпотентны.

## Часть III. Роадмап (детальный план)

> Принцип: **Additive Architecture** — старые EXE живут до паритета; каждый шаг проверяется golden-тестами; после каждого этапа — коммит + push (Server-first) + обновление сервера.

### Этап A — стабилизация Фазы 1 (1 сессия, ~2–4 ч)

1. **Playwright-проход** (браузер, не curl): главный экран — быстрый ввод, добавление позиций, пожелания, разделы; заказы — диалог, смена статуса; прайс — импорт/экспорт; конструктор — CRUD+reorder. Скриншоты + консольные ошибки.
2. **Очистка смоук-данных** из БД (2 заказа, тестовая позиция) — по подтверждению.
3. **Визуальный полиш минимальный**: крупные тач-таргеты для кассы, мобильная вёрстка (телефон — основное рабочее место).
4. **Бэкап-регламент**: nightly-копия `/opt/printcalc/data/printcalc.db` (cron на сервере) + в `SYNC_RUNBOOK`.

DoD: браузерный проход зелёный; БД чистая; бэкап автоматизирован.

### Этап B — порты калькуляторов (порядок из MIGRATION_PLAN, по одному за сессию)

Порядок: **Tablichki → Wide → Digital → Sign → Costing → CNC → Design(+PDF)**.

Для каждого модуля один и тот же цикл (проверен на Riso):

1. Выгрузить формулы/справочники с сервера (file:line доказательства).
2. Pure-функция + `XConfig` (frozen) + `CalculatorSpec` (input_schema).
3. Golden-тесты: независимая деривация 3–5 кейсов + границы диапазонов + ошибки дословно.
4. Регистрация в реестре → автопоявление в диалоге «+ расчёт» на главном экране.
5. Параллельная сверка со старым EXE на 10–20 кейсах (старое как оракул) — Этап 7 из MIGRATION_PLAN.

Особенности:
- **Sign** — два режима цены (средний риск), фото-логика опционально.
- **Costing** — модель амортизации станков из `equipment.json`.
- **CNC** — перевод формулы из JS в Python (средний риск).
- **Design** — форма уже JSON (114 позиций прайса M1) + генерация PDF (ReportLab).

DoD этапа: 8/8 калькуляторов в реестре, golden-тесты зелёные, сверка с EXE без расхождений.

### Этап C — данные и конфигурируемость (v3: «всё меняется без кода»)

1. **Конфиги калькуляторов в БД/JSON** — цены Ризографа, налог 6%, мин.заказ, коэффициенты — из констант кода в редактируемые настройки (админка). Закрытый словарь валидатора (ANTI-6b) расширяется регистрируемыми ключами.
2. **Админка прайса → админка всего**: материалы, доп.работы, срочности (сейчас в коде их нет вообще — PROPOSED), шаблоны Design.
3. **Миграция legacy-конфигов**: `riso_calc_config.json` и JSON-прайсы M2–M8 → загрузка в новые настройки (формат совместим).

DoD: ни одной цены, которую нельзя поменять из UI; golden-тесты переключены на конфиг из БД (значения те же).

### Этап D — продажи и клиент (v3 §22–30)

1. **Скрипты вопросов** (QUESTION_FLOW/SALES_SCRIPT): schema-driven диалог «Баннер? → размер → назначение → материал → люверсы…» с рекомендациями cross-sell (UPSELL_RULES R-01…R-12).
2. **Справочник терминов** (TERMS_GLOSSARY, 35 терминов): ссылка-«i» у каждого термина с кратким пояснением и «что предложить клиентом».
3. **История клиента** (CLIENT_HISTORY_MODEL): поиск по телефону/имени, «что брал раньше, по чём, скидки».
4. **Парсер ступень 2 (LLM)**: садится на интерфейс ступени 1 (те же items/unknown), жаргон-словарь пополняется подтверждениями пользователя (идея №5).

DoD: менеджер ведёт клиента по скрипту от «хочу баннер» до готовой сметы, не зная терминологии.

### Этап E — производство и материалы (v3 §31–39)

1. **Материалы/остатки/закупки** (MATERIAL_MODEL): расход по нормам (баннер ~1.1× площади и т.п.), списание при выполнении заказа, планировщик «что заканчивается».
2. **Операции выполнения** (OPERATIONS_CATALOG, 21 операция + ORDER_WORKFLOW): заказ → операции → чек-листы (PRODUCTION_CHECKLISTS) → «Готово».
3. **Себестоимость** (Costing-калькулятор + материалы): реальная маржа по факту заказа.

DoD: после «выполнен» остатки уменьшились, маржа посчитана.

### Этап F — интеграции и доставка (MIGRATION_PLAN Этап 8 + v3 Р1)

1. **EXE-пакет для офиса**: PyInstaller (uvicorn + webview) — локальный запуск с тем же UI; старые EXE сохраняются.
2. **WF-интеграция (V2)**: контракт `OrderExport` уже есть (txt). Далее — SQL-адаптер или импортируемый файл **только после** решения по серверу/лицензии WF (блокер — ответ Дениса).
3. **Мобильная PWA / роли / синхронизация** — V2 по MIGRATION_PLAN.

DoD: офис работает на десктоп-пакете; заказ попадает в WF одним действием.
