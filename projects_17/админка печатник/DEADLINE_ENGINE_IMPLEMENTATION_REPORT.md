## 4. Какие настройки добавлены

`settings.key = 'deadline_thresholds'` — JSON-словарь порогов в часах:
`3d=72, 24h=24, 12h=12, 2h=2, overdue=0` (дефолт ТЗ §4). Неизвестный ключ →
400 (ANTI-6b). notification_enabled/notify_* не вводились — канал один
(журнал+лента, решение владельца), флаги добавятся вместе с каналами.

## 5. Как работает urgency

`deadline − now` → часы остатка → порог: ≤2ч VERY_CRITICAL, ≤12ч CRITICAL,
≤24ч URGENT, ≤72ч WARNING, >72ч NORMAL, ≤0 OVERDUE. При двух дедлайнах
берётся ближайший активный. Вычисляется при чтении списка, в БД не хранится (§7).
Финальные заказы (выполнен/завершён/отменён) → None (§8). «Без дедлайна» → None,
в фильтр overdue и сортировку «в конец» (§18), никогда не считается просроченным.

## 6. Как работают notifications

Threshold-based: пороги 3d/24h/12h/2h/overdue; событие `reminder` пишется в
`deadline_events` ОДИН раз (частичный UNIQUE) при ленивом sweep на GET /api/orders —
без отдельного демона. Получатель — оператор, работающий со списком (лента в UI);
email не подключён (решение владельца 09-29, MVP). Существующий outbox/emailer
не тронут — это домен заявок, не дедлайнов (ТЗ §34: не смешивать).

## 7. Как работает сортировка

created (created_at, дефолт desc), deadline (по ближайшему; «без дедлайна» в конец),
urgency (OVERDUE→VERY_CRITICAL→CRITICAL→URGENT→WARNING→NORMAL→без дедлайна, внутри
уровня по ближайшему дедлайну — §13), id. Направление asc/desc. Неизвестный
ключ сортировки → 400. Комбинированная сортировка (§16) не делалась: существующий
UI имеет один sort key (§16 «не усложнять, если архитектура поддерживает один»).

## 8. Как работает фильтрация

deadline_filter: active/overdue/today/tomorrow/week/no_deadline (вычисляемые
условия — SQL не дублирует логику urgency). Статусный фильтр существующий
(добавлена кнопка «отменён»). Направление заказа (§14/§17) фильтром не сделано:
в модели orders нет поля направления (аудит B1), вводить справочник-дубликат
запрещено ТЗ; источник для будущего фильтра — calculator_id позиций.
