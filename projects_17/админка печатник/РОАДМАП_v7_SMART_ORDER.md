## 0. Два потока и рекомендуемый порядок

| Поток | Что это | Спека |
|---|---|---|
| **A — Smart Order Intelligence** | Детерминированный слой правил поверх parser v2: нормализация → проверка → подсказки | промт_печатник_6.md |
| **B — Reports Hub** | Сервис красивых Apple-style отчётов (`services_08/reports_hub/`) | reports-hub-spec.md |

**Рекомендация: A → B.** Почему:

1. Правила — узкое место производства: без них сотрудник вручную переводит «порезать поштучно»
   в операции — ровно то, что промт_4 §9 запрещает. Это прямая ценность продукта.
2. Отчёты этапов A (`PHASE_RULES_R*.md`) будут созданы как обычные .md — Reports Hub
   подхватит их **ретроспективно** через автообход (doc library сканирует все .md).
   Строить хаб раньше — значит строить витрину для пустой библиотеки.
3. ANTI-5: не вести два больших сценария одновременно.

Переключение потоков (например, B → A) — только явным решением Дениса, фиксируется здесь в журнале.

## 8. Каденция и правила ведения (для каждого этапа)

1. Один этап = одна сессия (ANTI-5). Этап начат → доведён до отчёта.
2. После каждого этапа: `python -m pytest tests_09/ -q` + mypy → commit → push →
   pull на whimco → рестарт → живой смоук → чистка смоук-данных (SYNC_RUNBOOK, CON-69).
3. Отчёт этапа — `PHASE_RULES_R<n>_REPORT.md` по образцу существующих PHASE-отчётов
   (шапка Статус/Дата, таблица файлов, метрики, открытые вопросы) — формат, пригодный
   для Reports Hub без переделки.
4. Журнал этапов ведётся здесь (§9); PROJECT_STATUS_REPORT.md обновляется по завершении потока A.

## Приложение A — черновик схемы YAML-пака ProductionRule

**Файл пака:** `engine/rules/packs/<product>.yaml` (pack = продукт = закрытый словарь,
зеркалит реестр калькуляторов).

```yaml
# engine/rules/packs/sticker.yaml
schema_version: 1
pack: sticker
product: sticker                      # ОБЯЗАТЕЛЬНО: токен закрытого словаря продуктов
rules:
  - rule_id: STICKER_CUT_CONTOUR_PLOTTER      # уникален глобально (все паки)
    when_facts:                               # v1: только точное равенство, значения — строки
      cutting: "true"
      cutting_mode: "contour"
    propose_operation: plotter_cut            # ТОЛЬКО токен каталога операций | null
    require:                                  # токены закрытого набора MissingItem.field
      - quantity
      - layout_with_cut_contour
    suggest:
      - kind: question                        # закрытый набор: question|finishing|material|upsell|layout
        label: "Макет: есть готовый макет с контуром резки?"
        options: ["Да, макет готов", "Нужно подготовить макет", "Макета нет"]  # ≤ 4, строки
        reason: "sticker + cut_contour → нужен контур в макете (QUESTION_FLOW §…)"
      - kind: material
        label: "Материал: самоклеящаяся плёнка (по умолчанию из реестра)"
        reason: "sticker → материал по умолчанию (MATERIAL_MODEL)"
```

```yaml
# engine/rules/packs/banner.yaml
schema_version: 1
pack: banner
product: banner
rules:
  - rule_id: BANNER_GROMMETS_STEP_CONFIRM
    when_facts:
      grommets: "true"
    propose_operation: grommets_install       # если есть в каталоге операций; иначе null + вопрос
    require: [quantity]
    suggest:
      - kind: question
        label: "Шаг люверсов: 30 см?"
        options: ["Да, 30 см", "Другой шаг"]
        reason: "факт из текста подтверждаем; канон: шаг 50 vs 30 см — вопрос Денису"
  - rule_id: BANNER_MONTAGE_OFFER             # БИЗНЕС-ПРАВИЛО: предложить, НЕ добавить (промт_6 §1)
    when_facts:
      grommets: "true"
    propose_operation: null
    suggest:
      - kind: upsell
        label: "Монтаж: нужен монтаж?"
        options: ["Да", "Нет", "Уточнить позже"]
        reason: "баннер + люверсы → вероятно уличный (UPSELL_RULES)"
```

**Правила валидации схемы (validator при старте, drift → ValueError):**

1. Обязательные поля пака: `schema_version`, `pack`, `product`, непустой `rules[]`;
   `pack == product`; `schema_version == 1`.
2. `rule_id` — уникален глобально (по всем пакам), формат `ПРОДУКТ_СУТЬ`.
3. `propose_operation` — токен существует в каталоге операций (`store.py`) или `null`.
4. Токены `require` — из закрытого набора полей MissingItem (quantity, size_mm, layout_with_cut_contour, …).
5. `suggest[].kind` — из закрытого кортежа; `options` — 1–4 строки; `reason` — обязателен
   (никакой магии: у каждой подсказки видно правило-источник).
6. Правило обязано иметь хотя бы `propose_operation` или непустой `suggest` — иначе это не правило.
7. `when_facts` — только equality в v1 (детерминизм; диапазоны/альтернативы — отдельная
   версия схемы через REGISTER-FIRST).
8. `when_product` наследуется от пака; перекрытие в правиле запрещено (однозначность).
