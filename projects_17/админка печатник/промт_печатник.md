1. Сначала изучи правила платформы

Перед началом любых действий обязательно ознакомься с файлом:

"/storage/emulated/0/PROJECTS/workstation/freebuff/SERVER_ACCESS_WHIMCO.md"

Это основной файл с правилами работы с сервером.

Также изучи доступные правила и документацию платформы Workspace OS, если они доступны в текущем рабочем окружении.

Правило: не начинай перенос, изменение или запуск проекта, пока не изучишь правила доступа к серверу и требования платформы.

2. Перенеси исходный проект на сервер

Исходный архив:

"/storage/emulated/0/PROJECTS/workstation/freebuff/projects_17/админка печатник/Калькуляторы.zip"

Не изменяй оригинальный архив.

Согласно правилам из "SERVER_ACCESS_WHIMCO.md":

1. перенеси архив на сервер;
2. выбери корректное место для проекта;
3. распакуй архив;
4. определи фактическую структуру проекта;

6. найди все существующие приложения, модули, калькуляторы, API, страницы и компоненты;

Если для выполнения какого-либо действия требуется дополнительное разрешение или есть ограничение, не обходи его — следуй правилам платформы.

4. Придумай маркетинговое имя

На основании реального функционала проекта предложи маркетинговое название единого приложения.

Не придумывай название до анализа проекта.

Предложи:

- 5–10 вариантов названия;
- короткое объяснение каждого;
- позиционирование;
- главный смысл названия;
- насколько название масштабируется при добавлении новых калькуляторов и функций.

После анализа выбери один основной вариант.

Не используй название просто потому, что оно красиво звучит. Оно должно соответствовать продукту.

5. Оцени ценность проекта

Дай объективную оценку продукта.

Оцени по шкале 0–10:

- полезность;
- потенциальный спрос;
- уникальность;
- удобство;
- качество текущей реализации;
- масштабируемость;
- коммерческий потенциал;
- техническое состояние;
- потенциал объединения существующих проектов;
- потенциал дальнейшего развития.

Отдельно ответь:

Стоит ли вообще объединять эти проекты в одно приложение?

Если да — объясни почему.

Если нет — объясни, какие проекты лучше оставить отдельными.

Не пытайся искусственно доказать необходимость объединения.

6. Проанализируй возможность объединения

Предполагаемая цель:

«Создать одно полноценное приложение, внутри которого разные калькуляторы и связанные инструменты работают как единая система.»

Определи:

- что можно объединить напрямую;
- что требует переработки;
- что необходимо вынести в общие сервисы;
- какие компоненты можно переиспользовать;
- какие компоненты необходимо переписать;
- какие части следует удалить;
- какие проекты логически несовместимы.

Построй карту:

Проект → модуль → функция → новый раздел единого приложения

8. Спроектируй новую архитектуру

На основании аудита разработай архитектуру единого приложения.

Не ограничивайся общей фразой вроде «Frontend + Backend + Database».

Опиши конкретно:

Frontend

- структура приложения;
- страницы;
- разделы;
- маршруты;
- компоненты;
- состояние;
- формы;
- отображение результатов;
- общие UI-компоненты.

Backend

- структура модулей;
- API;
- сервисный слой;
- бизнес-логика;
- калькуляторы;
- валидация;
- обработка ошибок.

Общий движок калькуляторов

Особое внимание удели тому, чтобы новый калькулятор можно было добавлять без переписывания всей системы.

Предложи архитектуру вида:

"Calculator → Input Schema → Validation → Calculation Engine → Result Schema → UI Renderer"

Если для данного проекта подходит более эффективная архитектура — предложи её.

14. Жёсткие правила работы

Соблюдай следующие правила:

1. Не галлюцинируй.
2. Не утверждай, что функция существует, пока не нашёл её в коде.
3. Не утверждай, что проект запускается, пока реально не проверил запуск.
4. Не переписывай код до завершения аудита.
5. Не удаляй существующий код без обоснования.
6. Не ломай рабочий функционал ради архитектурной красоты.
7. Сначала понять существующую систему → затем спроектировать новую → затем менять код.
8. Все архитектурные решения должны иметь обоснование.
9. При обнаружении противоречий между проектами сначала зафиксируй их.
10. Следуй правилам платформы и "SERVER_ACCESS_WHIMCO.md".
11. Не раскрывай секреты, токены, API-ключи и пароли в отчёте.
12. Не создавай дубликаты проекта без необходимости.
13. Перед потенциально разрушительными действиями создавай резервную копию или используй безопасный способ миграции.
14. Не принимай важные архитектурные решения на основании предположений.
15. Если чего-то невозможно проверить — прямо укажи это.

ВАЖНО

На первом этапе не начинай массовую переработку кода.

Сначала:

правила → перенос → распаковка → изучение → запуск → аудит → архитектура → рекомендации → MVP → только после этого реализация.

Главная цель — не просто «объединить несколько проектов», а определить, каким должно стать единое приложение, чтобы оно было технически поддерживаемым, понятным пользователю и пригодным для дальнейшего масштабирования.

ГРАНИЦЫ ДОСТУПА, РАЗРЕШЕНИЯ И ПОДТВЕРЖДЕНИЯ

1. Принцип минимально необходимого доступа

Работай по принципу least privilege: используй только те права и ресурсы, которые необходимы для выполнения текущего этапа задачи.

Не расширяй самостоятельно область доступа.

Не ищи и не используй:

- другие проекты пользователя, если они не нужны для текущей задачи;
- персональные файлы;
- секреты;
- пароли;
- токены;
- SSH-ключи;
- API-ключи;
- cookies;
- приватные credentials.

Если такие данные случайно обнаружены, не выводи их в отчёт и не копируй их в другие места.

6. Правило для архива

7. Правило резервного копирования

Перед любым изменением существующего рабочего проекта:

1. определить, существует ли резервная копия;
2. проверить возможность отката;
3. определить, какие именно файлы будут изменены;
4. только после этого выполнять изменение.

Если безопасный rollback невозможен — не выполняй изменение без явного подтверждения пользователя.

---

8. Подтверждение пакетных изменений

Если планируется большое количество изменений, не запрашивай подтверждение на каждую отдельную строку кода.

Сначала предоставь пользователю:

- что будет изменено;
- какие каталоги затронуты;
- какие сервисы затронуты;
- возможные риски;
- способ отката;
- ожидаемый результат.

После этого запроси одно явное подтверждение на весь обозначенный пакет изменений.

9. Необходимость остановки

Немедленно остановись и запроси решение пользователя, если:

- правила "SERVER_ACCESS_WHIMCO.md" противоречат поставленной задаче;
- недостаточно прав;
- обнаружен production-сервис, который нельзя безопасно трогать;
- существует риск потери данных;
- обнаружены неизвестные credentials;
- непонятно, какой проект является актуальным;
- обнаружены несколько конфликтующих версий проекта;
- архитектурное решение требует изменения внешней инфраструктуры;
- действие невозможно безопасно откатить;
- невозможно определить последствия действия.

Не угадывай.

Без этого действия: [что невозможно продолжить]

Подтвердить: Да / Нет»

Не выполняй действие до получения однозначного подтверждения.

---

11. Что считать достаточным подтверждением

Достаточным считается явное сообщение пользователя:

- «Да»;
- «Подтверждаю»;
- «Выполняй»;
- «Разрешаю»;

или другое однозначное разрешение именно на описанное действие.

Не считай молчание, предыдущие общие инструкции или первоначальную постановку задачи автоматическим разрешением на новые разрушительные действия.

---

12. Разделение режимов работы

Работай в трёх режимах:

РЕЖИМ A — READ ONLY

Изучение, анализ, аудит и проектирование.

Изменения данных и проекта запрещены.

РЕЖИМ B — PREPARE

Разрешены подготовительные действия, копирование и работа с изолированной копией, если это разрешено правилами.

Оригинальная рабочая система не изменяется.

РЕЖИМ C — APPLY

Изменение рабочего проекта.

Переход в этот режим возможен только после выполнения аудита и архитектурного плана, а для потенциально опасных действий — после явного подтверждения пользователя.

---

13. Главный принцип

По умолчанию — читать и анализировать.

Копировать — только в разрешённую область.

Изменять — только безопасную рабочую копию.

Удалять, перезаписывать, деплоить или менять production — только после явного подтверждения.

Если есть сомнение, действие считается требующим подтверждения.

16. ИЗМЕРИМЫЕ АРТЕФАКТЫ И КРИТЕРИИ ГОТОВНОСТИ

Работа выполняется не по принципу «этап завершён», а по принципу Definition of Done.

Каждый этап считается завершённым только тогда, когда созданы перечисленные артефакты и выполнены все критерии готовности.

Запрещено переходить к следующему этапу только на основании собственного утверждения «готово».

Для каждого этапа необходимо зафиксировать:

- статус;
- созданные артефакты;
- проверенные факты;
- найденные проблемы;
- невыполненные пункты;
- блокеры;
- критерии, которые выполнены / не выполнены.

Весь этап «Аудит + проектирование» считается завершённым только при одновременном выполнении следующих условий:

1. Исходный проект идентифицирован.

3. Проект перенесён в разрешённую рабочую область.
4. Структура проекта документирована.
5. Фактический запуск проверен или зафиксирована конкретная причина невозможности запуска.
6. Функциональность инвентаризирована.
7. Технический аудит завершён.
8. UX/UI аудит завершён.
9. Продуктовая ценность оценена.
10. Маркетинговое название выбрано.
11. Возможность объединения доказана или опровергнута.
12. Подготовлены ровно 10 рекомендаций.
13. Целевая архитектура разработана.
14. Архитектура калькуляторов разработана.
15. UI-архитектура разработана.
16. План миграции разработан.
17. MVP определён.
18. Все критические риски зафиксированы.
19. Все действия, требующие подтверждения, вынесены отдельно.

Главное правило

«Документировано» ≠ «проверено».

«Предложено» ≠ «реализовано».

«Запускается теоретически» ≠ «проверено запуском».

«Архитектура придумана» ≠ «архитектура подтверждена анализом исходного кода».

Каждое утверждение должно иметь соответствующий артефакт или фактическое доказательство.
