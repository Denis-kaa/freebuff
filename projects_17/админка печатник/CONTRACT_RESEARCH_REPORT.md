# CONTRACT_RESEARCH_REPORT.md — исследование договоров для договорного модуля «Печатник»

> Дата: 2026-09-11 · Источник: реальные рабочие документы ИП Жданова В.Ю. (9 файлов .docx из Download/MAX).
> Правило промт_6 §1/§15 соблюдено: документы изучены как есть, юридический текст не переписан.
> Пометки: **ФАКТ** — прямо из документа; **ВЫВОД** — сравнение нескольких документов; **РЕКОМЕНДАЦИЯ** — предложение для приложения; ⚖️ — требует проверки юристом.

---

## 0. Executive Summary

**ФАКТ:** в работе типографии уже есть связка «рамочный договор → счёт → акт → накладная/УПД»:
Договор №4665 → Счёт №222 → Акт №268 → Товарная накладная + УПД №18 (один заказ БФ «Благодарность»);
Договор №1708 → Счёт №222 → УПД №18 (тот же заказ, вторая волна).

**ВЫВОД:** реальная практика Дениса — это **Вариант B/C промт_6 §5**: рамочный договор (часто один на клиента или вообще «Б/н») + комплект документов на конкретный заказ (спецификация/счёт/акт). Подробное описание заказа в тело договора НЕ пишется — оно живёт в приложениях (Техническое задание, Спецификация) и в счёте/акте.

**РЕКОМЕНДАЦИЯ (главная):** строить модуль по архитектуре

```
Клиент (clients) → Договор (contract, рамочный, 1 на клиента/сделку, опционален: «Б/н»)
                       ↓
              Заказ (orders) + позиции (order_items) — источник данных
                       ↓
              Документ (document) = Счёт | Акт | Спецификация/ТЗ | Накладная | УПД | Договор
                       ↓
              Snapshot (полный) → HTML/PDF
```

Типовые шаблоны из интернета НЕ нужны: собственных 9 документов достаточно для всех типов клиентов (физлицо, ИП-исполнитель, юрлицо, НКО, бюджетник 223-ФЗ).

## 2. Артефакт B — единая модель данных

**РЕКОМЕНДАЦИЯ** (источник — фактура документов):

```
Company (настройки компании — singleton, заполняется 1 раз)
Customer (сущность clients, + реквизиты по типу: физлицо/ИП/юрлицо)
Contact  (существующие contacts)
Contract (рамочный договор, опционален; номер/дата/тип шаблона/статус/scan)
Order    (существующие orders)
OrderItem(существующие order_items)
Document (сгенерированный документ: type, number, date, order_id, contract_id,
          customer_id, template_id, snapshot_json, status draft/final, file_path)
```

- **Customer:** type (`individual` | `sole_proprietor` | `legal_entity`) — от него зависят условные блоки (§14 ниже). Физлицу: ФИО, телефон, email, паспорт+адрес (опционально — только для грантов, ⚖️). ИП/юрлицу: полное наименование, ИНН, КПП (юр), ОГРН/ОГРНИП, адрес, банк/р-с/к/с/БИК (бюджетнику — казначейские + л/с), подписант (ФИО/должность/основание) — **отдельные поля, не смешивать организацию и представителя** (промт_6 §5).
- **Contract:** минимум — номер, дата, тип шаблона (услуги/поставка/оферта), клиент, статус. Содержание (текст разделов) — из шаблона, в БД не хранится.
- **Document:** каждая генерация = запись со **полным snapshot** (§13). Веер документов (счёт+акт+накладная+УПД) на один заказ — **ФАКТ** практики → у Document общий order_id, у каждого свой type/number/date.

## 8. Артефакт H — рекомендуемый шаблон (структура)

Рамочный договор (базовый, из №7/№4665 — общая часть): 1 Преимбулы (условные) → 2 Предмет (отсылка к Спецификации) → 3 Цена и порядок оплаты (твёрдая цена, предоплата %, срок после акта) → 4 Права/обязанности → 5 Приёмка (акт, сроки) → 6 Ответственность (по закону РФ — как в №7 §5.1) → 7 Макеты/согласование ⚖️ → 8 Форс-мажор → 9 Споры → 10 Срок действия → 11 Заключительное → 12 Реквизиты (условные блоки) + Приложение: Спецификация. Отдельные шаблоны: budget_223 (поставка), грантовый (+аналитический отчёт), комплект «счёт/акт/накладная/УПД».

## 9. Snapshot-модель (промт_6 §13)

В `document.snapshot_json` фиксируется **всё**: template_version, executor_*, customer_*, items (с ценами), total, terms, сгенерированные number/date/total_words. Правка реквизитов клиента после генерации не меняет документ (паритет с §49 смет — тот же принцип уже реализован в calc_snapshots).

## 10. Юридические места ⚖️ (промт_6 §10 — кратко)

Неустойки 223-ФЗ (1% / 1/300 КС / 0,1%) — **не переносить** в обычный шаблон без юриста; паспортные данные — только при обоснованной необходимости (гранты) + 152-ФЗ согласие; «Директор» как должность ИП в актах/счетах — фактическая практика, но формулировка основания подписания для ИП («действующий на основании ОГРНИП…») должна быть единообразной ⚖️; интеллектуальные права на макеты в изученных договорах отсутствуют — пробел, РЕКОМЕНДАЦИЯ добавить пункт (⚖️ юрист).

## 12. Что НЕ делаем (§18 — чеклист соблюдён)

Типовые шаблоны интернета не привлекались; текст документов не переписан; все предложенные поля помечены или прямо из документов; компания/подписант и клиент/контакт разделены; договор и заказ разделены (Спецификация); ручной ввод — только незнакомых системе полей; ИИ не используется для подстановки переменных (§37).
