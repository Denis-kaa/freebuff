## 2. Новый роадмап (9 фаз §59 промт_4, адаптированный под текущее состояние)

> Принципы: не ломать работающее (Riso — эталон, §1); один шаг за раз (ANTI-5);
> каждый шаг = модель + API + тесты + UI + аудит (§62); UNKNOWN не заменять догадкой (§63).

### Этап 0. IMPLEMENTATION_AUDIT_REPORT (1–2 дня) — обязан по §2

Полный аудит по 15 пунктам §2 промт_4: архитектура, калькуляторы, API, модели данных,
что работает / legacy / переиспользуется / рефакторинг / дубли / единая модель /
интеграции / зависимости / план миграции / риски / список изменений по файлам.
Источники уже собраны (PHASE1_REPORT, CONSUMPTION_REPORT, CALCULATOR_MATRIX) —
нужно свести в один документ по форме и зафиксировать целевую схему БД.

**Результат:** документ, после которого разрешён массовый рефакторинг.

### Этап 1. Core domain: Client + Material Registry (неделя 1–2)

Минимальное ядро данных, без которого дальше всё упирается:

1. **Client** (§6 промт_4): Client ≠ контакт; таблица clients + contacts
   (канал, внешний id), без привязки к мессенджерам.
2. **Material Registry** (§18): единая таблица materials (id, name, aliases, unit,
   purchase_cost, roll_width, active) + миграция: материалы Wide/Табличек получают id.
3. Связать orders с client_id (nullable — пока можно без клиента).

**DoD (§62):** модели, API CRUD, тесты, admin-UI списка материалов, snapshot-правило §49 задокументировано.

### Этап 2. Расчёт как первоклассная сущность: Estimate + Snapshot (недели 3–4)

1. **Estimate** (§22, §24): смета создаётся из CalcResult автоматически
   (Client, Service, Parameters, Consumption, Cost, Price, Margin, Validity);
   статусы DRAFT→SENT→VIEWED→ACCEPTED→REJECTED→EXPIRED.
2. **Snapshot** (§49): при ACCEPTED фиксируются версии калькулятора/цен/политик —
   изменение цен задним числом запрещено.
3. Убрать «ручной перенос»: заказ создаётся из сметы кнопкой, все поля переносятся (§9).
   OrderExport остаётся только как мост для старого WF (пока WF живёт).

**DoD:** цикл «посчитал → смета → подтверждение → заказ» без ручного ввода.

### Этап 3. Consumption → API → заказы (неделя 5)

1. Endpoint `POST /api/consumption/calculate` (§48): material_id, items, policy.
2. Встроить расход в карточку заказа: materials[] с production/billing/waste (§13, §14 —
   трассировка показывается пользователю).
3. Материалы Wide (баннер 440/510, плёнка, холст) получают roll_width в реестре —
   раскрой считается при добавлении позиции.
4. Таблички → consumption (SHEET-режим), Digital → рулонная длина (Phase 3 ТЗ промт_3).

**DoD:** для баннера 3×1×2 оператор видит «раскрой: 2 шт поперёк, длина 1 м, отход X%».

### Этап 4. Production: Operations + Tasks + QC (недели 6–8)

1. **Operations** из OPERATIONS_CATALOG (сущность §32 промт_4: шаги, ПО, материалы,
   чеклист, критерии готовности).
2. **Production Plan**: заказ → операции → задачи (§31), статусы из ORDER_WORKFLOW.
3. **QC** (§35): чеклист проверки (размер/цвет/комплектность), только после QC — «Готов».
4. **Execution Assistant / Newbie Mode** (§33-34) — UI пошагового выполнения.

**DoD:** заказ автоматически превращается в производственное задание с чеклистом.

### Этап 5. Stock: Reserve → Estimated Stock → Purchase Planner (неделя 9–10)

1. **Reservation** (§20): при подтверждении заказа резервируется Production Consumption.
2. **Estimated vs Physical Stock** (§19): расчётный остаток помечен «~», кнопка
   «Коррекция остатка» (инвентаризация).
3. **Purchase Planner** (§21): Need = Required − Available − Reserved, рекомендация
   с округлением до упаковки/рулона.

**DoD:** «Не хватает: Баннер 440 — 7.4 м² → рекомендуемая закупка 10 м²».

### Этап 6. Communication Hub: Telegram → Email (недели 11–13)

1. Adapter Pattern (§4, §47): CommunicationService + TelegramAdapter (aiogram),
   единая модель Conversation/Message (§5), идемпотентность по external_message_id (§55).
2. **Unified Inbox** (§44): раздел «Сообщения», ответы прямо из системы.
3. Inquiry: сообщение → обращение → вопросы (QUESTION_FLOW, data-driven, §8) →
   параметры → калькулятор. AI на этом этапе — только детерминированный парсер.
4. **Client matching** (§45): не плодить дублей клиентов, сомнительные совпадения —
   оператору на подтверждение.
5. EmailAdapter (§43) — вторым каналом. MAX/VK — позже (§41-42: только по актуальной документации).

**DoD (MVP-цикл §60):** клиент пишет в Telegram «баннер 3×1, 2 штуки, люверсы» →
вопросы → расчёт → смета → подтверждение → заказ → резерв → задание.

### Этап 7. Payment Hub (неделя 14–15)

1. Платёжный домен (§28): Payment со статусами PENDING→SUCCEEDED→REFUNDED…,
   частичные оплаты/предоплата (§30).
2. PaymentProviderAdapter (§27): сначала TestAdapter, потом TBank (эквайринг/терминал).
3. Правило §29: только подтверждённый платёж меняет финансовый статус заказа.

### Этап 8. AI Assistant (после стабильного ядра, недели 16+)

1. LLM-парсер stage 2 (§7, §39): текст → структурированные параметры → валидация →
   калькулятор → AI объясняет результат. ИИ НЕ называет цену сам (§38).
2. Терминология по ⓘ (§37), поиск инструкции, помощь сотруднику.
3. AI_SAFETY_RULES — обязательные ограничения, логирование всех действий.

### Этап 9. Analytics / Files / Knowledge / Audit (параллельно, по мере надобности)

- Files с версиями (§36), Knowledge base (§37), Audit log (§50), Global search (§53),
  Dashboard-показатели (§54). Мелкие части можно вкраплять в предыдущие этапы.

## 4. Рекомендация

**Начать с Этапа 0 + 1 (аудит → Client + Material Registry), а не с мессенджеров.**

Почему так:

1. **Промт_4 сам требует:** §2 прямо запрещает большой рефакторинг до отчёта. Отчёт —
   самый дешёвый и обязательный шаг, всё для него уже изучено.
2. **Узкое место — не калькуляторы и не чат, а данные.** Сейчас заказ не знает, кто
   клиент и из какого материала изделие. Без Material Registry нельзя ни расход в
   заказ встроить (Этап 3), ни резерв/склад (Этап 5), ни Telegram-сметы (Этап 6).
   Client — ключ к сметам, истории, сообщениям. Это фундамент всего цикла §60.
3. **Соблазн сделать Telegram раньше — ловушка.** Красиво показать чат можно, но без
   Estimate→Order (Этап 2) получится «чат, из которого оператор вручную переписывает
   цифры» — ровно то, что промт_4 запрещает (§9) и что критерий §65 называет
   «функция не интегрирована».
4. **Что уже даёт бизнес-ценность и не требует ждать:** подключение consumption
   к заказам (Этап 3, неделя 5) — оператор сразу видит реальный расход и отходы.
   Это можно сделать сразу после Этапа 1, до Production/Payments.

Итоговый порядок: **0 → 1 → 2 → 3 → (4|5|6 по приоритету бизнеса) → 7 → 8**.
Первые 4 этапа дают законченный цикл «обращение → заказ без ручного ввода» для
приёмки на стойке; мессенджеры (6) подключаются поверх готового цикла.
