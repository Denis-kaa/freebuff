## 2. Сущности и их источники (EXISTING-основа)

| Сущность | Источник наполнения | Статус |
|---|---|---|
| Услуги, прайсы, материалы | текущие JSON-конфиги 6 модулей (миграция данных) | EXISTING → перенос |
| Термины | лейблы кода + определения (черновики, валидация практикой) | EXISTING токены / PROPOSED тексты |
| Операции, чек-листы, ПО | PROPOSED-стартеры этого набора | PROPOSED |
| Правила (бизнес + upsell) | выгруз BR-01…17 + R-01…12 | EXISTING формулы → data |
| Скрипты | генерация из QUESTION_FLOW | PROPOSED |
| Клиенты/заказы | ввод при работе | PROPOSED |

## 3. Хранение и целостность

- Единое хранилище (SQLite продакшн / JSON desktop) с id-связями: term ↔ operation ↔ service ↔ material ↔ rule. Урок дрейфа (T-02, BR-W1): никаких дублирующихся копий одного знания в разных модулях.
- Журнал изменений каждого знания (кто/когда/было→стало) — цена ошибки знания = ошибка цены для клиента.
- Версионирование: правка термина/операции создаёт новую ревизию, старая доступна (аддитивность — принцип AGENTS.md).

## 4. Метки достоверности (§15 дисциплина)

Каждое знание несёт `source`: `code` (факт из legacy), `validated` (подтверждено практикой), `draft` (предложено агентом/AI). UI показывает метку сотруднику; draft-знания нельзя пометить blocking-элементом чек-листа, пока не validated. Перевод в validated — действие владельца (список «черновики» в админке).

## 5. Доступ AI

AI читает базу (поиск, формулировки), пишет — только черновики (draft). Правила — AI_SAFETY_RULES. Деградация: база и без AI полноценна.
