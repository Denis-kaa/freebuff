## 2. Ключевые решения S3

1. **Endpoint тонкий, контракты не дублируются.** Вся логика — в готовых
   `rules.load_builtin_packs()` + `evaluate_text()` (S1/S2). API не знает о
   содержимом паков: новый пак YAML подхватывается без правки кода.
2. **parse_result опционален, но цепочка честная.** Без `parse_result` API
   сам вызывает parser v2 (`parser.parse(conn, text)`) — qty/unknown попадают
   в черновик по контракту R1 (нормализатор игнорирует нерелевантные поля
   ParseResult, т.к. парсер не знает wide-продуктов). С явным `parse_result`
   — берётся он (UI сможет переиспользовать уже сделанный вызов /api/parse).
3. **БД только читается** (словарь парсера): разбор — чистая операция,
   заказ создаётся отдельно. Смоук-данных не оставляет.
4. **Детерминизм через API закреплён тестом**: два вызова с тем же текстом →
   идентичный JSON (наследие идемпотентности evaluate_order, S2).
5. **Контракт «распознать ≠ предложить» на границе API**: тест
   `test_all_proposals_auto_false` прогоняет три эталонные фразы и требует
   `auto=false` у каждого предложения (движок падает на auto=True по
   `__post_init__` — контракт задублирован на обоих уровнях).
