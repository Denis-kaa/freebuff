## 0. СУТЬ ЗАДАЧИ (прочитай перед кодом)

Это **следующий слой после распознавания текста** — умный технологический разбор заказа.

Парсер (`parser.py` v2) уже извлекает факты из свободного текста. Но факт ≠ производство.
Сотрудник пишет «порезать поштучно» — система должна **сопоставить заказ с правилами
производства** и подсказать, что ещё необходимо, **не требуя от сотрудника знания
внутренней терминологии**.

Целевая цепочка:

```
Свободный текст
  ↓
1. РАСПОЗНАВАНИЕ   — что написал сотрудник? (parser.py — уже есть)
  ↓
2. НОРМАЛИЗАЦИЯ    — что это означает в терминах системы? (нужно построить)
  ↓
3. ПРОВЕРКА        — чего не хватает для расчёта/производства? (нужно построить)
  ↓
4. ПОДСКАЗКИ       — что обычно требуется / может быть предложено? (нужно построить)
  ↓
Калькулятор → Смета → Заказ → Производственное задание
```

**Основа — детерминированная, без ИИ.** LLM на этом слое не участвует (канон §37–§39:
LLM только поверх работающих сервисов, и ИИ никогда не называет цену и не решает
производственные правила сам).

## 1. ГЛАВНЫЙ ПРИНЦИП: «РАСПОЗНАТЬ» ≠ «ПРЕДЛОЖИТЬ»

Система разделяет два вида знания. Смешивать их запрещено.

| | ФАКТ (из текста) | ПРАВИЛО (из производства) |
|---|---|---|
| Источник | парсер, сотрудник | каталог операций, бизнес-правила, калькуляторы |
| Пример | `cutting = true`, `cutting_mode = individual` | `sticker + cutting + individual → plotter_cutting` |
| Можно ли добавить автоматически | ДА (это то, что сказал сотрудник) | **НЕТ** (только предложить) |
| Ответственность | «что написано» | «что обычно требуется» |

**Запрещено:** автоматически добавлять монтаж, макет, обработку края и любые
продажные/технологические допы. Система только **предлагает** — решение принимает
сотрудник. Пример из ТЗ: «Баннер 3×6» → предложить люверсы/монтаж/макет, но НЕ добавлять
их в заказ без подтверждения.

## 2. КОНТРАКТ ДАННЫХ (Contract First)

Новые сущности добавляются **аддитивно**, существующие контракты (items/unknown/
needs_operator/reasons, segment_id, volume_hints) не ломаются (Backward Compatibility).

### 2.1 Нормализованный черновик заказа — `OrderDraft`

```python
@dataclass(frozen=True)
class OrderDraft:
    segment_id: str | None          # связь с парсером v2 (мультизаказ)
    product: str                    # токен из закрытого словаря продуктов ("sticker", "banner", ...)
    size_mm: tuple[float, float] | None
    quantity: int | None
    finishings: tuple[str, ...]     # нормализованные обработки ("plotter_cut", "grommets", ...)
    material_hint: str | None       # подсказка материала из текста, если была
    facts: Mapping[str, object]     # всё, что извлек парсер (как есть)
```

### 2.2 Вердикт правил — `RuleVerdict`

```python
@dataclass(frozen=True)
class RuleVerdict:
    draft: OrderDraft
    proposed_operations: tuple[OperationProposal, ...]   # предложить операцию
    missing: tuple[MissingItem, ...]                     # чего не хватает для расчёта
    suggestions: tuple[Suggestion, ...]                  # контекстные подсказки (upsell/технология)
    ready_for_calculator: bool                           # можно ли считать прямо сейчас
```

### 2.3 Элементы вердикта

```python
@dataclass(frozen=True)
class OperationProposal:
    operation_token: str      # ТОЛЬКО из каталога операций store.py (закрытый словарь)
    label: str                # человеческое имя («Плоттерная резка — поштучно»)
    reason: str               # какое правило сработало («sticker + cut_individual → plotter_cut»)
    auto: bool                # False всегда в v1 — только предложить

@dataclass(frozen=True)
class MissingItem:
    field: str                # "quantity" | "size_mm" | "layout" | ...
    question: str             # «Количество?»
    blocking: bool            # блокирует расчёт (quantity) или только производство (layout)

@dataclass(frozen=True)
class Suggestion:
    kind: str                 # закрытый словарь: "finishing" | "material" | "layout" | "upsell" | "question"
    label: str
    reason: str               # правило-источник — ОБЯЗАТЕЛЬНО, никакой магии
    options: tuple[str, ...]  # варианты ответа: ("да", "нет", "уточнить позже")
```

### 2.4 Правило производства — `ProductionRule` (декларативное)

```python
@dataclass(frozen=True)
class ProductionRule:
    rule_id: str                    # "STICKER_CUT_INDIVIDUAL_PLOTTER"
    when_product: str | None        # "sticker" | "banner" | None (= любой)
    when_facts: Mapping[str, str]   # {"cutting": "true", "cutting_mode": "individual"}
    propose_operation: str | None   # токен каталога операций
    require: tuple[str, ...]        # ("layout_with_cut_contour",)
    suggest: tuple[Suggestion, ...] # контекстные подсказки
```

Правила живут **отдельно от кода** (YAML/Python-таблица) — каталог правил пополняется
без изменения движка (Additive Architecture).

## 3. ЗАКРЫТЫЙ СЛОВАРЬ (ANTI-6b — критично)

1. Все токены продуктов (`product`) — закрытый словарь, зеркалящий каталог калькуляторов
   реестра (`calculators/`: riso, tablichki, wide, digital, sign, cnc, cost, p0_services).
   Новый токен продукта = сначала регистрация, потом использование (REGISTER-FIRST).
2. Все `operation_token` — ТОЛЬКО из существующего каталога операций (12 операций-сид,
   `store.py: operations`). Правило не может предложить операцию, которой нет в каталоге.
3. Все `kind` у Suggestion — закрытый кортеж (как `INQUIRY_STATUSES` / `stock_movements`).
4. Валидатор при старте: каждое правило проходит проверку словарей; drift → `ValueError`
   (это фича, не баг — урок CON-8/ANTI-6b).
5. Жаргон не выдумывается: если парсер встретил неизвестный токен — он попадает в
   `unknown`/`needs_operator.reasons` (уже реализовано в parser v2), а не в правила.

## 4. ПРИМЕРЫ-ЭТАЛОНЫ (закрепить golden-тестами)

### 4.1 «Наклейка 50×30, 149 шт + резка по контуру»

```
РАСПОЗНАВАНИЕ (парсер):
  product=sticker, size=500×300 mm, qty=149, finishings=[cut_contour]

ПРОВЕРКА (правила):
  sticker + cut_contour → предложить операцию «Плоттерная резка»
  для контурной резки нужен макет с контуром → спросить: «Макет: есть готовый?»
    [Да, макет готов] [Нужно подготовить макет] [Макета нет]

ПОДСКАЗКИ (контекст):
  → только то, что предписано правилами для sticker + cut_contour
```

### 4.2 «Наклейка 20×30, 40 шт, с монтажной, порезать поштучно»

```
ПАРСЕР ИЗВЛЕКАЕТ ФАКТЫ:
  product=sticker, size=200×300 mm, qty=40, mounting_film=true,
  cutting=true, cutting_mode=individual

ПРАВИЛА ПРОИЗВОДСТВА:
  sticker + cutting + individual → plotter_cutting

ИНТЕРФЕЙС:
  «Операция: Плоттерная резка — поштучно» (предложение, кнопки ✓ / Изменить)

СМЫСЛ: сотрудник пишет «порезать поштучно» своим языком —
система переводит в терминологию производства.
```

### 4.3 «Баннер 3×6 + люверсы 30 см»

```
РАСПОЗНАНО: product=banner, size=3000×6000 mm, finishings=[grommets(step=30cm)]

ПРЕДЛОЖИТЬ (НЕ ДОБАВЛЯТЬ АВТОМАТИЧЕСКИ):
  ✓ Люверсы — шаг 30 см (факт из текста, подтверждение)
  ? Макет: готовый макет предоставлен?      → Да / Нет / Уточнить позже
  ? Монтаж: нужен монтаж?                   → Да / Нет / Уточнить позже
  (монтаж — бизнес-правило/продажная подсказка, НЕ факт из текста)
```

### 4.4 «Бэклит 80×60, 1440 dpi, резка по контуру»

```
РАСПОЗНАНО: product=backlit, size=800×600 mm, dpi=1440, finishings=[cut_contour]

СИСТЕМА ЗНАЕТ:
  контурная резка → вероятная технология = плоттерная резка
  для производства нужен контур в макете
  количество НЕ указано

ПОДСКАЗКИ (только недостающее, никакого «15 вопросов»):
  > Количество?                                 [blocking]
  > Макет: нужен готовый макет с контуром резки?
  > Подготовка макета: требуется?
```

### 4.5 Контекстность подсказок (обязательное поведение)

| Продукт | Спрашивать/предлагать |
|---|---|
| Наклейка + плоттерная резка | макет и контур |
| Баннер | люверсы, обработка края, монтаж, макет |
| Табличка ПВХ | крепление, отверстия, скругление/резка (если предусмотрено каталогом) |
| Фото на документы | документ, количество, печать/файл, подготовка фото |

**Запрещено:** показывать все вопросы всем. Подсказки зависят от контекста
(продукт + факты). Правило без `when_product`/`when_facts` не проходит валидацию.

## 5. ФАЗЫ РЕАЛИЗАЦИИ (каждая: модель + API + тесты + UI + отчёт, §62 промт_4)

### PHASE R0 — Регистрация и аудит правил (0.5–1 день)

1. REGISTER-FIRST: зарегистрировать новые элементы в реестре недостающих способностей
   (`python -m core_02.missing_registry register order_rules_engine --kind module`,
   `order_rules_engine.api`, `suggestions_ui`) — до написания кода.
2. Инвентаризация: свести из OPERATIONS_CATALOG.md, BUSINESS_RULES.md, QUESTION_FLOW.md,
   UPSELL_RULES.md, CALCULATOR_MATRIX.md — какие правила реально существуют в документации
   (не придумывать: если правила нет в документации — UNKNOWN, вопрос Денису).
3. **Выход:** таблица правил v1 (15–30 правил из документации) + список открытых вопросов.

### PHASE R1 — Нормализация (2–3 дня)

- `engine/rules/normalize.py`: ParseResult → OrderDraft (маппинг жаргона на токены словаря).
- Валидатор закрытых словарей (продукты ↔ калькуляторы реестра).
- Тесты: на всех примерах §4 факты нормализуются однозначно; неизвестное — не теряется.
- **DoD:** `OrderDraft` покрыт golden-тестами на 4 примера интервью + 6 из PROJECT_STATUS_REPORT.

### PHASE R2 — Движок правил (2–3 дня)

- `engine/rules/engine.py`: ProductionRule → RuleVerdict; правила — декларативная таблица
  `engine/rules/packs/*.yaml` (pack = продукт).
- `missing` вычисляется из требований калькулятора (Spec.required) + правил производства.
- Идемпотентность: повторный прогон вердикта не меняет результат.
- Тесты: каждое правило — юнит; анти-тест «правило с токеном вне словаря → ValueError».
- **DoD:** ready_for_calculator корректен на всех golden-примерах (в т.ч. 4.4 — False).

### PHASE R3 — API (1–2 дня)

- `api.py`: `POST /api/order/analyze` → RuleVerdict JSON (аддитивно, без ломки контрактов).
- Ручной ввод сотрудником (не только парсер) проходит через тот же analyze.
- Тесты: контракт ответа, мультизаказ (segment_id), 404-поведение для неизвестного продукта.
- **DoD:** живой смоук на сервере: curl с текстом «Наклейка 50×30, 149 шт + резка по контуру».

### PHASE R4 — UI подсказок (2–3 дня)

- В карточке заказа/диалоге расчёта: блоки «Распознано» → «Предложения» (операции,
  ✓/Изменить) → «Нужно уточнить» (MissingItem, кнопки Да/Нет/Уточнить позже).
- Ни одно предложение не применяется без действия сотрудника; подтверждённое — попадает
  в заказ (аудит: кто подтвердил).
- Mobile-first по канону приложения (единый стиль).
- **DoD:** сценарий §4.2 проходится от ввода до задания без знания внутренней терминологии.

### PHASE R5 — Связка с калькулятором и заданиями (1–2 дня)

- `ready_for_calculator=true` → авто-переход в существующий расчёт (без повторного ввода).
- Подтверждённые операции → генерация заданий (существующий конвейер operations/
  production_tasks, идемпотентно).
- **DoD:** цикл «текст → разбор → уточнения → смета → задание» — MVP-цикл §60 промт_4.
