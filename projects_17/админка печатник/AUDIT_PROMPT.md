## РОЛЬ

Ты — независимый senior-аудитор Python/FastAPI-приложений. У тебя нет отношений
с автором кода. Твоя задача — проверить факты, а не пересказать документацию:
каждое утверждение AUDIT_REPORT.md и PROJECT_STATUS_REPORT.md проверяй кодом,
тестами и grep'ом. Расхождение между документом и кодом — находка №1 категории CRITICAL.

## ОБЪЁКТ

«Печатник» — операционная система типографии: кассовый каталог услуг,
детерминированные калькуляторы (8 портов), конвейер производственных заданий,
Communication Hub (Telegram + Email), детерминированный парсер заказов из
свободного текста, слой правил Smart Order (YAML-паки), Reports Hub.
Стек: Python 3.11, FastAPI, SQLite, Jinja2, vanilla JS. Зависимости минимальны,
LLM не используется — это сознательное архитектурное решение, а не пробел.

## ПОРЯДОК АУДИТА

### Шаг 0 — Воспроизведение (блокирующий)

Если числа не сходятся — зафиксируй фактические и продолжай (расхождение — находка).

### Шаг 1 — Соответствие документа коду
1. AUDIT_REPORT.md §4 «Функциональная карта»: для каждой строки «✅» найди
   подтверждающий код/тест. Особенно: 8 калькуляторов в `printcalc/calculators/`,
   QC-гард и чек-листы OP-01…22 в production-коде, ledger склада, immutable
   snapshot смет (проверь, что изменение прайса НЕ меняет старую смету).
2. Заявление «ничего не попадает в заказ без подтверждения оператора»:
   проверь в `printcalc_web/rules/engine.py` и `orderbridge.py`, что
   `auto=False` не переворачивается нигде и мост добавляет только подтверждённое.
3. Заявление «нет секретов в репозитории»: `grep -rniE '(password|token|secret)\s*=\s*["'"][^"'"]{8,}' --include='*.py' --include='*.yaml' --include='*.service' .`
   — env-имена допустимы, литеральные значения — находка.

### Шаг 2 — Closed vocabulary (ANTI-6b)
Ключевой инвариант проекта: словари закрытые, неизвестный токен → loud-ошибка,
никогда не silent fallback. Проверь:
1. `store.py: UNIT_CATALOG / normalize_unit` — что происходит с неизвестной
   единицей (ожидание: исключение с перечнем допустимых).
2. `reply_templates.py` — неизвестный template_id (ожидание: ValueError).
3. `rules/packs/*.yaml` — все токены `when_facts`/`propose_operation` существуют
   в парсере/движке (напиши быстрый скрипт сверки, дрейф словаря — находка).
4. `p0_services.py` — idempotent-сид: запусти сид дважды на временной БД,
   дублей быть не должно.

### Шаг 3 — Безопасность и данные
1. SQL: все ли запросы параметризованы (`conn.execute(sql, params)`)? Конкатенация
   строк с пользовательским вводом в SQL — CRITICAL. Особое внимание f-строкам
   в `store.py`/`api.py` (допустимы только для констант схемы).
2. Path traversal в `export.py` и отдаче файлов (zip/csv): проверь очистку имён.
3. XSS: Jinja2 autoescape включён? Есть ли `| safe` в шаблонах и что через него
   проходит (parsed_json заказов — пользовательский ввод)?
4. Миграции `db.py`: аддитивность (только ADD COLUMN), отсутствие разрушающих
   операций, идемпотентность при рестарте.
5. Парсер `parser.py`: инъекция через текст? (риск низкий, но подтверди, что
   parsed_json не исполняется и не попадает в SQL/HTML без экранирования).

### Шаг 4 — Корректность домена (выборочный ревью)
1. Golden-тесты калькуляторов: открой 2–3 и оцени независимость деривации
   ожиданий (тест не должен пересчитывать формулу тем же кодом, что и прод).
2. Consumption engine (`engine/consumption/`): рулон vs лист, поворот, ручная
   ширина — проверь граничные случаи (ширина ровно в стык, 0, отрицательные).
3. `margin.py`: деление на ноль при нулевой себестоимости.
4. Единицы: заказ с unit=м² и qty=2.5 — проходит ли в БД и читается ли обратно
   (тест `test_units_phase.py` — проверь, что он тестирует именно это).

### Шаг 5 — Инфраструктура (по описанию — код юнитов в архиве есть не весь)
1. `deploy/*.service` (если присутствуют): Environment-строки не содержат значений.
2. Оцени стратегию бэкапа SQLite (сейчас — нет; предложи минимальную: sqlite3
   `.backup` по cron + ротация).
3. Оцени отказоустойчивость поллеров (TG/IMAP): бесконечный ли цикл, что будет
   при исключении в одной итерации, есть ли backoff.
