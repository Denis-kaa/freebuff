## Этап 3b: расход для Табличек (SHEET_NESTING) + выбор материала/рулона в UI

### Что сделано
- **SHEET_NESTING в движке** (`_calculate_sheet_nesting`): листовые материалы
  с известными размерами листа (sheet_width/sheet_height) раскрываются
  полистно — сколько изделий помещается на лист в обеих ориентациях
  (правило поворота владельца действует и здесь), расход = целые листы.
  Продукт-площадь ≠ производственный расход (целые листы) ≠ биллинг (листы) —
  три количества разделены (BLOCKER #2 промт_5). Изделие больше листа в обеих
  ориентациях → PRODUCT_DOES_NOT_FIT.
- **Сид канонических листовых материалов** дополнен размерами листа
  3000×2000 мм (ПВХ/Акрил/Композит 3 и 5 мм).
- **Расход Табличек в заказах**: tablichki добавлен в CONSUMPTION_CALCULATORS;
  позиция заказа с материалом «ПВХ 3 мм» и т.п. автоматически получает snapshot
  расхода (сколько листов, укладка на лист, отход).
- **UI диалога расчёта**: подсказка ширины рулона из реестра материалов по
  выбранному материалу wide (placeholder «из реестра: 1000 мм»), ручной ввод
  остаётся приоритетным (правило владельца).

### Тесты
- `tests/consumption/test_sheet_nesting.py` (6): укладка 30 шт/лист, переход
  через границу листа (31 шт → 2 листа), выбор лучшей ориентации, спасение
  поворотом, ошибка oversize, fallback без размеров листа.
- Итого: **167 passed**, mypy clean.

## Этап 4: Production — операции и задания

### Что сделано
- **Каталог операций — данные** (OPERATIONS_CATALOG §1-2): таблица `operations`
  (code, name, steps, checklist, equipment, minutes, role, **trigger**,
  position, enabled) + идемпотентный сид 12 стартовых операций
  (OP-01/02/04/05/07/08/09/13/14/19/20/21).
- **Генерация заданий по правилам** (§3): `generate_production_plan(order_id)`
  собирает триггеры заказа (калькулятор wide/tablichki/riso, доп-работы
  work_*, флаги install) и создаёт задания только для подходящих операций;
  сортировка по position — монтаж (OP-19) всегда последним; повторная
  генерация идемпотентна (дубликатов нет). Отказ от ламинации → OP-08
  не создаётся (проверено тестом — требование §3 каталога).
- **Жизненный цикл**: pending → in_progress → done, + blocked (закрытый
  словарь TASK_STATUSES). **QC-гард (§10)**: complete без всех пунктов
  чек-листа операции запрещён (проверяется длина и все true).
- **API**: GET /api/operations; POST /api/orders/{id}/production/generate;
  GET /api/orders/{id}/production; GET /api/production/tasks?status=;
  POST /api/production/tasks/{id}/start|complete|block.
- **UI**: раздел «Производство» в сайдбаре — доска заданий с фильтрами
  (все/ожидают/в работе/блок/готовы), диалог задания с шагами, чек-листом,
  заметкой и кнопками Взять/Выполнено/Заблокировать; в карточке заказа —
  кнопка «В производство» (генерация заданий).

### Модели/миграции
- `operations` (id, code UNIQUE, name, description, steps_json, checklist_json,
  equipment, minutes, role, trigger, position, enabled, timestamps).
- `production_tasks` (id, order_id→CASCADE, operation_id, status, sequence,
  checklist_result, notes, started_at, completed_at, created_at) + индексы.

### Тесты
- `tests/test_production.py` (8): сид идемпотентен; триггеры и исключение
  несоответствующих операций; ламинация появляется только с флагом; монтаж
  последним; идемпотентная регенерация; QC-гард (нельзя до старта, нельзя
  без чек-листа, нельзя с частичным); блокировка → возврат в работу;
  прогресс 100%; HTTP-цикл с 400 при неполном чек-листе.

### Известные ограничения
- Редактирование каталога — через API/БД (UI-редактор операций — следующий шаг).
- Последовательность строго по position; зависимостей «после X» пока нет.
- Прогресс заказа не меняет статус заказа автоматически (решение о связке —
  при внедрении ORDER_WORKFLOW-статусов промт_5, BLOCKER #4).

### UNKNOWN

- Генерация на заказе с несколькими позициями смешивает триггеры всех позиций

  при появлении реальных возражений производства.
