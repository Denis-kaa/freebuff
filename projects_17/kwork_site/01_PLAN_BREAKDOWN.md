## 0. TL;DR (зачем этот документ)

Бриф + промт — **короткие** (2 + 3 абзаца). Перед написанием `SPEC.md` нужно явно зафиксировать:

1. **Какая минимальная модель пользователей** нужна в MVP (без попытки построить полную B2B-иерархию, не укладывается в 30 000 ₽).

4. **Технический минимум**, который покроет все 3 принципа промт (изоляция, модульность, поэтапность) и впишется в бюджет.

Документ не заменяет SPEC.md — это **precursor-анализ**, аналог `lead_aggregator/PHASE1_RESEARCH.md`.

## 1. Модель пользователей B2B (user model)

### 1.1 Стандарт (нужно в MVP)

| Роль | Описание | Источник |
|---|---|---|
| **Клиент (Client User)** | Сотрудник компании-грузополучателя. Авторизуется в ЛК. Видит **только контейнеры / заявки своей компании** (per промт принцип №1: «клиент видит только свои контейнеры»). | промт §1, бриф «лк с дислокацией» |
| **Администратор КТК ТРАСТ (Admin)** | Сотрудник самой транспортной компании. Минимум: **загрузка 2 Excel-файлов** в БД (если нет иного канала — API/FTP) и **управление пользователями** (выдача доступов клиентам). UI-реестр заявок клиента НЕ в MVP Admin — см. §2.3 (заявки идут на email per §8 Decision 3). | логически выводится из Этапа 1 п.3 |

### 1.2 🔴 Вычеркнуть из MVP (выводится за 30 000 ₽)

| Роль | Почему вычеркиваем |
|---|---|
| Иерархия ролей внутри компании-клиента (диспетчер / менеджер / бухгалтер / директор) | В MVP — **плоский список** пользователей в компании. Каждая роль = кусок UI и прав; budget не позволяет. |
| Роли внутри КТК ТРАСТ (диспетчер / логист / суперадмин) | В MVP — единая роль «суперадмин» с доступом ко всему admin-функционалу. |
| Гость / анонимный пользователь | В MVP публичная часть сводится **только к странице входа** (см. §2.1 — landing out-of-scope). |

> 💡 **Правило:** в MVP не множим роли. Каждая новая роль = +N часов UI + auth-политики. 30 000 ₽ покрывают **2 роли**.

### 4.2 Выходные — нужно сделать исполнителю

| Ассет | Формат | Назначение |
|---|---|---|
| **SVG-логотип** (качественная конвертация 3 растровых вариантов) | SVG | Главная страница + шапка ЛК (плоский вектор); favicon (монохромная мини-версия) |
| **Favicon / App icons** | SVG + PNG комплект | Браузер (16/32/64/256 px) и PWA |
| **Иконки UI** | SVG-sprite | Навигация ЛК, действия в форме, статусы контейнеров |
| **Hero-визуалы / mockup фоновой карты** | SVG | Если будет лендинг (опц.) + основа для карты |
| **Empty/Error/Loading-состояния** | SVG / PNG | Качество UX, общее для всех страниц |
| **Тексты форм заявки** | text (RU) | Копирайтинг — нужно от клиента |
| **Подсказки / help-блоки** | text (RU) | Для UX — нужно от клиента |

### 4.3 Требования к качеству логотип-SVG (уточнить)

Бриф: *«требуется качественно перевести картинку лого в svg»*. **Качество не специфицировано** — нужно согласовать с клиентом:

- Уровень детализации (минимально читаемый размер; сохранять мелкие детали или flat-стиль?).
- Чистый авто-трейс или ручная отрисовка по эталону?
- Нужен ли плоский монохромный вариант (для favicon, печати)?
- Нужны ли цветовые токены из лого (HEX/RGB палитра)?
- Количество итераций правок лого — входит в бюджет 15 000 ₽ Этапа 2.

> 💡 **Default-pредложение для SPEC (если клиент молчит):** flat-вектор с сохранением основных форм + 1 монохромный вариант (для favicon) + 1 раунд ручных правок поверх авто-трейса. Это укладывается в бюджет Этапа 2.

> ⚠️ **Риск:** авто-трейс PNG → SVG часто даёт «грязный» результат; ручная отрисовка по эталону = дополнительные часы. Зафиксировать в SPEC и согласовать с клиентом до старта Этапа 2.

## 5. Архитектурный минимум (стек для 30 000 ₽)

### 5.1 По промт + бриф + бюджет

| Слой | Решение | Обоснование |
|---|---|---|
| **Backend** | **Python** (FastAPI **или** Flask) — НЕ PHP | Промт явно: «Python-скрипт парсинга/сведения 2 Excel-файлов»; в брифе альтернатива «php или питон» — это 🔴-блокер, нужно подтверждение клиента |
| **DB** | **SQLite с `PRAGMA journal_mode=WAL;`** | Промт явно: «с учётом WAL/изоляции». SQLite WAL — нативно и бесплатно, покрывает многоклиентский доступ на нагрузке B2B-MVP. PostgreSQL — overkill для 30 000 ₽ |
| **Frontend** | **Server-side rendering (Jinja2) + Bootstrap 5 + HTMX** | 30 000 ₽ не покрывают SPA (React/Vue); HTMX даёт интерактивность без JS-фреймворка |
| **Карта (Этап 2)** | **Leaflet.js** (open-source) поверх OSM-тайлов + SVG-overlay для линий маршрутов | Промт: «векторная графика / SVG». Leaflet даёт векторный рендер и плавное взаимодействие; чистый SVG на всю карту РФ = адская работа, не вписывается в бюджет |
| **Excel-pipeline** | `pandas` + `openpyxl`, фоновый таск (FastAPI BackgroundTasks) | Парсинг асинхронно, чтобы UI не зависал |
| **Аутентификация** | Email/пароль + сессии (Cookie) + bcrypt | OAuth — out-of-scope по бюджету |
| **Изоляция tenant** | На уровне SQL: `WHERE company_id = ?` из сессии пользователя | Database-per-tenant / schema-per-tenant = overkill; row-level фильтрация достаточна |
| **Заявки → куда** | **Email КТК-диспетчеру через SMTP** (в MVP) | UI-реестр заявок = дополнительные часы UI; email = native + экономит бюджет |
| **Загрузка Excel** | **Ручная загрузка через `/admin/upload`** (страница для админа КТК ТРАСТ) | Минимально для MVP. FTP/API = отдельный проект |

### 5.2 ЖЁСТКО OUT-OF-SCOPE (бюджет 30 000 ₽)

- ❌ Полноценный landing-сайт с маркетингом, блогом, SEO
- ❌ iOS / Android нативное мобильное приложение
- ❌ Telegram-бот для клиентов (промт принцип №3 упомянул «при необходимости» — не необходимость)
- ❌ Email-рассылки (mass mailing) — только уведомления о заявках
- ❌ Интеграция с 1С / CRM клиента
- ❌ Иерархия ролей внутри компаний-клиентов
- ❌ BI / графики / аналитика по дислокации (только таблица + карта)
- ❌ CI/CD, продвинутый мониторинг, системные логи в облако
- ❌ Native push-уведомления

## 6. Ключевые риски для 30 000 ₽

| # | Риск | Митигация |

## 8. Три острых решения для SPEC.md

> Ниже — рекомендации, на которых строится SPEC. Все три **нужно зафиксировать в ADR-NNN**, прежде чем писать код.

### 🔴 Решение 1. Структура входных Excel = БЛОКЕР

- **Контекст:** без 2 эталонных Excel-файлов парсер невозможно написать осмысленно — слепой парсинг = хрупкий код.
- **Решение для SPEC:** **заморозить схему БД и парсер до получения эталонных файлов**. Структура БД строится *вокруг* реальных полей файлов, а не наоборот.
- **Решение для запуска:** в момент старта Этапа 1 запросить у клиента:
  - 2 файла (текущий и предыдущий период), реальные или фикстуры;
  - описание структуры;
  - общий ключ (например, номер контейнера);
  - периодичность обновления (1 раз в день, по событию?).

### 🔴 Решение 2. Механика загрузки данных в MVP

- **Контекст:** «1С-интеграция» — out-of-scope по бюджету; FTP/API — отдельный проект.
- **Решение для SPEC:** в MVP Этапа 1 фиксируем **ручную загрузку Excel через `/admin/upload`** для админа КТК ТРАСТ. **Никаких API-интеграций.**
- **Экономия:** ~30 % времени Этапа 1 уходит на «правильную» интеграцию; отказ от неё — ключ к укладыванию в 15 000 ₽.

### 🟡 Решение 3. Обработка онлайн-заявок = Email, не БД-реестр

- **Контекст:** UI-реестр заявок с фильтрами/статусами для админа = дополнительные часы интерфейса и поддержки.
- **Решение для SPEC:** в MVP заявки из ЛК летят **на email диспетчера/администратора КТК ТРАСТ через SMTP**. БД-реестр заявок со статусом → **Этап 2** (по остатку бюджета) **или out-of-scope**.
- **Соответствие брифу:** email-доставка **сохраняет** требование брифа «оставление онлайн заявки» — клиентская сторона неизменна (ЛК-форма с кнопкой submit), изменяется **только канал доставки**: заявки летят диспетчеру КТК ТРАСТ на email вместо БД-таблицы. Это не scope-drop, а выбор канала по бюджету.
- **Экономия:** существенная. Email-доставка = 30 минут кода. CRUD-реестр = несколько часов.
