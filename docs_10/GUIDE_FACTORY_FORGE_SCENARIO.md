## 0. Одна картинка вместо тысячи слов

Весь путь проекта выглядит так:

```
 ТЫ (пользователь)
   │  говоришь: «сделай мне приложение для планирования ремонта»
   ▼
 ВХОД (сайт / приложение / Telegram / терминал)
   │  платформа получает задачу
   ▼
 SCENARIO («сценарий») — сборка кузен под задачу
   │  «мне нужны: поиск похожих идей + поиск похожей архитектуры»
   ▼
 FORGE («кузни») — отдельные мастерские, каждая решает ОДНУ задачу
   │  кузня ищет похожие идеи → кузня ищет похожую архитектуру → ...
   ▼
 FACTORY («фабрики») — куда кузни сдают результат
   │  Idea Factory / Architecture Factory / Code Factory ...
   ▼
 ПРОЕКТ (projects_17/<имя>/)
   │  код, документация, тесты, артефакты
   ▼
 ОТЧЁТ (Telegram / статус в реестре)
```

А теперь по порядку — что за звери такие Factory, Forge и Scenario.

---

## 1. Workspace — «жизнь пользователя» (самый верхний этаж)

Прежде чем говорить про Factory/Forge, надо понять, где мы вообще находимся.

**Workspace** — это «одна жизнь» человека или команды. У человека их может быть несколько: «Работа», «Дом», «Учёба». У каждого workspace — свои проекты, свои разговоры, своя память. Они не смешиваются.

**Project** — это конкретная цель внутри workspace: «приложение для ремонта», «сайт-визитка», «курс по физике». Проект — это не просто папка с кодом, а целая экосистема: идеи, документация, архитектура, решения, память, история.

Иерархия:

```
Workspace (твоя «жизнь»)
 └── Project «Ремонт кухни»
 └── Project «Отчёт для Иванова»
 └── Project «Сайт для друзей»
```

**Важно:** Workspace и Project — это *контейнеры*. Они сами ничего не делают, они только *содержат*. А делают работу — Factory, Forge и Scenario.

---

## 2. Главная идея: три уровня «производства»

Вся платформа строится на трёх простых понятиях. Запомни их — дальше всё ложится на них.

```
FACTORY  — «фабрика»: направление производства, набор кузен под одну большую тему
  │        (Idea Factory, Architecture Factory, Code Factory, Content Factory...)
  ▼
FORGE    — «кузня»: мастерская, которая умеет делать РОВНО ОДНУ задачу
  │        (искать конкурентов, расширять идею по векторам, искать похожую
  │         архитектуру, писать код по контракту...)
  ▼
TOOL     — «тулза»: кирпичик внутри кузни (промпт, скрипт, команда, API-вызов)
```

А **Scenario** стоит чуть в стороне и связывает их воедино:

```
SCENARIO — «сценарий»: сборка. Ты берёшь нужные кузни (из разных фабрик!)
           и собираешь из них цепочку, которая производит конкретный продукт.
```

Разберём каждый уровень по порядку.

---

## 3. Tool — кирпичики (промпты, скрипты, команды)

**Tool (тулза)** — это самый маленький элемент, «рука» системы. Это может быть:

- промпт (инструкция для модели),
- скрипт (python, bash),
- команда,
- вызов API,
- любой готовый элемент, который что-то *умеет делать*.

Тулзы ничего не решают. Они просто выполняют одну операцию: «вот данные — вот результат». Решения принимает кузня, которая эти тулзы собирает.

> **Аналогия:** тулза — это отвёртка, молоток или сверло. Сама по себе ничто, но в руках мастера — инструмент.

---

## 4. Forge — «кузня»: одна мастерская = одна задача

**Forge (кузня)** — это мастерская, которая умеет делать **ровно одну задачу**. Внутри кузни лежат тулзы (промпты, скрипты), которые кузня запускает, чтобы задачу выполнить.

Кузня **ничего не знает** про другие кузни и про то, куда пойдёт её результат. Она просто делает своё дело.

Примеры кузен (это уже живые примеры из нашего плана):

- **кузня «поиск конкурентов и занятых ниш»** — находит, кто уже делает похожее;
- **кузня «расширение идеи по векторам»** — показывает разные углы, видения, грани идеи;
- **кузня «поиск похожих идей»** — ищет, что похожее уже существует;
- **кузня «поиск похожей архитектуры»** — ищет, как похожие системы устроены внутри;
- **кузня «написать код по контракту»** — берёт описание и пишет код;
- **кузня «проверить тесты»** — гоняет тесты и возвращает результат.

Ключевой принцип: **одна кузня — одна задача**. Если задача сложная — это уже не одна кузня, а сценарий из нескольких.

> **Аналогия:** кузня — это цех. В одном цехе куют мечи, в другом — подковы. Цех с мечами не занимается подковами.

---

## 5. Factory — «фабрика»: направление производства

**Factory (фабрика)** — это направление производства: **набор кузен, которые вместе закрывают одну большую тему**. Фабрика — «готовый элемент» платформы: открыл фабрику — и у тебя есть весь инструментарий по этой теме.

Примеры фабрик (из нашего видения):

### Idea Factory — «фабрика идей»

Работает с идеей: куда её расширить, кто уже это делает, что займёт. Внутри неё кузни:

- кузня «расширение идеи по векторам» (разные углы и видения);
- кузня «поиск конкурентов и занятых ниш»;
- кузня «поиск похожих идей»;
- и своя **ресёрч-кузня** — исследовательская, потому что каждая фабрика ищет материал по-своему.

### Architecture Factory — «фабрика архитектуры»

Работает с устройством системы: как её спроектировать, на что опереться. Внутри неё кузни:

- кузня «поиск похожей архитектуры»;
- кузня «проектирование модулей»;
- кузня «риски и зависимости»;
- и тоже своя **ресёрч-кузня**.

### Code Factory — «фабрика кода»

Работает с реализацией: пишет код по контрактам, гоняет сборку и тесты.

> ⚠️ **Важно:** у каждой фабрики **своя** ресёрч-кузня. Исследование идей и исследование архитектуры — это разные способы искать, поэтому это разные кузни в разных фабриках. Общей «одной кузни на всех» нет.

> **Аналогия:** фабрика — это завод. На заводе идей — цеха по расширению идей и поиску конкурентов. На заводе архитектуры — цеха по проектированию. Завод — это всегда набор цехов (кузен).

---

## 6. Scenario — «сценарий»: сборка кузен под задачу

Вот тут самое интересное. **Scenario (сценарий)** — это не ещё один вид мастерской. Это **сборка**: ты берёшь нужные кузни — и не обязательно из одной фабрики! — и собираешь из них цепочку, которая производит конкретный продукт.

Пример. Мне пришла задача: «сделать сервис для ремонта квартир». Мне **не нужна** вся Idea Factory целиком и вся Architecture Factory целиком. Мне нужно только:

1. **кузня «поиск похожих идей»** (из Idea Factory) — а вдруг уже есть похожее;
2. **кузня «поиск похожей архитектуры»** (из Architecture Factory) — как такие сервисы устроены внутри;
3. может, ещё **кузня «поиск конкурентов и ниш»** (из Idea Factory).

Я выбираю эти кузни, собираю их в сценарий — и запускаю. Получается сценарий «разведка перед стартом проекта».

### Ты выбираешь кузни, а не фабрики

Главный принцип: **для задачи берутся отдельные кузни, а не фабрика целиком.** Фабрика — это «магазин», где лежат кузни. Сценарий — это «корзина покупок»: положил нужные кузни из разных магазинов — и готово.

Одна и та же кузня может работать в разных сценариях. Например, кузня «поиск похожих идей» пригодится и при запуске проекта, и при поиске нового направления для существующего.

### Даже «конвейер сборки» — это сценарий

Раньше в документации было понятие «Forge как процесс» — конвейер из шагов `FORGE → CHECK → BUILD → TEST → DEPLOY → REPORT`. Так вот, **это на самом деле сценарий**. Это цепочка кузен («подготовь», «проверь», «собери», «протестируй», «выпусти», «отчитайся»), собранная для производства кода. Слово «forge» там в названии — историческая случайность, по сути это scenario.

То же самое в коде платформы: есть «цепочка из 14 ролей» (`forge chain`) — explainer → lisa → risk → decomposer → architect → auditor → developer → frontend → devops → tester → fixer → acceptance → documenter → retrospective. Это тоже **сценарий**: готовый набор шагов, который платформа прогоняет, чтобы проект из задачи превратился в продукт.

## 8. Как это соотносится с кодом СЕЙЧАС (честно)

В коде платформы слова используются немного по-другому, чем в видении выше. Это нормально — видение опережает код. Вот честная таблица соответствия:

| Понятие в видении | Что в коде сегодня | Где |
|-------------------|--------------------|-----|
| **Scenario** (сборка кузен) | Реестр сценариев + цепочки ролей (`forge chain`, 14 ролей) | `core_02/scenario_registry.py`, `core_02/forge_facade.py` |
| **Роль** (≈ кузня) | Роли Blueprint v3: developer, architect, auditor… | `core_02/blueprint_v3.py` |
| **Tool** (тулза) | Промпты ролей, скрипты, тул-рантайм | `pompts_11/`, `scripts_01/tool_runtime.py` |
| **Factory** (фабрика) | Пока **только идея** из манифеста (документ 68). Как код не построена | `docs_10/engineering-memory/factory_forge_manifest.md` |
| Конвейер `FORGE→CHECK→BUILD→TEST→DEPLOY→REPORT` | Это сценарий, но исторически называется «Forge Pipeline» | `core_02/forge_pipeline.py` |
| Статусы проектов (UNFORGED…) | Журнал прогонов | `core_02/forge_registry.py`, `data_13/forge_registry.yaml` |

### История про Factory (важно знать, чтобы не спорить зря)

В платформу когда-то принесли манифест (документ №68), где впервые появилась идея иерархии `Workspace → Factory → Forge → Engine → Module → Tool → Skill → Prompt`. Платформа устроила официальное ревью (ARB — «архитектурный суд»). Вердикт `ARB-REV-001` — **CHANGES REQUIRED** («нужны изменения»):

1. **Видение — хорошее.** Проект как экосистема, знания не теряются, промпт — нижний уровень, а не центр.
2. **НО термин «Forge» уже занят** в другом значении (метасистема проектирования) — надо развести значения.
3. **НО 60–70% манифеста уже придумано** под другими именами (Architecture Forge ≈ ARB + DIS + AG, Knowledge ≈ Organizational Memory).

Тогда фабрику как отдельную систему решили не строить. **Но** твоё уточнение выше — «фабрика = набор кузен, сценарий = сборка кузен из разных фабрик» — это конкретное, рабочее определение, которое снимает главную проблему ревью (конфликт слов и неясность, что за чем). Это направление развития платформы. А всё, что уже есть в коде (роли, реестры, конвейер, wizard), отлично ложится на эту модель как «материальная база» для будущих фабрик.

### ⚠️ Про статус `UNFORGED`

В журнале прогонов есть статус `UNFORGED` — «не прогонялся через конвейер». Он значит ТОЛЬКО «проект не прогонялся через FORGE→CHECK→BUILD→…», **НЕ** «проект сломан». Проект может отлично работать через другой путь (например, wizard + сценарий + доставка в Telegram). Не пугайся, увидев UNFORGED у живого проекта.

## 9. Полный путь: от входа до реализации (сквозной пример)

Соберём всё вместе на живом примере.

**Вход 1 — сайт / приложение (будущее).** Пользователь открывает платформу и пишет задачу. *(Сейчас этого ещё нет — скоро расскажешь про это отдельно.)*

**Вход 2 — Telegram.** Пользователь пишет боту: `/task сделай приложение для планирования ремонта`.

**Вход 3 — MCP/API.** Другая программа (например, Cursor или скрипт) стучится в MCP-сервер / REST API.

**Вход 4 — Терминал.** Ты запускаешь wizard или forge-команду руками.

### Дальше по шагам

| Шаг | Что происходит | Кто это делает |
|-----|----------------|----------------|
| 1 | Задача попадает в платформу (очередь промтов / диспетчер) | `prompt_queue`, `prompt_dispatcher`, TG-бот |
| 2 | Реестр сценариев предлагает роли/кузни под задачу | `ScenarioRegistry.propose_roles(query)` |
| 3 | Wizard собирает задание: роль + модель + контракт | `scripts_01/wizard.py`, `core_02/wizard_lib.py` |
| 4 | Кузня (роль, например, `developer`) выполняет свою часть: создаёт артефакты | Blueprint v3 роль + модель |
| 5 | Роль явно просит прогнать проект через конвейер сборки | `ForgeFacade.initiate_forge()` |
| 6 | Сценарий сборки: FORGE → CHECK → BUILD → TEST → DEPLOY → REPORT | `ForgePipeline` |
| 7 | Статус записан в журнал, отчёт ушёл в Telegram | `ForgeRegistry.record_run()`, TG-отправка |
| 8 | Урок прогона ушёл в память платформы (Learning Loop) | `MemoryStore.record_learning_event()` |

### Режим «готовый сценарий» — forge chain

Есть и автоматический готовый сценарий: **`forge chain`** прогоняет проект через цепочку из **14 ролей** по очереди:

```
explainer → lisa → risk → decomposer → architect → auditor
→ developer → frontend* → devops → tester → fixer
→ acceptance → documenter → retrospective
```

(*`frontend` запускается только для веб-проектов.)

Из этих 14 ролей:

- **«лёгкие»** (аналитики и документы: explainer, risk, architect, auditor…) — только **проверяют**, что нужные артефакты существуют;
- **«тяжёлые»** (developer, tester, fixer, acceptance, devops) — реально **гоняют полный конвейер** сборки (пишут/собирают/тестируют);
- если что-то упало — можно продолжить с места остановки: `forge chain ... --resume`.

Команда:

```bash
python scripts_01/forge.py chain projects_17/interior_planner --json --quiet
```

Итог — JSON-отчёт: статус по каждой роли + общий статус (`ok` / `partial` / `degraded` / `failed`).

## 10. Словарик (для быстрого ответа новичку)

| Термин | Одной фразой |
|--------|--------------|
| **Workspace** | «Жизнь» пользователя: набор проектов с общей памятью |
| **Project** | Конкретная цель внутри workspace (экосистема, не только код) |
| **Tool** | Кирпичик: промпт, скрипт, команда. Сама по себе ничего не решает |
| **Forge** | Кузня: мастерская, решающая РОВНО ОДНУ задачу (искать конкурентов, писать код…) |
| **Factory** | Фабрика: набор кузен под одно направление (Idea / Architecture / Code / Content…) |
| **Scenario** | Сценарий: сборка нужных кузен из любых фабрик под конкретную задачу |
| **Роль** (в коде) | Текущее имя того, что в видении станет кузней. Сейчас роль — это скорее набор инструкций/промптов; будущая кузня будет оборачивать роль + тулзы в одну мастерскую |
| **Forge Pipeline** (в коде) | Историческое имя сценария сборки: FORGE→CHECK→BUILD→TEST→DEPLOY→REPORT |
| **ForgeFacade** | Единственная дверь из ролей в конвейер сборки |
| **ForgeRegistry** | Журнал: статусы проектов (UNFORGED…DEPLOYED) |
| **UNFORGED** | «Не прогонялся через конвейер» — НЕ значит «сломан» |
| **ARB** | Архитектурный суд: ревью крупных решений (вердикты APPROVED / CHANGES REQUIRED…) |

## 12. Три фразы, чтобы объяснить систему за 30 секунд

1. **Кузня (Forge)** — мастерская, которая умеет делать одну задачу: искать конкурентов, писать код, проектировать архитектуру.
2. **Фабрика (Factory)** — набор таких кузен под одно направление: Idea Factory, Architecture Factory, Code Factory.
3. **Сценарий (Scenario)** — ты берёшь нужные кузни из разных фабрик, собираешь в цепочку — и получаешь продукт.

А весь путь простой: **сказал → выбрал кузни → кузни сделали → конвейер проверил → отчёт пришёл**.
