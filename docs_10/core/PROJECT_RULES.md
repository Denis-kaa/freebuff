# PROJECT_RULES.md — Правила ведения проектов (канон)

> **Статус:** CANONICAL · единый источник истины о том, как мы ведём проекты на платформе.
> **Роль:** проект — **контейнер контекста**. Вся работа идёт через проект; внутри проекта живут его контекст, уроки, решения, паспорт.
> **Дата:** 2026-08-12
> **Источник:** фишка платформы (ведение проектов), AGENTS.md (канон), RULES.md (документирование), PROJECT_REQUIREMENTS.md (готовность), PROJECT_MIGRATION_TEMPLATE.md (портируемость), engineering-memory/templates/ (шаблоны EM), примеры: lead_aggregator, diet_platform, tg_terminal_messenger, content_factory, vkusvill_*.
> **Связь:** расширяет RULES.md (документ-типы) — здесь конкретно «как живёт проект».

---

## 0. Главная фишка платформы

> **Проект — контейнер контекста.** Мы создаём проект и идём **по проекту**: внутри фиксируем уроки, шаги, обоснования решений, паспорт/манифест, ADR и документацию. Уникальное для проекта — в проекте; тиражируемое — дополнительно в общей базе платформы, но **главное — в проекте**.

Из этого следуют все правила ниже.

---

## 1. Проект — объект работы (не процесс)

| Сущность | Роль |
|----------|------|
| **Project** | Объект работы: где живёт контекст, артефакты, решения, уроки (карта v1.1 §2) |
| **Scenario** | Исполняемый процесс-композитор поверх Factory (НЕ хранилище проекта) |
| **Factory / Forge** | Производственные возможности, которые проект *использует* |
| **Workspace** | Среда, где живут все проекты |

**Правило:** проект — это не «папка с кодом», а **контейнер**: код + контекст + память решений + уроки + паспорт.

## 2. Обязательный каркас проекта (паспорт + память)

При создании проекта в `projects_17/<slug>/` заводится каркас:

| Файл | Обязателен | Содержание |
|------|:----------:|------------|
| **`MANIFEST.md`** | ✅ | **Паспорт проекта**: назначение, версия, статус, архитектура, roadmap, индекс документов |
| **`LESSONS.md`** | ✅ | **Уроки проекта** (project-local, формат CON/CAN/ANTI/PB как в core_02/LESSONS.md) |
| **`decisions/DECISIONS.md`** + `ADR-NNN_*.md` | ✅ | **Реестр архитектурных решений** проекта (project-local ADR: Context/Options/Decision/Rationale/Consequences) |
| **`ROADMAP.md`** | ✅ | Этапы, статус, прогресс (PIPELINE_TEMPLATE) |
| **`README.md`** | ✅ | Что это, быстрый старт |

## 3. Что и где фиксируем (принцип «контекст в проекте»)

### 3.1 Всегда в проекте (главное — здесь)

1. **Уроки** — почему что-то сломалось/получилось; формат CON (подтверждено) / CAN (гипотеза) / ANTI (анти-паттерн) / PB (процессный баг) — в `LESSONS.md` проекта;
2. **Шаги и решения** — что делал, **почему принял такое решение**, альтернативы — в `STEPS.md` и/или `decisions/ADR-*`;
3. **Паспорт/манифест** — `MANIFEST.md` (обязателен, единый вход в проект);
4. **Архитектурные решения** — project-local ADR (`decisions/`), даже если решение кажется мелким;
5. **Документация по задаче** — README/SPEC/ROADMAP, всё что специфично для этого проекта.

### 3.2 Дополнительно в общей базе (если тиражируемо)

Если урок/паттерн **универсален для платформы** (а не уникален для проекта):

- **Платформенные уроки** → `core_02/LESSONS.md` (дубль-запись или кросс-ссылка на project-local);
- **Архитектурные решения платформы** → `docs_10/engineering-memory/decisions/ADR_NNN_*.md` + индекс `docs_10/decisions/DECISIONS.md`;
- **Документ-типы и правила** → `docs_10/core/RULES.md`, `docs_10/core/PROJECT_REQUIREMENTS.md`.

**Правило:** дублирование допускается **в одну сторону** — из проекта в общую базу, когда урок подтвердил тиражируемость. Обратное (общая база → проект) — только через кросс-ссылку, без копирования.

## 4. Порядок работы: задача идёт через проект

1. **Создать проект** (`projects_17/<slug>/`) с каркасом §2 (паспорт + LESSONS + decisions + README).
2. **Идти по проекту:** все шаги, решения, уроки — **внутри проекта**.
3. **TASK.md проекта** — вести задачи проекта (или через платформенный TASK.md, если это работа над самой платформой).
4. **Уроки фиксировать по ходу**, а не в конце (рабочий журнал, CON-5: ревью итерациями).
5. **При завершении** — обновить MANIFEST.md (статус, версия, roadmap), закрыть решения, поднять уроки.

**Важно:** задача НЕ существует «сама по себе» — она идёт через проект. Нет проекта → сначала создай каркас.

**Инструмент планирования (kickoff/planning-задачи):** для задач вида «начни проект / составь план / задокументируй шаги» используется **Blueprint v3 role pipeline** (Kwork Arbitr v3) — LIGHT-роли планирования `explainer → lisa → risk → decomposer → architect` (артефакты `brief.md` → `lisa_report.md` → `risk_matrix.md` → `decomposition.md` → `architecture.md` + ADR), затем HEAVY-роли `developer → tester → fixer → acceptance` через `ForgeFacade`. Каркас §2 — контейнер контекста; роли Blueprint v3 — производственный слой поверх него. Канон цепочки: `core_02/forge_facade.py::PIPELINE_CHAIN`; входные точки: `scripts_01/forge.py cmd_chain`, `ForgeFacade.run_chain`, `scripts_01/wizard.py`. См. `core_02/LESSONS.md` CON-60.

## 5. Работа по платформе = проект «сама платформа»

Когда мы действуем **по правилам платформы** и задача относится к самой платформе:

> **Наш проект — это сама платформа** (корень `freebuff/`).

Для платформенной работы каркас §2 живёт на уровне корня:

| Что | Где (для платформы) |
|-----|---------------------|
| Паспорт/манифест | `BUFFY.md` (идентичность) + `BUFFY_PROJECT.md` / `PLATFORM.md` |
| Уроки | `core_02/LESSONS.md` |
| Решения (ADR) | `docs_10/engineering-memory/decisions/` + `docs_10/decisions/DECISIONS.md` |
| Документация | `docs_10/` (core/engineering-memory/runbook/...) |
| Задачи | `TASK.md` (корень) |
| Версии/изменения | `CHANGELOG.md` (корень) |
| Документ-реестр | `docs_10/DOCUMENT_REGISTRY.md` |

**Правило:** для платформенных задач «проект» = корень платформы; уроки/решения фиксируются в платформенных канонических местах, а не в projects_17/<slug>.

## 6. Память проекта (Engineering Memory)

Долгоживущий контекст — через шаблоны EM (`docs_10/engineering-memory/templates/`):

- **`project_chronicle.md`** — хроника проекта (вехи, решения, повороты);
- **`decision_journal.md`** — журнал решений (Context / Options / Decision / Rationale / Consequences);
- **`lessons_learned.md`** — уроки в EM-формате (Lesson / Context / Example / Consequences);
- **`feature_story.md`** — история фичи;
- **`incident_report.md`** — инциденты;
- **`milestone_chronicle.md`** — вехи;
- **`task_retrospective.md`** — ретроспектива задачи.

**Правило:** память проекта живёт **в проекте** (или в `docs_10/engineering-memory/` для платформы) — рядом с кодом, чтобы следующая итерация видела оба слоя.

---

## 7. Портирование проекта (Project Local)

- Проект должен быть **самодостаточен** (PROJECT_MIGRATION_TEMPLATE.md): свои MANIFEST, decisions, LESSONS, ROADMAP, STEPS;
- Не должен иметь жёстких зависимостей от платформенных модулей (`freebuff_plugin`, `core_02`, `scripts_01`) в проектном коде;
- Платформенные ADR при экспорте конвертируются в project-local ADR (`decisions/`).
