## 🗺️ Roadmap (Phase 6–10)

### Phase 6: Agent Base Class (Q4 2026, ~2 месяца)

**Цель:** Реализовать ADR-019 — единую сущность "Агент" с композицией ролей.

#### Задачи
1. **`core_02/agent_base.py`** — BaseAgent class:
   - `compose_roles(role_ids: list[str***REMOVED***) -> Agent` — композиция через SmartRouter
   - `capability → SmartRouter.route()` — роутинг через capability-registry
   - `ForgeFacade` — единственный мост к Forge-слою
   - Lifecycle: CREATED → ACTIVE → PAUSED → DONE/FAILED (forward-only)
2. **Персистенс** — `agents` таблица в `context.db`:
   ```sql
   CREATE TABLE agents (
       agent_id TEXT PRIMARY KEY,
       role_ids TEXT,  -- JSON list
       capability TEXT,
       status TEXT,
       owner_chat_id TEXT,
       created_at TIMESTAMP,
       updated_at TIMESTAMP
   )
   ```
3. **Тесты** — `tests_09/test_agent_base.py` (hermetic, 15+ тестов)
4. **Документация** — ADR-019 статус PROPOSED → ACCEPTED

#### Success Criteria
- ✅ 15+ hermetic тестов (pytest pass)
- ✅ Агент создаётся через `Agent.compose(role_ids)`, исполняется через ForgeFacade
- ✅ Lifecycle transitions проверены (CREATED → DONE/FAILED)
- ✅ Персистенс: агенты сохраняются в `context.db`, переживают перезапуск

#### Риски
- **Композиция ролей сложна** — может потребоваться промежуточный "role resolver" слой
- **ForgeFacade overload** — если агенты начнут вызывать ForgeFacade напрямую, минуя Factory

**Mitigation:** Начать с простой композиции (role_ids = список строк), добавить resolver в Phase 7.

### Phase 7: Web UI MVP (Q1 2027, ~3 месяца)

**Цель:** React dashboard для управления задачами, контекстом, capability-роутингом.

#### Архитектура
```
┌──────────────┐
│  React App   │  ← localhost:5173 (Vite dev server)
│ (Three.js UI)│
└──────┬───────┘
       │ REST API
┌──────▼────────────────────┐
│ scripts_01/forge_api.py   │  ← FastAPI server (port 8410)
│ (/api/v1/...)             │
└──────┬────────────────────┘
       │
┌──────▼────────┐
│ core_02/      │  ← Forge layer
│ forge_facade  │
└───────────────┘
```

#### Задачи
1. **Frontend** — `frontend/` (NEW):
   - React 18 + Vite 5 (Android ARM64 compatible)
   - Three.js 3D workspace visualization (canvas + orbit controls)
   - Components: TaskManager, ContextViewer, CapabilityRouter, AgentMonitor
   - Tailwind CSS + shadcn/ui (dark mode)
2. **Backend** — расширение `scripts_01/forge_api.py` (v5.181.0):
   - `POST /api/v1/agents` — создать агента (role_ids + capability)
   - `GET /api/v1/agents/{agent_id***REMOVED***` — статус агента
   - `POST /api/v1/agents/{agent_id***REMOVED***/pause` — пауза
   - `POST /api/v1/agents/{agent_id***REMOVED***/resume` — возобновление
   - `GET /api/v1/context` — memory engine state (4 типа памяти)
   - `POST /api/v1/context/query` — search через MemoryStore
   - WebSocket `/ws/agents/{agent_id***REMOVED***` — real-time updates
3. **Security** — базовая auth:
   - Bearer token (SHA256 hash в `~/.freebuff_token`)
   - Chat ID scope (owner_chat_id проверяется через ForgeRegistry)
4. **Интеграция с FBM** — решение ADR-024:
   - **Option A (default):** FBM остаётся standalone (документация + фиксы уже сделаны)
   - **Option B (after Phase 7):** интегрировать через REST API (task endpoints, SSE/WebSocket)
   - **Option C (after Phase 7):** deprecate FBM, заменить на Web UI

#### Success Criteria
- ✅ React app запускается на Android Termux (Vite 5, без rolldown)
- ✅ Можно создать агента через UI, увидеть статус (ACTIVE → DONE)
- ✅ ContextViewer отображает 4 типа памяти (facts/interactions/traces/context)
- ✅ Bearer token защищает API (401 без токена)
- ✅ WebSocket обновляет статус агента в real-time

#### Риски
- **Vite 8+ не работает на Android** — rolldown (Rust) не компилируется → остаться на Vite 5
- **Three.js performance** — 3D может тормозить на слабых девайсах → fallback 2D mode
- **WebSocket stability** — может дропаться при сетевых сбоях → reconnect logic

**Mitigation:** Начать с Vite 5 (verified работает), добавить performance budget (60 fps), graceful WebSocket reconnect.

### Phase 8: Integration Adapters (Q2 2027, ~2 месяца)

**Цель:** Реализовать ADR-020 — единая граница для внешних мостов (REST API, Telegram, Slack, Discord).

#### Задачи
1. **`core_02/integration_base.py`** — BaseIntegration class:
   - **AuthSpec** — enum (none / bearer / vault / chat_id_scope)
   - **intent → capability routing** — закрытый словарь (40 intents → 36 capabilities)
   - **Нормализация входов** — unified InputMessage → capability + context
2. **Telegram Adapter** — рефакторинг `projects_17/tg_terminal_messenger/`:
   - Использовать BaseIntegration
   - intent = "analyze_conversation" → capability = "content:analysis"
   - RemoteSyncCoordinator → BaseIntegration hook
3. **REST API Adapter** — `scripts_01/forge_api.py` → BaseIntegration
4. **Slack Adapter** — `core_02/integrations/slack_adapter.py` (NEW):
   - Slack Events API (slash commands + interactive messages)
   - intent = "/freebuff analyze" → capability = "content:analysis"
5. **Discord Adapter** — `core_02/integrations/discord_adapter.py` (NEW):
   - Discord.py bot (commands + embeds)
   - intent = "!freebuff generate" → capability = "content:generation"

#### Success Criteria
- ✅ BaseIntegration протестирован (hermetic, 10+ тестов)
- ✅ Telegram CLI использует BaseIntegration (backward-compatible)
- ✅ Slack bot отправляет задачи в Freebuff через intent→capability
- ✅ Discord bot работает аналогично

#### Риски
- **40 intents сложно поддерживать** — может потребоваться embeddings-based роутинг
- **Slack/Discord rate limits** — может превысить лимиты при burst traffic

**Mitigation:** Начать с closed словаря (40 intents), добавить embeddings fallback в Phase 9.

### Phase 9: Production Hardening (Q2–Q3 2027, ~2 месяца)

**Цель:** Подготовить платформу к multi-user production.

#### Задачи
1. **Multi-user auth** — PostgreSQL + OAuth2:
   - `users` таблица (user_id, email, chat_id, roles)
   - OAuth2 flow (Google/GitHub)
   - JWT tokens (refresh + access)
2. **Rate limits** — Redis-based:
   - 100 req/min per user
   - 1000 req/min per tenant
   - Graceful 429 с Retry-After
3. **Audit log** — `audit_events` таблица:
   - (event_id, user_id, action, resource, timestamp, metadata)
   - Immutable append-only log
   - Retention: 90 дней → S3 archive
4. **Disaster recovery** — PostgreSQL replication:
   - Primary + read replica
   - Point-in-time recovery (PITR)
   - Backup strategy: full daily + incremental hourly
5. **Monitoring** — Prometheus + Grafana:
   - Metrics: request rate, error rate, p95 latency
   - Alerts: error_rate > 1%, p95 > 500ms

#### Success Criteria
- ✅ 2+ пользователя могут работать одновременно (изолированные workspace)
- ✅ Rate limits защищают от burst traffic (429 возвращается корректно)
- ✅ Audit log записывает все действия (immutable, GDPR-compliant)
- ✅ DR plan протестирован (restore from backup < 1 час)

#### Риски
- **PostgreSQL overhead** — может быть избыточным для 1-10 пользователей
- **OAuth2 complexity** — интеграция Google/GitHub может сломать Android Termux

**Mitigation:** Начать с SQLite multi-user (owner_chat_id scope), мигрировать на PostgreSQL при 10+ users.

   - Entry point: `freebuff_plugins`
   - Hooks: pre_forge / post_forge / memory_index
3. **Plugin marketplace** — Web UI раздел:
   - Browse plugins (GitHub repos)
   - Install via `pip install freebuff-plugin-*`
   - Community ratings
4. **Community integrations** — примеры:
   - `freebuff-plugin-notion` — sync с Notion API
   - `freebuff-plugin-gmail` — email ingestion
   - `freebuff-plugin-obsidian` — markdown vault sync

#### Success Criteria
- ✅ SDK опубликован на PyPI
- ✅ 3+ community plugins работают (Notion/Gmail/Obsidian)
- ✅ Plugin marketplace доступен через Web UI

#### Риски
- **Plugin security** — third-party код может быть вредоносным
- **API stability** — breaking changes в SDK сломают plugins

**Mitigation:** Sandboxed plugin execution (proot-distro containers), semantic versioning SDK.

## ⚠️ Risks & Mitigation

### Top 5 Risks

1. **Android Termux limitations** (HIGH)
   - **Risk:** Vite 8+, некоторые npm packages не работают на ARM64
   - **Mitigation:** Оставаться на Vite 5, тестировать каждую новую зависимость

2. **SQLite scaling** (MEDIUM)
   - **Risk:** При 10+ пользователях SQLite может стать bottleneck
   - **Mitigation:** Начать с SQLite (owner_chat_id scope), мигрировать на PostgreSQL в Phase 9

3. **ForgeFacade overload** (MEDIUM)
   - **Risk:** Если все компоненты вызывают ForgeFacade напрямую → tight coupling
   - **Mitigation:** Ввести промежуточный слой (ExecutionPlanner) в Phase 6

4. **Legacy code debt** (LOW)
   - **Risk:** FBM, Telegram CLI — 10k+ LOC без тестов
   - **Mitigation:** Не трогать legacy (ADR-024 Option A), фокус на новом коде

5. **Community plugin security** (LOW)
   - **Risk:** Third-party код может быть вредоносным
   - **Mitigation:** Sandboxed execution (proot-distro), code review перед marketplace
