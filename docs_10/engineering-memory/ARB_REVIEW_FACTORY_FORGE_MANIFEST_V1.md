### Ключевая находка: конфликт имён «Forge»

| Термин | В Buffy Forge (RFC-BF-001) | В Factory/Forge Manifest | Конфликт |
|--------|---------------------------|--------------------------|----------|
| **Forge** | Метасистема проектирования архитектуры Buffy. 6 форджей (Idea→Knowledge→Architecture→Implementation→Validation→Evolution) куют архитектурные артефакты для самой платформы. | Производственная линия внутри Factory. 9+ форджей (Idea, Research, Architecture, Prompt, Code, Test, Documentation, Release, Video, Book, Evolution) куют любые интеллектуальные продукты для пользователя. | **КРИТИЧЕСКИЙ:** одно слово — две несовместимые семантики |
| **Factory** | НЕТ в RFC-BF-001 (Buffy Forge — сам является «фабрикой архитектурных решений», но термин «Factory» не используется) | Производственная подсистема Workspace OS, содержащая Forge'ы | **УМЕРЕННЫЙ:** если Buffy Forge — это «Factory архитектурных решений», то Manifest предлагает другую «Factory» |

**Вывод AFC:** Manifest предлагает иерархию, которая на 60-70% дублирует уже спроектированное в Buffy под другими именами. Наиболее критично: Architecture Forge (Manifest) ≈ Architecture Forge (Buffy Forge L2) + DIS + ARB + AG, но с разной семантикой. Конфликт имён «Forge» — **blocking issue**.

## 1. Executive Summary

**Документ на ревью:** `factory_forge_manifest.md` — манифест, предлагающий иерархию:

```
Workspace OS → Workspace → Project → Factory → Forge → Engine → Module → Tool → Skill → Prompt
```

где Factory — производственная подсистема, а каждый Forge — независимая производственная линия для создания интеллектуальных продуктов (код, книги, видео, игры).

**Проблема:** AI-инструменты умеют выполнять отдельные задачи, но не сопровождают проект целиком. Workspace OS предлагается как решение — операционная система полного жизненного цикла проекта.

**Вердикт ARB:** CHANGES REQUIRED — видение валидно, но текущая форма имеет критический конфликт имён с Buffy Forge (RFC-BF-001) и должна быть переработана.

---

## 2. Problem Assessment

**Правильно ли сформулирована проблема?** — **ДА, с уточнениями.**

Manifest утверждает: «большинство AI-инструментов умеют выполнять отдельные задачи, но ни один не умеет сопровождать проект целиком». Это верно для рынка AI-инструментов в целом, но **Buffy уже решает эту проблему** на своём уровне: Organizational Memory (память проекта), Buffy Forge (архитектурное управление), Decision Intelligence (качество решений).

Manifest расширяет проблему до «любого интеллектуального продукта» (код, книги, видео, игры) — это **значительно шире**, чем текущий scope Buffy (архитектурное проектирование + код + документация). Это не ошибка, но это делает Manifest **визионерским документом**, а не конкретным архитектурным предложением.

**Оценка:** проблема сформулирована правильно, но масштаб предложения выходит далеко за пределы текущей архитектуры Buffy.

## 3. Architectural Assessment

**Насколько решение соответствует архитектуре Buffy?**

### Что совместимо

| Аспект | Совместимость | Комментарий |
|--------|---------------|-------------|
| Иерархический подход (абстракции на разных уровнях) | ✅ | Buffy Forge уже использует L0-L5 иерархию |
| Разделение ответственности (каждый Forge — одна задача) | ✅ | Соответствует принципу Separation of Concerns |
| Organizational Memory как фундамент | ✅ | Manifest's «Knowledge никогда не теряется» ≈ OM RFC §3 |
| Жизненный цикл (идея → реализация → эволюция) | ✅ | Buffy Forge описывает тот же цикл |

### Что несовместимо

| Аспект | Несовместимость | Тяжесть |
|--------|-----------------|---------|
| **Конфликт имён «Forge»** | Buffy Forge — метасистема архитектурного проектирования; Manifest Forge — runtime производственная линия. Одно слово = две несовместимые сущности. | 🔴 CRITICAL |
| **Scope** | Manifest: «создание любых интеллектуальных продуктов»; Buffy: проектирование архитектуры + генерация кода. Manifest в 10× шире. | 🟡 HIGH |
| **Runtime vs Design-time** | Manifest: runtime-производство (код, видео, книги); Buffy Forge §12 явно исключает runtime-исполнение. | 🟡 HIGH |
| **Factory как надстройка над Forge** | Buffy Forge сам является «фабрикой» без отдельного слоя «Factory» над ним. | 🟢 MEDIUM |

**Оценка:** Manifest совместим с Buffy на философском уровне (иерархия, разделение ответственности, память), но несовместим на уровне терминологии и scope.

## 4. Strongest Decisions

Самые сильные архитектурные решения документа:

1. **Project как экосистема** — «проект состоит не только из кода: идеи, исследования, архитектура, документация, память, решения, знания, артефакты». Это точно отражает философию Buffy и расширяет её.

2. **Knowledge никогда не теряется** — «становится частью Organizational Memory». Прямое соответствие OM RFC v5.92.0.

3. **Prompt — нижний уровень, не центр архитектуры** — «Prompt давно перестаёт быть центром архитектуры». Это зрелое понимание: ценность в иерархии (Skill → Tool → Module → Engine → Forge), а не в отдельных промтах.

4. **Иерархия абстракций** — Workspace → Project → Knowledge/Artifact → Factory → Forge → Engine → Module → Tool → Skill → Prompt. Даже если конкретные имена конфликтуют, сама идея многоуровневой системы правильная.

## 5. Architectural Risks

| Риск | Вероятность | Влияние | Описание |
|------|------------|---------|----------|
| **Naming fork** | 🔴 High | 🔴 Critical | Если оба предложения (Buffy Forge и Manifest) реализовывать одновременно, слово «Forge» будет означать две разные вещи в одной кодовой базе. Это создаст постоянную путаницу в коде, документации и коммуникации. |
| **Scope creep** | 🟡 Medium | 🟡 High | Manifest расширяет scope Buffy с «архитектурное проектирование» до «любой интеллектуальный продукт» (видео, книги, игры). Это требует ресурсов, которые сейчас не предусмотрены. |
| **Over-abstraction** | 🟡 Medium | 🟡 Medium | 10-уровневая иерархия (Workspace OS → ... → Prompt) до реализации конкретных механик может привести к «архитектуре ради архитектуры». |
| **Дублирование с Buffy Forge** | 🟡 Medium | 🟡 High | Architecture Forge (Manifest) ≈ Architecture Forge L2 (Buffy) + DIS + ARB + AG — но под другим именем и с другой семантикой. |
| **Размывание терминологии** | 🟢 Low | 🟡 Medium | Engine в Buffy = KnowledgeEngine (поисковый движок); Engine в Manifest = оркестратор процесса. Разные значения одного слова в одной платформе. |

## 6. Missing Concepts

Какие архитектурные сущности отсутствуют в Manifest:

1. **Конкретные контракты между Forge'ами.** Manifest описывает, ЧТО каждый Forge делает, но не КАК они взаимодействуют. Buffy Forge решает это через EventBus и явные события (`rfc.approved`, `drift.detected`).

2. **Механизм разрешения конфликтов.** Что происходит, когда Architecture Forge и Code Forge противоречат друг другу? Buffy Forge решает это через ARB как высшую инстанцию.

3. **Decision Trace.** Manifest не описывает, как отслеживать ПОЧЕМУ было принято то или иное решение. Buffy Forge + DIS предусматривают DecisionTrace (Evolution v5.93.0, I-2).

4. **Authority Model.** Кто имеет право финального решения? В Buffy: ARB как архитектурный суд. В Manifest: не определено.

5. **Границы между Project и Factory.** Manifest говорит «Factory ничего не знает о конкретном проекте», но и «Project содержит Factory». Это противоречие: если Factory универсальна, она не может быть внутри Project; если она внутри Project, она не может быть универсальной.

6. **Конкретные структуры данных.** Manifest — чистая концепция без схем, таблиц, API. Для сравнения: RFC OM v1 (v5.92.0) содержит полную схему Memory Store, SQL-запросы, Knowledge Graph.

## 7. Alternative Designs

Минимум три альтернативы:

### Альтернатива A: Интегрировать Manifest как расширение Buffy Forge

**Суть:** не создавать отдельную «Factory», а добавить уровень абстракции в Buffy Forge: Workspace → Project как организационные контейнеры над существующими L0-L5.

**Плюсы:**
- Нет конфликта имён
- Использует существующую инфраструктуру (OM, EventBus, KnowledgeEngine)
- Workspace/Project органично расширяют Buffy

**Минусы:**
- Не покрывает «любые интеллектуальные продукты» (видео, книги) — но это и не нужно сейчас
- Требует редизайна Buffy Forge §3

**Рекомендация:** самая чистая альтернатива.

---

### Альтернатива B: Переименовать Manifest → «Scenario OS» или «Pipeline OS»

**Суть:** сохранить идею Manifest, но полностью переименовать все сущности, чтобы избежать конфликта с Buffy Forge. Например: не «Forge», а «Mill» или «Pipeline»; не «Factory», а «Orchestrator» или «Workflow».

**Плюсы:**
- Нет конфликта имён с Buffy Forge
- Сохраняет визионерскую ценность Manifest

**Минусы:**
- Два набора имён для очень похожих концепций — когнитивная нагрузка
- Всё равно scope значительно шире текущего

---

### Альтернатива C: Отклонить Manifest, использовать Buffy Forge как есть

**Суть:** Buffy Forge (L0-L5) уже покрывает полный жизненный цикл архитектурного знания. Manifest добавляет мало нового к тому, что уже спроектировано.

**Плюсы:**
- Нет дополнительной сложности
- Buffy Forge уже документирован, зарегистрирован, прошёл ревью

**Минусы:**
- Теряет визионерскую ценность Manifest (Workspace OS, Project как экосистема)
- Manifest содержит идеи (Prompt — нижний уровень, не центр), которые стоит сохранить

## 8. Long-term Evolution

**Как будет выглядеть эта подсистема через 1, 3, 5 лет?**

### Через 1 год
- Если реализовать как Альтернативу A: Workspace → Project появляются как организационные контейнеры в Buffy. Factory/Forge Manifest НЕ реализуется как отдельная система.
- Конфликт имён решён: «Forge» означает только Buffy Forge (L0-L5).

### Через 3 года
- L0-L5 Buffy Forge полностью автоматизированы. Цикл Idea → Knowledge → Architecture → Implementation → Validation → Evolution работает.
- Manifest-идея «любого интеллектуального продукта» может быть пересмотрена: если Buffy научилась проектировать архитектуру, может ли она проектировать книгу? Вероятно, да — как новый L2+ extension.

- Но под ЕДИНОЙ терминологией Buffy Forge, без отдельной «Factory».

## 11. Оценка Factory vs Scenario

### Пользователь предложил разделение:

- **Factory** — проактивная: пользователь задаёт тему, система сама производит результат («контент-завод»)
- **Scenario** — реактивная/обслуживающая: помогает пользователю реализовать то, что он сам хочет, возможно с Factory внутри

### Архитектурная оценка:

**Существует ли прецедент такого разделения в Buffy?**

- **Частично.** `prompt_dispatcher.py` + EventBus — это реактивная система: пользователь отправляет промт → диспетчер маршрутизирует → агент выполняет. Это Scenario.
- **НЕТ прецедента проактивной Factory.** Buffy не имеет механизма «задал тему → система сама производит без участия пользователя». Даже Buffy Forge требует ARB-решений (человек + AI).

**Обосновано ли разделение архитектурно?**

Различие между проактивной («сама делает») и реактивной («помогает делать») системами — **реальное архитектурное различие**. Оно влияет на:
- Модель инициативы (кто запускает процесс)
- Модель контроля (кто принимает промежуточные решения)
- Модель обратной связи (когда пользователь вмешивается)

**Однако:** в существующей архитектуре Buffy это различие покрывается без остатка:
- **Scenario** = существующий механизм промтов (пользователь → диспетчер → агент)
- **Factory** = НЕ СУЩЕСТВУЕТ в Buffy, и Manifest не предлагает конкретного механизма инициативы (как именно Factory «сама производит» без участия пользователя?)

**Вывод:** разделение Factory vs Scenario — **архитектурно валидная идея**, но она сырая. Manifest не описывает, КАК Factory проявляет проактивность. Без конкретного механизма инициативы «Factory» — это просто переименованный Workflow/Orchestrator. **Не заслуживает отдельной сущности на данном этапе.**

## 12. Final Verdict

### Вердикт: **REJECT WITH ALTERNATIVE**

(По шкале promt57; эквивалент ARB Constitution: CHANGES REQUIRED — архитектура Manifest НЕ принимается в текущей форме, но визионерское ядро валидно)

**Почему REJECT, а не CHANGES REQUIRED:** ARB Constitution определяет CHANGES REQUIRED как «архитектура правильная, но нужны правки». Здесь ситуация иная: naming collision «Forge» делает архитектуру Manifest **несовместимой** с существующей — это не правки, а необходимость полного переименования всех сущностей. Сама идея «runtime Factory» ортогональна design-time Buffy Forge. Поэтому вердикт: REJECT WITH ALTERNATIVE — НЕ реализовывать Manifest как отдельную систему, но принять визионерское ядро и интегрировать в Buffy Forge.

### Обоснование

Factory/Forge Manifest содержит валидное визионерское ядро:
- Workspace OS как среда полного жизненного цикла проекта
- Project как экосистема (не только код)
- Prompt как нижний уровень, не центр архитектуры
- Многоуровневая иерархия абстракций

**Но в текущей форме документ не может быть принят по трём причинам:**

| # | Причина | Тяжесть |
|---|---------|---------|
| 1 | **Конфликт имён «Forge»** — Buffy Forge (RFC-BF-001) уже использует «Forge» для метасистемы архитектурного проектирования. Manifest предлагает «Forge» для runtime производственной линии. Это две несовместимые семантики одного слова. | 🔴 BLOCKING |
| 2 | **60-70% предложенного уже спроектировано в Buffy** — под другими именами. Architecture Forge (Manifest) ≈ Buffy Forge L2 + DIS + ARB + AG. Knowledge ≈ OM. Review Engine ≈ ARB Constitution. | 🟡 MAJOR |
| 3 | **Отсутствие конкретных механик** — Manifest не содержит схем данных, API, контрактов между уровнями, механизма инициативы Factory. Это чистая концепция без implementation path. | 🟡 MAJOR |

### Required Actions (для принятия)

1. **Переименовать все сущности Manifest** — «Forge» → другой термин (например, «Mill», «Pipeline», «Line»). Или пересмотреть Buffy Forge на предмет расширения семантики «Forge» до «любой мастерской» (что потребует редизайна RFC-BF-001).

2. **Сузить scope** — исключить Video Forge, Book Forge, Game Forge (не входят в текущий scope Buffy). Оставить: Idea, Research, Architecture, Code, Test, Documentation.

3. **Определить контракты между уровнями** — как Forge'ы взаимодействуют (EventBus? Direct API?). Минимум: формат события на каждом переходе.

4. **Разрешить противоречие Project ↔ Factory** — если Factory универсальна, она не может быть внутри Project. Либо Factory — общая для всех проектов, либо «Project blueprint» для каждого проекта.

5. **Определить механизм проактивности Factory** — если Factory «сама производит», КАК она узнаёт, что пора производить? Триггеры? Расписание? Завершение предыдущего Forge'а?

6. **Интегрировать с Buffy Forge, а не дублировать** — Альтернатива A (см. §7): Workspace → Project как организационные контейнеры над L0-L5 Buffy Forge.

## 14. Рекомендация ARB

**Не реализовывать Manifest как отдельную систему.** Вместо этого:

1. **Принять визионерское ядро** (Workspace OS, Project как экосистема, Prompt как нижний уровень) как философию Buffy.
2. **Интегрировать организационные концепции** (Workspace → Project) в Buffy Forge как контейнеры над L0-L5.
3. **Отклонить терминологию Manifest** для «Forge» и «Engine» — они уже заняты.
4. **Сохранить Factory/Forge Manifest** как визионерский документ (не RFC, а Vision), к которому Buffy может эволюционировать.
5. **CON-39 в LESSONS.md** — урок: «визионерские документы требуют AFC до присвоения имён; называть новую сущность именем существующей — архитектурный долг с первого дня».
