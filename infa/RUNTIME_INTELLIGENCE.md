1. Executive Summary

Современная оценка AI-систем пережила парадигмальный сдвиг: от изолированных тестов «модель-в-вакууме» (HumanEval, MMLU) к оценке сквозных рабочих процессов (Workflows) и агентных систем в реальных средах (SWE-bench Pro, Terminal-Bench, OpenHands Index) [[2***REMOVED******REMOVED***, [[38***REMOVED******REMOVED***.

Главный инженерный вывод исследования: оценивать необходимо не модель, а конфигурацию рабочего процесса (Workflow Execution Trace). Модель является лишь одним из компонентов в цепочке: Provider → Model → Runtime → Adapter → Configuration → Task → Workflow → Result. Любая система оценки, игнорирующая влияние промпт-инжиниринга, логики повторных попыток (retry logic) и инструментария (MCP/ACP), дает нерепрезентативные результаты.

Для построения универсальной, будущеустойчивой системы предлагается архитектура, основанная на принципах наблюдаемости (OpenTelemetry), многокритериальном принятии решений (MCDM) с персонализацией через контекстные бандиты, и строгом версионировании всех артефактов оценки.

3. Каталог метрик

Каталог расширен с учетом инженерной практики 2026 года.

Качество (Quality)

Функциональное: Pass@k, процент пройденных интеграционных тестов.

Архитектурное: Дельта цикломатической сложности, соблюдение принципов SOLID (оценка через LLM-as-a-Judge со строгим рубрикатором).

Семантическое: AST-подобие (абстрактное синтаксическое дерево) относительно эталонного решения, а не просто текстовое совпадение.

Чистота: Количество введенных уязвимостей (CVE-паттерны), утечек секретов (secrets leakage).


Производительность (Performance)

Латентность: Time to First Token (TTFT), Time to Last Token (TTLT), общая wall-clock time выполнения задачи.

Эффективность агента: Количество итераций (cycles), количество успешных/неуспешных tool calls, средняя длина диалога до решения.

Конкурентность: Throughput (задач в секунду) при заданном уровне параллелизма.


Экономика (Economics)

Прямые затраты: Стоимость одного успешного решения (Cost per Success), стоимость одной итерации.

Эффективность кэша: Cache hit rate (процент переиспользованных токенов).

Потери: Стоимость «брошенных» (abandoned) или зацикленных (looping) выполнений.


Надёжность (Reliability)

Стабильность: Дисперсия результатов при одинаковых входных данных (temperature sensitivity).

Устойчивость: Процент успешных восстановлений после ошибки инструмента (tool call retry success rate).

Галлюцинации: Частота вызова несуществующих API или вымышленных файлов.


Контекст и Память (Context & Memory)

Утилизация: Процент заполнения контекстного окна (Context window utilization %).

RAG-эффективность: Precision и Recall извлеченных фрагментов кода/документации.

Следование инструкциям: Оценка соблюдения негативных ограничений (negative constraints).


Инструменты (Tooling)

Совместимость: Процент успешных вызовов через MCP (Model Context Protocol) или ACP.

Точность: Parameter extraction accuracy (правильность заполнения аргументов функции).


UX и Человеческий фактор (Human-in-the-loop)

Вмешательство: User intervention rate (сколько раз пользователь прервал или исправил агента).

Переформулирование: Prompt rewrite count (сколько раз пришлось менять запрос для получения результата).

Принятие: Acceptance rate (процент кода, принятого пользователем без правок).

5. Персонализация

Глобальные лидерборды (например, Chatbot Arena) часто не отражают реальную пользу для конкретного разработчика. Исследования 2025–2026 гг. показывают, что персонализация может полностью перевернуть глобальные рейтинги: модель, занимающая 10-е место глобально, может быть абсолютным лидером для конкретного стека (например, Rust + WASM) [[32***REMOVED******REMOVED***.

Учитываемые факторы:

1. Технический контекст: Язык программирования, фреймворк, размер кодовой базы.


2. Стиль разработки: Предпочтение многословных комментариев vs. лаконичного кода, строгость типизации.


3. Бизнес-ограничения: Допустимая задержка (latency budget), лимит стоимости на задачу, требования к приватности (локальная vs. облачная модель).



Алгоритмы персонализации:

Bayesian Personalized Ranking (BPR): Обновление апостериорного распределения предпочтений пользователя на основе неявной обратной связи (например, пользователь отклонил 3 предложения модели А, но принял 5 от модели Б).

Иерархические байесовские модели (Hierarchical Bayesian Models): Позволяют использовать «коллективный prior» (статистику сообщества) для новых пользователей, быстро сходясь к их индивидуальным весам по мере накопления данных. Это решает проблему холодного старта.

Preference-Aware Rubric Learning: Динамическая корректировка весов критериев в LLM-as-a-Judge на основе истории решений пользователя [[28***REMOVED******REMOVED***.

6. Что именно нужно оценивать

Инженерно оправдан только Вариант 2 (и его расширения).

Оценка изолированной «Модели» (Вариант 1) в 2026 году является антипаттерном. Пользователь взаимодействует не с голыми весами нейросети, а с системой. Модель, занимающая первое место в LiveCodeBench, может проигрывать на практике из-за плохой поддержки JSON-вывода в конкретном Runtime или агрессивного truncation в Adapter'е.

Единица оценки: Workflow Execution Trace (хэш-сумма конфигурации).
Уровень оценки должен быть иерархическим:
Provider → Model (Version) → Runtime Engine → Adapter (Prompt/Tool) → Configuration (Temp, Top_P) → Task Context → Workflow Logic → Result.

Только оценивая весь этот пайплайн как единое целое (через сквозные трассировки), можно получить воспроизводимые и значимые метрики. Изменение промпт-шаблона или версии фреймворка агента должно рассматриваться как смена оцениваемого объекта.

8. Локальная и коллективная статистика

Совмещение трех уровней статистики требует архитектуры, обеспечивающей приватность и репрезентативность.

1. Локальная статистика (Personal): Хранится локально (SQLite/DuckDB). Содержит полные трассировки и индивидуальные веса MCDM. Никакие сырые данные не покидают машину пользователя.


2. Статистика команды (Team): Агрегированные, анонимизированные метрики. Например: «В нашем репозитории на TypeScript модель X дает на 15% меньше правок, чем модель Y». Используется гомоморфное шифрование или простая агрегация на доверенном сервере команды.


3. Общая статистика сообщества (Community): Построена на принципах Federated Evaluation и Differential Privacy. Сообщество обменивается не кодом или промптами, а векторами признаков и результатами оценки на стандартизированных, обезличенных задачах (Golden Datasets).



Архитектурный паттерн: Иерархическая байесовская модель. Глобальный лидерборд задает априорное распределение (prior). Локальная система обновляет его до апостериорного (posterior) на основе данных конкретного разработчика. Это обеспечивает точные рекомендации даже при малом объеме локальных данных.

9. Архитектурные выводы

Существующие разрозненные инструменты не являются оптимальными, но и изобретать велосипед не нужно. Оптимальная архитектура — это Observability-First Evaluation Orchestrator, построенный на проверенных индустриальных стандартах.

Предлагаемая архитектура (5 слоев):

1. Instrumentation Layer (Сбор): Автоматическая OpenTelemetry-инструментализация AI Runtime. Перехватывает все вызовы моделей, инструментов (MCP), тайминги и токены. Генерирует уникальный Trace ID и Config Hash.


2. Evaluation Engine (Анализ): Асинхронный конвейер.

Детерминированные проверки: Парсинг логов, проверка exit codes, подсчет токенов.

LLM-as-a-Judge: Запускается только для сложных метрик (качество рефакторинга) с использованием строго версионированных рубрикаторов (Rubric Versioning), чтобы избежать дрейфа оценок.



3. Metrics Store (Хранение): Колоночная база данных (ClickHouse или DuckDB), оптимизированная для быстрых агрегаций многомерных временных рядов и трассировок.


4. Personalization & Ranking Service (Принятие решений): Сервис, реализующий MCDM (например, TOPSIS) и Contextual Bandits. Он берет сырые метрики из хранилища, применяет веса пользователя (явные или выученные) и возвращает персонализированный рейтинг конфигураций для текущей задачи.


5. Version Control Registry (Целостность): Неизменяемый реестр (иммутабельный), который связывает Task Hash + Model Version + Prompt Template Hash + Runtime Version. Гарантирует, что результаты оценки всегда привязаны к конкретной, воспроизводимой конфигурации, предотвращая проблему «движущейся цели» (moving goalposts) [[52***REMOVED******REMOVED***.

10. Рекомендации

1. Откажитесь от оценки «голых» моделей. Всегда оценивайте связку Model + Runtime + Prompt Template.


2. Внедрите строгое версионирование. Любое изменение в промпте, температуре или версии фреймворка агента должно генерировать новый Config Hash.


3. Используйте MCDM (TOPSIS/Pareto), а не скалярные рейтинги. Инженеру важно видеть компромисс: «Эта конфигурация на 20% дороже, но снижает количество итераций на 40%», а не просто абстрактное число "8.5/10".


4. Начните с неявной обратной связи. Не заставляйте разработчиков заполнять анкеты. Используйте edit distance, acceptance rate и prompt rewrite count как основные прокси-метрики качества UX.


5. Защитите приватность по умолчанию. Настройте пайплайны сбора данных на автоматическое маскирование или хэширование фрагментов кода и переменных окружения перед отправкой в любые аналитические хранилища.

11. Возможные направления дальнейших исследований

Динамическая адаптация рубрикаторов LLM-as-a-Judge: Исследование методов, позволяющих системе автоматически калибровать строгость оценки под конкретный домен (например, медицинский код vs. игровой скрипт) без участия человека.

Экономическое моделирование агентов: Разработка метрик "Return on Compute" (RoC) — оценка бизнес-ценности, сгенерированной агентом, относительно стоимости его выполнения в реальном времени.

Обнаружение концептуального дрейфа (Concept Drift) в реальном времени: Алгоритмы для автоматического выявления моментов, когда глобальное обновление модели провайдера (даже без смены версии API) приводит к статистически значимому ухудшению качества на конкретных типах задач [[59***REMOVED******REMOVED***.

🔴 Red Team: Критический аудит собственных выводов

Как Principal Researcher, я обязан подвергнуть сомнению собственные рекомендации:

1. Где исследование может ошибаться: Предположение о надежности LLM-as-a-Judge для оценки «архитектурного качества» может быть чрезмерно оптимистичным. Даже с рубрикаторами, модели склонны к "сговору" (sycophancy) и могут высоко оценивать уверенно написанный, но архитектурно порочный код. Требует проверки: Сравнение оценок LLM-as-a-Judge с оценками старших инженеров-людей на большом наборе данных.


2. Что выглядит красиво только в теории: Использование TrueSkill для ранжирования моделей. На практике шум в парных сравнениях (особенно при оценке кода, где есть объективно правильный ответ) слишком велик, что приводит к раздуванию дисперсии и нестабильным рейтингам. Простой Bradley-Terry или детерминированный Pass@k надежнее.


3. Переусложнение (Overcomplication): Идея отслеживания AST-подобия для каждой правки может оказаться вычислительно неоправданной для больших кодовых баз. Корректировка: Ограничиться AST-анализом только для модульных функций и полагаться на интеграционные тесты (Pass/Fail) для оценки крупных изменений.


4. Сложность внедрения MCDM в реальном времени: Вычисление TOPSIS для каждой рекомендации в IDE может добавить недопустимую задержку. Решение: MCDM должен работать асинхронно для пост-анализа и выбора конфигураций, а не в hot-path генерации кода. В hot-path должны использоваться предварительно вычисленные кэшированные веса (Pareto front lookup).


5. Риск Federated Evaluation: Идея обмена векторами признаков между пользователями может столкнуться с жестким сопротивлением отделов безопасности (InfoSec) в корпоративной среде из-за риска обратного инжиниринга. Корректировка: Для enterprise-сегмента следует рекомендовать исключительно локальную оценку на изолированных Golden Datasets, без обмена данными с сообществом.



Итог аудита: Архитектура остается валидной, но требует строгого разделения на hot-path (минималистичный сбор метрик через OpenTelemetry) и cold-path (сложный MCDM-анализ и LLM-as-a-Judge). Персонализация должна опираться в первую очередь на неявные сигналы, чтобы избежать утомления пользователя.

Исследовательское дополнение: Инвариантные метрики для долгосрочной оценки AI-систем

Дата: 30 июля 2026 г.
Контекст: Продолжение исследования архитектуры универсальной системы оценки
Фокус: Устойчивость метрик к архитектурным сдвигам


---

1. Критерии устойчивости метрик

Прежде чем перечислять метрики, необходимо определить, что делает метрику инвариантной к изменениям архитектуры. Анализ исторических сдвигов (RNN → Transformer → MoE, prompt chaining → agents → MCP, облако → edge) показывает, что устойчивыми оказываются только те метрики, которые удовлетворяют одновременно трём условиям:

Критерий	Суть	Пример нарушения

C1. Task-outcome grounding	Измеряет результат относительно задачи, а не процесс внутри системы	«Количество tool calls» ломается при переходе от MCP к ACP
C2. Representation independence	Не зависит от способа кодирования (токены, эмбеддинги, байты)	«Токены на запрос» меняется с каждым новым токенизатором
C3. Time-normalized economics	Выражена в универсальных единицах (время, деньги, человеческий труд), а не в системных	«Итерации агента» теряют смысл при переходе к speculative execution


Метрика, нарушающая хотя бы один критерий, имеет срок жизни 1–3 года. Метрика, удовлетворяющая всем трём, остаётся релевантной десятилетиями — потому что она укоренена в фундаментальных свойствах информации, экономики и человеческой когниции.


---

2. Иерархия устойчивых метрик

Метрики ранжированы по убыванию устойчивости. Верхние уровни практически не меняются со сменой парадигм; нижние требуют периодической адаптации.

Уровень 0. Абсолютные инварианты (срок жизни: неограничен)

Эти метрики пережили все смены парадигм в истории вычислений и не зависят от того, что находится «внутри» системы.

1. Task Completion Rate (TCR) — бинарный факт достижения цели задачи.
Почему устойчива: Цель задачи определяется человеком и бизнес-контекстом, а не архитектурой системы. Независимо от того, решал ли задачу человек, rule-based система, LLM или агент — результат либо достигнут, либо нет.
Инженерная тонкость: Требует формализуемого определения «достижения цели» через acceptance tests, а не через внутренние эвристики системы.

2. Functional Correctness (FC) — процент прохождения независимых тестов.
Почему устойчива: Тесты — это спецификация, выраженная в коде. Спецификация не меняется при смене генератора. HumanEval, SWE-bench и все последующие бенчмарки построены именно на этом принципе, и он не устарел.
Инженерная тонкость: Тесты должны быть написаны до генерации решения, иначе возникает риск переобучения под тесты.

3. Cost per Successful Outcome (CpSO) — полная стоимость достижения цели в универсальных единицах ($, часы человеческого труда, кВт·ч).
Почему устойчива: Экономика — универсальный язык. Меняются компоненты стоимости (токены, GPU-часы, человеко-часы), но сама метрика остаётся осмысленной.
Инженерная тонкость: Необходимо включать скрытые стоимости: отладку, ревью, исправление регрессий, упущенную возможность.

4. Time-to-Value (TtV) — время от формулировки намерения до получения полезного результата, принятого пользователем.
Почему устойчива: Время — абсолютная величина. Не зависит от того, как результат был получен (одним вызовом модели, цепочкой агентов или гибридно).
Инженерная тонкость: Должно включать время верификации человеком, а не только генерации.

5. Human Intervention Rate (HIR) — частота, с которой пользователь вынужден вмешиваться в процесс.
Почему устойчива: Человек — константа. Его когнитивные ограничения, внимание и терпение не меняются со сменой архитектуры AI. Это, пожалуй, самая устойчивая метрика из всех существующих.
Инженерная тонкость: Измеряется через edit distance, rejection events, prompt rewrites — всё это объективные сигналы, не требующие субъективных оценок.


---

Уровень 1. Фундаментальные инварианты (срок жизни: 10+ лет)

6. Semantic Equivalence Score (SES) — степень семантической эквивалентности решения эталону, измеряемая через независимый оракул (тесты, формальная верификация, AST-изоморфизм).
Почему устойчива: Семантика — это то, что программа делает, а не то, как она написана. Меняются языки, фреймворки, стили, но семантика остаётся.
Инженерная тонкость: AST-подобие — слабая аппроксимация. Надёжнее — поведенческая эквивалентность через property-based testing.

7. Information Efficiency (IE) — отношение полезной информации в решении к объёму входных данных и вычислительных ресурсов.
Почему устойчива: Корни в теории информации Шеннона. Не зависит от того, кодируются ли данные в токенах, эмбеддингах или сырых байтах.
Инженерная тонкость: Практическая аппроксимация — compression_ratio(solution) / compute_cost(solution).

8. Failure Recovery Rate (FRR) — доля сбоев, из которых система восстановилась без вмешательства пользователя.
Почему устойчива: Надёжность — универсальное свойство любых систем, от паровых машин до агентов.
Инженерная тонкость: Требует чёткого определения «сбоя» (ошибка инструмента, галлюцинация, timeout, rate limit).

9. Graceful Degradation Curve (GDC) — как падает качество при увеличении сложности задачи, уменьшении контекста, ухудшении условий.
Почему устойчива: Характеристика кривой — это свойство системы в целом, а не её компонентов.
Инженерная тонкость: Строится через стресс-тестирование на параметризованном семействе задач.


---

Уровень 2. Структурные инварианты (срок жизни: 5–10 лет)

10. Maintainability Delta (MD) — изменение индексов сопровождаемости кода (Cyclomatic Complexity, Maintainability Index, Code Smells count) после вмешательства AI.
Почему устойчива: Метрики качества кода (измеряемые статическим анализом) пережили уже несколько поколений языков программирования.
Инженерная тонкость: Полезен не абсолютный индекс, а дельта — насколько AI улучшил или ухудшил код.

11. Test Coverage Delta (TCD) — изменение покрытия тестами.
Почему устойчива: Тестирование — фундаментальная инженерная практика.
Инженерная тонкость: Покрытие строк — слабая метрика. Надёжнее — покрытие ветвей и мутационное тестирование.

12. Security Regression Rate (SRR) — количество новых уязвимостей (CVE-паттерны, secrets leakage, OWASP Top-10), внесённых решением.
Почему устойчива: Уязвимости — объективное свойство кода, не зависящее от генератора.
Инженерная тонкость: Требует интеграции со SAST/DAST-инструментами.


---

Уровень 3. Контекстно-устойчивые метрики (срок жизни: 2–5 лет)

Эти метрики устойчивы в рамках текущей парадигмы, но могут потребовать переосмысления при смене архитектуры.

13. Acceptance Rate (AR) — процент сгенерированного контента, принятого пользователем без существенных правок.
Риск: Зависит от UX-паттернов IDE. При переходе от inline-completion к агентному режиму может потребовать переопределения.

14. Prompt Rewrite Count (PRC) — сколько раз пользователю пришлось переформулировать запрос.
Риск: В полностью автономных агентных системах пользователь может вообще не писать промптов — метрика теряет смысл.

15. Cache Hit Rate (CHR) — доля переиспользованных вычислений.
Риск: Зависит от механизма кэширования провайдера. При смене протокола кэширования метрика требует перекалибровки.


---

3. Антипаттерны: метрики, которые быстро устаревают

Метрика	Почему неустойчива	Срок жизни

Токены на запрос	Зависит от токенизатора, который меняется у каждого провайдера	1–2 года
Количество tool calls	Зависит от протокола (MCP, ACP, function calling) и granularity инструментов	1–2 года
Количество итераций агента	Зависит от scaffolding и стратегии retry	2–3 года
TTFT / TTLT	Зависит от железа, сети, batching-стратегии провайдера	1 год
Скорость в tokens/sec	Зависит от железа и оптимизаций inference engine	6–12 месяцев
Scores на конкретных бенчмарках (MMLU, HumanEval, GPQA)	Устаревают из-за загрязнения данных и сдвига задач	1–2 года
Количество параметров модели	Не коррелирует с качеством после появления MoE и дистилляции	Уже устарела
Размер контекстного окна в токенах	Зависит от токенизатора; реальная полезная длина — другая метрика	2–3 года


Общий принцип: любая метрика, привязанная к внутренней реализации системы (а не к её взаимодействию с миром), обречена на устаревание.


---

4. Практический вывод: как строить систему на устойчивых метриках

Архитектурный принцип: «Двойной контур оценки»

Система должна иметь два независимых контура метрик:

Контур A — Инвариантный (ядро системы)
Содержит метрики Уровней 0 и 1. Хранится вечно. Используется для:

Долгосрочного сравнения конфигураций

Персонализации (веса пользователя применяются именно к этому контуру)

Публикации агрегированной статистики сообщества

Принятия стратегических решений (какой провайдер, какой Runtime)


Контур B — Адаптивный (периферия)
Содержит метрики Уровней 2 и 3, а также специфичные для текущей парадигмы. Хранится с TTL. Используется для:

Оперативной отладки

Оптимизации текущей конфигурации

A/B-тестирования


Ключевые инженерные решения

1. Нормализация через «задачный эталон».
Каждая метрика должна быть нормирована относительно человеческой производительности на том же наборе задач. Например, не «время ответа 5 секунд», а «0.3× от времени человека». Это делает метрики сравнимыми даже при смене единиц измерения.

2. Разделение «что» и «как».
Метрики Уровня 0 отвечают на вопрос «что достигнуто?». Метрики более низких уровней — «как именно?». Система должна уметь отбрасывать «как» при смене парадигмы, сохраняя «что».

3. Метрики как код, а не как конфигурация.
Каждая метрика должна быть версионируемой функцией с чёткой спецификацией входных данных. Изменение определения метрики = новая версия функции, а не правка старой. Это предотвращает «дрейф метрик» (metric drift).

4. Обязательная проверка на invariance test.
Перед внедрением новой метрики необходимо провести тест: если заменить Runtime на принципиально иной (например, с агентов на single-shot LLM), сохраняет ли метрика смысл? Если нет — метрика принадлежит Контуру B.


---

5. Итоговая рекомендация

Для долгосрочной системы оценки следует построить ядро из пяти метрик Уровня 0:

1. Task Completion Rate — делает ли система свою работу


2. Functional Correctness — правильно ли она это делает


3. Cost per Successful Outcome — какой ценой


4. Time-to-Value — как быстро


5. Human Intervention Rate — насколько это удобно человеку



Эти пять метрик образуют минимальный достаточный набор, который:

переживёт смену парадигм,

покрывает все ключевые аспекты (качество, экономика, скорость, UX),

не требует пересмотра при появлении новых моделей, Runtime или протоколов.


Всё остальное — детализация, адаптация под конкретные домены и операционная аналитика — должно строиться поверх этого ядра, а не вместо него.


---

🔴 Red Team: самокритика

1. Риск абстрагирования до потери смысла. Чрезмерная устойчивость может привести к тому, что метрики станут слишком общими, чтобы различать системы. Например, TCR = 90% у двух систем — но одна решает тривиальные задачи, другая — сложные. Решение: метрики должны применяться не к «системе вообще», а к стратифицированным когортам задач (по сложности, домену, стеку).


2. Human Intervention Rate — не всегда хорошая метрика. В некоторых сценариях (например, exploratory coding) частое вмешешательство — это норма, а не дефект. Решение: метрика должна интерпретироваться в контексте типа задачи, а не абсолютно.


3. Cost per Successful Outcome игнорирует риск. Две системы могут иметь одинаковую среднюю стоимость, но одна — стабильна, другая — даёт редкие катастрофические выбросы. Решение: необходимо дополнять CpSO дисперсией и хвостовыми перцентилями (p95, p99).


4. Time-to-Value зависит от определения «ценности». Если ценность субъективна, метрика становится неинвариантной. Решение: ценность должна определяться через объективные критерии приёмки (тесты, acceptance criteria), зафиксированные до начала задачи.



Итог аудита: Предложенный набор метрик действительно устойчив, но только при условии их применения к стратифицированным когортам задач и в комбинации с дисперсионными показателями. Без этих оговорок система рискует стать либо слишком абстрактной, либо вводящей в заблуждение.

Runtime Intelligence: Фундаментальное инженерное исследование

Дата: 30 июля 2026 г.
Статус: Независимое исследование архитектуры AI Runtime Intelligence
Фокус: Формирование инженерной дисциплины уровня DevOps/SRE для AI-систем


---

1. Executive Summary

Runtime Intelligence — это инженерная дисциплина, объединяющая наблюдаемость (Observability), оценку производительности (Evaluation), анализ рабочих процессов (Workflow Analysis) и адаптивное управление (Adaptive Control) для AI Runtime и агентных систем.

Ключевое отличие от смежных областей:

Observability отвечает на вопрос «что происходит?»

Evaluation отвечает на вопрос «насколько хорошо?»

Runtime Intelligence отвечает на вопрос «почему это происходит, как это воспроизвести и как улучшить?»


Это не просто мониторинг или бенчмаркинг. Это цифровой двойник (Digital Twin) AI Runtime, позволяющий воспроизводить, анализировать и оптимизировать поведение системы в любых условиях.

Главный инженерный вывод: Современным AI-системам не хватает формализованной модели выполнения (Execution Model) и стандартизированного формата трассировки (Trace Format). Без этого невозможно построить воспроизводимую оценку, эффективную отладку или адаптивную оптимизацию.

APM	Производительность приложений	Реальное время	New Relic, AppDynamics

Runtime Intelligence	Полное понимание поведения системы + воспроизводимость + оптимизация	Непрерывно + анализ	Не существует как единая система


Критическое наблюдение: Ни одна существующая система не покрывает все три аспекта Runtime Intelligence одновременно. LangSmith фокусируется на трассировке, Braintrust — на оценке, OpenTelemetry — на телеметрии. Но ни одна не предоставляет формальную модель выполнения, позволяющую воспроизводить и сравнивать поведение систем.

5.3 Иерархическая модель (Multi-Agent)

Для multi-agent систем необходима иерархическая модель:

Runtime (координатор)  
├── State: EXECUTING  
├── Agent A  
│   ├── State: WAITING_TOOL  
│   └── Sub-task: "Search database"  
├── Agent B  
│   ├── State: EXECUTING  
│   └── Sub-task: "Analyze results"  
└── Agent C  
    ├── State: WAITING_USER  
    └── Sub-task: "Confirm decision"

Каждый агент имеет собственную машину состояний, но подчиняется общей логике Runtime.

5.4 Существующие модели

Аналогии из других областей:

1. BPMN (Business Process Model and Notation) — стандарт для моделирования бизнес-процессов. Использует:

Tasks, Events, Gateways

Pool и Lane для различных участников

Подпроцессы для иерархии



2. Statecharts (Harel) — расширение конечных автоматов:

Иерархические состояния

Параллельные состояния

History states



3. Petri Nets — математическая модель для распределенных систем:

Places (состояния)

Transitions (события)

Tokens (ресурсы)




Применимость к AI Runtime:

BPMN слишком тяжеловесен для динамических агентных систем

Statecharts хорошо подходят для одиночных агентов, но сложны для координации

Petri Nets мощны для анализа, но сложны для реализации


Вывод: Необходима гибридная модель, сочетающая:

Иерархические состояния (из Statecharts)

Явные события и переходы (из FSM)

Поддержку параллелизма (из Petri Nets)

Простоту реализации (из простых FSM)

Проиграть события в хронологическом порядке

Для LLM calls — использовать записанные responses (если доступны) или повторить вызовы

Для tool calls — воспроизвести с теми же параметрами



3. Валидация:

Сравнить финальное состояние с outcome

Проверить метрики (допустимы небольшие отклонения для недетерминированных моделей)




Проблемы воспроизводимости:

1. Недетерминированность LLM. Даже с одинаковыми параметрами результаты могут отличаться.

Решение: Использовать temperature=0 для воспроизводимости



2. Внешние зависимости. Tool calls могут зависеть от внешних систем (API, базы данных).

Решение: Mock внешних систем при воспроизведении

Решение: Сохранять snapshots внешних данных



3. Временные зависимости. Некоторые операции зависят от времени (rate limits, timeouts).

Решение: Использовать virtual time при воспроизведении

8. Memory Architecture

Память — это не просто "контекст", это состояние, которое мутирует во времени. Оценка Runtime без учета его архитектуры памяти некорректна, так как две одинаковые модели с разной стратегией управления памятью покажут радикально разные результаты на длинных задачах.

Типы памяти в AI Runtime:

1. Session Memory (Краткосрочная): Буфер сообщений текущего диалога. Ограничена контекстным окном. Стратегии: FIFO, summarization, sliding window.


2. Working Memory (Оперативная): Внутреннее состояние агента (текущий план, извлеченные факты, переменные). Часто реализуется через скрытые промпты или специальные токены мышления (thinking tokens).


3. Long-Term Memory (Долгосрочная):

Vector Memory: Эмбеддинги прошлых взаимодействий для семантического поиска (RAG).

Graph Memory: Сущности и связи между ними (Knowledge Graph), позволяющая отвечать на вопросы о связях ("Что делал пользователь на прошлой неделе?").

Key-Value / Relational: Структурированные факты (предпочтения пользователя, настройки).



4. Episodic Memory: Запись конкретных успешных или неуспешных эпизодов выполнения задач для последующего few-shot обучения или retrieval.



Влияние на оценку:
Сравнивать два Runtime можно только при эквивалентных состояниях памяти. Если один агент использует Graph Memory, а другой только Vector Memory, разница в результатах может быть обусловлена архитектурой памяти, а не качеством базовой модели.
Решение: В ExecutionContext (из раздела 6) должен быть включен memory_state_hash — хэш-сумма состояния памяти на момент начала задачи, чтобы гарантировать воспроизводимость условий.

9. Storage Architecture

Разнородность данных Runtime Intelligence требует полиглотного хранения (Polyglot Persistence). Использование одной СУБД для всего приведет к деградации производительности или стоимости.

Тип данных	Характеристики	Оптимальное хранилище	Обоснование

Events / Telemetry	Высокая скорость записи, append-only, временные ряды	ClickHouse или Apache Kafka + TimescaleDB	Колоночное хранение обеспечивает молниеносную агрегацию по временным интервалам.
Workflow Execution Traces	Иерархические JSON/Protobuf, требуют сложных запросов по путям	DuckDB (локально) или MongoDB / PostgreSQL (JSONB) (централизованно)	Поддержка полуструктурированных данных и мощные операторы для работы с JSON-путями.
Analytics / Metrics	Агрегированные данные для дашбордов (Cost, Latency, TCR)	ClickHouse или Parquet файлы в Object Storage	Дешево, быстро, идеально для OLAP-запросов.
Workflow Graphs / Dependencies	Связи между задачами, агентами, артефактами	Neo4j или Amazon Neptune	Нативная поддержка обхода графов (Cypher), поиск причинно-следственных связей.
Artifacts (Code, Images, Logs)	Большие бинарные или текстовые файлы	Object Storage (S3, MinIO) с дедупликацией по Content-Addressable (SHA-256)	Дешево, масштабируемо, неизменяемо.
State / Checkpoints	Быстрое чтение/запись, низкая латентность, временные данные	Redis или SQLite (для локальных ранов)	In-memory скорость для восстановления состояния агента после сбоя.
Knowledge / Embeddings	Векторный поиск для RAG и семантического анализа трассировок	Qdrant, Milvus или pgvector	Оптимизированы для HNSW-поиска и фильтрации по метаданным.


Архитектурный паттерн: CQRS (Command Query Responsibility Segregation). Запись событий идет в быстрый поток (Kafka), который асинхронно материализует данные в специализированные хранилища (ClickHouse для метрик, S3 для артефактов, Neo4j для графов).

10. Versioning Strategy

Воспроизводимость невозможна без строгого версионирования каждого артефакта, влияющего на результат. Предлагается гибридный подход: Semantic Versioning для кода и Content-Addressable Storage (CAS) для данных.

Артефакт	Стратегия версионирования	Пример

Runtime / Framework	SemVer (Major.Minor.Patch)	openhands@0.9.1
Model	Provider + Name + Date/Version	anthropic/claude-3-5-sonnet-20241022
Prompt Template	CAS (SHA-256 хэш содержимого)	sha256:a1b2c3d4...
Configuration	CAS (хэш нормализованного JSON)	sha256:e5f6g7h8...
Tool / Plugin	SemVer + CAS манифеста	web_search@1.2.0 (sha256:...)
Knowledge Base	Хэш состояния индекса (Dataset Version)	kb_v4_2024-07-30
Workflow Definition	CAS (хэш DAG/WEM спецификации)	sha256:i9j0k1l2...
Memory State	Хэш снапшота памяти на момент старта	mem_sha256:m3n4o5p6...


Ключевая концепция: Reproducibility Hash (ReproHash)
Для любой оценки вычисляется единый ReproHash = SHA256(Model + Prompt_Hash + Config_Hash + Tool_Versions + Memory_State_Hash). Две оценки с одинаковым ReproHash гарантированно выполнялись в идентичных условиях. Любое изменение в провайдерском API (даже без смены версии модели) должно приводить к генерации нового ReproHash через обновление Config_Hash.

12. White Spots (Неисследованные области)

1. Детерминированный реплей недетерминированных систем: Не существует общепринятого стандарта "записи и воспроизведения" (record & replay) для агентных систем, где LLM-ответы по определению стохастичны, а внешние API меняют состояние.


2. Экономика циклов агентов: Метрики оценивают итоговую стоимость, но нет моделей для прогнозирования стоимости на основе графа выполнения до его завершения (предиктивный budget enforcement).


3. Кросс-платформенная миграция состояния: Как перенести "память" и "контекст" агента из одного Runtime (например, OpenDevin) в другой (например, Cursor) без потери смысла? Формат интероперабельности памяти не исследован.


4. Оценка "негативной работы": Сколько времени/денег агент потратил на тупиковые ветки рассуждений (hallucinated tool calls, infinite loops) перед тем, как прийти к верному решению? Текущие метрики это усредняют, скрывая неэффективность.

Фаза 1 (0-6 мес.): Стандартизация телеметрии. Разработка и утверждение расширения OpenTelemetry Semantic Conventions специально для AI Agent Events (tool calls, memory ops, planning steps).

14. Red Team Audit (Критический аудит)

Как Distinguished Architect, я обязан найти слабые места в предложенной архитектуре:

1. Риск экспоненциального роста стоимости хранения.
Критика: Сохранение полных Workflow Execution Traces со всеми артефактами, логами и снапшотами памяти для каждого выполнения быстро приведет к терабайтам данных и огромным счетам за S3/ClickHouse.
Митигация: Внедрить строгую политику TTL (Time-To-Live) и семплирования. Хранить полные трассировки только для failed tasks, edge cases и случайно выбранных 1% успешных tasks. Для остальных хранить только агрегированные метрики.


2. Переусложнение (Overengineering) Capability Detection.
Критика: Динамическое зондирование (probing) каждого нового Runtime на все возможные возможности может быть медленным, ненадежным и вызывать ложные срабатывания (false positives) из-за сетевых сбоев или rate limits.
Митигация: Использовать декларативные манифесты возможностей, предоставляемые самими разработчиками Runtime, а динамическое зондирование применять только как механизм валидации (validation), а не первичного обнаружения.


3. Иллюзия воспроизводимости (Reproducibility Illusion).
Критика: Даже при полном совпадении ReproHash, провайдеры моделей могут тихо обновить веса или изменить промпт-хакинг на уровне API, что сделает воспроизведение невозможным без ведома системы.
Митигация: Явно документировать, что ReproHash гарантирует воспроизводимость нашей конфигурации, но не контролирует "черный ящик" провайдера. Для критичных задач требовать использования open-weight моделей, развернутых локально.


4. Сложность внедрения MCDM и Contextual Bandits.
Критика: Алгоритмы вроде TOPSIS или байесовских бандитов требуют тонкой настройки весов и гиперпараметров. В реальных условиях разработчики не будут вручную настраивать матрицы предпочтений.
Митигация: Предоставлять готовые, предобученные профили ("Profile: Cost-Optimized Startup", "Profile: Enterprise Security-First"), которые пользователь выбирает одним кликом, а система уже использует их как prior для бандитов.


5. Нагрузка на Runtime (Observability Tax).
Критика: Перехват каждого tool call, сериализация памяти и отправка событий могут добавить 10-20% оверхеда к латентности, что неприемлемо для real-time приложений.
Митигация: Инструментация должна быть реализована на уровне eBPF или через легковесные sidecar-прокси с буферизацией и пакетной отправкой (batching), а не через синхронные вызовы в коде приложения.

15. Итоговое заключение

Runtime Intelligence не должна быть "еще одним дашбордом для просмотра токенов". Это фундаментальная инженерная дисциплина, требующая строгого подхода к данным, состояниям и воспроизводимости.

Предложенная архитектура отвергает идею оценки "голых моделей" в пользу оценки Workflow Execution Trace с жестким версионированием (ReproHash). Использование полиглотного хранения, событийной шины и разделения на инвариантные и адаптивные метрики обеспечивает систему устойчивостью к будущим изменениям в архитектуре AI (переход к агентам, новым протоколам вроде MCP, локальным SLM).

Главный риск — не техническая невозможность, а операционная сложность и стоимость хранения данных. Успех зависит от строгого применения семплирования, асинхронной обработки и фокуса на инвариантных метриках (Уровень 0: Task Completion, Functional Correctness, Cost per Success, Time-to-Value, Human Intervention Rate), которые переживут любую смену технологических парадигм.

Введение: Смена парадигмы

Мы живём в эпоху, когда AI-системы перестали быть просто моделями. Сегодня это сложные распределённые агентные системы, объединяющие LLM, инструменты (MCP/ACP), память и динамические рабочие процессы. Но наши методы оценки и отладки всё ещё застряли в прошлом десятилетии.

Проблема: Мы оцениваем модели в вакууме (HumanEval, MMLU), а в продакшене страдаем от непредсказуемого поведения агентов, которые зацикливаются, тратят деньги на бесполезные вызовы инструментов и теряют контекст через 10 итераций.

Решение: Новая инженерная дисциплина — Runtime Intelligence. Это не мониторинг и не бенчмаркинг. Это цифровой двойник вашего AI Runtime, позволяющий отвечать на три главных вопроса:

1. Почему агент повёл себя именно так?


2. Как воспроизвести это поведение для отладки?


3. Как улучшить систему на основе данных?




---

Глава 1. Почему существующие подходы не работают

1.1. Оценка модели ≠ Оценка системы

Представьте, что вы сравниваете два автомобиля. Один — спорткар с мощным двигателем, но летней резиной. Второй — седан с обычным мотором, но с полным приводом и зимними шинами. В снегопад седан уверенно объедет спорткар.

То же самое с AI-системами. Модель — это только двигатель. Результат зависит от:

Provider → Model → Runtime → Adapter (Prompt/Tools) → Configuration → Task → Workflow → Result

Ошибка на любом уровне (например, плохой промпт-шаблон или агрессивный truncation) превращает топовую модель в посредственного агента.

Вывод: Оценивать изолированную модель — антипаттерн. Нужно оценивать Workflow Execution Trace — полный след выполнения задачи.

1.2. Разрыв между Observability и Evaluation

Сегодняшний ландшафт инструментов фрагментирован:

Что нужно Что есть
Ответ на «почему?» Prometheus показывает, что упала метрика
Воспроизводимость LangSmith показывает, что вызвали инструмент
Оптимизация MLflow хранит гиперпараметры

Ни одна система не даёт формальную модель выполнения агента, позволяющую воспроизвести ошибку, понять её причину и исправить.

Глава 3. Воспроизводимость — Священный Грааль

Без воспроизводимости любая отладка превращается в гадание.

3.1. Reproducibility Hash (ReproHash)

Мы вводим единый хэш, который однозначно идентифицирует конфигурацию выполнения:

ReproHash = SHA256(  
    Model_Version +  
    Prompt_Template_Hash +  
    Config_Hash +  
    Tool_Versions +  
    Memory_State_Hash  
)

Две трассировки с одинаковым ReproHash гарантированно выполнялись в идентичных условиях.

3.2. Что нужно для воспроизведения

1. Восстановить контекст: Загрузить конфигурацию, промпт, версии инструментов по хэшам.


2. Воспроизвести события: Проиграть события в хронологическом порядке.


3. Валидировать: Сравнить финальное состояние с оригиналом.

Глава 4. Память и состояние

AI-системы — это не stateless-сервисы. Они обладают памятью, которая мутирует во времени.

Решение: Включать memory_state_hash в ExecutionContext. Любое изменение памяти — новая трассировка.

Глава 6. Метрики, которые не устаревают

Большинство сегодняшних метрик устаревают через 1–2 года (токены на запрос, количество tool calls, TTFT). Нам нужны инвариантные метрики — те, что переживут смену архитектур.

6.1. Уровень 0: Абсолютные инварианты

Эти метрики не зависят от того, что находится «внутри» системы — человек, rule-based система, LLM или агент.

1. Task Completion Rate (TCR) — достигнута ли цель?


2. Functional Correctness (FC) — процент пройденных тестов


3. Cost per Successful Outcome (CpSO) — цена успешного решения в $ или человеко-часах


4. Time-to-Value (TtV) — время от запроса до полезного результата


5. Human Intervention Rate (HIR) — частота вмешательства пользователя



Почему они работают: Они укоренены в фундаментальных свойствах информации, экономики и человеческой когниции.

6.2. Уровень 1: Фундаментальные инварианты (10+ лет)

6. Semantic Equivalence Score (SES) — эквивалентность решения эталону


7. Information Efficiency (IE) — полезная информация на единицу ресурсов


8. Failure Recovery Rate (FRR) — доля сбоев, из которых система восстановилась



6.3. Что НЕ нужно использовать

Метрика Почему устаревает
Токены на запрос Зависит от токенизатора провайдера
Количество tool calls Зависит от протокола и granularity
Количество итераций Зависит от scaffolding и retry-стратегии
TTFT / TTLT Зависит от железа, сети, batching

Общий принцип: Любая метрика, привязанная к внутренней реализации, обречена.

Глава 9. Отказоустойчивость и Red Team аудит

Любая архитектура должна быть подвергнута критике. Вот главные риски и их митигация:

9.1. Риск 1: Экспоненциальный рост стоимости хранения

Проблема: Полные трассировки всех выполнений → терабайты данных → огромные счета.

Решение:

· TTL (Time-To-Live) для старых трассировок
· Семплирование: полные трассировки только для failed tasks и 1% успешных
· Для остальных — только агрегированные метрики

9.2. Риск 2: Иллюзия воспроизводимости

Проблема: Даже при одинаковом ReproHash провайдер может тихо обновить веса модели на сервере.

Решение:

· Явно документировать, что ReproHash гарантирует воспроизводимость конфигурации, а не поведения провайдера
· Для критичных задач — использовать open-weight модели локально

9.3. Риск 3: Нагрузка на Runtime (Observability Tax)

Проблема: Перехват каждого события добавляет 10-20% латентности.

Решение:

· Инструментация через eBPF или sidecar-прокси (а не синхронные вызовы в коде)
· Буферизация и пакетная отправка событий

9.4. Риск 4: Переусложнение Capability Detection

Проблема: Динамическое зондирование всех возможностей медленное и ненадёжное.

Решение:

· Использовать декларативные манифесты от разработчиков Runtime
· Динамическое зондирование — только для валидации, а не первичного обнаружения

1. Архитектурная жизнеспособность и узкие места



Иерархическая конечная автомата (HSM) для агентов: Предложенная модель переходов состояний (IDLE → PLANNING → EXECUTING → WAITING_TOOL и т.д.) отлично ложится на событийно-ориентированную архитектуру (Event-Driven Architecture). Workflow Execution Trace (WET): Сбор JSON-трассировок для каждого LLM-вызова (с вложенными массивами payload) приведет к экспоненциальному росту логов. Для edge-устройств или локальных развертываний хранение WET в JSON убьет I/O накопителя.

Решение: Использование бинарной сериализации (Protobuf/FlatBuffers) на уровне hot-path (сбор телеметрии) с асинхронной выгрузкой в колоночные БД (ClickHouse/DuckDB) в Parquet-формате.



2. Оценка метрик (Инварианты Уровня 0)
Концепция инвариантных метрик (Уровень 0) полностью решает проблему "метрического дрейфа".



Task Completion Rate (TCR) & Functional Correctness (FC): Фундаментальные метрики, но их автоматизация требует 100% покрытия детерминированными тестами. В задачах генеративного дизайна или нечеткой логики автоматический подсчет FC невозможен без LLM-as-a-Judge, что снова вводит рекурсивную погрешность.

Cost per Successful Outcome (CpSO): Идеальная бизнес-метрика. Включает CPU/RAM overhead, стоимость токенов API и сетевые задержки.

Human Intervention Rate (HIR): Самый точный прокси для UX. Легко измеряется через дельту правок (edit distance) или количество ручных отмен.


3. Персонализация и MCDM (TOPSIS)
Использование многокритериального анализа (TOPSIS) — сильный математический шаг. Однако вычисление TOPSIS или построение фронта Парето на каждый запрос (hot-path) создаст недопустимую задержку.



Корректировка архитектуры: MCDM должен работать строго в cold-path. Система должна пересчитывать веса и рейтинги конфигураций асинхронно (например, раз в сутки) и складывать готовые лукапы (key-value) в in-memory кэш для мгновенного доступа во время runtime.


4. Критическая уязвимость: Иллюзия воспроизводимости
Документ предполагает, что связка Task Hash + Model Version + Prompt Template Hash гарантирует воспроизводимость. Это фундаментальная ошибка при работе с закрытыми API (OpenAI, Anthropic). Провайдеры регулярно обновляют веса "под капотом" без смены мажорной версии.



Вывод: 100% воспроизводимость WET и семантическая эквивалентность (SES) достижимы только при использовании локальных open-source моделей с фиксированными сидами (seeds) и quantized-весами (например, развертывание Llama.cpp на собственном железе).

## Введение: Конец эпохи «оценки в вакууме»

Ваша модель занимает первое место в LiveCodeBench, но в продакшене агент зацикливается, сжигает бюджет на бесполезные вызовы инструментов и теряет контекст на десятой итерации. Почему? 

Потому что пользователь взаимодействует не с «голыми весами» нейросети, а со сложной распределенной системой. Результат определяется цепочкой: 
`Provider → Model → Runtime → Adapter (Prompt/Tools) → Configuration → Task → Workflow → Result`.

Ошибка на любом уровне (например, агрессивный truncation в адаптере или плохая стратегия retry) превращает топовую модель в посредственного агента. Нам нужна новая дисциплина. Не просто мониторинг и не бенчмаркинг, а **Runtime Intelligence** — цифровой двойник AI-системы, отвечающий на три вопроса: *Почему это произошло? Как это воспроизвести? Как это улучшить?*

## 1. Workflow Execution Trace (WET): Новая единица истины

Логи, метрики и разрозненные трейсы не дают полной картины. Стандартом де-факто для оценки должен стать **Workflow Execution Trace (WET)** — упорядоченная, иерархическая и причинно-следственная последовательность событий, полностью описывающая выполнение задачи.

## 2. Метрики, которые переживут смену парадигм (Инварианты)

Большинство современных метрик имеют срок жизни 1–2 года. «Количество tool calls» ломается при смене протокола (MCP на ACP). «Токены на запрос» теряют смысл при смене токенизатора. 

Инженерная система должна опираться на **Инварианты Уровня 0** — метрики, укорененные в фундаментальных свойствах экономики, информации и человеческой когниции. Они не зависят от внутренней реализации системы:

1. **Task Completion Rate (TCR):** Бинарный факт. Достигнута ли формальная цель задачи (пройден ли acceptance test)?
2. **Functional Correctness (FC):** Процент прохождения независимых, написанных заранее тестов.
3. **Cost per Successful Outcome (CpSO):** Полная стоимость достижения цели в универсальных единицах ($ или человеко-часах), включая скрытые затраты на отладку.
4. **Time-to-Value (TtV):** Время от формулировки намерения до получения *принятого* пользователем результата.
5. **Human Intervention Rate (HIR):** Частота, с которой пользователь вынужден вмешиваться (отмены, ручные правки, переписывание промпта). *Самая устойчивая UX-метрика.*

**Антипаттерн:** Никогда не используйте для стратегических решений метрики, привязанные к внутренней реализации (TTFT, tokens/sec, parameter count). Они создают иллюзию контроля.

---

## 3. Архитектура Runtime Intelligence

Система не должна влиять на hot-path (генерацию ответа). Предлагается событийно-ориентированная 5-слойная архитектура с паттерном CQRS:

1. **Instrumentation Layer:** Асинхронный экспорт (OTLP) через eBPF или sidecar-прокси. Перехватывает состояния конечного автомата агента (PLANNING → WAITING_TOOL → EXECUTING) без блокировки основного потока.
2. **Data Processing (CQRS):** Stream-процессинг (Kafka/Flink), который агрегирует сырые события в WET, считает стоимость в реальном времени и строит графы зависимостей.
3. **Polyglot Storage:** 
   - *ClickHouse/DuckDB:* Для метрик и временных рядов.
   - *MongoDB/PostgreSQL (JSONB):* Для хранения иерархических WET.
   - *Neo4j:* Для анализа причинно-следственных графов и lineage.
   - *S3 (Content-Addressable):* Для артефактов (код, логи) с дедупликацией по SHA-256.
4. **Intelligence Engine:** Асинхронный анализ. LLM-as-a-Judge (с версионированными рубрикаторами), MCDM-ранжирование и контекстные бандиты для персонализации.
5. **Visualization & API:** Trace Explorer, дашборды и Reproducibility Runner.

---

## 4. Священный Грааль: Воспроизводимость и ReproHash

Как доказать, что регрессия качества вызвана изменением в системе, а не «тихим» обновлением весов на стороне провайдера? 

Вводится концепция **Reproducibility Hash (ReproHash)**:
`ReproHash = SHA256(Model_Version + Prompt_Hash + Config_Hash + Tool_Versions + Memory_State_Hash)`

Две трассировки с одинаковым `ReproHash` гарантированно выполнялись в идентичных условиях. 
*Важное предупреждение (Red Team):* 100% воспроизводимость семантического результата достижима только при использовании локальных open-weight моделей с фиксированными `seed`. Для закрытых API (OpenAI, Anthropic) `ReproHash` гарантирует воспроизводимость *нашей конфигурации*, но мы должны использовать моки внешних зависимостей и сохранять полные ответы LLM для критичных вызовов, чтобы эмулировать детерминизм при реплее.

3. **Иллюзия воспроизводимости.** Провайдеры могут обновлять веса моделей без смены версии API.
   *Митигация:* Четкое документирование границ гарантий. Для критичных пайплайнов (финансы, медицина) — требование к использованию локально развернутых open-weight моделей с фиксированным квантованием.

Большинство современных метрик имеют срок жизни 1–2 года. «Количество tool calls» ломается при смене протокола (MCP на ACP). «Токены на запрос» теряют смысл при смене токенизатора. 

Инженерная система должна опираться на **Инварианты Уровня 0** — метрики, укорененные в фундаментальных свойствах экономики, информации и человеческой когниции. Они не зависят от внутренней реализации системы:

1. **Task Completion Rate (TCR):** Бинарный факт. Достигнута ли формальная цель задачи (пройден ли acceptance test)?
2. **Functional Correctness (FC):** Процент прохождения независимых, написанных заранее тестов.
3. **Cost per Successful Outcome (CpSO):** Полная стоимость достижения цели в универсальных единицах ($ или человеко-часах), включая скрытые затраты на отладку.
4. **Time-to-Value (TtV):** Время от формулировки намерения до получения *принятого* пользователем результата.
5. **Human Intervention Rate (HIR):** Частота, с которой пользователь вынужден вмешиваться (отмены, ручные правки, переписывание промпта). *Самая устойчивая UX-метрика.*

**Антипаттерн:** Никогда не используйте для стратегических решений метрики, привязанные к внутренней реализации (TTFT, tokens/sec, parameter count). Они создают иллюзию контроля.

## 3. Архитектура Runtime Intelligence

Система не должна влиять на hot-path (генерацию ответа). Предлагается событийно-ориентированная 5-слойная архитектура с паттерном CQRS:

1. **Instrumentation Layer:** Асинхронный экспорт (OTLP) через eBPF или sidecar-прокси. Перехватывает состояния конечного автомата агента (PLANNING → WAITING_TOOL → EXECUTING) без блокировки основного потока.
2. **Data Processing (CQRS):** Stream-процессинг (Kafka/Flink), который агрегирует сырые события в WET, считает стоимость в реальном времени и строит графы зависимостей.
3. **Polyglot Storage:** 
   - *ClickHouse/DuckDB:* Для метрик и временных рядов.
   - *MongoDB/PostgreSQL (JSONB):* Для хранения иерархических WET.
   - *Neo4j:* Для анализа причинно-следственных графов и lineage.
   - *S3 (Content-Addressable):* Для артефактов (код, логи) с дедупликацией по SHA-256.
4. **Intelligence Engine:** Асинхронный анализ. LLM-as-a-Judge (с версионированными рубрикаторами), MCDM-ранжирование и контекстные бандиты для персонализации.
5. **Visualization & API:** Trace Explorer, дашборды и Reproducibility Runner.

## 4. Священный Грааль: Воспроизводимость и ReproHash

Как доказать, что регрессия качества вызвана изменением в системе, а не «тихим» обновлением весов на стороне провайдера? 

Вводится концепция **Reproducibility Hash (ReproHash)**:
`ReproHash = SHA256(Model_Version + Prompt_Hash + Config_Hash + Tool_Versions + Memory_State_Hash)`

Две трассировки с одинаковым `ReproHash` гарантированно выполнялись в идентичных условиях. 
*Важное предупреждение (Red Team):* 100% воспроизводимость семантического результата достижима только при использовании локальных open-weight моделей с фиксированными `seed`. Для закрытых API (OpenAI, Anthropic) `ReproHash` гарантирует воспроизводимость *нашей конфигурации*, но мы должны использовать моки внешних зависимостей и сохранять полные ответы LLM для критичных вызовов, чтобы эмулировать детерминизм при реплее.

## 5. Практика: Как выбирать лучшую конфигурацию (MCDM)

Вместо скалярного рейтинга «8.5/10» инженерная система должна использовать **Многокритериальное принятие решений (MCDM)**, например, метод **TOPSIS**. ## 6. Red Team Audit: Где архитектура может дать сбой

Любая серьезная спецификация должна содержать анализ собственных слабых мест:

1. **Экспоненциальный рост стоимости хранения.** Полные WET с артефактами быстро съедят бюджет. 
   *Митигация:* Строгий TTL и семплирование. Хранить полные трассировки только для `failed` задач, edge cases и 1% успешных. Для остальных — только агрегированные метрики Уровня 0 в ClickHouse.
2. **Observability Tax (Налог на наблюдаемость).** Синхронный перехват событий добавит 10-20% латентности. 
   *Митигация:* Только асинхронная инструментация (fire-and-forget через OTLP), буферизация на уровне sidecar или eBPF.
3. **Иллюзия воспроизводимости.** Провайдеры могут обновлять веса моделей без смены версии API.
   *Митигация:* Четкое документирование границ гарантий. Для критичных пайплайнов (финансы, медицина) — требование к использованию локально развернутых open-weight моделей с фиксированным квантованием.

# Formal Specification of AI Runtime Intelligence (RFC v2.0)

## 1. Математическая модель Runtime

Мы определяем AI Runtime $R$ как детерминированную (в рамках заданной конфигурации) систему переходов с памятью и ограничениями.

$$R = (S, E, T, A, M, C)$$

Где:
*   $S$: Конечное или счетное множество **состояний** (States). $s \in S$.
*   $E$: Множество **событий** (Events). $e \in E$.
*   $T$: Функция переходов $T: S \times E \rightarrow S$. Определяет, как событие меняет состояние.
*   $A$: Множество **действий** (Actions/Side-effects), выполняемых при переходе (например, HTTP-запрос, запись в БД).
*   $M$: Пространство **состояний памяти** (Memory State Space). $m \in M$.
*   $C$: Множество **ограничений** (Constraints), например, $C_{time***REMOVED***$ (budget), $C_{cost***REMOVED***$, $C_{safety***REMOVED***$.

**Состояние системы в момент времени $t$** описывается кортежем: $\Sigma_t = (s_t, m_t, h_t)$, где $h_t$ — история событий (Trace).

---

## 2. Runtime Invariants (Инварианты выполнения)

Инварианты — это логические утверждения, которые должны быть истинны ($\top$) для любого валидного Trace. Они формулируются с использованием элементов линейной темпоральной логики (LTL).

1.  **Инвариант жизненного цикла (Lifecycle Completeness):**
    $\Box (TaskStarted \rightarrow \Diamond (TaskCompleted \lor TaskFailed \lor TaskCancelled))$
    *(Всегда истинно, что после старта задачи неизбежно наступит одно и только одно из состояний завершения).*

2.  **Инвариант причинности инструментов (Tool Causality):**
    $\forall e_{result***REMOVED*** \in Trace: (e_{result***REMOVED***.type == ToolResult) \rightarrow \exists e_{invoke***REMOVED*** \in Trace_{< e_{result***REMOVED******REMOVED***: (e_{invoke***REMOVED***.type == ToolInvoke \land e_{invoke***REMOVED***.tool\_id == e_{result***REMOVED***.tool\_id)$
    *(Невозможно получить результат инструмента, если ему не предшествовал вызов этого же инструмента в той же ветке выполнения).*

3.  **Инвариант исключительности состояний (State Mutually Exclusive):**
    $\forall t: \neg (s_t == Executing \land s_t == Waiting)$
    *(Агент не может находиться в состоянии активного выполнения и ожидания одновременно, если это не описано как иерархическое состояние с явным разделением потоков).*

4.  **Инвариант бюджета (Constraint Preservation):**
    $\forall t: Cost(h_t) \le C_{cost***REMOVED*** \land Time(h_t) \le C_{time***REMOVED***$
    *(Система обязана инициировать переход в $TaskCancelled$ или $TaskFailed$ до нарушения ограничений).*

## 3. Formal Semantics of States (Семантика состояний)

Чтобы разные Runtime интерпретировали состояния одинаково, мы привязываем их к примитивам распределенных систем:

*   **`WAITING_LLM`**: *Asynchronous I/O Await (Future/Promise).* Поток управления агентом приостановлен (yield/suspend), но системный рантайм не блокирует ресурсы CPU. Это состояние ожидания внешнего оракула.
*   **`WAITING_TOOL`**: *Actor Mailbox Suspension / Callback Registration.* Агент отправил сообщение внешнему актору (инструменту) и зарегистрировал continuation.
*   **`PLANNING`**: *Local Synchronous Computation.* Процессорное время тратится на внутреннюю логику (генерация DAG, оценка условий). Внешние I/O блокированы или отсутствуют.
*   **`RECOVERING`**: *Saga Compensation / State Rollback.* Выполняется детерминированная последовательность действий для отката побочных эффектов (side-effects) перед повторной попыткой.

---

## 4. Модель причинности (Causality Model)

Временной порядок (Wall-Clock Time) недостаточен для распределенных агентных систем. Мы вводим **отношение "происходит до" (Happens-Before, $\rightarrow$)**, основанное на логических часах Лампорта или векторных часах (Vector Clocks) для мультиагентных систем.

*   **Trace как Poset (Частично упорядоченное множество):** Trace — это не плоский список, а DAG событий $G = (V, E_{causal***REMOVED***)$, где ребра $E_{causal***REMOVED***$ обозначают причинно-следственную связь.
*   **Правило причинности:** Событие $A \rightarrow B$, если:
    1. $A$ и $B$ происходят в одном потоке/агенте, и $A$ предшествует $B$.
    2. $A$ — это отправка сообщения (например, `ToolInvoke`), а $B$ — получение этого сообщения (например, начало выполнения инструментом).
    3. Транзитивность: если $A \rightarrow B$ и $B \rightarrow C$, то $A \rightarrow C$.

**Инженерное следствие:** При сравнении двух Trace мы сравниваем не временные метки, а **изоморфизм их причинных DAG**. Это делает оценку устойчивой к сетевым задержкам и джиттеру.

---

## 5. Модель конкуренции и согласованности памяти (Concurrency Model)

Для мультиагентных систем или агентов с фоновыми задачами требуется строгая модель согласованности (Consistency Model).

*   **Working Memory (Локальная):** Thread-local или Actor-local. Гарантированная строгая согласованность (Linearizability). Конфликтов нет.
*   **Shared Knowledge Base (Глобальная):**
    *   Для *append-only* данных (логи, эпизодическая память): Используем **CRDT** (Conflict-free Replicated Data Types), конкретно G-Set или LWW-Element-Set. Это гарантирует сходимость (convergence) без блокировок.
    *   Для *mutable* данных (настройки, текущие цели): Используем **Optimistic Concurrency Control (OCC)** с векторами версий (Version Vectors). При конфликте запускается детерминированная стратегия разрешения (например, "последний писавший побеждает" или "вызов агента-арбитра").
*   **External Tool State:** Подчиняется правилам **Saga Pattern**. Если агент $A$ и агент $B$ вызывают транзакционные инструменты, каждый шаг должен иметь компенсирующее действие (compensating transaction) для отката в случае параллельного конфликта или ошибки.

## 6. Runtime Calculus (Алгебра выполнения)

Мы можем описать поведение агента с помощью упрощенного процессного исчисления (аналог $\pi$-calculus или CCS), что позволяет формально верифицировать workflows.

Определим базовые операторы:
*   $P ; Q$ : Последовательное выполнение (Sequential composition).
*   $P \parallel Q$ : Параллельное выполнение (Parallel composition).
*   $P + Q$ : Недетерминированный выбор (Choice, например, ветвление планировщика).
*   $P^*$ : Итерация (повторение до достижения условия).
*   $\rho(P)$ : **Оператор рефлексии**. Функция, которая принимает Trace выполнения $P$, оценивает его (Evaluation Engine) и возвращает модифицированный процесс $P'$ для следующей итерации.

**Формальное определение цикла агента:**
$$Agent \equiv Plan ; (Execute \parallel Observe)^* ; \rho(Evaluate) ; Adapt$$

Это позволяет доказывать свойства, например, *Liveness* (система не зайдет в тупик) и *Safety* (система не нарушит инварианты безопасности).

---

## 7. Execution Semantics (Классификация инструментов для Replay)

Для корректного воспроизведения (Replay) каждый инструмент (Tool) должен быть аннотирован своими семантическими свойствами:

| Свойство | Определение | Влияние на Replay |
| :--- | :--- | :--- |
| **Pure** | Не имеет побочных эффектов, вывод зависит только от ввода. | Можно безопасно кэшировать и пропускать при Replay. |
| **Deterministic** | Всегда возвращает одинаковый результат для одинаковых входов (но может иметь side-effects). | Можно проигрывать заново, результат предсказуем. |
| **Stochastic** | Результат варьируется (например, LLM call, генерация случайных чисел). | **Обязательна запись (Recording)** результата при первом прогоне. Replay использует записанный результат, а не вызывает инструмент снова. |
| **Idempotent** | Многократный вызов с теми же аргументами эквивалентен однократному. | Безопасен для автоматических Retry при сбоях сети. |
| **Transactional** | Изменяет внешнее состояние, не является идемпотентным (например, `charge_card`). | Требует Saga-компенсации при откате. Replay требует режима "Dry-run" или мокинга. |

## 8. Security as First-Class Events (Модель безопасности)

Безопасность не может быть постфактум-анализом. Она встраивается в $T$ (функцию переходов) как guard conditions (условия-сторожа).

Добавляются новые типы событий и инварианты:
*   `SECURITY_GUARDRAIL_TRIGGERED`: Событие блокировки (например, обнаружена попытка Prompt Injection или вывод запрещенного контента).
*   **Инвариант безопасности:** $\Box (ToolInvoke \rightarrow \Diamond^{-1***REMOVED*** GuardrailValidationPassed)$
    *(Невозможно выполнить инструмент, если ему не предшествовало успешное прохождение проверок безопасности).*
*   **Context Poisoning Detection:** Мониторинг энтропии и аномальных паттернов в $M$ (памяти). Если векторное представление текущего контекста резко отклоняется от базовой линии, генерируется событие `CONTEXT_ANOMALY`.

## 9. Runtime Economics (Модель полезности)

Мы переходим от простого учета затрат к теории полезности (Utility Theory).

Определим **Expected Utility ($U$)** одного шага выполнения (например, одного LLM-запроса или вызова инструмента):

$$U = P(success | action) \times V_{task***REMOVED*** - (C_{compute***REMOVED*** + C_{context***REMOVED*** + C_{risk***REMOVED***)$$

Где:
*   $P(success | action)$: Ожидаемая вероятность успеха задачи при данном действии (оценивается эвристически или через легковесную модель).
*   $V_{task***REMOVED***$: Ценность успешного выполнения задачи (задается пользователем).
*   $C_{context***REMOVED***$: Маржинальная стоимость деградации контекстного окна (cost of context pollution).
*   $C_{risk***REMOVED***$: Ожидаемая стоимость потенциальной ошибки (например, штраф за галлюцинацию).

**Инженерное применение:** Runtime использует это для **Adaptive Budgeting**. Если $U < 0$ для следующего шага планирования, агент должен немедленно перейти в состояние `TaskFailed` или запросить помощь человека (`HumanIntervention`), вместо того чтобы бесконечно тратить токены на бесполезные размышления (Cost of Reflection).

---

## 10. Adaptive Runtime (Closed Feedback Loop / MAPE-K)

Чтобы Runtime Intelligence стал системой *управления*, а не просто логирования, мы внедряем петлю обратной связи, основанную на архитектуре **MAPE-K** (Monitor, Analyze, Plan, Execute, Knowledge) из области автаномных вычислений (Autonomic Computing).

1.  **Monitor:** Сбор событий в реальном времени (Observability layer).
2.  **Analyze:** Вычисление метрик в реальном времени (например, "rate of tool failures > 30% за последние 2 минуты").
3.  **Plan:** Decision Engine принимает решение об изменении конфигурации $C$. Например: "Снизить temperature до 0.1", "Переключиться с модели А на модель Б", "Включить строгий режим валидации".
4.  **Execute:** Динамическое применение новой конфигурации к текущему Workflow (Hot-reload конфигурации без прерывания Trace).
5.  **Knowledge:** Обновление кэша `CapabilityProfile` и весов персонализации на основе исхода.

Это превращает `ReproHash` из статического идентификатора в **базовую линию (baseline)**. Если адаптивный рантайм меняет конфигурацию, генерируется *новый* `ReproHash`, позволяя точно оценить, дало ли адаптивное изменение прирост полезности ($ \Delta U $).
