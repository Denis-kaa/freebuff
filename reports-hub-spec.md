# reports-hub-spec.md — сервис отчётов Reports Hub для платформы Workspace OS

> **Статус:** SPEC (код ещё не написан) · **Дата:** 2026-09-12
> **Автор спеки:** Buffy (по итогам интервью с Денисом, 6 раундов ask_user)
> **Размещение:** `services_08/reports_hub/` (сервис платформы, не отдельный проект)
> **Первый профиль:** проект «печатник» (`projects_17/админка печатник/`)

---

## 1. Проблема и цель

Сейчас отчёты о работе по проектам платформы — это Markdown-файлы в корне проекта
(`PROJECT_STATUS_REPORT.md`, `PHASE_*_REPORT.md`, `РОАДМАП_v6_ЕДИНАЯ_СИСТЕМА.md`, `FINAL_REPORT.md`…).
Они читаются только в редакторе: нет навигации, нет метрик наглядно, на телефоне читаются плохо,
переслать заказчику/себе «красиво» нельзя.

**Цель:** отдельное приложение-сервис в платформе, которое:

1. **Автоматически** собирает факты из файлов проекта (Markdown-отчёты, роадмапы, git, метрики);
2. Генерирует **красивый отчёт в стиле Apple** — mobile-first, light+dark, открывается в браузере;
3. Собирает **мини-сайт с индексом всех отчётов** (все проекты + отчёт по самой платформе);
4. Все **последующие отчёты** формируются в этом же виде — единый канон подачи отчётности платформы.

## 3. Не-цели (v1)

- ❌ Не редактирует и не перезаписывает исходные Markdown-документы (только читает).
- ❌ Без базы данных — всё строится из файлов, состояние = сгенерированный сайт + history-JSON.
- ❌ Без полноценной авторизации/пользователей — только token-гейт.
- ❌ Без PDF/DOCX-экспорта (заложить в архитектуре, не реализовывать).
- ❌ Без LLM-агента внутри сервиса в v1: LLM-слой = hook + override-файлы (см. §9).
- ❌ Не заменить печатник и его UI — сервис отчётов независим (B-Rule 2: терпим к отсутствию).

## 4. Архитектура

### 4.1 Принципы (AGENTS.md)

- **Additive Architecture:** сервис ничего не переписывает; читает проекты через их owner-файлы.
- **Contract First:** внутренняя модель отчёта — dataclass-контракт `ReportModel` (JSON-сериализуемый);
  сайт = детерминированный рендер модели. Модель версионируется (`schema_version`).
- **Single Source of Truth:** факты берутся из исходных доков; отчёт никогда не «запоминает» правки
  в обход источника (правки резюме — только через override-файлы, переживающие перегенерацию).
- **Observability:** каждая генерация пишет `site/manifest.json` (timestamp, список проектов,
  статистика, ошибки парсинга). Ошибки парсинга не молчат — попадают в раздел «Диагностика».
- **Graceful degradation:** нет LLM → детерминированные резюме; нет git-истории → раздел скрывается;
  нет токена в env → сервер стартует, но отдаёт 401 на всё (урок TG-поллера: приложение стартует).

### 4.3 Конфигурация проектов

Каждый проект может иметь owner-файл **`projects_17/<slug>/reports_hub.yaml`**:

```yaml
# reports_hub.yaml — профиль отчёта для reports_hub
title: "Печатник — админка печатного цеха"
accent: "#c9a876"          # опционально: явный акцент (приоритет ниже авто-извлечения? — см. §6.3)
logo: "worktree/Калькуляторы/Калькулятор макетов/logo.png"  # для авто-акцента
docs:                      # какие доки включить в библиотеку (glob, приоритет списком)
  - "PROJECT_STATUS_REPORT.md"
  - "РОАДМАП_v6_ЕДИНАЯ_СИСТЕМА.md"
  - "PHASE_*_REPORT.md"
  - "research/FINAL_REPORT.md"
  - "*AUDIT*.md"
timeline_sources:          # источники хронологии этапов
  - "PROJECT_STATUS_REPORT.md"
metrics:
  loc_paths: ["printcalc/src/**"]
roadmap: "РОАДМАП_v6_ЕДИНАЯ_СИСТЕМА.md"
blockers: "PROJECT_STATUS_REPORT.md"   # раздел «открытые вопросы»
```

**Автообход (если `reports_hub.yaml` нет):** сервис сканирует `projects_17/*/`,
ищет сигнатуры отчётности (`PROJECT_STATUS_REPORT.md`, `PHASE_*`, `ROADMAP*`, `РОАДМАП*`, `FINAL_REPORT.md`,
`MANIFEST.md`). Нашёл — строит отчёт по default-профилю; не нашёл — карточка «нет данных»
(серая, с причиной «нет отчётной документации»).

Служебные/мусорные каталоги исключаются списком в `services_08/reports_hub/config.py`
(например `.freezer`, `trash_21`, копии-бэкапы) + per-project `exclude: true` в yaml.

## 5. Данные и извлечение

### 5.1 Детерминированный слой (основа)

1. **Markdown-парсер** (свой, без тяжёлых зависимостей): заголовки h1–h4, таблицы, списки,
   блочные цитаты `> Статус: …`, `**жирные**` метки, inline-код. Выход — дерево секций.
2. **Извлечение хронологии этапов:** поиск таблиц вида «этап/дата/коммит/результат»
   (у печатника — §1 PROJECT_STATUS_REPORT: 13 этапов с коммитами) → секция Timeline.
3. **Метрики regex-слоем:**
   - тесты: `(\d+)\s*passed` → `249 passed`;
   - mypy: `mypy clean` / число файлов;
   - строки кода: подсчёт по `loc_paths` (только .py, exclude tests — отдельно);
   - коммиты: `git log --follow --oneline` по каталогу проекта (с деградацией вне git);
   - прогресс этапов: из роадмапа — статусы 🔴/🟡/🟢/✅, % готовности;
   - даты: из шапок доков (`Дата: YYYY-MM-DD`).
4. **Роадмап/«что дальше»:** секции `Дальнейшие шаги|Следующие шаги|Roadmap|Этапы` → чек-лист.
5. **Проблемы/блокеры:** секции с `OPEN_QUESTIONS`, «открытые вопросы», «⚠», «BLOCKED», «Решить».

### 5.2 Что НЕ доверяем парсеру (анти-галлюцинация)

- Парсер не «додумывает» факты: нет данных → секция помечается `источник не найден`,
  а не заполняется пустышкой (канон «не молча», UNKNOWN не заменяется догадкой §63).
- Числа-метрики выводятся с указанием источника (файл + строка) в tooltip/сноске отчёта.

### 5.3 LLM-слой (поверх, опционально)

- **Hook-интерфейс:** `summaries.py` определяет `SummaryProvider` (Protocol) и две реализации:
  `DeterministicProvider` (первые абзацы секций, усечение до 2–3 предложений) и
  `LlmSummaryProvider` (вызывается, только если настроен).
- **Провайдеры LLM (гибрид, приоритет по env):**
  1. `REPORTS_HUB_LLM=api` + ключ → внешний API (совместимый с OpenAI-протоколом);
  2. `REPORTS_HUB_LLM=local` → локальная модель платформы через ModelCatalog/Factory;
  3. не задано → DeterministicProvider.
- **Ограничения (канон §38):** LLM пишет ТОЛЬКО executive-summary и карточки доков
  (пересказ), никогда — цифры и статусы. Цифры всегда из детерминированного слоя.
- **Кэш:** сгенерированные LLM-резюме сохраняются в `summaries.json` (см. §9), чтобы
  перегенерация не тратила токены и не меняла тексты без причины.

## 6. Дизайн: Apple-стиль, mobile-first

### 6.1 Дизайн-токены

| Токен | Light | Dark |
|---|---|---|
| `--bg` | `#ffffff` | `#000000` |
| `--bg-secondary` | `#f5f5f7` | `#1d1d1f` |
| `--card` | `#ffffff` | `#1d1d1f` |
| `--text` | `#1d1d1f` | `#f5f5f7` |
| `--text-secondary` | `#6e6e73` | `#86868b` |
| `--separator` | `#d2d2d7` | `#424245` |
| `--accent` | авто/`#0071e3` | авто/`#0a84ff` |
| `--good/--warn/--bad` | `#34c759 / #ff9f0a / #ff3b30` | те же (iOS-палитра) |

- **Шрифт:** `-apple-system, BlinkMacSystemFont, "SF Pro Text", "Helvetica Neue", Arial, sans-serif`.
- **Типографика:** Large Title 28–34px/700, tracking −0.02em; Section 21px/600; Body 15–17px/400;
  secondary 13px. Табличные цифры — `font-variant-numeric: tabular-nums`.
- **Карточки:** radius 16–18px, тень только на light (`0 2px 12px rgba(0,0,0,.06)`),
  на dark — граница 1px `--separator`. БЕЗ градиентов, glassmorphism, glow, bento-сетки без нужды
  (см. `anti-slop-design-system.md` — состав осознанный, не декоративный).
- **Motion:** только переходы прозрачности/смещения 150–200ms ease-out; `prefers-reduced-motion` уважается.

### 6.2 Mobile-first композиция

- Базовая сетка — **одна колонка**: large title → сводка → метрики (2×2 плитки) → timeline (вертикальная
  линия с точками) → roadmap (чек-лист) → блокеры → библиотека доков (карточки).
- Sticky-шапка с blur (`backdrop-filter: saturate(180%) blur(20px)`, rgba-фон) — как навбар apple.com;
  в ней переключатель темы (системная/светлая/тёмная) и якорная навигация (горизонтальный скролл-пилюли).
- Таблицы этапов на мобильном превращаются в карточки-строки (дата · текст · коммит-чип);
  на `min-width: 720px` — полноценная таблица.
- Касательные цели: кнопки/строки ≥ 44px высотой; нижняя sticky-панель «скачать ZIP» на проектной странице.

### 6.3 Акцентный цвет (авто по логотипу)

1. Если в конфиге проекта указан `logo` (или найден `logo.png`/`app.ico` в проекте) — извлечь
   доминирующий насыщенный цвет (k-means по пикселям, stdlib+Pillow при наличии; при отсутствии
   Pillow — пропустить шаг молча в лог диагностики);
2. Иначе — `accent` из `reports_hub.yaml`;
3. Иначе — системный `#0071e3`.
Приоритет: **логотип > конфиг > дефолт** (решение интервью №17). Для dark-темы акцент
автоматически осветляется (HSL +L до контраста ≥ 4.5:1 на чёрном).

### 6.4 Страницы

1. **`index.html` — главная-галерея:** заголовок «Отчёты», дата генерации; сетка карточек проектов
   (название, акцент-полоса/логотип, 3 ключевые цифры, бейдж статуса, «изменений с прошлой генерации: ±N»);
   сверху закреплена карточка «Платформа Workspace OS»; внизу отдельная секция серых карточек
   «нет данных» (проекты без отчётности, с причиной).
2. **`projects/<slug>/index.html` — статус-отчёт проекта** (§7.1).
3. **`projects/<slug>/docs/<doc>.html` — полный рендер документа** из библиотеки (§7.2).
4. **`platform/index.html` — отчёт по платформе** (§7.3).
5. **Diff-сводка** — блок на главной + бейджи в отчётах (§8).

Все страницы — **самодостаточные HTML** (inline CSS, JS без внешних CDN, шрифты системные):
страница открывается и с сервера, и локально по file:// (для пересылки одним файлом).

## 7. Контент отчётов

### 7.1 Статус-отчёт проекта (секции по порядку)

1. **Executive summary** — 2–4 предложения (LLM/override/детерминированное) + строка «состояние на
   дату N, источник: PROJECT_STATUS_REPORT.md».
2. **Метрики — развёрнутая панель** (решение №2 интервью, вариант «развёрнутая»):
   - плитки: тесты (X passed), mypy (clean, N файлов), строки кода, коммиты (за период);
   - прогресс-бары по этапам роадмапа (🟢/🟡/🔴 → 100/50/10% + подпись источника);
   - динамика по PHASE-отчётам (полоса «этапов закрыто по месяцам»);
   - статистика типов документов (12 PHASE-отчётов, 17 research-файлов, …).
3. **Хронология этапов (Timeline)** — таблица/карточки: № этапа, название, коммит (чип, моно),
   дата, суть результата (1 строка из отчёта). Источник: `PROJECT_STATUS_REPORT.md` §1.
4. **Что сделано — подробно** — свёрнутые (`<details>`) карточки по этапам с полным текстом
   соответствующих секций PHASE-отчётов.
5. **Roadmap / Что дальше** — чек-лист из роадмапа + «Дальнейшие шаги» статус-отчёта, с бейджами
   приоритета (если указаны в источнике).
6. **Проблемы, блокеры, открытые вопросы** — из `PHASE1_OPEN_QUESTIONS.md`, секций «открытые
   вопросы Денису» и т.п.; каждая позиция: текст + источник + (если есть) дата.
7. **Библиотека документов** — сетка карточек (см. 7.2).
8. **Диагностика генерации** (скрытый `<details>`) — какие источники не найдены/не распарсились.

### 7.2 Библиотека документов

- Карточка: имя файла (человеческое), дата из шапки, статус-цитата (`> Статус: …`), тип
  (PHASE-отчёт / роадмап / аудит / research / спека), размер.
- Клик → `docs/<doc>.html`: полный рендер markdown (заголовки→оглавление sticky сбоку на
  десктопе, аккордеон на мобильном), таблицы стилизованы, коммиты и статусы — чипами.
- Резюме на карточке: LLM/override/детерминированное (первый абзац).
- Исходный .md доступен по ссылке `?raw=1` (скачать), если сервер включён.

### 7.3 Отчёт по платформе (freebuff) — полный срез (решение №21)

Источники:
- `TASK.md` — открытые задачи (5.1 Flutter, 5.2 Foreground Service, …) с статусами;
- `CHANGELOG.md` — последние релизы (версия, дата, 3–5 ключевых строк);
- живые метрики: pytest-счётчик (`pytest --collect-only -q`, цель `3342+ passed` из CODE_QUALITY_STANDARD §11.6),
  MissingRegistry (`data_13/missing_registry.yaml`: 45 записей — 28 implemented · 16 registered · 1 design_ready,
  `check` exit 0), git-статистика (коммиты/неделю, активные ветки);
- `docs_10/` — счётчики ADR, аудит-документов, runbook-ов.

Композиция: large title «Платформа Workspace OS» → плитки живых метрик → открытые задачи →

## 8. Diff между генерациями (решение №11 + №15)

- Перед записью новой модели: `site/data/history/<slug>.json` (предыдущая `ReportModel`)
  сравнивается с новой **посекционно** (по секциям §7.1): новые секции, изменение числа пунктов,
  изменение метрик, новые даты/коммиты.
- Результат:
  - **бейджи в отчёте:** `NEW` (новая секция/пункт), `±N` (изменение количества/значения);
  - **сводка на главной:** у карточки проекта «Изменения: +2 этапа, тесты 249→261, 1 новый док»;
  - **manifest.json** хранит агрегат по всем проектам.
- Перезапись history-JSON — атомарно (tmp → rename), после успешной генерации.
- Первая генерация: diff-блок отсутствует (пишется «первая генерация»).

## 9. Резюме агента: override-механизм (решение №10 + №19)

- Файл **`services_08/reports_hub/summaries.json`** (рядом с кодом, коммитится):

```json
{
  "schema_version": 1,
  "project:админка печатник:exec": "Текст executive summary, написанный агентом…",
  "project:админка печатник:doc:PROJECT_STATUS_REPORT.md": "Резюме документа…",
  "platform:exec": "Резюме отчёта платформы…"
}
```

- Приоритет резюме: **override summaries.json → LLM-провайдер → детерминированное**.
- При генерации неиспользованные ключи не удаляются молча — список «осиротевших» ключей
  попадает в диагностику (док переименован/удалён).
- «Сейчас ты будешь писать» = при **первой** генерации агент Buffy заполняет summaries.json
  осмысленными текстами (и это основной путь в v1, пока LLM-провайдеры не настроены);
  разовая правка готового HTML допустима, но при следующей `generate` будет перезаписана —
  поэтому постоянные правки только через summaries.json.

## 10. CLI и сервер

### 10.1 CLI

```bash
python -m services_08.reports_hub generate [--project SLUG] [--platform] [--all] [--force]
python -m services_08.reports_hub serve    [--host 0.0.0.0] [--port 8310]
python -m services_08.reports_hub list                  # найденные проекты + статус профилей
python -m services_08.reports_hub diff     [--project SLUG]  # показать diff последней генерации в терминале
```

- `generate` без флагов = `--all` (все проекты с данными + платформа).
- `--project` — перегенерация одного проекта (остальной сайт не трогается, manifest обновляется).
- Генерация идемпотентна: повторный запуск без изменений фактов → побайтово те же HTML
  (кроме timestamp в manifest) — облегчает diff и кэширование.

### 10.2 Сервер (serve)

- stdlib `http.server`-совместимый (ThreadingHTTPServer), без внешних зависимостей;
- **token-гейт (решение №16):** все запросы требуют `?token=…` (или cookie после первого входа),
  токен из env `REPORTS_HUB_TOKEN`; нет токена в env → сервер стартует и отдаёт 401 + подсказку
  в лог (не молча, не падает);
- раздаёт `site/`, endpoint **`/download/zip`** — архив всего сайта для локального просмотра
  (решение №8 интервью про «сервер + zip»);
- HTML генерируются заранее; сервер ничего не считает на лету (кроме zip) — предсказуемость.

### 10.3 Деплой (решение №20)

- systemd-юнит **`reports-hub.service`** на whimco, аналог `printcalc-web.service`;
- **порт `8310`** (8300 занят печатником; конфликт проверен);
- `WorkingDirectory=/opt/freebuff`, рестарт после `git pull` — регенерация вручную/по ssh;
- регенерация по расписанию — вне v1 (можно повесить на тот же юнит таймер позже).

## 11. Edge cases

| Случай | Поведение |
|---|---|
| Проект без отчётных доков | Серая карточка «нет данных» на главной (решение №12); причина в подсказке |
| `reports_hub.yaml` битый (YAML-ошибка) | Проект помечается «профиль невалиден: <ошибка>», сайт генерится без него, ошибка видна в диагностике главной |
| Два проекта с одинаковым slug | Ошибка генерации с перечислением конфликтов (namespace-правило B-Rule 5) |
| Файл-источник удалён между генерациями | Секция помечается «источник отсутствует», diff покажет −N; summaries-ключ попадёт в «осиротевшие» |
| Пустой git (нет истории) | Раздел Timeline из git скрывается, остаётся из доков |
| Очень большой док (>200KB md) | Полный рендер всё равно строится, но в библиотеке карточка помечается «тяжёлый» |
| Доки с одинаковым именем в подкаталогах | Слаг пути: `docs/<относительный-путь-слаг>.html` |
| Кириллица в именах файлов/папок («админка печатник») | URL-слаги транслитерируются/хешируются при коллизии; в UI — оригинальные имена |
| Нет Pillow для извлечения акцента | Фолбэк на accent из конфига → дефолт; запись в диагностику |
| LLM недоступен при настроенном провайдере | Фолбэк на детерминированные резюме + запись в диагностику (не молча) |
| Отчёт платформы при отсутствии TASK.md | Плитки метрик остаются, секция задач — «источник отсутствует» |
