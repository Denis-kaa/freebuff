# Спецификация: исследование карьерного профиля и портрета для резюме

> **Короткое имя:** `career-profile`
> **Статус:** Draft / research specification
> **Дата:** 2026-08-28
> **Тип артефакта:** исследовательская спецификация + требования к будущему CV
> **Код в этой итерации:** не изменяется

## 1. Цель

Исследовать доступные локальные материалы пользователя — проекты, документацию, отчёты, рабочие артефакты, историю фриланса, обучение и устойчивые увлечения — и на их основе собрать проверяемый профессиональный портрет для написания резюме.

Итоговый профиль должен быть достаточно подробным для подготовки:

- универсального резюме;
- русскоязычного CV для российского рынка;
- при необходимости — отдельных версий под AI/LLM, Python/backend, системную архитектуру и фриланс;
- краткого профиля для Telegram/LinkedIn/Kwork/сопроводительного письма.

Исследование не должно автоматически превращать все найденные материалы в утверждения резюме. Каждый факт классифицируется по источнику, статусу, степени уверенности и необходимости ручной проверки.

## 2. Решения, полученные в интервью

| Область | Решение |
|---|---|
| Основная цель | Универсальный профиль, из которого можно делать разные версии резюме |
| Первичный рынок | Россия |
| Первичный язык | Русский |
| Целевой уровень | Middle |
| Позиционирование | Creator: самостоятельный создатель продуктов и технической экосистемы |
| Главные треки | Python/backend; AI/LLM; архитектура систем; Telegram/Android/Termux |
| Ценность для работодателя | Работающие продукты; сложность инженерных задач; бизнес-эффект; обучение и рост |
| Android/Termux | Упоминать нейтрально, как контекст автономной работы, не как единственный главный тезис |
| Достоверность | В основной профиль включать только подтверждённые факты; неподтверждённое выносить в список проверки |
| Личные интересы | Искать и учитывать все устойчивые интересы, если они подтверждены материалами |
| Экспериментальные проекты | Включать всё с маркировкой `completed`, `active`, `prototype`, `research`, `paused` или `abandoned` |

| Пробелы | Фиксировать открыто и конструктивно |
| Заголовки профиля | Подготовить 3–5 вариантов профессионального позиционирования |
| Формат файла | `career-profile-spec.md` |

## 3. Границы исследования и приватность

### 3.1. Разрешённые источники

Исследователь может анализировать:

- документы и README проектов;
- исходный код и тесты как доказательство технических навыков;
- отчёты аудитов, handoff-документы, changelog и roadmap;
- проектные решения и архитектурные документы;
- материалы фриланса и коммерческих предложений;
- документы по вакансиям и сопроводительным письмам;
- явно оформленные профили, портфолио и публичные ссылки;
- локальные заметки об обучении и интересах;
- результаты запуска, тестирования и иные репродуцируемые артефакты.

### 3.2. Нельзя делать без отдельного запроса

Не включать в карьерный профиль и не распространять:

- пароли, токены, API keys, cookies и секреты;
- приватную переписку и личные сообщения;
- медицинские, финансовые, семейные и иные чувствительные данные, не относящиеся к карьере;
- содержимое `.env` и секретных хранилищ;
- персональные данные третьих лиц;
- неподтверждённые догадки о возрасте, месте проживания, доходе, работодателе или образовании;
- утверждения о production/commercial impact, если есть только прототип или документация;
- публичные ссылки как «портфолио», если нельзя доказать их принадлежность пользователю.

Несмотря на пожелание собрать максимально широкий черновик, основной результат должен быть профессионально безопасным. Сведения, которые могут быть интересны, но не подходят для CV, помещаются в отдельный раздел `Потенциально личное / исключить из резюме`.

## 4. Результаты исследования

Исследование должно создать или заполнить следующие логические разделы этого spec-файла.

### 4.1. Executive profile

Короткое описание кандидата в 3–5 предложениях:

- кто он как специалист;
- какую проблему умеет решать;
- какие продукты и системы создаёт;
- в какой среде умеет работать;
- чем отличается от типичного кандидата.

Формулировки должны быть основаны на доказанных фактах, а не на рекламных эпитетах.

### 4.2. Основные профессиональные треки

Для каждого трека описать:

- уровень подтверждения;
- технологии и инструменты;
- типовые задачи;
- проекты-доказательства;
- результаты;
- ограничения и пробелы;
- возможные названия роли.

Обязательные треки:

1. **Python / backend / automation**
   - Python, CLI, FastAPI/HTTP, SQLite, интеграции, фоновые процессы, тестирование;
   - автоматизация и инженерные инструменты;
   - реальные API, storage и operational concerns.

2. **AI / LLM / agentic systems**
   - LLM-инструменты, Model Gateway, routing, capability-based selection;
   - memory, context, RAG/knowledge, orchestration, agent bridges;
   - использование AI для создания работающих решений;
   - чёткое разделение между созданными механизмами и заявлением о production AI/ML.

3. **System architecture**
   - модульные границы, контракты, event-driven подход;
   - state, persistence, observability, backward compatibility;
   - ADR, forensic analysis, design-first и contract-first работа;
   - архитектурные решения должны иметь ссылки на документы и код.

4. **Telegram / Android / Termux / local-first engineering**
   - Telethon/Telegram-боты и TUI;
   - Termux/Android ARM64;
   - локальные модели, ограниченные RAM/CPU, OOM resilience;
   - нейтральная формулировка: умение создавать и поддерживать инструменты в ограниченной мобильной среде.

### 4.3. Проекты и продукты

Каждый найденный проект описывать по единому шаблону:

```text
Project:
- Название:
- Тип: own product | freelance/client | employment | research | learning | infrastructure
- Директория / ссылка:
- Период:
- Статус: completed | active | prototype | research | paused | abandoned | unknown
- Проблема пользователя:
- Роль кандидата:
- Что лично спроектировано:
- Что лично реализовано:
- Стек:
- Архитектурные решения:
- Интеграции:
- Тесты / verification:
- Измеримый результат:
- Бизнес-ценность:
- Ограничения:
- Доказательства:
- Уверенность: confirmed | probable | needs verification
- Формулировка для CV:
- Формулировка, которую нельзя использовать без проверки:
```

На основании уже найденного контекста необходимо отдельно исследовать как минимум следующие направления, не считая их автоматически завершёнными:

- **Freebuff / Buffy / Workspace OS** — собственная AI-инженерная платформа и knowledge/memory workspace;
- **termux-ai-agent** — локальный AI-агент;
- **blueprints_v3 / Kwork Arbitr v3** — система агентов и фриланс-ориентированных сценариев;
- **LEVIATHAN** — агентский framework, router/orchestrator/memory;
- **fcc-claude** — форк/эксперименты с Claude Code, ModelRouter и workflow;
- **phone-agent** и **phone-mcp-server** — инструменты управления телефоном и MCP;
- **tg-terminal-toolkit / tg_terminal_messenger** — Telegram TUI;
- **lead_aggregator** — поиск и доставка релевантных заказов, адаптеры, фильтрация и dedup;
- **interior_planner** — визуальный инструмент планирования интерьера;
- **vkusvill_research / vkusvill_demo** — исследование вакансии и демонстрация reverse-engineering legacy Excel/VBA/forecasting logic;
- **imperial-phuket clone** — аудит, оценка и handoff веб-проекта;
- **public-request-parser** — спецификация универсального поиска публичных запросов;
- **sheet_project** — конфигурируемый генератор Excel-дашбордов;
- **model_dispatcher** — диспетчер задач/моделей;
- прочие проекты из `projects_17`, `projects`, `kwork`, `buffy-playground_19` и связанных каталогов.

### 4.4. Опыт трудоустройства и фриланса

Найти явные сведения о:

- работодателях и должностях;
- датах и длительности;
- типах договорённостей;
- клиентах и заказчиках;
- задачах и личной ответственности;
- коммерческих результатах;
- повторных заказах, сдаче, поддержке и handoff;
- доменах: AI, веб, Telegram, автоматизация, аналитика, Excel/VBA, маркетинг и другие.

Если опыт найден только косвенно, не называть его трудоустройством. Использовать отдельные категории `freelance`, `client project`, `own project`, `research`.

### 4.5. Образование и самообучение

Собрать:

- формальное образование;
- курсы и сертификаты;
- самостоятельно освоенные технологии;
- длительные исследовательские треки;
- книги, конспекты и систематизированные базы знаний;
- доказательства самостоятельного роста: сложность от простых скриптов к архитектуре, тестированию и эксплуатации.

Не придумывать дипломы, специальность или сертификаты. Если данных недостаточно, добавить вопрос пользователю.

### 4.6. Устойчивые интересы и увлечения

Искать все подтверждённые интересы в следующих областях:

- создание собственных продуктов;
- AI, программирование и агентные системы;
- исследования, обучение и систематизация знаний;
- дизайн, тексты, сайты, медиа и визуальные проекты;
- Android, Termux, железо, локальные модели и техническая самостоятельность;
- предпринимательство и фриланс;
- любые повторяющиеся темы в книгах, проектах и заметках.

Для каждого интереса определить:

- повторяемость во времени;
- связь с профессиональным профилем;
- безопасную формулировку для раздела «О себе»;
- стоит ли включать в CV или оставить для интервью/портфолио.

### 4.7. Навыки и матрица доказательств

Сформировать таблицу:

| Навык | Категория | Уровень уверенности | Проекты-доказательства | Признак владения | Что уточнить |
|---|---|---|---|---|---|

Категории:

- языки программирования;
- backend/API;
- базы данных и хранение;
- Telegram/мессенджеры;
- AI/LLM;
- архитектура;
- тестирование и качество;
- DevOps/операционная среда;
- web/frontend;
- Excel/VBA/аналитика;
- продуктовые и фриланс-навыки;
- коммуникация, исследование и документирование.

Уровень нельзя определять только по наличию слова в README. Нужны признаки: код, тесты, запуск, повторное использование, отчёт о результате или подтверждённый клиентский контекст.

### 4.8. Достижения и метрики

Извлечь только проверяемые показатели:

- число реализованных тестов и результаты test suite;
- количество проектов, если реестр действительно подтверждает число;
- число интеграций, инструментов, модулей и сценариев;
- объём обработанных страниц/файлов/артефактов;
- время, сроки, экономия или коммерческий эффект;
- ограничения среды и достигнутый результат;
- запущенные сервисы, handoff и принятые работы.

Каждая цифра сопровождается:

- точным источником;
- датой;
- пояснением, что именно измерено;
- ограничением применимости.

Не использовать широкие маркетинговые цифры без первоисточника. Например, число AI-проектов третьей стороны нельзя выдавать за личное достижение кандидата.

### 4.9. Рабочий стиль

Реконструировать стиль работы по фактам:

- системность и документирование;
- способность работать автономно;
- исследование перед реализацией;
- additive architecture и сохранение обратной совместимости;
- deterministic-first подход;
- внимание к policy, безопасности и доказательствам;
- способность поддерживать долгие проекты и восстанавливать контекст;
- использование AI-инструментов как множителя продуктивности;
- умение работать в ресурсно ограниченной среде.

Любой вывод о soft skills должен иметь примеры поведения или артефакты.

## 5. Рекомендуемая структура будущего резюме

Spec должен подготовить данные для следующей структуры:

1. Имя и контакты.
2. Рекомендуемый заголовок.
3. Краткое summary на 4–6 строк.
4. Ключевые навыки.
5. Избранные проекты с 2–4 достижениями каждый.
6. Опыт работы и фриланса — если подтверждён.
7. Образование и обучение.
8. Дополнительные интересы — только релевантные.
9. Ссылки на портфолио/GitHub/демо.

Резюме не должно быть каталогом всех 62+ проектов. Полный каталог хранится в исследовательском приложении, а CV использует наиболее сильные и релевантные доказательства.

## 6. Варианты позиционирования для проверки

После исследования подготовить 3–5 вариантов, не выбирая окончательный без сравнения с целевой вакансией:

1. **AI / LLM Engineer и создатель агентных инструментов**
   - для ролей, где важны AI-assisted development, LLM, агенты, память и автоматизация.

2. **Python Automation / Backend Developer**
   - для задач API, Telegram-ботов, CLI, SQLite, интеграций и автоматизации.

3. **AI Systems / Solution Architect**
   - для архитектуры, контрактов, event-driven систем, orchestration и platform thinking.

4. **Independent Product Creator / Technical Founder**
   - для портфолио, стартапов, фриланса и ролей с высокой автономностью.

5. **Automation Engineer for Legacy-to-AI Transformation**
   - для задач reverse-engineering Excel/VBA/legacy logic, shadow-mode validation и создания прикладных решений.

Для каждого варианта указать:

- кому подходит;
- какие проекты поставить первыми;
- какие пробелы мешают;
- какие формулировки нельзя обещать без дополнительной проверки.

## 7. Статусы и достоверность

Использовать следующие уровни:

- **CONFIRMED** — подтверждено кодом, тестом, официальным документом, явным проектным артефактом или ручным ответом пользователя;
- **PROBABLE** — сильный вывод из нескольких источников, но не готовый факт CV;
- **NEEDS VERIFICATION** — возможно, но требует ответа пользователя или первоисточника;
- **EXCLUDE** — не использовать в резюме.

Статус проекта определять комбинацией:

1. явных документов (`README`, `MANIFEST`, `STEPS`, handoff, release note);
2. состояния кода и тестов;
3. наличия запускаемых артефактов;
4. свидетельств реального использования или передачи клиенту.

## 8. Открытые вопросы пользователю после исследования

Если они не будут закрыты локальными источниками, запросить:

- настоящее имя и предпочтительное написание;
- город/часовой пояс и формат удалённой работы;
- email, телефон и ссылки, предназначенные для CV;
- точные должности и даты трудоустройства;
- клиенты, которым разрешено называться публично;
- финансовые или бизнес-результаты, если их можно раскрывать;
- образование, курсы и сертификаты;
- английский и другие языки;
- целевые вакансии и нежелательные направления;
- какие проекты реально запускались пользователем лично;
- какие проекты можно публиковать;
- какие формулировки пользователь считает преувеличением.

## 9. Правила написания фактов для резюме

- Писать «разработал», «спроектировал», «настроил» только при доказательстве личного вклада.
- Для документационного проекта использовать «спроектировал» или «подготовил спецификацию», а не «внедрил».
- Для прототипа писать «создал прототип» или «исследовал feasibility», а не «запустил production-систему».
- Не смешивать возможности платформы с личными достижениями пользователя.
- Не выдавать инструменты, которыми пользовался AI-агент, за навыки пользователя без подтверждения его участия и понимания результата.
- Не считать количество строк кода самостоятельным достижением.
- При наличии тестов указывать их как доказательство инженерной дисциплины, но не подменять ими бизнес-результат.
- Всегда отделять `built`, `designed`, `researched`, `integrated`, `planned` и `documented`.
- Не включать секреты и приватные данные.

## 10. План дальнейшего исследования

### Этап 1 — Инвентаризация

Собрать список проектов, каталогов и документов, убрать архивы/дубликаты из основного анализа и зафиксировать источники.

### Этап 2 — Извлечение фактов

Для каждого проекта заполнить карточку из раздела 4.3. Отдельно отметить явные достижения, технологии и статусы.

### Этап 3 — Верификация

Сверить claims с кодом, тестами, changelog, handoff и пользовательскими ответами. Удалить или пометить неподтверждённые формулировки.

### Этап 4 — Синтез

Сгруппировать проекты по профессиональным трекам, выделить повторяющиеся паттерны работы и наиболее сильные доказательства.

### Этап 5 — Позиционирование

Сравнить 3–5 вариантов заголовка и выбрать рекомендуемый для Middle-профиля российского рынка.

### Этап 6 — CV-ready output

Подготовить фактический набор блоков для будущего резюме, но не писать финальное резюме до отдельного подтверждения пользователя.

## 11. Критерии готовности spec

Спецификация считается готовой к написанию резюме, если:

- основные профессиональные треки описаны доказательно;
- проекты разделены по типу и статусу;
- есть не менее 5–8 сильных проектов-кандидатов для CV;
- для ключевых навыков есть конкретные evidence links;
- неподтверждённые факты отделены от подтверждённых;

## 22. Ключевые риски и пробелы для резюме

1. **Нет подтверждённого трудоустройства в IT** — весь опыт самостоятельный/фриланс; нужно честное разделение.
2. **«Вайб-кодинг» vs классическая разработка** — пользователь сам позиционирует себя как организатора AI-разработки, не кодировщика; это сильная сторона для AI-вакансий, слабая для классических.
3. **Незаконченное высшее (ТюмГУ 2002–2005)** — образование не IT; акцент на практику.
4. **Много прототипов, мало подтверждённых production-результатов** — нужно выбрать 5–8 сильных кейсов с цифрами.
5. **Клиентские проекты без явного разрешения на упоминание** (GapirAI, Whimco, Imperial Phuket, Rokus).
6. **Зарплатная вилка размыта** (60–80к → 150к) — нужно выбрать целевую.
7. **GitHub без звёзд/сообщества** — это нормально для личного портфолио, но не выдавать за open-source успех.
8. **Контакты и личные данные уже в открытых резюме** — проверить актуальность телефона/email/города.
9. **Приватные материалы на телефоне** — не включать, не упоминать.
